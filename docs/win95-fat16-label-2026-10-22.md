# Win95 FAT16 label handoff — normal installed desktop pending

Fresh normal RTM r30 finished Setup phase one and its requested reboot:
the inner VM exited 0 after 450 s. USOS correctly stopped before booting
the target because fsck.fat 4.2 returned 1. Its report contained only a
WINDOWS95 volume label in the root directory versus a blank boot-sector
label. No later disk mount, handoff patch or target reboot occurred.

The new preparation step is limited to the explicit public release tag
95 passed by the preparation caller, a FAT16 marker and nonzero FAT16 root-entry and
FAT-size fields. It uses the already packaged fatlabel 4.2 to read the
root label. Only the exact WINDOWS95 root label paired with eleven blank
BPB label bytes (zero or space) is normalized. Other formats, labels and
nonblank BPB labels receive no write. Both FAT32 BPB fields are zero, so
the helper also rejects a misleading FAT16 marker in such a BPB.
The caller still clears W9X_VM_KEY immediately after Setup; normalization
does not depend on retaining a private key. An omitted release tag is a no-op.

After normalization the helper reads the boot sector again and requires
an exact match to the old sector with only the eleven label bytes changed.
It independently verifies the root label. The normal read-only fsck runs
after this, and again after the existing USOS handoff changes; a nonzero
result still stops preparation. No structural repair or fsck exit-code
exception was introduced. Temporary boot sectors stay in RAM; ordinary
logs stay beside the USOS preparation logs.

The upstream [fatlabel 4.2 manual](https://raw.githubusercontent.com/dosfstools/dosfstools/v4.2/manpages/fatlabel.8.in)
documents reading the root-directory label and updating both label
locations. The binary already present in the frozen initrd has SHA-256
`2be4ffdef6b19f72dde9dc4184b306ba5a1677a8a14ea1a37346d3ecfc1af58b`.

Validation uses no physical disk. Ten synthetic host cases pass,
including non-95/FAT32 exclusion, unexpected labels, short reads, utility
and readback failures, and a remaining structural fsck error that blocks
the mount and PHASE1.OK. The existing read-only-fsck and verification-order
cases also pass.

Real Linux experiments used separate overlays of the stopped owned
r30 target. R31 took 7.147 s: fsck changed from 1 to 0 after fatlabel,
only the boot label bytes changed, and hashes of five Windows files stayed
identical. R35 ran the actual new full w9x_phase1_verify in 10.475 s with
W9X_VM_KEY empty and the public release argument 95:
label readback, both strict fscks, the existing handoff patch and completion
marker all passed. A separate real FAT32 image retained its full hash.
These experiments used initrd script transport, independent completion
nonces, clean exits and no UART command upload. Their original target was
never modified. This is metadata/handoff proof, not Windows desktop,
native target boot, USB, network or second-start proof.

R32 was an earlier lower-level experiment with a nonempty context flag.
Integration inspection caught that the real caller clears that flag before
verification. R33 inputs were never launched and were superseded. R35
validates the corrected public-argument API; a fresh normal install is next.
