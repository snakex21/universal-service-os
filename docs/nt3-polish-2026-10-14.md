# Windows NT 3.x and Windows 3.x polish (2026-10-14)

Polish round for the NT 3.1 / 3.5 / 3.51 flow (docs/nt351-2026-10-08.md,
docs/nt35-2026-10-09.md, docs/nt31-2026-10-09.md) and the Windows 3.x flow
(docs/windows-early-2026-10-07.md), after the X470 hardware passes. Open
items from the X470 runs: no Polish characters, no user name / password /
automatic logon from the answer screen, VGA only, an empty-looking window at
the first logon.

## 1. Answer profile on NT 3.x: account, password, automatic logon

The answer screen already offered USOS profiles for every NT 3.x entry
(`answer_screen.profileCapable`, `answer/nt3.zig`), but the rendered
WINNT.SIF carried only the owner, organisation, computer name and time
zone: NT 3.x GUI Setup has no answer key for the Administrator password, an
own account or the automatic logon (INITIAL.INF: with `STF_GUI_UNATTENDED`
the password is always blank and the "local account" page is skipped).

Now:

| Profile field | WINNT.SIF line (nt3.zig) | Applied by usosnt3.exe |
|---|---|---|
| user name | `;USOS-USER=` | `NetUserAdd` (level 1, password never expires) + `NetLocalGroupAddMember(Administrators)`; Winlogon `DefaultUserName` |
| password | `;USOS-PASSWORD=` | that account's password and the Administrator's (`NetUserSetInfo` level 1003) |
| option "automatic logon" | `;USOS-AUTOLOGON=1` | Winlogon `AutoAdminLogon=1`, `DefaultPassword` |
| locale / keyboard | `;USOS-LOCALE=0000LLLL`, `;USOS-KEYBOARD=KKKKKKKK` | section 2 |

Winlogon `DefaultDomainName`: the computer name Setup configured
(`Control\ComputerName\ComputerName`); on a domain controller
(`ProductOptions ProductType = LanmanNt`, NT 3.1 Advanced Server) the
account domain from `LookupAccountName`. (During NT 3.1 GUI Setup the
account domain is still `MACHINENAME`.)

The `;USOS-` lines are INF comments, Setup ignores them. micro-Linux
(`nt4_csmwrap_target.sh nt3_profile_files`) turns them into
`C:\USOS\NT3\ACCOUNT.TXT` and `INTL.TXT` and removes the account lines from
every WINNT.SIF copy on C:. usosnt3.exe applies them:

- NT 3.5 / 3.51: in the `usosnt3` service at the first start of the
  installed system inside the install VM (after the driver work, before the
  restart);
- NT 3.1 (no usosnt3 service): `POST.CMD` at the end of GUI Setup runs
  `C:\USOS\NT3\USOSNT3.EXE /polish` (USOSNT3.EXE is now staged for 3.1 too).

ACCOUNT.TXT is overwritten with zeros and deleted after use;
`nt4_vm_finish` deletes it too if it is still there. With the automatic
logon the password stays in Winlogon `DefaultPassword`, as on every Windows
with that option. Netapi and newer kernel32 calls go through
`GetProcAddress`; every static import of usosnt3.exe exists in the NT 3.1
kernel32/advapi32 (test `test_usosnt3_imports_exist_on_nt31`). An own
account named Administrator or Guest is not created. Without a profile
nothing changes: Administrator with a blank password. The profile editor
offers "automatic logon" for NT 3.x (options.zig rule, `.native`).

## 2. Polish characters (locale, keyboard, code pages, fonts)

All NT 3.x CDs in the library are English. The NT 3.51 CD has everything
Polish needs: the layout DLLs (`KBDPL1.DLL` Polish (Programmers),
`KBDPL.DLL` Polish (214)), the code pages (`c_1250`, `c_852`, `c_10029`) and
the Central European bitmap fonts; LANGUAGE.INF
`[Options] 00000415 = locale.nls, 0415, 1250, 852, 10029`. GUI Setup never
switches the locale in unattended mode, and text-mode Setup copies only the
default keyboard layout and code pages. So:

- micro-Linux (`nt4_csmwrap_target.sh nt3_stage_intl`) copies the CD files
  the locale needs into `C:\USOS\NT3\INTL`, under their expanded names: the
  layout DLL of TXTSETUP `[Files.KeyboardLayout]` (3.1: TXTSETUP.INF) and,
  for a Central European / Cyrillic / Greek / Turkish locale,
  `c_<ACP>.nls`, `c_<OEMCP>.nls`, `c_<MACCP>.nls`, the OEM fonts
  (`vga852.fon`, `app852.fon`, `cga40/80852.fon`, `ega40/80852.fon`) and the
  six ANSI bitmap fonts (`vgasyse`, `vgafixe`, `sserifee`, `couree`,
  `serifee`, `smallee`); files the CD lacks are skipped. USOS ships no
  Microsoft file: they come from the user's CD at install time.
- usosnt3.exe expands them with the system's own `expand.exe` (the 3.5 /
  3.51 CDs use MSCF cabinets, which lz32 `LZCopy` only copies; the 3.1 CD
  uses LZ, `LZCopy` is the fallback) to `system` (fonts) / `system32`;
  every later check refuses a still-packed file (`unpacked()`: a packed
  `c_1250.nls` as ACP stopped the next start with STOP 0x7F in QEMU).
- Then what LANGUAGE.INF `InstallOption` / LAYOUT.INF would do:
  - `Control\Keyboard Layout` `00000415 = kbdpl1.dll`;
  - `Control\Nls\CodePage` `ACP=1250`, `OEMCP=852`, `MACCP=10029`, the file
    values and `OEMHAL=vga852.fon`, only when every code page file and every
    matching bitmap font is installed (else only the locale and the keyboard
    change);
  - win.ini (registry-mapped) `[GRE_Initialize] FONTS.FON / FIXEDFON.FON /
    OEMFONT.FON`, the `[Fonts]` VGA-res bitmap fonts, `[FontSubstitutes]`
    `Arial CE = Arial` etc.; system.ini `[386Enh]` WOA fonts;
  - `Control\Nls\Language Default=0415`;
  - `HKU\.DEFAULT`: `Control Panel\International` `Locale` and 22 locale
    values (`GetLocaleInfoW` + `RegSetValueExW`; `GetLocaleInfoA` converts
    through the locale's code page and hung the service right after
    `c_1250.nls` was installed), `Keyboard Layout\Active`;
  - `config\userdef` (the Default User hive winlogon copies for every new
    profile) saved again from `.DEFAULT` with `RegSaveKey`, as GUI Setup
    makes it (changes written into a `RegLoadKey`-ed userdef stayed in
    `userdef.LOG`, the new profile still had US settings).

The locale comes from the profile (locale / keyboard fields), else from the
menu language: the UEFI menu writes `locale=` / `keyboard=` into
`request.ini` (`win9x_preparation.formatRequest`, every answer) and
`w9x_csmwrap_prepare.sh w9x_nt3_ui_locale` adds them to the answer when it
names none. A Polish menu therefore installs NT 3.x with the Polish
programmer's layout.

NT 3.5 and 3.1 CDs have the code page files and KBDPL1 but no CE bitmap
fonts: there the keyboard layout and the locale (formats) change, the ANSI
code page stays 1252.

## 3. "Display Settings" at every logon

NT 3.5x GUI Setup in unattended mode never runs the Display applet, so the
`Control\GraphicsDrivers\DetectDisplay` key stays and userinit.exe opens
"Display Settings" at every logon (visible behind Program Manager in the
2026-10-12 QEMU screenshots). usosnt3.exe deletes the key. NT 3.1 has none.

The "Introducing Windows NT" window from the X470 report (Main group icon,
INTRO.EXE, a Win16 Accent DemoMaker demo) renders completely in QEMU (std
VGA, 640x480x16): title, text box, Continue/Exit, the controls page. The
almost empty window on the X470 is not reproduced; it may be the Display
Settings window above, or RX 560-specific (palette / planar VGA under
CSMWrap). To check on the X470 after this build: does an empty window still
appear at logon, and does INTRO.EXE draw when started from the icon?

## 5. Windows 3.1 / WfW 3.11

- **Polish keyboard:** the Polish 3.1 and WfW 3.11 Setup defaults to the
  typist layout (`defkeydll = poldll`, KBDPL.DLL, QWERTZ). `windows_inf.bas`
  (W3INF.BAS, run by INSTALL.BAT before Setup) now switches it to the
  programmer's layout (`poldl1`, KBDPL1.DLL, AltGr letters) when
  `[keyboard.tables]` lists it. Code page 1250 and the CE fonts were already
  installed by the PL editions. The English 3.11 and 3.0a have no Polish
  files (nothing to switch; an own layout DLL and CE fonts would be needed).
- **Resolution (research only, nothing changed):**
  - SUPERVGA.DRV "Super VGA (800x600, 16 colors)" is on the user's 3.1 PL /
    WfW 3.11 PL / 3.11 EN media. It sets BIOS mode 6Ah (or vendor modes)
    with INT 10h AH=00h and checks the result; no VBE call. QEMU's
    SeaVGABIOS has 6Ah; whether the RX 560 VBIOS accepts 6Ah or lists VBE
    102h is unknown: needs an X470 probe (USOSDIAG mode list + a 6Ah set).
    If 6Ah works: an opt-in 800x600 start item (`svgamode=106`); if only
    102h exists: USOSV10 could map AH=00 AL=6Ah to 4F02h BX=0102h.
  - SVGA256.DRV (WfW / 3.11 media) is chip-specific (needs the third-party
    SVGAPatch); modern AMD cards may have no 8 bpp modes.
  - PluMGMK vbesvga.drv (VBE LFB, up to 32 bpp, 3.1 / WfW, standard and 386
    enhanced mode) has no licence and is DDK-derived: USOS cannot bundle it;
    at most a user-supplied file in DATA. Known issue with VBADOS
    VBMOUSE.DRV on WfW (issue #123).
  - Windows 3.0a: no SVGA driver on its media; stays VGA.
