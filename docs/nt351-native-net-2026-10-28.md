# Native NT 3.51 LAN (no install VM), 2026-10-28

Goal: the first desktop of a native NT 3.51 install on the X470 (I211,
CSMWrap, no VM) has TCP/IP over DHCP without user input. Until now the native
path skipped LAN (`NT351 LAN skipped: native install`).

## Why the VM path's LAN did not carry over

1. **INF patch between VM starts.** GUI Setup installs the original MS
   Loopback adapter unattended only after `usos_nt351_vm_patch` added the
   `;USOS-NT351-LOOP-AUTO` lines to `system32\OEMNADLB.INF` (expanded by
   text mode). Natively there is no stop between text mode and GUI Setup.
2. **No HAL PCI bus.** The NT 3.x MBR hides the PCI BIOS on machines with
   more than 8 buses (X470; `docs/nt351-2026-10-08.md`), so NTDETECT records
   no PCI bus and the 3.51 HAL has no PCI bus handler. The qualified
   `usosnet351.sys` (f579, QEMU only) finds the card through
   `NdisReadPciSlotInformation` and maps / connects it as BusType 5 (PCI):
   all of that fails without the handler. The I211 sits at 04:00.0.
3. **Interrupts.** f579 relies on INTx (CheckForHang every 2 s is only a slow
   fallback). Without the PCI BIOS nothing guarantees a usable 8259 line.

## Changes

- **Local-source patch** (`tools/nt351_network_setup.sh`
  `usos_nt351_source_patch`, called from `tools/nt4_csmwrap_target.sh` before
  WINNT.SIF is copied): `OEMNADLB.IN_` of `$WIN_NT$.~LS` is a one-file MSZIP
  cabinet; `usos-fb-ui --nt3-cab-get` extracts it
  (`src/compat/win3x/nt3_cab_file.zig`, own code on `cab.zig`), the existing
  pinned awk patch runs (original sha256 5f64... WS / bc73... Server ->
  df77... / 22e9...), `--nt3-cab-put` writes the cabinet back (stored
  deflate blocks) and the result is extracted again and compared. Any
  failure restores the answer without network (`WINNT.NONET`), so GUI Setup
  never meets the interactive loopback options page.
- **USOSNET351N.SYS** (`tools/nt/usosnet/bin/i386/usosnet351n.sys`, same
  source as f579, `USOSNET_NT351`), staged only on the native path under the
  same `C:\USOS\NT3\USOSNET351.SYS` name; the VM path keeps the qualified f579:
  - when the NDIS bus scan finds no card, `Cf8Find` scans CF8h/CFCh (buses
    0-255) and every later config access of the binary goes there
    (`NdisRead/WritePciSlotInformation` -> `UsPciRead/UsPciWrite`, interrupts
    off on this CPU per address/data pair);
  - driver timer 20 ms (NdisMInitializeTimer + one-shot NdisSetTimer, the 95
    RTM pattern; CheckForHang then does nothing): RX / TX polling every tick,
    a card found through CF8h/CFCh is always polled (chip interrupts masked,
    no NdisMRegisterInterrupt): nothing routed its INTx, and connecting the
    line register's 8259 IRQ could unmask another device's level interrupt;
    with a HAL PCI bus the IRQ path and its watchdog stay as before;
  - MpHalt: a timer run NDIS already deferred finds `Halted` (adapter block
    kept), everything else is freed.
- **usosnt3** (`nt351_network`): BusType 5 when
  `HARDWARE\DESCRIPTION\System\MultifunctionAdapter\N` has Identifier `PCI`
  (HAL PCI bus), else BusType 1 + BusNumber 0. With BusType 1 the 3.51 NDIS
  maps BAR0 through `HalTranslateBusAddress(Isa, 0)`; the DMA adapter still comes from `NdisMSetAttributes(...,
  NdisInterfacePci)` (`HalGetAdapter` takes the attribute type, as AHCINT's
  PCIBus DMA adapter without a PCI bus handler).
- Workstation client policy, workgroup, DHCP and TCP/IP: unchanged (the same
  `usos_nt351_answer`, `CLNT351.REQ`, `NET351.ON` as the VM path).

NDIS 3.51 facts used (disassembly of the user's NT 3.51 Workstation CD
`I386\NDIS.SY_`, sha256 948d...ab1b, with its `NDIS.DBG`; no bytes copied):
`NdisMMapIoSpace` -> `HalTranslateBusAddress(miniport+0x108 BusType,
+0x104 BusNumber)` then `MmMapIoSpace`; `NdisMRegisterInterrupt` ->
`HalGetInterruptVector(+0x108, +0x104, ...)`; `NdisMAllocateMapRegisters`
-> `HalGetAdapter` with InterfaceType = the `NdisMSetAttributes` type
(+0x10C); `NdisMInitializeTimer` lays out KTIMER / KDPC +0x28 / function
+0x48 / context +0x4C / miniport +0x50 (= WDK 7.1 `NDIS_MINIPORT_TIMER`); the
timer DPC takes the miniport lock (+0x30), defers while the miniport is busy
(+0x2E) and skips a halting miniport (+0x4A3). The CF8h/CFCh layout is the
PCI Local Bus specification's configuration mechanism #1. The NT5 sources in
`Desktop\doors` were not used for this change. Own code, GPL-3.0-or-later.

## Tests

Host only (`tools/tests/test_nt351_native_net.py`, `test_usosnet351.py`,
`test_nt351_client_takeover.py`, zig test of `nt3_cab_file.zig`): imports of
USOSNET351N within the original NDIS.SYS 3.51 export table, CF8h/CFCh code,
source wiring, cabinet round trip; with `USOS_NT351_OEMNADLB` set to the CD's
`OEMNADLB.IN_` the real cabinet gets the pinned patch (PASS 2026-10-28, 7-Zip
also tests the rebuilt cabinet OK).

Not done: QEMU (the Micron with the installed NT 3.51 was not attached to the
dev PC; the planned check is a copy of it with `-device igb` behind a
pcie-root-port on a q35 with 12 root ports, so the PCI BIOS is hidden as on
the X470) and the X470. Unproven on hardware: text mode expanding the rebuilt
cabinet, the unattended loopback page natively, BusType 1 mapping on the
X470, 20 ms polling throughput, DHCP.

NT 3.5 native LAN stays off (its NDIS 3.5 build needs its own bus/slot
registry pair and the same INF step). NT 4.0 native already runs the NT4 LAN
staging (usosnet4 with the HAL PCI bus handler, MBR keeps the PCI BIOS).

## X470 run 2026-10-28 (B261028-204354, NT 3.51 WS, Micron NVMe): two stops

Evidence read offline from the Micron (copies only):

1. **GUI Setup: "A non-existent section was referenced in a Setup Script
   command in section: Identification"** (USOSANS.TXT: on "Setup is
   preparing network card choices..."). `system32\OEMNADLB.INF` (expanded
   by text mode from the rebuilt `~LS\OEMNADLB.IN_`) had sha256 f2f2a6...,
   not the pinned df77ec...: same length, but it began `08 96
   [Identification]` and lacked the last two bytes, so `read-syms
   Identification` found no section. Cause: `cab.build` wrote one stored
   deflate block (BTYPE 00). The 3.51 MSZIP decoder (`SETUPDD.SYS` RVA
   0x204B0, identical in GUI Setup's `SETUPDLL.DLL`; own disassembly of the
   user's files) reads LEN, requires an empty bit buffer, then copies LEN
   input bytes: it never consumes NLEN, so NLEN (`~0x69F7` = `08 96`) becomes
   data. Run under unicorn (`tools/nt3/mszipcheck/setupdd_mszip.py`), the
   decoder turns the deployed cabinet into exactly the f2f2a6... file on the
   Micron, and the CD's own cabinets decode correctly.
   Fix: `cab.build` writes fixed-Huffman blocks (BTYPE 01, greedy LZ77 inside
   each 32 KiB block, no code 285); the same decoder (both binaries) returns
   the pinned df77ec... bytes. Also covers the native NT 3.5 `INITIAL.IN_`
   (`nt35_initial.zig`, same `cab.build`). Over-large blocks (incompressible
   data) are refused (`TooLarge`), never written as stored blocks.
   Test: `tools/tests/test_nt351_cab_fixed_huffman.py` (zlib always; the real
   decoder with `USOS_NT351_SETUPDD`).
2. **STOP 0x0000000A (C0000000, 2, 0, 801207DC)** on the start after the
   aborted GUI Setup (Setup's "not completed" path restarts; `Setup`
   SetupType 0, SystemSetupInProgress 1, `autosetp` still in BootExecute).
   Banner 3079532 KB: BOOT.INI still had text mode's entry without options.
   801207DC (3.51 MP kernel 1057, own disassembly) is the working-set list
   growth routine (NT5 name MiAddWorkingSetPage): it reads the PTE of
   `&Wsle[LastInitialized]` and that address was in page 0 (PTE C0000000).
   Callers on the stack: MiLocateAndReserveWsle (801201EB) <-
   MiAddValidPageToWorkingSet (80120042) with WsInfo 801477B0 = the system
   working set (the fault VA was system space) <- fault resolution
   (80126D68, 80125838) <- MmAccessFault (8012A41A) <- KiTrap0E. The kernel
   ran on 3 GB because `/MAXMEM=1024` (NATIVE.TXT) only reached BOOT.INI in
   the first-start service *after* a successful `post()`, and post() was
   refused (NET351: no NDISLoop binding after the failed network page). The
   3.51 memory manager is only proven with /MAXMEM=1024 on this machine; why
   the 3 GB system working set list breaks was not analysed further.
   Fix (`usosnt3.c`): the native BOOT.INI finish runs at `/setup` (20 s after
   start, after INITIAL.INF's `ChangeBootIniTimeout 30`) and in the service
   *before* `post()`, so a refused post still leaves /MAXMEM and the
   pagefile cap.

The Micron was patched in place (log `C:\USOS\NT3\PATCH-*.TXT`, originals in
`C:\USOS\NT3\PATCH-BAK-*`): fixed INF + cabinet, BOOT.INI options, SYSTEM /
SYSTEM.ALT `Setup\SetupType` 0 -> 1 (GUI Setup runs again from INITIAL.INF)
and `usosnt3` Start 2 -> 4 (/setup sets it back to 2), first-run records
renamed `*-RUN1.*`. Not yet confirmed on the X470.
