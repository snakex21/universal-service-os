# Windows 95 RTM / OSR1 (SETUP 4.0.0.950) — integration 2026-10-23

Work by **Codex** (branches `fix/win95-*`, 2026-10-21..23), reviewed and
integrated by Claude. This page replaces Codex's 21 dated per-fix notes.

> **Evidence status: QEMU only.** Every runtime result below was measured on
> overlays of installed copies, not in one fresh end-to-end USOS
> installation. **No fresh end-to-end install, no X470 run.** OSR2 / 98 / ME
> were not regression-tested in a VM by this work. The driver rebuilt during
> integration (below) has not run at all yet.

## Scope: which media

The root `SETUP.EXE` (NE) version decides; the `WIN95\SETUP.EXE` DOS stub
has no version resource.

| Source | Root launcher | Path |
|---|---|---|
| Windows 95 RTM PL OEM | 4.0.0.950 | new 950 path (FAT16, event controller, NDIS 3) |
| Windows 95 OSR1 EN OEM | 4.0.0.950 | new 950 path |
| Windows 95 OSR2 / OSR2.5 EN OEM | 4.0.0.1068 | unchanged OSR2 path (FAT32, timed controller) |
| Windows 95 OSR2.1 PL | 4.0.0.1111 | unchanged OSR2 path (X470 PASS) |

An unknown 95 version, or a 95 source without a root `SETUP.EXE`, stops
before any disk write (new behaviour).

## What changed

**Disk (`tools/w9x_filesystem.sh`, `pe_file_version.c`).** 950 gets FAT16:
type 06h, at most 2047 MiB (below the 2 GiB FAT16 cluster limit), 32 KiB
clusters, real 255/63 CHS. FAT32 MBR entry and `mkfs.fat` arguments for every
other system are byte-identical to before. `pe_file_version` gained a bounded
NE `RT_VERSION` reader. After Setup phase 1, a FAT16 boot sector with a blank
BPB label and the root label `WINDOWS95` gets only its 11 label bytes set by
`fatlabel` (read back and compared) before the strict read-only fsck.

**Setup phase-1 input (`w9x_95_event_wait.sh`, `win95_rfb_events.c`,
`win95_ui_classify.h`).** A blocking RFB receiver (QEMU reverse VNC, VNC
keymap `en-us` from the pinned `qemu-11.0.3-r0.apk`) waits for display
events instead of the timed disk/screen polling, emits only classified page
roles, requires a stable enabled Next button, and stops on an unknown page
with an enabled Next (`unsupported <heading hash>`). New page roles: RTM PL
single-field OEM COA (`xxxxx-OEM-xxxxxxx-xxxxx`), setup options heading,
Communication page, first Finish text; OSR1 EN welcome, COA, owner,
directory, setup type, hardware, communication, components, the network
adapter selector (Have Disk / Cancel, nothing installed), copy, finish.

*Integration gate (Claude):* the event controller and the new roles run only
for SETUP 950. `w9x_csmwrap_target.sh` writes `setup_version=` to
`/run/w9x-target.result`; `w9x_csmwrap_prepare.sh` sets
`W9X_VM_95_SETUP950=1` only for an exact `4 0 0 950`. OSR2 / OSR2.1 keep the
timed controller and the old page roles unchanged (tests in
`test_w9x_phase1_qemu.py`, `test_w9x_95_ui.py`).

**Network.** For 950 only:

- `usosnet` NDIS 3.0 variant: 95 RTM/OSR1 `NDIS.VXD` exports neither
  `NdisMSetAttributesEx` nor `NdisMSetPeriodicTimer`. The variant registers
  MajorNdisVersion 3 with 0x3C-byte characteristics and the four-argument
  `NdisMSetAttributes`, and keeps a 20 ms driver timer re-armed with the
  one-shot `NdisSetTimer` (cancelled in Halt). The inbox `NE2000.SYS` of both
  editions registers 0x3C bytes and uses EthDB+0xD8 (Codex's observation,
  numbers only). *Integration:* Codex's parallel `USOSNET_NDIS31` was reworked
  into `USOSNET_W95RTM` inside the existing NT 3.5x NDIS 3.0 family, and the
  mingw/Zig build replaced by `tools/nt/usosnet/build95rtm.py` (WDK 7.1, the
  `build351.py` flow). New binary `bin/i386/win95-rtm/usosnet4.sys`
  (sha256 `e075652b…`); the other usosnet binaries are unchanged
  (rebuild-compare: identical code and data). Staged with
  `inf/usosnet95rtm.inf`; a missing variant stops preparation.
- `NFILES.BAT`: copies the original Client for Microsoft Networks / TCP/IP
  files from the target's own `C:\WIN95` CABs with its own `EXTRACT.EXE`
  (nothing Microsoft in the repository); existing files are kept.
- VNETSUP `ComputerName` / `Workgroup` / `Comment` from the answer's
  `[Network]`, so GUI PnP does not ask for them.
- `TCP95.REG`: MSTCP Winsock globals (helper/provider, resolver, RPC
  transports). These restate the values of the original `NETTRANS.INF`
  `MSTCP.AddReg` as machine settings, like the existing `NET95.REG`.
- `NET95L.BAT`: 950's first GUI PnP replaces the early TCP/IP classes;
  after `RunOnce\Setup` is gone, `NET95.REG` + `TCP95.REG` are imported again
  once (`NLATE.OK`).

**Display.** `w9x_vesa950.sh` NOPs the 4-byte `CALL FAR [VDDEntryPoint]`
(`VDD_DRIVER_UNREGISTER`) in the *target copy* of the MIT vmdisp9x
`VESAMINI.DRV` (input/output SHA-256 pinned, MIT notice appended; the vendor
copy is untouched; a different vmdisp9x version makes a 950 install stop).
Without it the warm restart hangs in `Disable`. Source-level equivalent: omit
that one call in `enable.c::Disable`. `VESBIND.EXE` (own 16-bit DOS tool,
OpenWatcom, no C runtime) plus `VESALATE.BAT` bind the PCI display that 950
GUI Setup creates later (`Display\0001`, VGA) to the existing VESA class, with
hive backup and rollback.

**Desktop policy (`windows_usos_lan.c`).** In a VM, build 950 with an exact
`PHASE1.OK` and no `RunOnce\Setup` may run the LAN policy (it otherwise
defers in a VM; real hardware is unaffected). With IE 5.x / 6.x installed,
`about:blank` is kept instead of the IE3 `START.HTM` fallback (also applies to
OSR2 with the compat pack's IE).

**Fail-soft (integration).** Codex's `NFILES` / `NET95L` / `VESALATE` failure
paths ended in an endless `PAUSE` loop ("Windows start withheld"). They now
write one line to `C:\USOS9X\USOSLOG.TXT` and Windows starts (without the
USOS network setup, or with its current display).

**Test harness** (`tools/tests/coverage/`, Codex): fixture completion marker
instead of UART command echo, USB report PCAP / PS/2 trace audit, fixed HID
root ports for replug, persistent `-blockdev` nodes for USB storage replug.
The real-QEMU scripts are `run_fixed_hid_ports_qemu.py` and
`run_persistent_usb_storage_qemu.py` (not collected by pytest).

## PID: OEM ProductID made 95 Setup ignore MSBATCH.INF (2026-10-26)

Evidence: X470 950 native SETUPLOG `CmdLine=... C:\WIN95\MSBATCH.INF /IS /IW /P I ...`
(the batch reaches SUWIN), but no `Batchfile=` line and all `batch settings` at
defaults (Express=0, EBD=1). Same on the 2026-10-20 OSR2 run (OEM ProductID);
an OSR2 run with the stock answer (no ProductID) logs `Batchfile=C:\WIN95\MSBATCH.INF`
and Express=1. `/P I` is not the cause (DETLOG shows it working).

Mechanism (read from the user's 950 PL CD, SUWIN.EXE / SETUPX.DLL): SUWIN reads
`[Setup] ProductID` (IpGetProfileString, up to 23 chars) from the temp-dir copy
and lstrcpys it 6 bytes into its 24-byte product ID buffer; the batch file path
follows that buffer. A 23-char OEM ID overwrites the path start with its last
5 digits, the loader's findfirst fails, Setup silently uses defaults. The first
6 bytes come from WINSETUP's appended `/U:xxxxxxxxxxxxxxxxx` (string resource
0x7f); PIDValidate for ProductType 9 wants `ddddd-OEM-ddddddd-ddddd` there.
With the batch loaded SUWIN also skips the "floppy in drive" restart prompt
(`[0x695b]&2`). 950 netdi knows no `PrimaryLogon` (only PrimaryProvider /
ValidatedLogon / LogonDomain): FIRSTBT's Network\Logon swap stays needed.

Fix (tools/w9x_pid95.sh, native phase 1 only, USOS answers only): 950 OEM ID ->
`ddddd-` into this target's WINSETUP.BIN template (same length, in place) and
ProductID = the 17-char rest; other IDs of 18+ chars are dropped. QEMU-free,
host tests only (tools/tests/test_w9x_pid95.py); X470 verification pending.
