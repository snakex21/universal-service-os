# NT 5.2 USB input on xHCI-only boards (Server 2003 x86, XP x64), 2026-09-27

Status: **parked on branch `feature/nt52-usb3`** (NT 5.2 deprioritised by the
user; Vista, Linux and 1.0 come first). Not merged, not on the stick.

The X470 has only xHCI (no EHCI), and the user's PS/2 port is a combo port
their keyboard does not work on. NT 5.2 has no inbox xHCI driver.

## 1. Server 2003 x86 SP2: the XP USB3 backport

**Import check with export forwarders followed**
(`tools/tests/check_nt52_driver_imports.py --source-iso <2003 CD1>`): every
import of `ntoskrn8`, `wdf01000`, `wdfldr`, `ksecd8`, `ucx01000`, `usbd8`,
`usbhub3`, `usbxhci`, `wpprecor` and `genahci` resolves against the 2003 SP2
kernel (5.2.3790.3959), HAL and inbox modules. 282 of the 317 names they
take from `ntoskrn8.sys` are forwarders to `ntoskrnl`; all end at real 2003
exports. (On Windows 2000 about 24 do not.)

**Integration** (same mechanism and bundle format as XP SP3):
`tools/xp_driver_overlay.py` recognises a Server 2003 SP2 source
(`WIN51I?.SP2`) and builds a source-bound bundle with the XP set **minus**
the StorPort backport and the community ACPI (the system's own StorPort and
ACPI stay; no service-pack cabinet is rebuilt):

- text mode: TXTSETUP.SIF `[SourceDisksFiles.x86]`, `[FileFlags]`,
  `[HardwareIdsDatabase]` (`PCI\CC_0C0330` usbxhci, `USB\ROOT_HUB30`,
  `USB30_HUB`, `USB20_HUB` usbhub3, `PCI\CC_010601` genahci),
  `BootBusExtenders` (KMDF), `BusExtenders` (UCX), `InputDevicesSupport`
  (usbxhci, usbhub3), `SCSI.Load` (genahci); DOSNET `[Files]` and
  `[FloppyFiles.1]`;
- GUI phase and installed system: the INFs (usbxhci, usbhub3, genahci) with
  boot start, HIVESYS.INF and SETUPREG.HIV registry rows (KMDF 1.11 keys,
  CriticalDeviceDatabase for the controllers and hubs), crash dump off;
  `DriverSigningPolicy=Ignore` in the automatic answer, as for XP.

The package builder adds a bundle for every Server 2003 SP2 ISO in DATA's
`Windows Server 2003\Images` (`nt52_driver_sources` in the manifest); the
staging (`xp_driver_stage.sh`) accepts it for `windows-server-2003`. XP SP3
bundles rebuild byte-identical with the refactored builder.

**QEMU** (TCG; no PS/2 controller at all, `-machine pc,i8042=off`; input only
through `qemu-xhci` + `usb-kbd` + `usb-tablet`; target on AHCI):

- First attempt with no 8042 at all (`-machine pc,i8042=off`): NTDETECT
  ("Instalator sprawdza konfigurację sprzętu...") hangs, on both paths. Not a
  driver problem; the X470 has an 8042, so the harness now keeps it and routes
  the pointer to the USB tablet (`mouse_set`).
- With the 8042 present, both paths (SeaBIOS stand-in and OVMF -> CSMWrap),
  target on AHCI: **text-mode Setup stops with STOP 0xDEADBEEF
  (0x00000005, 0, 0, 0x00000003)** before any file copy. 0xDEADBEEF is not a
  Microsoft bug check code, so it is raised by the backport itself
  (`ntoskrn8.sys` / KMDF), not by the kernel. The same 2003 media without the
  bundle (GenAHCI only, `nt5_storage_stage.sh`) reaches text-mode copy and
  GUI Setup (docs/nt52-2003-xp64-2026-09-27.md).
- **Parked** here (timebox). Next diagnostic steps, in order: the same run
  without `qemu-xhci` (does the crash need the controller?); the bundle
  without the USB3 part (KMDF + GenAHCI only); `ntoskrn8.sys` against the
  5.2 kernel build (the XP extender may bugcheck on an unexpected kernel);
  a kernel debugger on the serial port to get the caller. Master keeps the
  working state: GenAHCI only, no USB input.

## 2. Server 2003 hands-off to the desktop

With a product key in usos-xp.ini or the answer profile the answer is
`FullUnattended`; Server 2003 additionally gets `AutoLogon=Yes`,
`AutoLogonCount=1` (one Administrator logon, so Setup ends on the desktop),
the licensing mode, and the setup-end script (`/PAE`, no "Manage Your
Server"). No key is in the tooling; without one Setup stops at the key page.

## 3. XP x64 (NT 5.2 amd64): options (research only)

| Option | What exists | Usable by USOS? |
|---|---|---|
| (a) Community x64 port of the Windows 8 USB3 stack | Reported working on XP x64 SP2 (MSFN thread "Are there any USB 3.0/xHCI drivers for Windows XP x64?"; George King's XP2ESD project, reboot12's XP x64 builds on MDL), with an x64 kernel extender | Modified Microsoft binaries: USOS must not bundle them. Only as a user-supplied driver in `DATA\Drivers` (the XP/NT5 driver folders are not wired yet), and it needs an x64 KMDF + extender integration like the x86 one: not small |
| (b) Vendor drivers with official XP x64 support binding AMD xHCI | AMD's own USB 3.0 drivers start at Windows 7; for the X470 chipset (Promontory, 1022:43D0 family) and the CPU xHCI (1022:145F/149C) there is no XP x64 driver. ASMedia's old XP drivers bind only VEN_1B21 (ASM104x/114x), not the AMD IDs; an INF edit would be unsigned and untested | Not realistic |
| (c) Add-in card | **Renesas uPD720201/uPD720202** PCIe USB 3.0 cards: official Renesas driver 3.0.23.0 lists Windows XP x64 (and 2003 x64). A USB 2.0 EHCI PCIe card would use the inbox `usbehci`, but PCIe EHCI cards are rare | **Recommended**: cheap card, official driver the user supplies; the keyboard and mouse go on the card |

Recommendation for XP x64 on the X470: a Renesas uPD720202 card plus its
official driver (user-supplied). USOS would need the NT5 `DATA\Drivers`
hook (text-mode F6 or GUI-phase `OemPnPDriversPath`) to install it
unattended; that hook is not implemented (parked with NT 5.2).

Sources: https://msfn.org/board/topic/183774-are-there-any-usb-30xhci-drivers-for-windows-xp-x64/ ,
https://drivers.softpedia.com/get/MOTHERBOARD/Renesas/Renesas-Electronics-uPD720201-uPD720202-USB-30-Driver-30230.shtml ,

## 4. User-supplied NT 5.2 drivers (generic hook, done)

`tools/nt5_user_drivers.sh`: for the Server 2003 x86 and XP x64 UEFI
profiles, packages in `DATA\Drivers\<system>\Storage|USB|Other\<package>\`
with an INF for the target architecture are copied to
`C:\USOS\Drivers\User\<Class>-NN\` and listed in WINNT.SIF
`[Unattended] OemPnPDriversPath`; GUI-mode device installation and the
installed system use them (an xHCI driver installs during GUI Setup's device
phase). Mismatched architectures and loose INFs are skipped with a log line;
empty folders add no key (XP x86 and 2000 never call it). Text-mode (F6)
storage integration of user packages is not part of it. The installer now
creates `Drivers\Windows XP x64\` and `Drivers\Windows Server 2003\` (with
`Storage`, `USB`, `Other`) and the matching `Systems\Windows\...` folders.
Host-tested (`tools/tests/test_nt5_user_drivers.py`); not yet in a QEMU run
with a real package.

The community XP x64 USB3 port was **not** downloaded by the agent (third-party
modified Microsoft binaries from forum links): the user fetches it and puts
the extracted package in `DATA\Drivers\Windows XP x64\USB\<name>\` (or in
`%LOCALAPPDATA%\USOS\test-assets\xp64-usb3\` for an import check first).

## 5. X470 STOP 0xA5 (ACPI) and the Server 2003 ACPI bundle

X470 (CSM on, build B260927-201324): both NT 5.2 systems stop at the start of
text mode with **STOP 0xA5 (0x11, 0x8, <table>, 0x20120913)**: ACPI_BIOS_ERROR,
"cannot enter ACPI mode", on firmware tables built with iASL 20120913. The
stock 5.2 ACPI.SYS (ACPI 1.0b-era) cannot parse them; QEMU's tables are
simple, so QEMU never showed it. XP x86 works on this board because its
package replaces ACPI.SYS with the community ACPI 2.0 driver.

**Server 2003 x86 (this branch):** the NT 5.2 bundle is now **community
ACPI + GenAHCI** (the same `ACPI/acpi.sys` XP x86 uses), integrated exactly
as for XP: text mode (TXTSETUP/DOSNET, the file in `~BT` and the local
source) and the installed system (ACPI.SYS replaced inside SP2.CAB, so PnP
and SFC take the community one). Import check with forwarders: 134 imports,
0 missing on 2003 SP2. The KMDF/USB3 part stays off (`NT52_USB3=False`,
section 1). QEMU (TCG, OVMF without CSM -> CSMWrap, target on AHCI):
text-mode copy, restart, second CSMWrap boot, GUI Setup at the product-key
page (build B260927-205416 on this branch). QEMU cannot show the 0xA5 fix
itself; that needs the X470. XP x86 target digest identical.

**XP x64:** the same MSFN project ("Compiling ACPI v2.0 driver for Windows XP
SP3 and Windows 2003 SP2 (x32/x64)", msfn.org topic 183464; daniel_k and
others; also Win-Raid "Modded ACPI Drivers Depot") publishes **x64 builds**.
They are compiled from leaked Microsoft source: same rule as the USB3 port,
never bundled; the user supplies it privately. It must replace ACPI.SYS in
text mode (a user `Storage`-style F6 hook is not enough: ACPI is a boot bus
driver), so XP x64 needs a small "user ACPI replacement" step in the NT5
staging before it can pass 0xA5 on the X470. Not built.

**F7 (non-ACPI HAL):** XP x64 / 2003 x64 have **no** non-ACPI HAL (AMD64
Setup offers only ACPI HALs), so F7 is not an option. Server 2003 x86 with
F7 ("Standard PC", i8259 PIC, one CPU) needs MP/`$PIR` interrupt routing
from the CSM for every PCIe device; on AM4 that is at best partial (no APIC,
one of 16 threads, likely no working AHCI/USB interrupts). Not viable in
practice.

## 6. What the user can test on the X470

- **Server 2003 x86** (once this branch is merged and deployed): Setup should
  pass the 0xA5 with the community ACPI; storage through GenAHCI. Still no
  USB input (USB3 off): keyboard/mouse need a PS/2-capable device or the
  unattended profile with a key (hands-off to the desktop).
- **XP x64**: blocked by 0xA5 until a user-supplied x64 community ACPI can
  be staged; USB needs a Renesas uPD720202 card + official driver
  (`DATA\Drivers\Windows XP x64\USB\`, hook on this branch) or the private
  x64 USB3 port.
