# Bind the real Windows 95 source950 display after Setup

RTM GUI Setup can create an active PCI display bound to inbox VGA in class0001
after the early VESA step has populated class0000. The old VESA95.OK guard
then skips every subsequent start, leaving class0000 unused. R124 actually
restarted VGA; R128 proved that changing only the existing device's Driver
value selects VESA1024×768. This branch performs that binding through the
original DOS REGEDIT after the actual RunOnce\\Setup subtree is gone.

For the USOS/profile answer and exact SETUP `4 0 0 950`, VESA95.BAT calls
VESALATE.BAT before its old done guard. A user's own answer and other source
versions retain the previous path. The new hook requires early REG95.OK and
VESA95.OK, clears stale exports, exports RunOnce, and returns without hive
writes or a late journal while Setup is still present.

After Setup, original REGEDIT exports Display classes, Enum and IDConfigDB.
The new 16-bit DOS VESBIND.EXE parses these text exports, requiring exactly
one actual PCI or legacy PNP0900 Display device. Its Driver must resolve to
the inbox MSDISP.INF VGA/supervga class or the existing VESA class0000. The
latter must identify USOSVESA.INF, vesamini.drv, vesamini.vxd and a valid
default mode. CurrentConfig must be an actual four-digit profile string.
Ambiguous adapters, custom drivers, malformed/duplicate fields and oversized
input lines fail closed. No QEMU vendor ID, PCI address or instance is baked
into the code, and no missing Enum device is created.

The generated REGEDIT4 fragment contains only the selected existing device's
Driver=Display\\0000 and the active profile's BitsPerPixel/Resolution from
the existing VESA default mode. After hives are backed up in C:\\USOS9X, the
hook imports that fragment and checks fresh Enum/Config exports with the
same helper. Failure restores the saved hives; RUN/ERR journals withhold
Windows start. Success restores SYSTEM/USER attributes, writes VLATE.OK and
removes VLATE.RUN. It requests no restart and does not repeat on the next
boot. All its scratch/backup files live alongside the helper in C:\\USOS9X.

VESBIND links no compiler runtime. Its own MZ entry normalizes SS:SP to
DGROUP for small-model near pointers, preserving the physical stack top;
DOS I/O and the required string/format routines are USOS code. The build
uses pinned OpenWatcom wcc/wasm/wlink; `--vesbind` builds only this helper.
It is included in STAGED for the CSMWrap payload. Microsoft code is neither
patched nor added to this repository.

## Validation so far

- Six host cases execute the C parser and generator: actual device path and
  current profile, PCI/legacy variants, multiple/custom adapters, malformed
  and duplicate fields, independent binding/mode readback, Setup boundary,
  source scope and original DOS line limits. Six prior VESA cases pass.
- R146b: original 950 DOS executed PLAN, CHECK and ambiguous-device rejection
  using synthetic text only. Exact output matched; exit85/0.72s. The initial
  own-entry prototype failed because SS differed from DS; that startup was
  corrected before this successful test. No Windows registry was attached.
- R147: the actual pending Setup hive, with the early completion-file
  precondition supplied explicitly on a new overlay, exported the genuine
  RunOnce\\Setup subtree. The late hook returned; entire hives and other
  core files stayed byte-identical, attributes7, no late flags; exit85/0.955s.
  This is a boundary test, not a fresh normal-flow claim.
- R148: original DOS copied the exact hook/helper and the trace-free MIT
  VESA950 derivative onto an installed R124 overlay. It did not run the
  installed hook manually. Entire hives and display classes unchanged,
  exit85/1.427s. R149 readonly C/ESP strict fsck PASS/6.246s.
- R150: normal AUTOEXEC ran the hook automatically on the installed overlay.
  Its source used VGA640 and Display0001; the real boot reached login and
  desktop1024×768. After normal poweroff, offline readback confirmed the
  selected real Enum device now uses Display0000, the exact two-section
  fragment, active profile0001 with16/1024×768, VLATE.OK and no RUN/ERR,
  attributes7. Display classes and all checked core files remained identical
  to the staging overlay. QEMU exit0/323.53s; source images unchanged and
  PS/2 counters zero. No restart, USB or network test was repeated.

Dependency: `937ea392` (fix/win95-vesa950-unregister), validated separately
in R145 with the exact trace-free file: warm restart and second VESA1024
desktop, normal poweroff. The final normal installation integration remains
separate from these installed-overlay tests. OSR1 and X470 results remain
separate. No merge, push or deployment has been performed.
