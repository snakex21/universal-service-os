# Windows Embedded POSReady 2009 (2026-10-10)

Status: **experimental entry, ready for an X470 test** (2026-10-11). In
QEMU the install runs hands-free: Setup, the First Boot Agent (FBA) with the
X470 driver step, and the typed Administrator logon. The finish check
(community acpi.sys hash, GenAHCI, USB3) passes. The finished disk then
starts under OVMF + CSMWrap on q35 (AHCI disk, qemu-xhci USB keyboard and
mouse) to the logon and the desktop. GenAHCI, USBXHCI and kbdhid are bound
there (section 5). Build B261010-221038-59BE314C (not deployed).

## 1. The media is not a classic XP source

The user's ISO is in the library at
`OS\Windows\Windows Embedded POSReady 2009\Windows Embedded POSReady 2009 (XP SP3) EN.iso`
(678 625 280 bytes, SHA-256 `92b3096d...4d82cd`, tag file `WIN51.POS`).

- `I386` is a **Windows PE 2005**, i.e. a Server 2003 SP1 PE (`TXTSETUP.SIF`
  says 5.2). `winpeshl.ini` starts `%SystemDrive%\Setup\SetupLauncher.exe`.
- SetupLauncher runs the .NET Setup (`/unattended:unattended.xml` when that
  file is in `\Setup`). Setup does the following:
  - applies `Setup\WIM\setup.wim` (image 1 "WESCore", XP 5.1.2600 SP 5512);
  - adds the optional components (`I386\WOC*.CAB`);
  - runs offline PnP from `..\i386` with `sp3.cab;driver.cab;wocdrvrs.cab`;
  - writes the registry and the boot files.
- At its first start the installed system runs the **First Boot Agent (FBA)**.
  FBA restarts three times before the first logon.
- **Product key: required.** The SKUs are OEM, VL, Eval 120 and Eval 365,
  and there is no default key. Without a key Setup stops with "Invalid
  product key".

## 2. Flow (step 620, like NT 4.0: the whole install in a VM on the target)

| Piece | Where |
|---|---|
| Catalog entry `windows-embedded-posready-2009` (UEFI only, not in the BIOS Core) | `src/catalog/windows_legacy.zig` |
| Profile `posready-x86-qemu-csmwrap` (backend win9x_uefi), XP icon, XML answer | `src/catalog/os_profiles.zig` |
| Answer: POSR.SIF with FullName / ComputerName / ProductKey (5x5), key field `key.windows-embedded-posready-2009`, key prompt at start | `src/flow/answer/posready.zig`, `answer_profiles.zig`, `win9x_key_prompt.zig` |
| Step 620 branch `POSR` | `tools/w9x_csmwrap_prepare.sh` |
| Target disk | `tools/posready_csmwrap_target.sh` |
| VM loop, after-setup step, finish | `tools/posready_qemu_install.sh` |
| Answer template | `tools/posready_unattended.xml` |
| First logon: X470 drivers | `tools/posready_first.cmd`, `tools/posready_x470.reg` (generated by `tools/posready_reg.py` from `xp_driver_overlay.py`) |
| DATA layout row | `installer/internal/winhost/data_layout.go` |

The DATA folder is `Systems\Windows\Windows Embedded POSReady 2009\Images` for
the ISO. A user's own answer `Unattended\*.xml` is used as it is.

Disk layout (MBR):

| Partition | Content |
|---|---|
| 1 | FAT16 (0E), ~1.9 GiB from sector 63, active. It holds the PE: SYSLINUX chains `/NTLDR`, which is `I386\SETUPLDR.BIN` for the PE start, plus `\MININT` and `\I386` (Setup's cabs). It also holds `\Setup` with `unattended.xml`, and `\USOS\POSR` with FIRST.CMD, LOGON.CMD, X470.REG, LOGON.REG and DRV (the source of the copy on partition 2). It stays the **system partition**: NTLDR and BOOT.INI live here. |
| 2 | NTFS, POSReady (C:). Setup formats it (`ModifyPartition ID="2"`). It ends at 32 GiB at most. After Setup it also gets `\USOS\POSR` (scripts, logs, DONE.TXT). |
| 3 | The CSMWrap ESP, written by `xp_csmwrap_esp.sh` after the VM. |

VM runs (each guest restart ends QEMU; IDE, SeaBIOS, **one CPU**):

1. PE, then Setup unattended, for about 2 minutes. Then
   `posready_after_setup` runs in micro-Linux. It copies the disc's
   `Setup\NTLdr` / `Setup\NTDetect.com` over the PE loader on partition 1,
   adds `/execute` to BOOT.INI, puts the USOS MBR code back and makes
   partition 1 active. It also copies `\USOS\POSR` from partition 1 onto
   partition 2 (ntfs3 read-write; only a new folder, compared after the
   copy).
2. Runs 2-4 are the FBA ("Installing Components", "Resetting Setup Flag").
   Inside FBA, POSReady runs the answer file's `<RunOnce>`. Batch files need
   `FilePath="C:\WINDOWS\system32\cmd.exe"` with `/c ...` in `Attributes`.
   A command line in `FilePath` was skipped. FBA also mangles every `%`:
   `%11%` gave "Invalid Path: [%\cmd.exe]" in `WINDOWS\FBA\FBALOG.TXT`, and
   `for %d` broke too. Inside FBA the FAT16 Setup partition has **no drive
   letter** (D:, E:, F: were all missing), so the RunOnce is the fixed
   `/c C:\USOS\POSR\FIRST.CMD`, the copy on the Windows partition. FIRST.CMD
   does this:
   - copies the community `acpi.sys`, first to `dllcache`, then to
     `system32\drivers`;
   - copies GenAHCI, StorPort, ntoskrn8 and KMDF 1.11, plus the USB3 xHCI
     drivers;
   - runs `regedit /s X470.REG`, which holds the same services and
     CriticalDeviceDatabase rows as the XP path's hives;
   - runs `regedit /s LOGON.REG`, a HKLM RunOnce for `C:\USOS\POSR\LOGON.CMD`.
3. The last run stops at the classic logon dialog, because POSReady has no
   autologon answer. `Administrator` plus Enter is typed into it
   (`W9X_VM_ANSWER` after the idle time; the password is blank). LOGON.CMD
   then compares `acpi.sys` with `fc /b`, after FBA's PnP: the Tablet
   lesson. If the stock file came back, it copies the community one again
   and logs `ACPI RESTORED`. It then writes `C:\USOS\POSR\DONE.TXT` and
   shuts down. The VM loop looks for DONE.TXT on partition 2 (ntfs3, read
   only).
4. `posready_vm_finish` (read only) checks the following, then
   `xp_csmwrap_esp.sh` adds the ESP:
   - `C:\USOS\POSR\FIRST.LOG` (FBALOG.TXT is copied to the logs too);
   - BOOT.INI;
   - the acpi.sys SHA-256 against the community one;
   - that genahci.sys and usbxhci.sys are present.

## 3. Findings (QEMU 2026-10-10)

- The disc's `Setup\USB\ntldr` is a plain NTLDR. What starts the PE from disk
  is `SETUPLDR.BIN` as `\NTLDR` with `\MININT`. A BOOT.INI with `\I386
  /MININT` fails on the missing SYSTEM hive.
- Setup treats the **active** partition as the system partition. It wrote
  BOOT.INI for `partition(2)\Windows` there and a Microsoft MBR, but left
  SETUPLDR as NTLDR, so the restart failed with "Error loading operating
  system".
- NTLDR in the root of the NTFS partition (written by Linux ntfs3) stopped
  with TRAP 6. Most likely a **harness artefact, not ntfs3**: on 2026-10-10
  the files ntfs3 wrote in `posready_after_setup` read back as zeros in the
  VM (FIRST.CMD was 1144 zero bytes, so FBA ran it without effect). The
  harness killed the outer QEMU after a guest `sync`, which sends no FLUSH
  for loop/raw writes, so QEMU's unwritten qcow2 metadata for the newly
  allocated clusters was lost. NTLDR read as zeros gives exactly an invalid
  opcode (TRAP 6). The harness now powers the guest off (`poweroff -f`) so
  QEMU closes the qcow2 itself; after that the same copy was intact and
  NTLDR (on partition 1) read the ntfs3-modified volume fine. The NTLDR on
  NTFS layout itself was not retried. On real hardware there is no qcow2
  layer; step 620 `sync`s before the VM opens the disk.
- FBA configures the File Based Write Filter (`fbwf.cfg`, "Found volume to
  protect, c:"), but with `EnablePostFBA=0`: the driver step's writes in
  FBA and at the logon persisted.
- **"hal.dll missing or corrupt"**: Setup installs no `ntkrnlpa.exe` (its
  log says "could not be found"). On a CPU with NX, NTLDR loads the PAE
  kernel. The fix is `/execute`, which means no DEP and no PAE, so the system
  sees at most 4 GiB. The HAL and kernel pair Setup chose were consistent
  for both 1 and 2 CPUs.
- In the test harness, `cache=unsafe` combined with killing QEMU lost late
  qcow2 writes. The harnesses now use `cache=writeback` and power the guest
  off instead of killing QEMU.
- The user's key is an evaluation key: the desktop says "Evaluation copy".

## 4. Tests

- `tools/tests/test_posready.py`, 13 tests: the template has no key; the
  answer XML is built from POSR.SIF; the .reg matches the XP overlay;
  the scripts have CRLF line endings; the driver set matches the XP selection;
  step 620 routes POSReady; the scripts' syntax is valid; the RunOnce and
  LOGON.REG use the fixed `C:\USOS\POSR` path; the after-setup step copies
  `\USOS\POSR` onto partition 2; the marker and finish read partition 2.
- Zig: `posready.zig` (key shape, POSR.SIF), the key prompt, and the routing
  golden (additions only).
- Go: DATA layout count 45.
- QEMU end to end with `tools/tests/run_posready_micro_linux_qemu.py --vm
  host --finish --boot`. Stage 1, the after-setup step and the finish plus
  ESP ran through the **real micro-Linux** (nested). The install VM itself
  ran on the host QEMU (pc/SeaBIOS/IDE, whpx); it was not run under
  micro-Linux's own qemu-system-i386 (TCG), because that takes too long for
  this session. Harness options: `--qemu` (a renamed QEMU copy, so other
  sessions' QEMU is never touched), `--after-first` (redo the after-setup
  step on a saved image), `--stage inspect` (C:\USOS\POSR, FBA log tail,
  read only) and `--stage marker`.

## 5. Status and open points

- **Driver step: works in QEMU** (2026-10-11, host QEMU install VM, the
  after-setup and finish steps in the real micro-Linux). FBALOG:
  `*** Hidden *** (ExitCode: 0x0)`. FIRST.LOG lists the 12 drivers and 3 INFs
  copied, `regedit X470 0`, `regedit LOGON 0`, then `USOS POSReady first
  logon` without `ACPI RESTORED` (FBA's PnP left the community acpi.sys in
  place). The finish check passed and the CSMWrap ESP was added.
- **OVMF + CSMWrap boot** (q35, TCG, EPYC-Rome, 2 CPUs, AHCI disk, qemu-xhci
  usb-kbd + usb-mouse): logon dialog, then the desktop. In that session
  `Services\genahci\Enum` = the ICH9 AHCI controller, `Services\USBXHCI\Enum`
  = qemu-xhci, and `Services\kbdhid\Enum` = the QEMU USB keyboard. A "Found
  New Hardware" wizard opens for one QEMU device without a driver.
- Offline injection from micro-Linux (services, CriticalDeviceDatabase in
  the SYSTEM hive) was considered and not done: micro-Linux has no hive
  writer that can add keys (`vista_hive.h` only edits existing cells), and
  the FBA RunOnce plus the logon check now work. The copy onto C: is the
  only offline write.
- Stick path, as far as tested: stage 1, the after-setup step, the marker
  and the finish run in the real micro-Linux with this build's scripts. The
  install VM under micro-Linux's own qemu-system-i386 (`--vm nested`, TCG
  inside the whpx outer VM) did not finish run 1 (PE + Setup) within 60
  minutes on 2026-10-11, so the VM loop itself on the target is still
  unproven. On the X470 that QEMU runs on bare metal (TCG, or KVM with the
  phase1-kvm flag), which is much faster than TCG nested in whpx.
- The X470 is untested. Watch for:
  - stock ACPI coming back (the Tablet lesson: FIRST.CMD fills `dllcache`,
    LOGON.CMD re-checks after FBA, and the finish step checks the hash);
  - GenAHCI at the first real start;
  - USB.
- Only one CPU and no PAE. Next step: MP (2 CPUs in the VM) and PAE (add the
  missing ntkrnlpa.exe / ntkrpamp.exe).
- No autologon after the first logon. Administrator has a blank password,
  and the profile's password is not applied.
