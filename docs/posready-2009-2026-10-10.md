# Windows Embedded POSReady 2009 (2026-10-10)

Status: **parked, groundwork only**. The install mechanism works in QEMU up to
Setup's product key check. Without a real POSReady 2009 product key, Setup
stops with "Invalid product key", so nothing was installed and nothing is
wired into the menu or the micro-Linux payload yet.

## 1. The media is not a classic XP source

The user's ISO is in the library at
`OS\Windows\Windows Embedded POSReady 2009\Windows Embedded POSReady 2009 (XP SP3) EN.iso`
(678 625 280 bytes, SHA-256 `92b3096d...4d82cd`, created 2008-12-02, tag file
`WIN51.POS`). Nothing was found in Downloads.

- `I386` is a **Windows PE 2005**, i.e. a Server 2003 SP1 PE: `TXTSETUP.SIF`
  has MajorVersion 5 and MinorVersion 2, and `winbom.ini` has
  `WinBOMType=WinPE`. It is **not** an XP text-mode install source, so the
  XP CSMWrap path (local source `$WIN_NT$.~LS`, TXTSETUP/DOSNET, the driver
  overlay) cannot be used as it is.
- `I386\system32\winpeshl.ini` starts `%SystemDrive%\Setup\SetupLauncher.exe`.
  SetupLauncher runs `presetup.cmd`, then the .NET 1.1 `Setup.exe`
  (`/unattended:unattended.xml` when that file exists in `\Setup`), then
  `postsetup.cmd`.
- Setup's actions are embedded in `Microsoft.Embedded.Setup.Data.POSReady.dll`:
  PID, DiskConfig, VolumeFormat, CopySourceFiles, then the **WIM** step
  (`Setup\WIM\setup.wim`, image 1 "WESCore (Eval)", XP 5.1.2600 SP 5512,
  155 directories and 2904 files, 373 MB). After that come offline
  Plug-n-Play from `..\i386` cabs `sp3.cab;driver.cab;wocdrvrs.cab`, the
  regional settings, the drive letters, the computer name and admin
  password, the optional components (`I386\WOC*.CAB`, 21 cabs), the user
  accounts, RunOnce, the registry, and BootPreparation.
- The first boot of the installed system runs the **First Boot Agent
  (FBA)**. Per the USB-install chapter of the bundled docs, FBA needs the
  Setup files again.
- **Product key: required.** The SKUs are OEM (MPC 00817), VL (00851),
  Eval 120-day (00860) and Eval 365-day (00861). There is no default key and
  no `WINNT.SIF`. There is no key in `%LOCALAPPDATA%\USOS\test-assets\private-keys`.
- The answer file schema is in the CHM: `Documentation\POSReady_2009_English.chm`,
  "Answer File Reference" and "Sample Answer File".

## 2. Mechanism (proved in QEMU up to the key check)

A CD cannot take `\Setup\unattended.xml` without a remaster. Instead,
`tools/posready_csmwrap_target.sh` (micro-Linux) writes the PE onto the target
disk itself:

| Partition | Content |
|---|---|
| 1, FAT16 (0E), active, ~1.9 GiB from sector 63 | syslinux, then `chain.c32 ntldr=/NTLDR`. `\NTLDR` is `I386\SETUPLDR.BIN`, next to `\NTDETECT.COM`. `\MININT` holds a copy of I386 (the PE). `\I386` is a second copy, because Setup reads its cabs from `..\i386`. Also `\Setup` with `unattended.xml` (and optionally `presetup.cmd` / `postsetup.cmd`), `\Program Files`, `\Documentation`, the tag files and `winbom.ini`. |
| 2, type 07, rest of the visible disk | Empty. Setup formats it as NTFS (`ModifyPartition ID="2"`) and installs there. |

The template answer file is `tools/posready_unattended.xml`. Its
`@PRODUCT_KEY@` would be filled at run time from the answer profile, and no
key is ever committed. It sets the EULA as accepted, workgroup, DHCP, a few
optional components (.NET 2.0, Notepad, Calculator, Paint, WordPad, command
line utilities, Disk Management) and time zone 85.

Dead ends found on the way (all QEMU, 2026-10-10):
- The disc's `Setup\USB\ntldr` is a plain NTLDR. It looks for `\WINDOWS`, and
  a BOOT.INI with `\I386 /MININT` fails on the missing SYSTEM hive. What
  works is `SETUPLDR.BIN` as `\NTLDR` with the PE in `\MININT`.
- PE then names its boot partition **X:**, and SetupLauncher finds `X:\Setup`.
- The test harness first used `cache=unsafe` and killed QEMU, which lost the
  qcow2 metadata of the late writes: `\Setup` read back empty, and SYSLINUX
  found no config. It now uses `cache=writeback`.
  `tools/tests/run_nt3_micro_linux_qemu.py` has the same pattern
  (`cache=unsafe`, then kill).

Result: with `--vm host` (this PC's QEMU, pc/SeaBIOS/IDE), SYSLINUX loaded
SETUPLDR, which loaded PE (blue desktop) and then SetupLauncher. The POSReady
wizard showed "Validating Answer and/or Device Files" as passed and stopped at
"Processing Answer File":
- an empty key failed with "The 'Value' attribute has an invalid value";
- a well-formed fake key failed with **"Invalid product key"**.
So the answer file is accepted and the key is the only blocker found so far.

## 3. Planned flow once a key exists (not built)

The plan follows the NT 4.0 VM pattern (`tools/posready_qemu_install.sh`,
draft):

1. Run 1 is PE plus Setup in micro-Linux's `qemu-system-i386` on the real
   target disk (IDE, 2 CPUs, so the offline PnP picks the ACPI
   multiprocessor HAL). `-no-reboot` ends the run.
2. Set partition 2 active. Runs 2 and later: FBA, then the first logon. A
   RunOnce writes `C:\USOS\POSR\DONE.TXT` and shuts down.
3. **X470 drivers, still open.** The image comes from the WIM, not from
   TXTSETUP, so the XP driver overlay cannot be used. The X470 needs, offline
   in the installed system:
   - the community `acpi.sys` (stock SP3 ACPI is 0xA5 on the X470);
   - GenAHCI with storport (CriticalDeviceDatabase `PCI\CC_010601`, service
     Start 0);
   - optionally the KMDF + USB3 set.
   All of these come from `media/.../Windows XP UEFI-CSM PAE/Drivers/x86`.
   POSReady's own offline PnP also takes `sp3.cab`/`driver.cab`, so the
   DRVINDEX issue from XP Tablet probably applies as well: FBA or PnP could
   restore the stock `acpi.sys`. Check `drvindex.inf` in the image.
4. Then `xp_csmwrap_esp.sh` adds the CSMWrap ESP, and a menu entry is added
   (catalog, `route_as`, DATA folder
   `Systems\Windows\Windows Embedded POSReady 2009\Images`), mirroring
   MCE/Tablet.
