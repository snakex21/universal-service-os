# NVMe for the NT family: usosnvme (2026-10-11)

Polish-round item: install and run Windows NT 3.1 to Server 2003 (x86) on an
NVMe disk, with one SCSIPORT miniport of our own. Branch `feature/nvme-nt`.

## 1. The driver: `tools/nt/usosnvme`

Own code, GPL-3.0-or-later, written clean-room from the **NVM Express Base
Specification** (registers, admin / NVM command layouts, queues, PRPs) and
the **public SCSI miniport documentation** (ScsiPort interface). No
Microsoft source code and no other NVMe driver's source was read. The model
for the build and the per-version rules is AHCINT (`tools/vendor/ahcint`),
which is a third-party driver: ages2001/AHCINT, GPL-3.0, modified by USOS
(MODIFIED.txt, patches 0001-0010). usosnvme copies no AHCINT code; it
follows the same, already proven, per-version ScsiPort constraints
(structure sizes, PCI access, no interrupt under CSMWrap).

| Build | For | Specifics |
|---|---|---|
| `2KXP`  | 2000 / XP / 2003 x86 | PnP ScsiPort (`PnpInterface\5 = 1`), resources from PnP, 64-bit DMA |
| `NT4`   | NT 4.0 | non-PnP: the miniport scans PCI (class 01-08-02), claims BAR0, no interrupt, init data 0x4C, PE 4.00 |
| `NT351` | NT 3.5 / 3.51 | + PCI config through CF8h/CFCh (the NT 3.x MBR can hide the PCI BIOS), Isa registration, reported as a PCI bus master, PE 3.51 |
| `NT31`  | NT 3.1 | + init data 0x40, no SlotNumber / MaximumNumberOfTargets, EISA bus master, PE 3.10 |

Build: `tools\nt\usosnvme\build.cmd all` (WDK 7.1, the AHCINT/usosusb
toolchain). Every import resolves on its kernel (fixtures in
`tools/tests/data`, `tools/tests/test_usosnvme.py`); no build imports memset /
memcpy (NT 3.1 exports neither). 10-11 KB each.

How it works:

- Controller start (HwInitialize, again after a timeout): CC.EN = 0 and wait
  for RDY = 0 (SeaBIOS in CSMWrap left it enabled with its own queues), admin
  queue 16 entries, CC = NVM, 4 KiB pages, 64/16-byte entries, wait RDY,
  INTMS = all; IDENTIFY controller (MDTS, VWC, serial / model / firmware),
  Set Features Number of Queues (1/1), CREATE I/O CQ (32, IEN = 0) and SQ.
- Namespace: the first one in the active list (CNS 02h; NSID 1 on NVMe 1.0).
  **Only 512-byte LBAs without metadata** are exposed. Any other format (4Kn,
  metadata) gives no disk, a red line in VGA text row 9
  (`USOSNVME: NVMe namespace 1 uses 4096-byte sectors; only 512-byte sectors
  are supported`) and an event-log entry (usosnvme, unique id 0x4E560003).
- Polled: every command is submitted and completed in HwStartIo (one at a
  time), interrupts masked three ways (INTMS, PCI INTx disable, IEN = 0).
  NT 3.x / 4.0 report no interrupt to ScsiPort (as AHCINT patch 0006).
- READ / WRITE 6/10/12/16 via PRP1, PRP2 or one PRP list page, split at
  min(MDTS, 128 KiB); FUA passed through; LBA range checked.
- SCSI: INQUIRY (+ VPD 00h, 80h serial), READ CAPACITY 10/16, MODE SENSE
  6/10 (caching page, WCE = VWC, DPOFUA), SYNCHRONIZE CACHE 10/16 and SRB
  flush / shutdown -> NVMe FLUSH, TEST UNIT READY / START STOP / VERIFY etc.
  succeed, REQUEST SENSE, autosense. Target 0, LUN 0 only.
- A timeout: ABORTED COMMAND sense (the class driver retries), the
  controller is restarted before the next command, a VGA line + event.
- Status line on success (VGA text row 9; AHCINT uses 0 and 8, usosrst 1-7):
  `USOSNVME 1.0 VVVV:DDDD NS1 <MiB> MiB x512 chunk <K>K VWC <0/1> VS <ver> OK`.

## 2. Flow wiring (only for an NVMe target)

Target detection everywhere is the micro-Linux device name `/dev/nvme*`.

- **XP SP3 / Server 2003 SP2 x86** (`xp_driver_overlay.py`,
  `xp_driver_stage.sh`): every source-bound bundle carries `USOSNVME.SY_` /
  `USOSNVME.IN_` in I386 and a second metadata set in `NVME/`
  (TXTSETUP.SIF: SourceDisksFiles, FileFlags, `PCI\CC_010802 = "usosnvme"`,
  `SCSI.Load`, `SCSI`; DOSNET.INF; HIVESYS.INF and SETUPREG.HIV: service
  Start 0, group SCSI miniport, `Parameters\PnpInterface\5 = 1`,
  CriticalDeviceDatabase `pci#cc_010802`), hash-pinned in `nvme.sha256`. The
  apply step copies `NVME/` over the base set only when the target is NVMe;
  a SATA target gets the base set, byte-identical to the previous bundle
  (checked: payload.sha256 differs only by the two new files). The INF
  (`usosnvme.inf`, class SCSIAdapter, `PCI\CC_010802`) goes to `%windir%\inf`
  so GUI-mode PnP installs the device with our service (no NULL driver).
- `legacy_xp_staging.sh`: an NVMe target with a logical block size other than
  512, or a system without the driver in its flow (2000, XP x64), stops
  before any write with a clear message.
- **NT 4.0** (`nt4_csmwrap_target.sh`): NVMe target -> `C:\USOS\NT4\USOSNVME.SYS`
  + `Services\usosnvme` (Start 0, SCSI miniport) in DRIVERS.REG; POST.CMD
  copies it. The install VM itself still runs on IDE (usosnvme just finds no
  controller there).
- **NT 3.x**: the NT351 / NT31 builds are in micro-Linux
  (`usr/lib/usos/nt3/USOSNVME.SYS`, `USOSNVME31.SYS`) but **not wired yet**
  (NT 3.5x registers drivers through USOSNT3.EXE, 3.1 through INITIAL.INF:
  next step). **Windows 2000**: the 2KXP build imports resolve on 2000 by
  construction (same imports as AHCINT minus the trace ones), wiring into
  `w2k_stage.sh` (legacy vs PnP mode decision, as for AHCINT) is the next
  step.

## 3. CSMWrap / INT 13h on NVMe

The pinned CSMWrap 3.1.2-usos4 already has SeaBIOS NVMe support (strings
`nvme_controller_setup`, `NVMe NS %u: ...` in the binary); `skip_nonbootable`
applies only with a strict boot order, so no rebuild was needed.

| QEMU (OVMF without CSM, TCG) | Result |
|---|---|
| `run_csmwrap_boot_disk_qemu.py --layout nvme-target` (target on NVMe, bootable decoy on AHCI) | `USOS-TARGET USOS-DECOY`: CSMWrap tags the NVMe as boot disk, it is 0x80, decoy 0x81 read through INT 13h. PASS |
| `... --layout nvme-decoy` (target on AHCI, decoy on NVMe) | 0x81 = the NVMe, read through INT 13h. PASS |
| `run_nvme_freedos_probe.py` (FreeDOS 1.4 on an NVMe-only PC) | CSMWrap -> USOS MBR -> FreeDOS kernel from NVMe, `C: HD1`, DIR, a file written and read back. PASS (9x / DOS use the same INT 13h path) |

## 4. QEMU results

**XP Media Center Edition 2005 SP3 (XP SP3 flow, PL user settings),
target = `-device nvme` only:** `run_csmwrap_xp_prepared.py --nvme
--run-through --reboots 1` with `USOS_TEST_PROBE_EXPORTS=USOS_XP_EDITION=mce`
(the MCE disc has its own key; no XP Pro key was at hand), the bundle rebuilt
with this branch (`add_driver_source`), `--tree-scripts xp_driver_stage.sh`.

- micro-Linux: `/dev/nvme0n1`, guard snapshot, `[XP_DRIVERS] NVME PASS`,
  `APPLIED PASS`, `XP_VERIFY PASS`, CSMWrap ESP PASS.
- CSMWrap -> SETUPLDR from the NVMe (INT 13h) -> text mode loads usosnvme:
  `USOSNVME 1.0 1B36:0010 NS1 12288 MiB x512 chunk 128K VWC 1 VS 00010400 OK`,
  `12285 MB Disk 0 at Id 0 on bus 0 on usosnvme [MBR]`, files copied,
  restart; GUI Setup from the NVMe ("Installing Devices" ...).
- GUI Setup ran hands-free from the NVMe (Installing Devices, Registering
  components), restart, second CSMWrap boot, automatic logon -> **XP desktop**
  (about 35 minutes TCG from the first CSMWrap boot).
- The VM was then stopped hard (`quit`) and the disk booted again
  (`--reboots 1`): CSMWrap -> XP from the NVMe -> desktop again. PASS.

**NT 4.0 Workstation PL, target = NVMe:** `run_nt3_micro_linux_qemu.py --tag
NT4 --nvme --scripts --boot` (answer with the user's OEM key in a local file,
no SP6a at hand -> RTM kernel, boot CPU `EPYC-Rome,level=3`):
`storage: NVMe target /dev/nvme0n1, usosnvme staged next to AHCINT`, install
VM PASS (175 s, whpx), finish PASS; boot under OVMF + CSMWrap from the NVMe
behind a PCIe root port (bus 1+, as the X470 M.2), the only disk: logon
screen, Ctrl+Alt+Del + blank password -> **desktop 1024x768** (usosvbe). The
system disk is served by usosnvme (no other disk exists). PASS.

## 7. X470 test plan (Micron 3400 512 GB, MTFDKBA512TFH)

Prerequisites: M.2 slot forced to **Gen3** in the BIOS (the X470 sees the
Micron only then), CSM off, Secure Boot as usual. Identify the Micron by its
serial in the USOS disk picker; it may be wiped only with the user's
approval. The Micron is a client drive with 512-byte LBA format as shipped
(LBA format 0); if the picker stops with "uses 4096-byte sectors", the
namespace must be reformatted to 512 B first (`nvme format` in Linux).

1. **INT 13h / DOS probe (no Windows):** MS-DOS 6.22 or Win98 SE entry to the
   Micron -> CSMWrap boots it; proves SeaBIOS NVMe on the real controller.
2. **XP SP3 PL** (or MCE) to the Micron: expected the blue row-9 line
   `USOSNVME 1.0 1344:xxxx NS1 ~488386 MiB x512 ... OK` (1344 = Micron) early in text mode,
   `Disk 0 ... on usosnvme`, the full install, desktop, PAE. A photo of the
   text-mode screen with the row-9 line is the key evidence. A red line =
   the reason (stop/ready timeout, CSTS value, 4Kn).
3. Reboot twice, copy a few GB, shut down cleanly, boot again (flush path).
4. **NT 4.0 WS PL** to the Micron (needs the SP6a for Zen): desktop; POST.LOG
   lists `USOSNVME.SYS` copied.
5. If anything fails on hardware: photo of row 9, and from the BIOSTAR SSD
   side nothing is needed (usosnvme keeps no on-disk trace yet); the event
   log (usosnvme, ids 0x4E5600xx) if Windows comes up.
