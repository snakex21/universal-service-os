# Windows 95 first boot: DELKEY before the real-mode import

Base: `564a4eee`, branch `codex/w95-firstboot`. This piece fixes the
post-Setup display preparation; it is not a complete first-desktop PASS.

The original 950 `REGEDIT /L` restores the hive's read-only/system/hidden
attributes. A subsequent DOS read/write open therefore fails before any
CREG header, checksum or key checks. Extracting that file to an ordinary
host file clears those FAT attributes, explaining the successful host run
on the same hive bytes. It was not a different hive layout.

In QEMU, using the X470 micron7 `SYSTEM.VL` and original installed 950
REGEDIT:

| Order | Result |
| --- | --- |
| DELKEY on the original copy | 0 |
| REGEDIT import, then DELKEY | import 0, DELKEY 2, FAT attributes `0x27` |
| Same import, clear attributes through DOS INT 21h, then DELKEY | 0, attributes `0x20` |
| DELKEY before REGEDIT | both 0 |

The initial fixture's older floppy REGEDIT did not import successfully;
that attempt is explicitly excluded from the diagnosis. No Microsoft
file or hive is stored in this repository.

The generated `VESALATE.BAT` now deletes the legacy `Enum\Root\*PNP0900`
subtree before importing `VLATE.REG`, after saving both hives. Rollback
clears attributes again before restoring the backups. An error is written
durably to `VLATE.ERR` before the handled `VLATE.RUN` is removed.

`VESBIND DELKEY hive key [log]` preserves the existing return codes and
silent four-argument interface. The optional adjacent `VLDEL.LOG` records
the exit code and the exact validation/write stage (`hive-open`, headers,
checksums, path, subtree, writes, completion). Logging failure returns 3 so
the caller restores the backup. Reasons are also copied to the existing
USOS log on failure. The change stays within the existing source-950 late
hook; it does not add that hook to OSR2+.

The actual generated batch was executed under original DOS/REGEDIT in
QEMU, using the X470 B1 hive with explicit existing REG95/VESA95 completion
markers as fixture preconditions. Result: debug-exit 85, 4.003 s,
`VLATE.OK`, no RUN/ERR, legacy enum subtree absent, final hive attributes
7, and `VLDEL.LOG` exit 0/reason complete. This is not a fresh-install
test or proof that PnP cannot recreate the devnode on later GUI boots.

Private evidence root: `K:\USOS-VM\W95RTM-FIRSTBOOT-20261025`, cases
`delkey-attrs`, `delkey-own-attrs`, `vesalate-production`. Images remain
preserved. Host tests: 17 synthetic/generator checks and the separately
enabled original-hive check; original-hive copies stay beside their private
source, including under test. Full first boot and two GUI-start checks are
still pending.

## Bounded GRPCONV and the original Setup value

`USOSGRPW.EXE` is a6656-byte OpenWatcom i386 GUI4.0 program without CRT,
importing only KERNEL32/USER32. It launches the original Windows directory's
`GRPCONV.EXE -s`, pumps messages while waiting on that process, and enforces
a120-second deadline. On timeout it terminates only descendant PROGMAN
processes found through one Toolhelp snapshot, then its own GRPCONV. It
always returns0 to the Setup chain and logs beside its executable.

Two isolated installed950 QEMU tests completed without operator input:

- Original GRPCONV completed in2576ms with its own exit1; the watchdog
  returned0. This is process completion, not proof of a fresh conversion.
- A test-only300-second GRPCONV spawning a test-only PROGMAN was stopped at
  the120-second deadline. Both termination calls succeeded, helper elapsed
  120027ms, helper exit0; the fixture then requested normal Windows shutdown.
  QEMU exited0/139.641s. The fixture's shutdown is not product behaviour.

The tested watchdog SHA256, independently read from both closed floppy
payloads, is`f3604356faccca33faf30a45ff20c1a220712c89935be6f66ad15a780d5b2956`.

The real SYSTEM.1ST values are`Programy w menu Start` (RTM PL) and
`Programs on the Start menu` (OSR1 EN). `VESBIND WRAPGRP export output.reg`
matches the exact executable basename/`-s` command under RunOnce\Setup,
preserving the original quoted value name. Nonmatching commands are not
replaced; ambiguous matches fail without output. This also avoids guessing
names for other source languages.

Only the950 TZFIX:PENDING path uses WRAPGRP, after the hive backups. It
checks that the watchdog exists, imports the generated fragment, and checks
the actual re-export. Other source versions retain their previous path.
The watchdog is included in the build, payload packer, release requirement
list and golden payload inventory. Host checks:20synthetic/parser checks
(one optional original-hive check not rerun),21TZFIX and9payload-list PASS.

The actual generated TZFIX.BAT was tested with original950 DOS/REGEDIT,
separately using RTM PL and OSR1 EN SYSTEM.1ST: debug-exit85/2.458s and
85/2.254s respectively. Both have TZFIX.OK, no BAD, TZDST.PND, exact original
localized step now pointing to USOSGRPW.EXE, and final hive attributes7.

An initial component fixture stopped at an actual Microsoft Networking
password dialog: AutoAdminLogon alone did not bypass it on the older
installed source. The failure overlay is preserved. Deleting the stale
Network\Logon key before restoring username/LMLogon values eliminated that
dialog in the component test; the product's unsupported950 REGEDIT /D at
that point still needs assessment in the real new-payload flow.

Observed startup order on already installed950: ordinary RunOnce executed
with no taskbar, then Run executed with a taskbar. Recreating Setup as a
subkey alone did not execute its added value in that state. Whether a long
message-pumping ordinary RunOnce process blocks the desktop is the next
small observation, before choosing the first-desktop integration design.

## Ordinary RunOnce coordinator and native restart contract

`USOSFB.EXE` is a source950-only Win32GUI4.0 helper withoutCRT. FIRSTBT.BAT
arms an ordinary RunOnce value after phase1, without creating Setup. It
refuses to expose a desktop after any required late-preparation or package
check fails. The journal separates the original Setup-to-DOS transition
from the sole post-add-ons restart, and refuses automatic retries of an
interrupted installation phase. Its error screen holds the desktop for
repair; it never automatically powers off the machine.

The generated queue ran through original950 DOS/REGEDIT in
`firstbt-queue-dos`: debug-exit85/0.970s, all6original Setup values unchanged,
ordinary USOSFirstBoot present, no ERR, final hive attributes7. The host
assertion was corrected against the same closed hive: original950 REGEDIT
retains doubled separators and omits a trailing NUL. No QEMU rerun for that
assertion correction. Win95 accepted the same path form in native tests.

`coordinator-contract-r3` completed in41.132s with no operator input. A
synthetic package ran at tray=0, exactly one coordinator final restart
occurred, `/setup /check` ran at tray=0, LAN/IE defaults completed at tray=0,
and only then the Run fixture saw tray=1. FIRSTBT.OK records one final
post-add-ons restart. Optional display/DOS-box-mouse work was excluded from
this orchestration fixture; real late markers were represented by test
preconditions. This is not a fresh-install or full-resolution/network PASS.
Two earlier failure fixtures remain preserved: the first correctly caught
the selected DOS-box mouse missing from the older SYSTEM.INI; the second
reached its post-restart LAN check and caught a missing Favorites path.

`USOSLAN /setup /refresh` now accepts only the verified source950 phase1/
VLATE boundary and applies defaults before the taskbar. Only this explicit
handoff may initialize an absent OS Favorites value in Windows\\Favorites;
existing user paths and other systems keep their earlier behaviour. The
positive coordinator test exercised that case. USOSRES/setup similarly
requires source950 plus phase1/VLATE/FIRSTBT markers; it can exercise the
actual display policy in native QEMU and avoids the ordinary Run deletion
delay while Explorer is still synchronously waiting in RunOnce.
