# Windows 7 SP1 x64 (PE10 donor path) on NVMe: Setup's disk check (2026-10-21)

Branch `fix/w7x64-nvme-setup`. Not merged, not deployed, no hardware run yet.

## X470 failure

Build `B261021-194837-FCE78840` on the Kingston, original Windows 7 Ultimate
SP1 PL x64 ISO, native UEFI path (x64 PE10 donor runs the ISO's own
`sources\setup.exe`, UefiSeven), Micron 3400 NVMe in M.2 as the only target.
Setup's disk page lists "Dysk 0 - Nieprzydzielone miejsce 476.9 GB"; on
select: "Nie można zainstalować systemu Windows na tym dysku. System Windows
potrzebuje sterownika urządzenia [Standardowy kontroler NVM Express]", Dalej
disabled. The PE10's inbox stornvme drives the disk; Setup refuses it. No
logs were available on this host (Kingston and Micron not attached).

## Root cause

Windows 7 / Vista Setup's check is a lookup of the disk stack's device IDs in
the media's `sources\hwcompat.txt` (`IsDeviceIDPresent ... in hwcompat
list`, setupact.log of the x86 runs, `docs/nvme-nt6-2026-10-12.md`
section 7). The Windows 7 list predates NVMe, so `PCI\CC_010802` served by
the donor's `stornvme.inf` fails, whatever the install image contains. It runs
on the disk page, before any `offlineServicing` work.

What the PE10 path did for NVMe until now:

* `usos-nvme-packages.flag` (SP1 media) adds KB2990941 / KB3087873 (with
  KB4474419, KB2685811) as `<servicing>` packages to the generated answer:
  they service the installed system, after the disk page;
* the bundled and user driver library (`usos-win7-drivers`, including DATA
  `Drivers\x64\NVMe\MS_StorNVMe`, an INF + SYS without a catalog) reaches only
  `offlineServicing` / `PnpCustomizationsNonWinPE` DriverPaths, by design: the
  PE10 is never given Windows 7 drivers.

Neither reaches the hwcompat check. `docs/windows7-pe10-handoff` already
noted "Pełna instalacja na NVMe w tej nowej ścieżce nie jest jeszcze
potwierdzona"; the 6in1 image passed because its own (PE10) Setup and media
are newer. Loading a driver with "Załaduj sterownik" would not help: Setup
then migrates the PE-loaded boot driver through the Windows 10
`DriverStoreOfflineAddDriverPackageW`, which refuses NT 6.1 images
(0x80070032, x86 path section 3).

## Fix (`tools/windows7_modern_startup.cmd`)

Same route as the x86 donor path (`windows_x86_csmwrap.cmd :nvme_setup`,
X470 PASS Windows 7 SP1 x86 on the Micron, 2026-10-14):

1. `:nvme_setup`, only with `usos-nvme-packages.flag` and an NVMe controller
   in the PE (`Services\stornvme\Enum` Count not 0): `robocopy` the ISO's
   `sources` without `install.wim/.esd/.swm` to `X:\USOS-src\sources`
   (`boot.wim` separately; dropped when the RAM disk has no room), append
   `stornvme.inf:` / `PCI\CC_010802` to the copy's `hwcompat.txt`, start Setup
   from that copy (working directory = the copy, as on x86) with the
   unchanged `/installfrom:<ISO>\sources\install.wim` and answer. Windows 7
   Setup stays on `X:` (from a SUBST drive it crashed in WinSetup.dll on x86).
   Any failure keeps the original Setup (SATA unchanged; NVMe refused as
   before). Nothing is injected into the PE, so nothing is migrated.
2. The installed system gets stornvme from the `<servicing>` packages
   (unchanged). `:nvme_target`, after Setup: in the one new installation,
   when `stornvme.sys` exists, check `CriticalDeviceDatabase\pci#cc_010802`
   in the offline SYSTEM hive; if Setup left none, add it (stornvme, SCSIAdapter)
   and set stornvme Start 0. Logged, never fatal.

Not needed here: the x86 `nodump` step (that donor booted from the NVMe
staging partition; this one boots from the USB stick).
