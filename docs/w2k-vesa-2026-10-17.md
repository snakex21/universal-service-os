# Windows 2000: VESA display (2026-10-17)

Before: Windows 2000 on the X470 (MPS and ACPI flows, CSMWrap) ran with the
stock `vga.sys` at 640x480x16. The RX 560 has no 2000 driver.

## What USOS does (phase 1)

- **Own miniport:** `usosvbe.sys` (GPL-3.0-or-later, `tools/nt4/usosvbe`), the
  NT 4.0 build **unchanged**. The NT 4.0 build already runs on X470 at
  1024x768x16. All 8 of its imports (6 `VideoPort*`, `MmIsAddressValid`,
  `PsGetCurrentProcessId`) resolve on the 2000 SP4 kernels, every 2000 HAL and
  `videoprt.sys`. 2000's videoprt still loads legacy (NT 4.0-size) miniports,
  and on x86 its `VideoPortInt10` uses the same V86 path in CSRSS. So no NT5
  build is needed (QEMU result below).
- **Display driver:** the CD's own `framebuf.dll`. Text-mode Setup installs
  it from `[files.vga]` of TXTSETUP.SIF. The CD's `I386\FRAMEBUF.DL_` goes
  along as a second source, and 2000's own `expand.exe` unpacks it. **USOS
  never ships any Microsoft file.**
- **When:** at setup end, not in text mode. Text-mode and GUI-mode Setup
  stay on VGA, so a VESA problem cannot break the install.
  `w2k_stage.sh` (section 11, `usos_w2k_vesa_stage`) writes these files to
  `C:\USOS\W2K`: `USOSVBE.SYS`, `FRAMEBUF.DL_`, `VESA.REG` and `vesa.cmd`.
  `usos-setup.cmd` (`[SetupParams] UserExecute`, the existing 2000
  setup-end hook for Professional and Server) calls `vesa.cmd`, which:
  1. uses `framebuf.dll` (or expands it from the CD's copy; with neither,
     VGA stays and the log says so);
  2. copies `usosvbe.sys` to `system32\drivers`;
  3. runs `regedit /s VESA.REG`: `Services\usosvbe` (Start 1, Group Video),
     `Device0` with InstalledDisplayDrivers = framebuf and VgaCompatible 0,
     plus DefaultSettings **1024x768x16 @60** in `Device0` and in the current
     hardware profile's copy;
  4. adds a boot.ini entry `"Windows 2000 [VGA mode]" /fastdetect /basevideo`
     that uses the default entry's ARC path, and sets the timeout to 5 s. It
     writes boot.ini through a copy that must still contain `default=` and
     the new entry, and keeps the old file as `C:\USOS\W2K\boot.ini.usos`.
  It logs to `%SystemRoot%\usos-setup.log`.
- The PnP `vga` service (on the PCI display device) and `VgaSave` stay as
  they are. Full-screen consoles, Safe Mode and `/basevideo` use them.
- **Off switch:** DATA
  `Systems\Windows\Windows 2000\Unattended\vesa-off.txt` (any content). With
  it, nothing is staged and VGA 640x480 stays (`legacy_xp_staging.sh`,
  `USOS_W2K_VESA=off`).
- **Package:** `usr/lib/usos/w2k-drivers/usosvbe/usosvbe.sys`
  (`build_xp_uefi_csm_trial.py w2k_driver_files`). Staging stops before any
  target write if the file is missing.

Tests (host, no Microsoft files): `tools/tests/test_w2k_usosvbe.py` checks:
- imports against `tools/tests/data/w2ksp4_exports.txt`, a list of export
  names only, generated from the 2000 SP4 PL CD with `--dump-exports`;
- the staged files against goldens (VESA.REG byte for byte, the order of the
  vesa.cmd checks);
- the wiring.

`test_w2k_staging.py` has the updated package list.

## QEMU (not hardware evidence)

2026-10-17 runs, q35 + OVMF + CSMWrap 3.1.2-usos11, `-vga std`,
`-nodefaults`, TCG, 2 vCPUs, 2000 Pro SP4 PL (W2KPLCMA4.811):
- **Preparation PASS on both flows.** The log says `VESA staged` and
  `APPLIED PASS ... VESA usosvbe at setup end (vesa.cmd)`.
- **Both flows (ACPI after about 40 min, MPS after about 75 min) stopped at
  the end of GUI Setup's "Installing devices" with a fatal error:**
  "Inicjowanie podsystemu zabezpieczeń nie było możliwe" (the security
  subsystem could not be initialized). `setuperr.log` shows that Setup
  cannot create `RegisteredProcessors` in `Control\Session Manager` because
  of "insufficient system resources", which looks like a SYSTEM hive or
  registry quota problem. This happens before setup end: vesa.cmd never ran,
  and the only VESA change at that point is files in `C:\USOS\W2K`. So it is
  **not caused by the VESA change**, but it blocks the QEMU check of VESA.
  It needs its own investigation: an A/B run with `vesa-off`
  (`USOS_W2K_VESA=off`), the SYSTEM hive size after device install, and a
  comparison with the q35 PASS of 2026-10-13 (B261013-164951).
- **Not yet verified in QEMU:** that the desktop comes up at 1024x768x16,
  that [VGA mode] gives 640x480, and that restart works.

## X470 test

The QEMU run is not hardware evidence. The X470 check is a fresh 2000 SP4
install (MPS flow first, `acpi-off.txt` present) from a build with this
change. Expected:
- the first boot after Setup comes up at 1024x768;
- `%SystemRoot%\usos-setup.log` contains `vesa on`;
- `Services\usosvbe\Device0\UsosVbeDiag` (regedit) reads
  `... set=1024x768x16/... ok`;
- `[VGA mode]` in the boot menu gives 640x480;
- restart works.

In-place option on the existing 2000 Server SP4 MPS install:
1. Copy `usosvbe.sys` to `system32\drivers`.
2. Make sure `system32\framebuf.dll` exists (otherwise
   `expand FRAMEBUF.DL_ framebuf.dll` from the CD's I386).
3. Import `VESA.REG`.
4. Add the `[VGA mode]` line to boot.ini by hand.
5. Reboot.

Risks:
- VBIOS V86 calls under the MPS/ACPI HAL with xhci98 polling.
- No HwResetHw: after the switch to VESA, a STOP screen may not show.
  `[VGA mode]` is the way back.

## Later

- **Phase 2:** `usosres.exe`, a first-logon mode picker
  (EnumDisplaySettings / ChangeDisplaySettings CDS_TEST, then
  CDS_UPDATEREGISTRY). It takes the profile's `display=WxH`, otherwise
  "auto" = the largest mode up to 1920x1080 (32 bpp, then 16). The profile
  `display=` for 2000 then means Full HD on X470.
- XP x86 / 2003 x86: **not needed**. The user confirmed XP runs Full HD on
  the X470 (2026-10-17), so no VESA work there.
- XP x64 / 2003 x64 would need an amd64 build.
