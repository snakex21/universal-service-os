**Detection evidence and limits.** Whistler and Neptune lack the SetupData BuildNumber key, but their TXTSETUP.SIF [Version] DriverVer supplies 5.1.2542.0 and 5.50.5111.1. The text parser uses this before the coarse SetupData version; a caller-supplied executable version still takes priority. The real micro-Linux NT5 source probe reads DriverVer, logs driver_version/source_identity and rejects a pre-release source in an RTM folder before patching. Missing DriverVer stays unknown; malformed or duplicate DriverVer fails closed. The PE/NE parser and non-NT5 legacy detection remain host-side helpers, not automatic 9x/UEFI source detection. PRODSPEC alone would select the wrong release. WinPE SIF is separately marked so FLP does not become Server 2003. Version 4.10.0.999/4.90.0.2525 stores its build in the low word, unlike NT's 5.1.2542.0. A zero/missing build is unknown, not a beta. A 4.0 version requires NT versus 9x lineage so Windows 95 RTM/OSR is not misclassified as an NT4 beta.

Conservative family thresholds: NT 5.1 nonzero build <2600 → Whistler; NT 5.0 <2195 → W2K beta (5111 has a separate Neptune rule); NT 5.50 → Neptune; NT 6.0 <6000 → Longhorn; NT 6.1 <7600 → 7 beta; 4.90 <3000 → Millennium; 4.10 exactly 999 → Nashville; 4.10 >999 and <1998 → Memphis; 4.0 win9x <950 → Chicago; 4.0 NT <1381 → NT4 beta; NT3 boundaries 3.10/511, 3.50/807, 3.51/1057. **Clock option and VM arguments.** Profiles accept beta_clock=off, beta_clock=auto, or YYYY-MM-DD (empty preserves existing behavior). Dates are strict Gregorian dates from 1980 through 2099. Auto lookup requires both system id and exact build; an unknown build errors. The test dates above are selected dates for experiments, **not confirmed expiry dates**. Except the Windows 7 public statement and dates supplied by the brief, no authoritative expiry window was established. [Microsoft confirms the Windows 7 Beta expiry and earlier shutdown date](https://blogs.windows.com/windowsexperience/2009/05/26/clarification-on-the-date-for-bi-hourly-shutdowns-for-the-windows-7-beta/); the brief's “no timebomb” must not be assumed for a stock build 7000 image.

The central answer dispatcher emits ;USOS-BETA-CLOCK only for catalog beta ids; direct RTM renderers never emit it. A mixed profile therefore leaves NT4, 98 SE, Me RTM, POSReady and WinFrame unchanged. Non-beta plans omit [beta], and runtime helpers ignore and log non-beta settings even in user-supplied answers or inherited environment variables. The existing preparation reads beta metadata, rejects duplicates, validates it, and logs BETA_CLOCK with host_rtc=unchanged. **9x phase-1 QEMU still uses base=localtime and physical RTC is unchanged**; this metadata has no 9x clock effect. Runtime auto receives build=0 and stops until measured build integration exists. It must receive a measured build before auto can be used; no build is guessed from the catalog name. The shared helper generates one quoted QEMU argument, e.g. -rtc base=1999-12-11T12:00:00. Default still generates base=localtime. Native/NT5 plans carry the setting as [beta] clock=... for future integration; they do not change RTC today. There is no editor widget yet; this host-tested option is in the profile file.

**Physical clock project — not implemented.** Before a non-VM beta preparation, USOS should validate the exact source/build, save a restore ticket under EFI/USOS/Clock with job id, target serial/GUID, original UTC/local-time convention and original RTC, then apply the selected test time in micro-Linux immediately before the existing reboot. A beta answer should disable automatic W32Time/NTP for that installation only, keeping that change in the job record. No fabricated universal registry/answer directive has been emitted in this delivery. Windows 9x has no W32Time service; optional sync applications require separate handling.

Every next USOS entry, including after a failure, must detect the restore ticket before starting another OS. Restore from a trusted current-time source when available; otherwise restore the saved value as a **lower bound** and explicitly record uncertain elapsed time. A monotonic timer does not survive arbitrary shutdowns, so an exact “current time” cannot be reconstructed from one old RTC snapshot alone. Do not silently claim it has been restored accurately. A verified restoration clears the ticket; logs retain job id, original/guest/restored times and source of restored time. Dates in unrelated systems and certificate checks are affected by motherboard RTC rollback, so the default remains off until restoration is implemented and reviewed. RTC writes/restoration were neither performed nor tested in this task.
