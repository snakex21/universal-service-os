# Windows 98 SE — poprawka RAM i naprawa istniejącej instalacji

## Przyczyna i zakres

Użytkownik potwierdził 2 GB RAM oraz fizyczną instalację dochodzącą do
przygotowania pierwszego uruchomienia. Późniejszy start zatrzymał się na logo.
Duża ilość RAM jest znanym problemem Windows 98 SE, lecz sam obraz ekranu nie
rozstrzyga, czy to jedyna przyczyna na tym komputerze.

USOS dołącza niezmodyfikowany Patcher9x 0.9.91 z poprawką RAM Rudolpha Loewa.
Wybiera wyłącznie `mem`; pozostałe poprawki CPU/TLB i opcja `16m` nie są
stosowane. To modyfikacja zarządzania pamięcią, bez wpisu ograniczającego
Windows do 512 MB. Patcher i CWSDPMI są przypięte sumami SHA-256; licencje,
informacja o pochodzeniu i źródła towarzyszą pakietowi na ESP.

## Obsługa

Windows → Windows 98 SE → obraz ISO → Automatic (DOS Setup).

- **Napraw RAM w zainstalowanym Windows 98**: wybierz dysk i zatwierdź
  ZASTOSUJ POPRAWKE RAM. Naprawa nie formatuje i nie przebudowuje partycji.
  Po potwierdzeniu sukcesu wyjmij pendrive i uruchom Windows z dysku.
- **Nowa instalacja Windows 98 SE**: wybierz dysk, rozmiar 8/4/2 GiB i
  zatwierdź usunięcie jego dotychczasowych partycji. Poprawka trafia do
  `C:\WIN98` po skopiowaniu źródła, zanim ruszy Setup.

Naprawa obsługuje układ tworzony przez USOS: pojedynczą aktywną partycję
FAT32 w pierwszym wpisie MBR. Wymaga `C:\WINDOWS\WIN.COM`,
`C:\WINDOWS\SYSTEM\KERNEL32.DLL` i `C:\WINDOWS\SYSTEM\VMM32.VXD`.
Bez tych plików kończy się przed zapisem. Obraz ISO nadal jest potrzebny
do uruchomienia oryginalnego DOS-u, również w trybie naprawy.

Przed zmianą zachowuje VMM32.VXD i istniejące luźne VMM.VXD/VCACHE.VXD
w pierwszym wolnym `C:\USOS98\RAMBK0`–`RAMBK9`. W tym samym katalogu
zostaje `PATCH.LOG`. Nie nadpisuje wcześniejszych katalogów kopii.
Po błędzie lub wykryciu przez upstream braku nowych poprawek nie ogłasza
sukcesu; należy odczytać log. Patcher zachowuje też własne pliki `.BAK`.

## Start DOS i Setup

Oba tryby korzystają z oryginalnego DOS-u z ISO i źródła FAT16 w RAM.
Filtr INT 13h udostępnia wyłącznie wybrany dysk docelowy jako C:.
MEMDISK używa domyślnego dla upstream `safeint`. CWSDPMI otrzymuje `-s-`,
więc nie tworzy pliku wymiany na dysku. Instalator rusza przez `SETUP /IS`:
pomija ScanDisk i związany z nim ekran wymagający dodatkowego ENTER.
Pozostałe pytania oryginalnego instalatora Windows pozostają interaktywne.

## Zweryfikowane wyniki

Build `B260912-131019-36278D30`: pełny `build.bat` PASS oraz
`tools/tests/run.ps1 -Suite all` PASS, włącznie z QEMU UEFI x86_64 i ARM64.
Core ma 245000 bajtów przy limicie 245760 bajtów części PM32.

Produkcja w QEMU Pentium III, 2048 MiB RAM, źródło USOS 16 GiB i pusty
cel 32 GiB: wybór nowej instalacji → partycja 8 GiB → SYS/COPY → poprawka
RAM → oryginalny graficzny Setup, bez dodatkowego ENTER po drodze.
Źródło przez cały przebieg miało zero zapisów. Odczyt niezależnym parserem
FAT32 potwierdził niezmienione 95 plików ISO, 115683656 bajtów, oraz zgodność
obu dodanych VXD bajt w bajt z osobnym zastosowaniem poprawki wersją Win32.

Tryb naprawy: domyślne ANULUJ zachowało zero zapisów na obu dyskach.
Próba na dysku bez `C:\WINDOWS` wyświetliła odmowę i również zachowała
zero zapisów. Lokalne dowody są w `zig-out/win98-work/`:
`ram-release-final-build.log`, `ram-all-tests.log`, `ram-native-gui.png`,
`ram-native-blockstats.txt`, `ram-source-verify.log`, `repair-confirm.png`,
`repair-cancel-stats.txt`, `repair-missing.png`, `repair-missing-stats.txt`.

Próba dodatnia naprawy użyła prawdziwej instalacji po pierwszym uruchomieniu.
Na osobnej kopii cofnięto poprawkę RAM, a następnie zastosowano ją z menu
USOS w oryginalnym DOS-ie. Wynik: PASS. Spośród 2574 istniejących plików
zmienił się wyłącznie `WINDOWS\SYSTEM\VMM32.VXD`. Kopia w `RAMBK0` była
bajt w bajt zgodna z plikiem sprzed naprawy. Wynik patchowania był identyczny
z niezależnym uruchomieniem przypiętej wersji Win32. MBR i sektory rozruchowe
pozostały niezmienione, a źródło USOS miało zero zapisów. Dowody:
`repair-done.png`, `repair-applied-stats.txt`, `repair-verify.log`,
`repair-applied-dos.log`. Upstream pozostawił dodatkowo swoje `.BAK` i `.P9X`.

Osobny start z 2048 MiB RAM i samym dyskiem po instalacji doszedł do ekranu
„Informacje o użytkowniku” po pierwszym restarcie, bez USOS ani MEMDISK.
Potwierdzono start z oryginalnym kodem MBR zapisanym przez Setup
(`standard-2gb-continuation.png`). Pierwsza próba startu zwróciła błąd dysku;
nie udało się go odtworzyć w izolowanej próbie oryginalnego obrazu. Dodano
do lokalnego narzędzia testowego oczekiwanie na zwolnienie pliku przez
poprzednią VM przed kolejnym startem. Przyczyna pierwszego błędu pozostaje
nieustalona; produkcyjny kod MBR nie został zmieniony w tej poprawce.

Drugie odizolowane uruchomienie oryginalnego obrazu z kodem Setup, tym razem
z normalnym zapisem do osobnej kopii dysku, również doszło do tego ekranu
(`standard-boot-check.png`). Sam dysk po naprawie także uruchomił Windows
z 2048 MiB RAM i doszedł do dalszej konfiguracji
(`repair-2gb-result.png`). Wcześniej automatyczny ScanDisk zakończył kontrolę
po przerwaniu poprzedniej sesji testowej.

Nie jest to potwierdzenie pełnej instalacji do pulpitu ani poprawności
sterowników na fizycznym MS-7100. Testy zatrzymano przed podaniem danych
użytkownika i klucza produktu.

## Wdrożenie na Kingston

Zaktualizowano Kingston DataTraveler 3.0, 61991813632 bajty,
GPT `31c644bf-74dd-4807-9cb2-46745adeadd4`, do
`B260912-131019-36278D30`. Aktualizator zweryfikował model, rozmiar, UUID
dysku i trzech partycji. Wszystkie pięć etapów zakończyło się PASS.
Układ GPT i obrazy DATA zostały zachowane.

Osobny odczyt zwrotny potwierdził obie aplikacje EFI, metadane wydania,
wszystkie 10 plików pakietu `ram-patch` i niezmieniony oryginalny obraz
Windows 98 SE na DATA. Core SHA-256:
`B2EDF2888CBBDA6720E319EA1BB0E98C141EBA8DF034234FEA21509A8D1DE5C2`.
Logi: `ram-kingston-update.log`, `ram-kingston-readback.log`.
