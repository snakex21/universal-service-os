# USB mouse for DOS programs (2026-10-18)

On the X470 without CSM, CSMWrap's SeaBIOS serves the USB mouse as the BIOS
PS/2 pointing device (INT 15h C2xxh; it far-calls the C207h handler from its
USB poll). A DOS program needs an INT 33h driver on top of that. USOS already
ships one: VBADOS 0.67 `VBMOUSE.EXE` (Javier S. Pedro, GPL-2.0-or-later,
unmodified, `tools/vendor/vbados/0.67`, source `VBADOS.TGZ` on the ESP). It
reads the mouse only through INT 15h C2xxh (VirtualBox/VMware integration is
detected and skipped on real hardware), so it works with the SeaBIOS USB
emulation unchanged. It was already loaded by `INSTALL.BAT` for MS-DOS /
Windows 3.x disks installed under CSMWrap (`C:\DOS\VBMOUSE.EXE` in
AUTOEXEC.BAT and the start menu); Windows 3.x uses it through VBMOUSE.DRV.
CuteMouse was not added: VBMOUSE does the same job, is already vendored and
audited, and has an `uninstall` action that the 9x hand-over below needs.

## What is new

| Where | What | Gate |
|---|---|---|
| FreeDOS RAM session (BIOS menu, also "Legacy BIOS mode (CSMWrap)") | `FDAUTO.BAT` loads `C:\VBMOUSE.EXE` before the Doszip file manager; `VBMOUSE.EXE` + `VBADOS.TXT` on the RAM disk (`freedos_tools.zig`, `build_freedos_support.py`, payload `EFI/USOS/dos-native/freedos/`) | always (on a BIOS PC it uses the PS/2 or SMM-emulated mouse; with no mouse it prints an error and stays out) |
| MS-DOS 6.22 RAM session (`LIVE.BAT`) | loads `C:\VBMOUSE.EXE` (the file was already on the RAM disk) | always, same reason |
| Windows 95 / 98 / 98 SE under CSMWrap, MS-DOS mode | `C:\USOS9X\DOSMOUSE.BAT` + `INWIN.COM` (USOS, GPL-3.0-or-later); AUTOEXEC.BAT runs `DOSMOUSE SETUP` at every start, which appends `CALL C:\USOS9X\DOSMOUSE.BAT` to `C:\WINDOWS\DOSSTART.BAT` once (FIND checks; a blank line first in case the file lacks a final line break) | `U9CSM=1`, not Me |

Unchanged: the MS-DOS / Windows 1.x-3.x installs (VBMOUSE already there;
`USOSKBC /M` puts its trampoline around whichever C207h handler is
registered, so VBMOUSE keeps working under it).

## Who owns INT 15h C207h (hand-over)

SeaBIOS keeps one C207h pointer for the whole machine (every V86 VM too).
The rule:

* **Plain DOS, MS-DOS mode, Windows 3.x**: VBMOUSE.EXE owns it.
* **Windows 9x / Me desktop**: USOSMOUS.DRV registers USOSKEY.COM's `mcb`
  (Enable / USOSATTACH) and removes it again (Disable: C200h off, C207h 0:0).
  USOSKEY.COM itself never calls C2xxh (host test checks it), so the TSR
  loaded from AUTOEXEC.BAT does not compete with VBMOUSE in DOS.
* **VBMOUSE must not be resident when Windows 9x starts** (98 SE finding:
  VBMOUSE.EXE next to Windows' own mouse stops Windows at KERNEL init). So
  `DOSMOUSE.BAT` does not leave the driver behind: it loads VBMOUSE, opens a
  nested `%COMSPEC%`, and when the user types `EXIT` it runs
  `VBMOUSE UNINSTALL` (C200h off, C207h 0:0, INT 33h/2Fh restored, memory
  freed) and then `EXIT`s the MS-DOS mode shell, i.e. back to Windows. If
  the unload fails (another TSR hooked INT 33h/2Fh after VBMOUSE) it says so,
  tells the user to restart with Ctrl+Alt+Del and returns to the prompt
  instead of starting Windows.
* `INWIN.COM` (INT 2Fh AX=1600h) stops DOSMOUSE inside a DOS box: a
  real-mode driver there would steal the global C207h pointer from
  USOSMOUS.DRV.

"Command prompt only" start (F8 / BootGUI=0): type `DOSMOUSE`; `EXIT`
unloads the driver (the primary shell ignores the EXIT that follows), then
`WIN` as usual. Do not type `WIN` at DOSMOUSE's nested prompt (Windows would
start with VBMOUSE resident). A PIF with its own MS-DOS mode CONFIG/AUTOEXEC
skips DOSSTART.BAT: no mouse there (not handled).

## Windows Me

Me has no "Restart in MS-DOS mode" and no real-mode command prompt start (IO.SYS
ignores BootGUI=0; the F8 menu has no command-prompt entry). Nothing of the
MS-DOS-mode part applies, so INSTALL.BAT writes no DOSSTART line for Me and
the Micron Me install needs no in-place files. Real-mode DOS only exists on
a Me startup floppy (not part of USOS).

## DOS boxes inside Windows 9x / Me (design only, not built)

Today a DOS box gets no mouse: USOSMOUS.DRV is a Win16 `mouse.drv` that feeds
USER directly; Windows' VMOUSE (which virtualises INT 33h per VM) is not
loaded (`[386Enh] mouse=` removed) and would get no input anyway. On Me the
DOS-box guard even pauses the BIOS mouse while a DOS box is open, because a
packet must never be far-called into a DOS VM's memory.

A working DOS-box mouse needs a VxD: a VMD/VMOUSE-compatible pointer source
that takes the packets (from the TSR ring, polled at ring 0, or a ring-0
C207h handler reached through a V86 break point in the system VM) and posts
them with `VMOUSE_Post_Pointer_Message` (or as a full *VMD replacement), so
VMOUSE's own INT 33h emulation serves the focused DOS VM and Windows gets
the same stream. That is the "VxD-level mouse" already parked in
docs/win9x-modern-2026-09-30.md; it would also replace the Me DOS-box pause.
Heavy (new VxD, DDK-level work, hardware-only testing): not started.

## Wheel (2026-10-18, needs CSMWrap patch 0016)

VBADOS VBMOUSE 0.67 already speaks the IntelliMouse protocol through the BIOS:
it asks for "streaming" packages (C205h BH=1), sends the knock (sample rates
200, 100, 80) and reads 4-byte packets when C204h then says device ID 3, and
it offers the CuteMouse wheel API (INT 33h AX=0011h -> 574Dh, CX bit 0; the
wheel count in BH of AX=0003h, event mask bit 7). SeaBIOS used to refuse
C205h BH=1 and never answered ID 3, so VBMOUSE fell back to 3-byte packets.
CSMWrap patch 0016 (USB wheel mice in the HID report protocol, IntelliMouse
emulation) makes the unmodified VBMOUSE.EXE report the wheel; no VBMOUSE
change. Older CSMWrap or a wheel-less mouse: VBMOUSE reports no wheel, as
today. The motion values in the probe are the same in both modes.

## Tests

* `tools/tests/legacy_bios/run_dos_mouse_probe.py` (QEMU, OVMF -> CSMWrap
  3.1.2-usos11 -> SeaBIOS -> FreeDOS 1.4 from NVMe, `i8042=off,vmport=off`,
  qemu-xhci usb-kbd + usb-mouse, `M33TEST.COM` (`m33test.S`) shows the
  INT 33h state):
  * `--mode session`: VBMOUSE from AUTOEXEC; INT 33h reset FFFFh, 3 buttons,
    X/Y follow `mouse_move` both ways (0,0 -> 88,24 -> 40,8), left press
    seen and counted. **PASS** 2026-10-18.
  * `--mode dosmouse`: DOSMOUSE.BAT + INWIN.COM as DOSSTART.BAT calls them;
    mouse checked at the nested prompt, `EXIT` -> "Driver uninstalled",
    INT 33h gone afterwards. **PASS** 2026-10-18 (FreeCOM, not COMMAND.COM 7).
  * `--csmwrap <efi> --wheel` (CSMWrap 3.1.2-usos11-int13x + 0016, throwaway
    build): `M33TEST` also shows AX=0011h (574Dh, CX=0001h) and the summed
    AX=0003h wheel count: QEMU `mouse_move 0 0 1` x3 -> -3 (up), then
    `0 0 -1` x5 -> +2. Session and dosmouse **PASS** 2026-10-18; the same
    session probe with 3.1.2-usos11 shows no wheel (CX=0, sum 0), **PASS**.
* `tools/tests/test_dos_mouse.py` (host): session wiring, payload lists,
  DOSMOUSE order (INWIN before load, unload before EXIT, failed unload never
  reaches EXIT), the DOSSTART append, the INSTALL.BAT lines (CSMWrap branch,
  not Me), staging lists, USOSKEY.COM makes no C2xxh call.

Not tested: MS-DOS 7.x COMMAND.COM and a real 98 MS-DOS mode (no 9x VM run by
decision; QEMU only with ready images), and nothing on the X470 yet.

## X470 checks

1. Legacy BIOS mode (CSMWrap) -> FreeDOS: the pointer moves in Doszip.
2. Same -> MS-DOS session: `EDIT` shows a mouse cursor, clicks open menus.
3. A 98 SE install made with this build: Start -> Shut Down -> "Restart in
   MS-DOS mode": banner "USB mouse for DOS programs is on", `EDIT` with mouse,
   `EXIT` -> "Driver uninstalled" -> Windows starts and its mouse works.
