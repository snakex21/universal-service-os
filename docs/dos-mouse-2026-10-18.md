# USB mouse for DOS programs (2026-10-18)

On the X470 without CSM, CSMWrap's SeaBIOS serves the USB mouse as the BIOS
PS/2 pointing device (INT 15h C2xxh; it far-calls the C207h handler from its
USB poll). A DOS program needs an INT 33h driver on top of that. USOS already
ships one: VBADOS 0.67 `VBMOUSE.EXE` (Javier S. Pedro, GPL-2.0-or-later,
unmodified, `tools/vendor/vbados/0.67`, source `VBADOS.TGZ` on the ESP). It
reads the mouse only through INT 15h C2xxh (VirtualBox/VMware integration is
detected and skipped on real hardware), so it works with the SeaBIOS USB
emulation unchanged. It was already loaded by `INSTALL.BAT` for MS-DOS /
Windows 3.x disks installed under CSMWrap (`C:\DOS\VBMOUSE.EXE` in
AUTOEXEC.BAT and the start menu); Windows 3.x uses it through VBMOUSE.DRV.
CuteMouse was not added: VBMOUSE does the same job, is already vendored and
audited, and has an `uninstall` action that the 9x hand-over below needs.

## What is new

| Where | What | Gate |
|---|---|---|
| FreeDOS RAM session (BIOS menu, also "Legacy BIOS mode (CSMWrap)") | `FDAUTO.BAT` loads `C:\VBMOUSE.EXE` before the Doszip file manager; `VBMOUSE.EXE` + `VBADOS.TXT` on the RAM disk (`freedos_tools.zig`, `build_freedos_support.py`, payload `EFI/USOS/dos-native/freedos/`) | always (on a BIOS PC it uses the PS/2 or SMM-emulated mouse; with no mouse it prints an error and stays out) |
| MS-DOS 6.22 RAM session (`LIVE.BAT`) | loads `C:\VBMOUSE.EXE` (the file was already on the RAM disk) | always, same reason |
| Windows 95 / 98 / 98 SE under CSMWrap, MS-DOS mode | `C:\USOS9X\DOSMOUSE.BAT` + `INWIN.COM` (USOS, GPL-3.0-or-later); AUTOEXEC.BAT runs `DOSMOUSE SETUP` at every start, which appends `CALL C:\USOS9X\DOSMOUSE.BAT` to `C:\WINDOWS\DOSSTART.BAT` once (FIND checks; a blank line first in case the file lacks a final line break) | `U9CSM=1`, not Me |

Unchanged: the MS-DOS / Windows 1.x-3.x installs (VBMOUSE already there;
`USOSKBC /M` puts its trampoline around whichever C207h handler is
registered, so VBMOUSE keeps working under it).

## Who owns INT 15h C207h (hand-over)

SeaBIOS keeps one C207h pointer for the whole machine (every V86 VM too).
The rule:

* **Plain DOS, MS-DOS mode, Windows 3.x**: VBMOUSE.EXE owns it.
* **Windows 9x / Me desktop**: USOSMOUS.DRV registers USOSKEY.COM's `mcb`
  (Enable / USOSATTACH) and removes it again (Disable: C200h off, C207h 0:0).
  USOSKEY.COM itself never calls C2xxh (host test checks it), so the TSR
  loaded from AUTOEXEC.BAT does not compete with VBMOUSE in DOS.
* **VBMOUSE must not be resident when Windows 9x starts** (98 SE finding:
  VBMOUSE.EXE next to Windows' own mouse stops Windows at KERNEL init). So
  `DOSMOUSE.BAT` does not leave the driver behind: it loads VBMOUSE, opens a
  nested `%COMSPEC%`, and when the user types `EXIT` it runs
  `VBMOUSE UNINSTALL` (C200h off, C207h 0:0, INT 33h/2Fh restored, memory
  freed) and then `EXIT`s the MS-DOS mode shell, i.e. back to Windows. If
  the unload fails (another TSR hooked INT 33h/2Fh after VBMOUSE) it says so,
  tells the user to restart with Ctrl+Alt+Del and returns to the prompt
  instead of starting Windows.
* `INWIN.COM` (INT 2Fh AX=1600h) stops DOSMOUSE inside a DOS box: a
  real-mode driver there would steal the global C207h pointer from
  USOSMOUS.DRV.

"Command prompt only" start (F8 / BootGUI=0): type `DOSMOUSE`; `EXIT`
unloads the driver (the primary shell ignores the EXIT that follows), then
`WIN` as usual. Do not type `WIN` at DOSMOUSE's nested prompt (Windows would
start with VBMOUSE resident). A PIF with its own MS-DOS mode CONFIG/AUTOEXEC
skips DOSSTART.BAT: no mouse there (not handled).

## Windows Me

Me has no "Restart in MS-DOS mode" and no real-mode command prompt start (IO.SYS
ignores BootGUI=0; the F8 menu has no command-prompt entry). Nothing of the
MS-DOS-mode part applies, so INSTALL.BAT writes no DOSSTART line for Me and
the Micron Me install needs no in-place files. Real-mode DOS only exists on
a Me startup floppy (not part of USOS).

## DOS boxes inside Windows 9x / Me (USOSVMD.VXD v2, 2026-10-19)

Without the VxD a DOS box gets no mouse: USOSMOUS.DRV is a Win16 `mouse.drv`
that feeds USER directly, and Windows' VMOUSE (which virtualises INT 33h per
VM) gets no input from it. On Me the v3 DOS-box guard even pauses the BIOS
mouse while a DOS box is open.

### The Me callback hazard (v1, 2026-10-18) and the fix

SeaBIOS keeps **one** INT 15h C207h far pointer for the whole machine and
far-calls it from its USB poll (INT 08h) in **whatever VM is current**. v1
registered USOSKEY's `mcb` there. On 95/98/98 SE that code is in the TSR
loaded from AUTOEXEC.BAT (global V86 memory, the same in every VM), but on
**Me** it is the copy USOSKEY.DRV installs in the system VM's
`GlobalDosAlloc` block - private V86 memory. A poll that lands while a DOS VM
is current runs whatever that DOS VM has at the same segment:offset (a hang
or a protection error, most likely when a DOS box is open or on Alt+Enter).
That is why v3's guard pauses the mouse; v1 with the guard lifted kept the
hazard (it was documented as "the next step").

v2 removes the dependency instead of guarding it: in VMOUSE mode the C207h
handler is a **VMM V86 callback** allocated by USOSVMD.VXD with
`Allocate_V86_Call_Back` at Device_Init. VMM's callbacks are breakpoints in
its global V86 area: the same address in every VM, trapping to ring 0 with
EBX = the VM that was current. The VxD reads the packet words (Z, Y, X,
status after VMM's simulated far return) from that VM's stack through **its**
high linear mapping, and writes to the system VM's memory only through the
**system VM's** high linear mapping. No V86 code in any private memory runs
for the mouse, whichever VM is current; the bridge's `mcb` is never
registered in this mode.

### What runs where (VMOUSE mode)

* `USOSVMD.VXD` (`src/platform/win9x/usosvmd.asm`, USOS, GPL-3.0-or-later),
  static VxD from `[386Enh] device=`:
  * init order `VMD_INIT_ORDER - 1` (just before VMOUSE in every phase; the
    DDK suggests Undefined for minidrivers, but the claim must land before
    VMOUSE's own Device_Init and its PS/2 detection); a type VMOUSE clears
    back to 0 during its init is claimed again at the next check;
  * Device_Init: if VMOUSE is loaded and has no mouse yet
    (`VMD_Get_Mouse_Data` type 0) it claims it with `VMD_Set_Mouse_Data`
    (serial type, no IRQ, 3 buttons) so VMOUSE's own PS/2 code never runs
    (its INT 15h C2xx probing hung the X470 / resets the emulated mouse ID to
    0 on Me) -> mode **minidriver**. If VMOUSE already has a mouse (another
    minidriver, its own PS/2 code) -> **observer**: never posts, so there is
    never duplicate motion; USOSMOUS then stays on its plain path. No VMOUSE
    -> nothing. Then `Allocate_V86_Call_Back`.
  * the callback queues each packet in the VxD's own ring (posted from a
    20 ms global time-out with `VMD_Post_Pointer_Message`: b1=20h, b2=08h,
    b3=10h, X as read, Y negated, overflow skipped) and copies it into the
    shared-block mouse ring (`USKY` v4) for USOSMOUS's wheel;
  * each time-out re-reads VMOUSE's mouse type; a change (someone else took
    the mouse later) switches to observer for good.
  * PM API (INT 2Fh AX=1684h BX=0 ES:DI -> `USOSVMD `): 0 status, 1 attach
    (USOSMOUS hands over the shared block, gets the callback address and the
    mode), 2 status block (64 bytes) for USOSDBG.
* `USOSMOUS.DRV` VMOUSE mode, only when `C:\USOS9X\USOSVMD.ON` exists, the
  VMOUSE and USOSVMD APIs answer, attach succeeds and the VxD says
  minidriver:
  * the BIOS registration (C205h, knock, C207h = the VxD's callback, C200h)
    goes through the system VM's real-mode INT 15h vector with DPMI 0302h,
    so a VxD that hooks V86 INT 15h C2xxh (Me's VMOUSE virtualises the BIOS
    mouse: in the 2026-10-19 X470 log none of USOSMOUS's C2xx calls reached
    SeaBIOS, only VMOUSE's own init with its V86 callback FD62:24F7) cannot
    swallow it;
  * USER's event procedure goes to VMOUSE (`VMDAPI_SET_MOUSE_EVENT_CALLBACK`):
    VMOUSE moves the pointer on the desktop and serves DOS boxes;
  * the 20 ms timer stays, **for the wheel only**: VMOUSE has no wheel, so
    the Z bytes the VxD copies into the shared ring are summed and sent to
    USER with AX=0800h exactly as in v4 (IE / Explorer scrolling unchanged);
    motion and buttons are skipped there;
  * `USOSPAUSE` does nothing; Disable takes the VMOUSE callback back and
    switches the BIOS mouse off through the same direct path.
  * new exports: `USOSVMDMODE` (9, USOSKEY.DRV), `USOSVMDINFO` (10, USOSDBG).
* `USOSKEY.DRV`: the v3 guard is armed unless USOSMOUS's `USOSVMDMODE`
  answers 1. The flag file alone is no longer enough: with the flag but no
  VxD (or an observer VxD) the bridge's mcb is registered again and the
  guard must stay. So when the VxD is active the guard never starves the
  DOS box; when it is not, everything is as in v3/v4.

DOS boxes see the mouse through VMOUSE's INT 33h: windowed (QuickEdit off,
the DOS program owns the mouse) and full screen. The wheel is not passed to
DOS programs in a DOS box (VMOUSE has no wheel API); in MS-DOS mode VBMOUSE
still has it.

### Logs

USOSDBG 1.7 `VMD` lines (also inside every USOSLOG MOUSE record): the flag,
what USOSMOUS decided (APIs, VxD mode, VMOUSE mode, event callback accepted,
the C207h target, direct INT 15h errors, wheel polls) and the VxD's status
block (VMOUSE version, mouse type at init / now, callbacks, how many came
while a DOS VM was current, last VM and packet, posted, ring drops, error
bits). The C2 ring line (CSMWrap usos15) shows whether SeaBIOS got the VxD's
callback.

### Enabling (in place)

`[386Enh] device=*vmouse` and `device=C:\USOS9X\USOSVMD.VXD` in SYSTEM.INI
(`U9FIX /CSM` deletes only `mouse=*vmouse` lines, not these), the new
USOSMOUS.DRV / USOSKEY.DRV, and `C:\USOS9X\USOSVMD.ON`. No registry change.
Off: delete `USOSVMD.ON` (USOSMOUS then never enters VMOUSE mode and the
guard is back); removing the two `device=` lines unloads VMOUSE/USOSVMD too.
**Only removing the `device=` lines stops the VxD from loading**: the flag
alone does not help against a boot failure inside the VxD (the v2 run below).

Provenance: USOS's own implementation from the **public Windows 95 DDK
documentation** - DOCS\KERNEL (VMM services, V86 callbacks,
Client_Reg_Struc, Map_Flat), DOCS\DESGUIDE\MOUSE.DOC (the VMOUSE minidriver
model, `Mouse_Event`, the VMD PM API), INC32\VMM.INC / VMD.INC (service
numbers, DDB, control block and register layouts). No Microsoft code is
copied; the driver links no DDK code (own DDB and control proc, `int 20h`
service dispatch only). Toolchain: OpenWatcom `wasm` + `wlink`
(`format windows vxd`), built by `tools/build_win3_usb_keyboard.py`.

Host tests: `tools/tests/legacy_bios/test_usosvmd.py` (layout, LE/DDB,
exact service set; at ring 0 in Unicorn: Device_Init claim / observer / no
VMOUSE / no callback, the callback reading a DOS VM's stack and writing the
system VM's ring, drain mapping, type change, PM API) and
`test_usosmous_vmd_emu.py` (USOSMOUS.DRV in Unicorn: VMOUSE mode only with
flag + both APIs + minidriver, C207h = the VxD's callback through DPMI
0302h, never the mcb, USER's procedure to VMOUSE, timer sends only the
wheel, USOSVMDMODE / USOSPAUSE / Disable, observer / no VxD / no flag keep
the plain path). **Not exercised end to end**: CSMWrap + USB cannot run in
QEMU and no 9x VM is run by decision, so VMOUSE loading with the VxD, the
DOS-box mouse, Alt+Enter and closing a DOS box are unverified until the
X470 run (kit: in-place on the Micron Me disk).

### v2 boot bluescreen on Windows Me and v3 (2026-10-19)

First X470 boot of v2 on the Micron Me disk: bluescreen at startup,
`VMM(01) + 00009676 Error 0E : 0028 : C000A676`. Root cause, confirmed in
Me's VMM (VMM32.VXD unpacked with an own W4 decoder, object 1 disassembled
with its fixups; scratchpad analysis, not in the repo):

* VMM 4.x links every 4.0 DDB backwards through `DDB_Prev` (+3Ch) once all
  static VxDs are loaded, and walks that chain for the reverse-order
  control messages (Destroy_Thread, VM_Not_Executeable2, Destroy_VM2,
  End_PM_App2, Destroy_Process, ...). The walk at VMM object 1 + 963Fh does
  `mov ecx,[ecx+3Ch]` / `call [ecx+18h]`; + 9676h is that call.
* v2 declared SDK 4.0 but its DDB stopped after `DDB_Service_Table_Size`
  (38h bytes); its status block followed directly, so Device_Init wrote the
  VMOUSE version and mouse-type bytes over `DDB_Prev` (+3Ch) and the
  callback address over `DDB_Size` (+40h). VMOUSE (init order 34000000h)
  came right after USOSVMD (33FFFFFFh), so the first reverse message went
  VMOUSE -> USOSVMD -> garbage -> page fault inside VMM.

v3 (`usosvmd.asm`, DDB version 3, PM API status BX=0300h):

* the full 50h-byte 4.0 VxD_Desc_Block (`DDB_Win32_Service_Table` 0,
  `'Prev'`, `DDB_Size` 50h, `'Rsv1'..'Rsv3'`); the status block, rings and
  Mouse_Instance start at DDB+50h. Nothing writes the DDB; Init_Complete and
  every time-out compare `DDB_Size` / `Rsv1..3` (read only; `DDB_Prev` is
  VMM's) and set err bit 80h when they changed (USOSDBG prints it);
* a second, latent v2 bug found on the way: VMM's V86 breakpoint dispatcher
  (Me VMM object 1 + 8B58h) does **not** simulate the far return, and
  VMOUSE's own BIOS-mouse callback (98 SE DDK debug VMOUSE.VXD,
  `VAD_BIOS_Far_Call`) reads the packet at SS:SP+4..+0Ah and ends with
  `Simulate_Far_Ret`. v2 read SS:SP+0..+6 (the return address as Z/Y) and
  never returned, so the first mouse packet after USOSMOUS registered the
  VxD's callback would have re-run the breakpoint for ever. v3 reads the
  arguments above the return address and calls `Simulate_Far_Ret`;
* claim timing re-checked and kept (just before VMOUSE in every phase): in
  the 98 SE debug VMOUSE `VMD_Get_Mouse_Data` only reads static data, so the
  pre-Device_Init calls touch no state VMOUSE builds later; VMOUSE's BIOS
  mouse setup is in its PS2_Device_Init path. `VMD_Set_Mouse_Data` AL (IRQ)
  stays 0: information only (Int 33h function 24h), there is no documented
  "none" value, and the VxD virtualises no IRQ (`MIF_NoIRQ`).

Provenance of v3: the fixes come from the public DDK headers / docs plus a
behaviour analysis of Microsoft binaries supplied by the user (Me's VMM, the
98 SE DDK debug VMOUSE), allowed by the project's local policy; only facts
(field use, calling convention) were taken, no code.

Boot-failure diagnostics. A failed boot has to explain itself without photos:

* CMOS breadcrumbs from the VxD were considered and rejected: the RTC alarm
  bytes 01h/03h/05h are CSMWrap patch 0009's APM record and are re-armed
  (40/0/1) at every CSMWrap start, i.e. before Windows on the next boot, and
  the other CMOS bytes are firmware-owned or inside checksummed ranges (a
  write could reset the X470's BIOS settings);
* instead the in-place kit (scratchpad `me-vmd2-kit`) turns on Me's own
  logged boot where Me honours it (MSDOS.SYS `BootMenu=1`,
  `BootMenuDefault=2` = "Logged", `BootMenuDelay=2`; if Me ignores these
  nothing changes), so C:\BOOTLOG.TXT lists every VxD load and init phase,
  and its `--off` mode removes the two `device=` lines, restores MSDOS.SYS
  and copies BOOTLOG.TXT / BOOTLOG.PRV, USOSLOG.TXT and USOSDBG logs off the
  disk first (the next boot is then the plain v4 path);
* on a successful boot the status block (USOSDBG `VMD` lines, every USOSLOG
  MOUSE record) has the mode, callback counters and the err bits incl. 80h.

Host tests added: DDB_Size 50h, `'Prev'`, `'Rsv1..3'` bytes as in Me VMM's
own DDB, status at DDB+50h or later, a capstone scan proving no instruction
writes an absolute address inside the DDB, a whole session (Device_Init,
Init_Complete, attach, 70 callbacks from both VMs, time-out, PM API copy)
leaving the 50h DDB bytes exactly as "VMM" left them, `ddb_check`, and the
callback ending with `Simulate_Far_Ret` with the arguments above the return
address. No 9x QEMU run (no ready 98/Me image; win98qi is an installer), so
v3 is host-tested only until the X470 run.

## Wheel (2026-10-18, needs CSMWrap patch 0016)

VBADOS VBMOUSE 0.67 already speaks the IntelliMouse protocol through the BIOS:
it asks for "streaming" packages (C205h BH=1), sends the knock (sample rates
200, 100, 80) and reads 4-byte packets when C204h then says device ID 3, and
it offers the CuteMouse wheel API (INT 33h AX=0011h -> 574Dh, CX bit 0; the
wheel count in BH of AX=0003h, event mask bit 7). SeaBIOS used to refuse
C205h BH=1 and never answered ID 3, so VBMOUSE fell back to 3-byte packets.
CSMWrap patch 0016 (USB wheel mice in the HID report protocol, IntelliMouse
emulation) makes the unmodified VBMOUSE.EXE report the wheel; no VBMOUSE
change. Older CSMWrap or a wheel-less mouse: VBMOUSE reports no wheel, as
today. The motion values in the probe are the same in both modes.
