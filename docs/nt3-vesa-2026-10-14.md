# NT 3.5 / 3.51: VESA display (usosvbe NT 3.x build) - 2026-10-14

Goal: more than 640x480x16 on Windows NT 3.51 and 3.5 (UEFI flow, X470
without CSM through CSMWrap). Same design as NT 4.0 (`docs/nt4-2026-10-07.md`,
`tools/nt4/usosvbe/README.md`): our own VBE miniport `usosvbe.sys` + the
**CD's own `framebuf.dll`** (never shipped by USOS).

## Findings (static analysis of the users' CDs for local diagnosis)

Checked on the NT 3.51 WS (build 1057), NT 3.5 WS (807) and NT 3.1 WS (511)
CDs: `videoprt.sys`, `framebuf.dll`, `vga.sys`, `winsrv.dll`, `ntoskrnl.exe`,
`TXTSETUP.SIF` / `VIDEO.INF`.

- **videoprt exports**: all six routines the miniport uses
  (`VideoPortInitialize`, `Int10`, `MapMemory`, `UnmapMemory`,
  `SetRegistryParameters`, `ZeroMemory`) exist in 3.1, 3.5 and 3.51. The
  kernel has `MmIsAddressValid` and `RtlQueryRegistryValues`, but **no
  `PsGetCurrentProcessId`** (NT 4.0 build's trace) -> not used in the NT 3 build.
- **`VIDEO_HW_INITIALIZATION_DATA`**: 3.5/3.51 reject `HwInitDataSize > 0x28`;
  **3.1 accepts exactly 0x20**. The NT 3 build passes 0x20 (one binary for all).
- **`VIDEO_PORT_CONFIG_INFO`**: same field offsets up to `HardwareStateSize`;
  `Length` = 0x48 (3.5x), 0x38 (3.1). The NT 4.0 check (>= offset of `Master`)
  would fail on 3.1 -> NT 3 build checks >= 0x38.
- **`VideoPortInt10`** (3.51): needs SeTcbPrivilege of the caller; on its first
  call (global flag) allocates linear 0..FFFFFh in the *current* process,
  frees `[VdmPhysicalVideoMemoryAddress, +Length]` and maps that physical range
  there; before every call it CRC32s C0000h-C0FFFh of the current process
  (`HardwareInformation.Crc32`) **without a fault handler**; then
  `Ke386CallBios(0x10, CONTEXT)` with a zeroed CONTEXT (ES = 0, like NT 4.0:
  buffers at linear 7000h / 7200h; the kernel's stub sits at 1000:0000,
  stack 1000:1FFC; the kernel's first `Ke386CallBios` maps the ROMs from
  `\Device\PhysicalMemory`). NT 3 build: Vdm range = A0000h/20000h (as for
  VGA; 0/0 would make the free release the whole low-MB allocation). After
  the first good int 10h call, a call is skipped while C0000h/C0FFFh are not
  valid in the current process (protects against the unguarded checksum
  from a process other than CSRSS). A first version skipped the call *before*
  any success too: C0000h is not mapped in CSRSS until videoprt's first call,
  so every call was skipped (`4F00=FFFFFFFF vp=65535`, framebuf failed, STOP
  C0000143 "framebuf is bad or missing" with VgaStart off).
- **HwInitialize** runs on IRP_MJ_CREATE (first open = CSRSS/winsrv), close
  sends `IOCTL_VIDEO_RESET_DEVICE` - as on NT 4.0.
- **framebuf.dll** (3.1, 3.5, 3.51): same IOCTL numbers as NT 4.0; mode filter
  `NumberOfPlanes == 1`, `AttributeFlags & GRAPHICS`, bpp 8/16/24/32; picks the
  mode equal to DEVMODE width/height/bpp (and frequency unless 0), else fails;
  all-zero DEVMODE = first mode. Masks from the mode info (BITFIELDS).
  `QUERY_POINTER_CAPABILITIES` / `QUERY_COLOR_CAPABILITIES` failures are not
  fatal. 16 bpp direct colour works with the existing mode list (no 8 bpp
  palette mode needed).
- **framebuf mode match + 15 bpp**: framebuf compares DEVMODE bpp with
  planes x BitsPerPlane, which is 16 for 5:5:5 too, and takes the first hit:
  the sorted list put 1024x768x15 first (`set=1024x768x15/116`). The NT 3
  build lists no 15-bit modes.
- **Display selection**: winsrv reads `Services\<drv>\Device0`
  `InstalledDisplayDrivers` (REG_MULTI_SZ), `VgaCompatible`,
  `DefaultSettings.{BitsPerPel,XResolution,YResolution,VRefresh,Interlaced,Flags}`
  (VIDEO.INF writes the same set). NT 3.5x installs vga.sys as **VgaSave**
  (Group "Video Save", Start 1, no `vga` key) **and VgaStart** (Group
  "Video Init", Start 1, `Device0\ForceVga` = 1), both NT 3.5 and 3.51.
  "Video Init" loads before "Video", so VgaStart is `\Device\Video0` and wins
  (QEMU: 640x480 with usosvbe registered and loaded) -> usosnt3 sets VgaStart
  Start = 4, as the NT 4.0 VESA.REG does. VgaSave stays.
- **`/BASEVIDEO`**: the 3.x video port has no BASEVIDEO logic (only vga.sys
  reads `SystemStartOptions`). The NT 3 build returns STATUS_NO_SUCH_DEVICE
  from DriverEntry when `SystemStartOptions` contains BASEVIDEO, so the
  `[VGA mode]` entry that nt4_vm_finish writes keeps 640x480x16.
- **framebuf.dll on disk**: NT 3.5/3.51 text-mode Setup copies it
  (`[files.video]` of the VGA display); `expand.exe` is installed too (MSCF
  `.DL_`). NT 3.1 installs it only for Dell DGX and has no expand.exe
  (`FRAMEBUF.DL_` is SZDD there).

## Wiring

- `tools/nt4/usosvbe/build-nt3.cmd` -> `bin/nt3/i386/usosvbe.sys` (PE 3.10,
  `-DUSOSVBE_NT3`), packed as `usr/lib/usos/nt3/USOSVBE.SYS`.
- `tools/nt4_csmwrap_target.sh` (NT 3.5x branch): `\USOS\NT3\USOSVBE.SYS` and
  the CD's `FRAMEBUF.DL_`; without USOSVBE.SYS the log says VGA.
- `tools/nt3/usosnt3` `vesa()` (end of `post()`): expands FRAMEBUF.DL_ with
  NT's expand.exe only if `system32\framebuf.dll` is missing; copies
  `drivers\usosvbe.sys`; registry:
  - `Services\usosvbe`: Type 1, Start 1, ErrorControl 0, Group "Video"
  - `Services\usosvbe\Device0`: InstalledDisplayDrivers = "framebuf"
    (REG_MULTI_SZ), VgaCompatible 0, DefaultSettings.BitsPerPel 16,
    XResolution 1024, YResolution 768, VRefresh 60, Interlaced 0, Flags 0
  - `Services\VgaStart` Start 4 (when the key exists)
  - VgaSave untouched (full-screen consoles, [VGA mode]).
  POST.LOG: `vesa on` / `vesa off: ...`.
- Tests: `tools/tests/test_nt3_usosvbe.py` (imports against the NT 3.1/3.5/3.51
  export lists; `[videoprt.sys]` added to nt35/nt31 fixtures).

## Results (QEMU only, 2026-10-14)

Nested micro-Linux harness (`tools/tests/run_nt3_micro_linux_qemu.py --scripts
--lib nt3/USOSNT3.EXE=... --lib nt3/USOSVBE.SYS=... --boot --reboots 1`),
install hands-free to DONE.TXT, then q35 + OVMF + CSMWrap, `-vga std`
(SeaVGABIOS / bochs VBE 3.0, 16 MB), EPYC-Rome, 12 root ports:

| | install | logon / desktop | UsosVbeDiag |
|---|---|---|---|
| NT 3.51 WS (1057) | PASS | 1024x768, 65536 colours (Display applet: 1024 by 768, 60 Hz) | `try=1 es=0000 vbe=0300 mem=16384k list=93 modes=61 set=1024x768x15/116 ok` (before the 15 bpp change) |
| NT 3.5 WS (807) | PASS | 1024x768 | `try=1 es=0000 vbe=0300 mem=16384k list=93 modes=55 set=1024x768x16/117 ok` |
| NT 3.51 `[VGA mode]` (/basevideo) | - | 640x480x16 via VgaSave (usosvbe does not start) | - |

POST.LOG: `VgaStart Start = 00000004`, `vesa on` (framebuf.dll was already
installed by Setup on both CDs; the expand fallback did not run).
The first logon on NT 3.51 shows the Display Settings applet once (NT 3.5x
display detection after Setup; OK/Cancel closes it).
The harness's `--reboots` second start fails on NT 3.5 with "CONFIG\SYSTEM
missing or corrupt" - also on the plain VGA baseline (no USOSVBE.SYS): the
harness kills QEMU right after the first logon, while the hive is being
written. Not a VESA issue; a real shutdown is fine.

Not done: **NT 3.1** (needs the INITIAL.INF registry path of nt31_initial_inf,
a `vga` service order decision - 3.1 has no VgaSave/VgaStart pair, only
`vga` in Group "Video" - and SZDD expansion of FRAMEBUF.DL_ without
expand.exe on the installed system). The miniport binary already accepts the
3.1 sizes and its imports resolve on 3.1.

## X470 risks (not tested on hardware)

- QEMU's VBE is SeaVGABIOS (bochs); the RX 560's legacy VBIOS under CSMWrap
  already works with the same miniport code on NT 4.0 (1024x768x16), but the
  NT 3.x V86 path differs: videoprt maps the low MB itself on its first
  call and `Ke386CallBios` maps the ROMs from the firmware's configuration
  data; VBIOS stack use runs on the kernel's 1000:1FFC stack.
- The RX 560 may list no 5:6:5 1024x768 mode or only 15/24/32 bpp ones: with
  no exact DEVMODE match framebuf fails -> STOP C0000143 at boot. Then boot
  `[VGA mode]`. (The NT 4.0 X470 run used 1024x768x16, so 5:6:5 exists there.)
- The NT 3.x MBR hides the PCI BIOS (INT 1Ah B101) on machines with > 8 buses:
  if the VBIOS uses INT 1Ah PCI calls during 4F00h/4F01h/4F02h, it gets "no
  PCI BIOS". Unknown for the RX 560 VBIOS (it worked under NT 4.0 without the
  hook).
