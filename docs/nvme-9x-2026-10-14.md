# usosnvme for Windows 95 OSR2 / 98 / 98 SE / Me (2026-10-14)

Status: **experimental, QEMU only, no hardware run yet.** Design:
[research/nvme-9x-2026-10-13.md](research/nvme-9x-2026-10-13.md) (option C). NT driver:
[nvme-nt-2026-10-11.md](nvme-nt-2026-10-11.md).

## What it is

`usosnvme.mpd` is the usosnvme NVMe core (`tools/nt/usosnvme/src/usosnvme.c`) built with
`USOSNVME_W9X` (`tools\nt\usosnvme\build.cmd w9x`, WDK 7.1, the same compiler as the NT builds).
It is a SCSI miniport that Windows' own `SCSIPORT.PDR` loads under IOS. The PE image
imports only `SCSIPORT.SYS` names that the 9x port driver resolves. It does not import ntoskrnl.
Committed build: `tools/nt/usosnvme/bin/W9X/usosnvme.mpd`. The INF is `usosnvme9x.inf`
(staged as `USOSNVME.INF`). Our own code, GPL-3.0-or-later. AHCINT's `AHCI_W9X` (GPL-3.0,
vendored) served as the model for the technique (VMM `_MapPhysToLinear` through `int 20h`,
`HwAdapterState`), and no code was copied from it. nvme9x was not read.

What differs from the NT4 build (`#ifdef USOSNVME_W9X`):

| Item | 9x |
|---|---|
| PCI | CF8h/CFCh port I/O (no HAL); scans all buses itself like NT4, using the given slot first |
| BAR | VMM `_MapPhysToLinear`; **BAR above 4 GiB: refused** (`SP_RETURN_NOT_FOUND`, the disk stays on INT 13h) |
| `HwAdapterState` | Required by SCSIPORT.PDR. The restore (Windows exits to real mode) flushes, sends CC.SHN normal shutdown and leaves the controller disabled. CSMWrap 3.1.2-usos9 SeaBIOS then re-arms its own queues on the next INT 13h call (before usos9 every INT 13h read timed out, see below) |
| I/O queue | **qid 2**. SeaBIOS (CSMWrap) created qid 1 before Windows. A stray BIOS doorbell for qid 1 then hits a deleted queue, not our ring (falls back to qid 1 if the controller grants fewer queues) |
| PRPs | Built from the physical fragments that `ScsiPortGetPhysicalAddress` reports. A command ends where a fragment does not end on a page boundary (see QEMU findings) |
| Debug | Port E9h (QEMU `-debugcon`), only when E9h reads back E9h. Lines start with `USOSNVME` |

512-byte LBA only (the 4Kn check is as on NT). Polled, no interrupt.

## Flow (UEFI menu, 9x CSMWrap path)

Gate: target `/dev/nvme*` **and** an empty
`DATA\Systems\Windows\<9x folder>\Unattended\nvme-experimental.txt`. Without it the path is
unchanged (MS-DOS compatibility mode through SeaBIOS INT 13h).

1. `w9x_csmwrap_prepare.sh` passes `W9X_NVME_DRIVER=1` to `w9x_csmwrap_target.sh`.
2. The target script runs `w9x_nvme_check` (`tools/w9x_nvme.sh`). It refuses when the LBA size is not 512,
   the device is not class 010802, or BAR0 is above 4 GiB, and logs the reason. Then compatibility mode stays and
   the files are removed from `C:\USOS9X`. If the check passes, it adds the PC's `PCI\VEN_xxxx&DEV_yyyy` to
   `USOSNVME.INF` (next to `PCI\CC_010802`) and writes `SET U9NVME=1` to `U9ENV.BAT`.
3. INSTALL.BAT (`U9NVME=1`) copies `USOSNVME.INF/.MPD` next to Setup (`C:\WIN98` etc.): the copy
   source, and the INF for a Setup that sees the controller.
4. After the VM phase 1 the prepare script copies the INF into `C:\WINDOWS\INF` and the MPD into
   `C:\WINDOWS\SYSTEM\IOSUBSYS` (`w9x_nvme_inject`, mtools). Windows' first start on the PC
   then binds the new PCI device through the INF.

## Shut down from NVMe (2026-10-15)

X470, 98 SE on the Micron NVMe, CSMWrap usos8: Start -> Shut down ended at the plain-text
"It's now safe to turn off your computer" screen (no LOGOS.SYS), and the CMOS record showed that
5301h/5307h were never called. Cause: 98's APM power-off runs in real mode. After the VMM returns,
WIN.COM re-executes itself from disk as `WIN.COM /z`, and that child calls APM. usosnvme had
replaced SeaBIOS's admin queue at its start and disabled the controller at the exit, so every
SeaBIOS INT 13h read timed out, the exec failed, and the parent printed the text screen.

Fix in the BIOS, not in the driver: CSMWrap 3.1.2-usos9 patch 0010 (docs/research/csmwrap.md
section 14). Before each INT 13h transfer SeaBIOS checks the controller. If it is stopped or shut
down, SeaBIOS rebuilds its admin queue and I/O queue pair 1 in its POST memory. If another driver's
admin queue is running, it refuses the call. Writes after a re-arm use FUA. usosnvme.mpd is
**unchanged**. It cannot return SeaBIOS's queues, because their addresses and head/tail/phase
state live in SeaBIOS's memory and the driver already reset the controller at its start. Its
flush + CC.SHN before the handoff remains the data-safety step. The same fix also makes INT 13h
work after "Restart in MS-DOS mode" from NVMe.

QEMU: `tools/tests/csmwrap/run_csmwrap_nvme_rearm_qemu.py` replays usosnvme's register sequence
from a boot sector on QEMU NVMe (pc and q35 PASS with usos9; the usos8 control fails as on the
X470). 98 SE itself cannot reach this point in QEMU, because the VMM exit hangs under CSMWrap there.
X470 quick test: replace only the CSMWrap binary (see the commit message); the 98 partition stays
as it is.

## Windows 95 OSR2 on the X470 (2026-10-17)

User result (Codex branch `codex/nvme-9x-fe-me-95`: `/P I` for 95 with the NVMe flag, Setup
page classifier): 95 OSR2.1 PL installs and runs from the Micron NVMe. Start -> Shut down stays on
the "Poczekaj na zamknięcie systemu" logo (LOGOW.SYS). Not yet known: whether usosnvme.mpd
binds on 95 or the disk runs in MS-DOS compatibility mode (SeaBIOS INT 13h).

Power-off path: the same as 98 SE. The 95 OSR2.1 PL WIN.COM (built from WIN.CNF, read-only
disassembly) has the `z` switch handler: INT 13h read of disk 80h sector 1, then INT 15h 5300h,
5301h (real-mode connect), 530Eh, 530Fh, 5308h, 5307h BX=1 CX=3 (all devices off), 5304h.
VPOWERD.VXD disconnects its protected-mode connection at exit. So 95 also powers off from
real mode after the VMM has returned, and it needs CSMWrap usos9+ (NVMe re-arm) exactly like
98 SE. The APM driver (`*PNP0C05`, MACHINE.INF `APM_DRV`) is installed only when Setup's
Detection Manager finds the APM BIOS (MSDET.INF `DetectAPMBIOS`, a software-interrupt probe,
not the PnP BIOS, so `/P I` should not remove it). Without it 95 would show "safe to turn off"
(LOGOS.SYS), not hang on LOGOW.SYS.

A hang on LOGOW.SYS therefore means one of: (1) the VMM exit itself does not finish (a VxD or
the disk flush; usosnvme's `HwAdapterState` restore on 95's SCSIPORT.PDR is untested), (2) the
`WIN.COM /z` child or its INT 13h read stalls (controller handed back in a state the re-arm
refuses), (3) the APM 5307h path in CSMWrap. No fix until the X470 tells which one.

X470 checks (no rebuild, nothing written by USOS; about 10 minutes):

1. NVMe binding, in Windows 95: Control Panel -> System -> Performance. "Your system is configured
   for optimal performance" = usosnvme.mpd serves C:. "Some drives are using MS-DOS compatibility
   mode" = it does not. Then Device Manager -> SCSI controllers: the USOS NVMe entry (no yellow
   mark), and System devices: "Advanced Power Management support" (PL: "Obsługa zaawansowanego
   zarządzania energią") present or not. `C:\WINDOWS\IOS.LOG`, if it exists, lists the drives
   IOS left in compatibility mode (open in Notepad); no IOS.LOG, or one naming only the floppies,
   = C: is on the miniport.
2. Where the shutdown stops: after the hang, hold the power button, then boot the USOS stick once
   to the UEFI menu. CSMWrap usos8+ keeps an APM record in CMOS and the menu appends it to
   `EFI\USOS\Logs\apm-off.txt`. Step 0 (armed, 5307h never called) = the hang is before the
   power-off call (cases 1/2); path 1 (INT 15h) with step 1-15 = inside CSMWrap's 5307h path
   (step table in docs/research/win9x-acpi-2026-10-15.md).
3. Optional: F8 at "Uruchamianie systemu Windows 95" -> Logged (BOOTLOG.TXT), then Shut down.
   The tail of `C:\BOOTLOG.TXT` shows how far the VMM exit got (`EndTerminate = KERNEL` = done).
   "Restart in MS-DOS mode" also leaves the VMM and needs INT 13h from NVMe afterwards: a DOS
   prompt there means the controller hand-back works.

## A second BIOS disk (USB stick) on the 9x NVMe path (2026-10-18)

X470 user result: Windows Me on the Micron NVMe (usosnvme.mpd) boots when the NVMe is alone. When a
FAT32 USB stick is plugged in before boot, real-mode IO.SYS still starts from the NVMe as C:
(`C:\WINDOWS\WNBOOTNG.STS` and `NDISLOG.TXT` were written there). Then Windows stops with
"cannot find KRNL386.EXE", so after the switch to protected mode C: is no longer the Windows
partition. There is no IOS.LOG.

**BIOS numbering is correct.** `run_csmwrap_boot_disk_qemu.py` has a new layout, `nvme-usb`
(target on NVMe, decoy on qemu-xhci usb-storage, the X470 case). With 3.1.2-usos11 it PASSES:
the NVMe is 80h and the stick 81h (`usb-target` PASSES as well). The usos4 rule (patch 0005)
already works across controllers. This part needs no change.

**How 9x IOS ties a protected-mode disk to its INT 13h unit and its letter.** This comes from a
read-only disassembly of Windows Me `IOS.VXD` and `DISKTSD.VXD` (`win9x\*.CAB`). The
disassembly was done for diagnosis only, and no Microsoft code was used.

- **Real mode (IOS init).** IOS reads sector 0 of each BIOS hard disk 80h..83h through INT 13h.
  - When MBR word 0xDA = 0 and dword 0xDC = 0, IOS writes a stamp: unit, seconds, minutes,
    hours. Then it reads the sector back.
  - When dword 0xDC is not 0, IOS keeps the existing value.
  - When word 0xDA is not 0, or the write fails, IOS uses a 512-byte dword checksum.
- **Protected mode (DiskTSD).** DiskTSD reads sector 0 of each new disk through its driver. For
  us that is SCSIPORT plus usosnvme.mpd. The disk takes the first unused table entry with the
  same stamp (and the same checksum, in checksum mode).
  - No match: the disk gets the number after the last BIOS unit. The BIOS unit stays on the
    real-mode mapper.
  - Matched disks 80h..87h are registered with INT13.VXD.
- **Drive letters.** Letters follow DOS. Each volume is matched to its DOS letter by volume serial
  plus BIOS unit and partition start.
- **The miniport has no part in this.** A SCSI miniport cannot report a BIOS unit, and
  SCSIPORT.PDR passes none. The only input that comes from usosnvme.mpd is sector 0. The USOS
  MBR leaves 0xDA..0xDF zero, so the first 9x boot stamps it, with unit 80h.
- **If the NVMe is ever left unmatched, C: fails as seen.** The real-mode mapper then sends C:
  reads as INT 13h to SeaBIOS. SeaBIOS refuses NVMe calls while another driver's admin queue is
  running (usos9, section above), so C: cannot be read.

On paper the stamp logic matches the NVMe to 80h even with the stick present, so the failing step
is not identified yet. The kit below collects the deciding data: the MBR stamps of both disks,
and BOOTLOG.TXT on whichever disk was C: at the end. Note: a 9x boot also **writes** an IOS stamp
into the MBR of every BIOS disk whose bytes 0xDA..0xDF are zero, and that includes a user's stick.

**Mitigation: CSMWrap 3.1.2-usos11-int13x (patch 0014, experimental, not in the flow).**

- With `int13_boot_disk_only = true` in csmwrap.ini, CSMWrap tags its boot disk with IBV1 "USOX"
  instead of "USOS" (the same patch-0005 hash).
- SeaBIOS moves that one disk to 80h and drops every other hard disk from the boot list before it
  maps drives. INT 13h then has one hard disk, the configuration that works on the X470.
- With no match, or with more than one match, nothing is dropped.
- Without the key the binary behaves as usos11.
- Cost: a USB stick is not visible in Me or in DOS mode while the key is set. Me has no xHCI
  driver, so the BIOS is its only path to the stick.

QEMU, `run_csmwrap_boot_disk_qemu.py --only` with the int13x binary:

| Run | Layouts | Result |
|---|---|---|
| `--only` | nvme-usb, same-port0, usb-target, nvme-target | all PASS: `USOS-TARGET NO-DRIVE-81` (INT 13h 81h fails, decoy not written). Serial log: `USOS boot disk only: USB MSC Drive ... not mapped` |
| without `--only` | nvme-usb, same-port0 | `USOS-TARGET USOS-DECOY`, usos11 behaviour unchanged |

Windows 9x was not run in QEMU (no installed image, user preference: no VM installs). Build:
`run_build_vm.py --patches tools/vendor/csmwrap/3.1.2-usos11-int13x/patches --usos-version
3.1.2-usos11-int13x`. The pinned Alpine toolchain gave identical usos1 and repeat binaries,
SHA-256 `e0ec207b…a054be`. In-place kit for the Micron: replace the CSMWRAP partition's
`EFI\BOOT\BOOTX64.EFI` and add the ini line. The README has the rollback, a read-only MBR-stamp
script and BOOTLOG instructions.

Next step: after the X470 run, if the stick should stay usable in 9x through the real-mode
mapper, find the failing step from the BOOTLOG and stamp data. Otherwise wire
`int13_boot_disk_only` into `xp_csmwrap_esp.sh` for 9x targets with `W9X_NVME_DRIVER=1` (a new
pinned CSMWrap version).
