# Windows 2000 with the ACPI HAL on the X470 (2026-10-12)

Goal: 2000 Pro / Server SP4 on the ASRock X470 Master SLI/ac (CSM off,
CSMWrap) with the ACPI HAL (`halmacpi.dll`) instead of the MPS HAL, for all
cores, power-off and later NVMe. Today the X470 runs with `acpi-off.txt`
(MPS HAL, `docs/windows-2000-modern-2026-09-30.md`).

## What blocks it (from the X470 tables, no VM runs)

Source: the USOS ACPI dump of this board (`EFI\USOS\Logs\acpi\2E4F2079-...`
on the stick; DSDT + 7 SSDTs), read with an own AML lister.

1. **No clock interrupt before any driver runs.** The firmware hands over
   with the HPET on and in LegacyReplacement mode, timer 0 interrupts off
   (usosrst 1.3: `cfg 00000003 t0 00008030`). IRQ 0 and IRQ 8 never fire.
   The 2000 ACPI HAL calibrates its stall loop on IRQ 0 during HAL init, so
   it hangs right after SETUPLDR (X470 run 5, 2026-10-04: black screen with
   `_`). The MPS HAL survived that far; usosrst clears the bit later, too
   late for the ACPI HAL. XP is not affected: the board's DSDT
   `HPET._STA` switches the HPET off (`HPEN = 0`) unless
   `_OSI("Windows 2006")` or later; XP's acpi.sys gets there, 2000's
   HAL does not.
2. **ACPI 2.0 `QWordConst` outside a method.** `\_SB.PCI0` has
   `Name(MAB/MAL/MAM, QWordConst)` at namespace level (DSDT revision 2).
   2000's acpi.sys is ACPI 1.0b and must parse these at table load. All
   other ACPI 2.0 opcodes on this board (`CreateQWordField`, `ToInteger`,
   `Continue`, one `QWordConst` in an SSDT) are inside method bodies, which
   only matter if 2000 runs those methods (`PCI0._CRS` uses the QWord fields
   only `If (MAL)`, and MAL is 0 here).
3. Not blockers on paper: FADT revision 6 (2000 reads the 1.0 part), MADT
   with 16 threads (Pro uses 2, Server 4). 2000 and the MBR below use the
   RSDT; the dump only records the XSDT, Aptio normally fills both
   (unverified; with no RSDT the MBR still clears the HPET bit).

There is no licensed ACPI 2.0 driver for NT 5.0 to bundle (section 2 of the
2026-09-30 doc), so USOS fixes the tables and the clock itself.

## The fix: `w2k-acpi-mbr-440.bin` (own code, GPL-2.0-or-later)

`src/platform/bios/xp/xp_geometry_fix_mbr.S` built with `-DUSOS_W2K_ACPI`
(the default XP MBR stays byte-identical). Before the VBR it:
- clears HPET general configuration bit 1 (LegacyReplacement) when an HPET
  answers at FED00000h, so the PIT/RTC drive IRQ 0/8 again;
- walks RSDP (E0000h-FFFFFh) -> RSDT -> FACP.DSDT and every SSDT and turns
  each `Name(NNNN, QWordConst)` into `Name(NNNN, DWordConst)` + 4 `NoopOp`
  (same length), values above 4 GiB become 0, then makes the checksum valid.
  On the X470 dump this changes exactly 3 names (15 bytes + checksum) in the
  DSDT and nothing in the SSDTs.

`legacy_xp_staging.sh` selects it for Windows 2000 when ACPI is on (no
`acpi-off.txt`); `prepare_xp_target.sh` / `prepare_xp_ntfs_target.sh` write
it, `legacy_xp_resume.sh` recognises it by the marker hash. With
`acpi-off.txt` nothing changes.

Test: `tools/tests/legacy_bios/test_w2k_acpi_mbr.py` (unicorn; synthetic HPET
and tables, fail-safe run without them, wiring checks).

## X470 test (user)

1. Stick with a build containing this change.
2. DATA `Systems\Windows\Windows 2000\Unattended\`: rename `acpi-off.txt`
   to `acpi-off.txt.off` (rollback: rename it back = MPS install as today).
3. Fresh 2000 Pro SP4 install from the UEFI menu, as before.
4. Report: where it stops (photo), or the HAL at the end (Device Manager ->
   Computer: "ACPI Multiprocessor PC"), CPU count, Start -> Shut Down powers
   off, USB keyboard/mouse.

Reading the result:
- black `_` right after SETUPLDR again: the clock is not the (only) cause;
  next step is a diagnostic HAL-stage marker.
- STOP 0xA5 (ACPI_BIOS_ERROR): acpi.sys rejects more AML; the parameters
  say which object; next step is a broader AML rewrite or own table set.
- Setup runs but no USB or a device conflict: ACPI IRQ routing (`_PRT`)
  under 2000; xhci98 polls anyway.
