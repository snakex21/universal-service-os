# Windows 2000 with the ACPI HAL on the X470 (2026-10-12)

Goal: 2000 Pro / Server SP4 on the ASRock X470 Master SLI/ac (CSM off,
CSMWrap) with the ACPI HAL (`halmacpi.dll`) instead of the MPS HAL, for all
cores, power-off and later NVMe. Today the X470 runs with `acpi-off.txt`
(MPS HAL, `docs/windows-2000-modern-2026-09-30.md`).

## What blocks it (from the X470 tables, no VM runs)

Source: the USOS ACPI dump of this board (`EFI\USOS\Logs\acpi\2E4F2079-...`
on the stick; DSDT + 7 SSDTs), read with an own AML lister.

1. **No clock interrupt before any driver runs.** The firmware hands over
   with the HPET on and in LegacyReplacement mode, timer 0 interrupts off
   (usosrst 1.3: `cfg 00000003 t0 00008030`). IRQ 0 and IRQ 8 never fire.
   The 2000 ACPI HAL calibrates its stall loop on IRQ 0 during HAL init, so
   it hangs right after SETUPLDR (X470 run 5, 2026-10-04: black screen with
   `_`). The MPS HAL survived that far; usosrst clears the bit later, too
   late for the ACPI HAL. XP is not affected: the board's DSDT
   `HPET._STA` switches the HPET off (`HPEN = 0`) unless
   `_OSI("Windows 2006")` or later; XP's acpi.sys gets there, 2000's
   HAL does not.
2. **ACPI 2.0 `QWordConst` outside a method.** `\_SB.PCI0` has
   `Name(MAB/MAL/MAM, QWordConst)` at namespace level (DSDT revision 2).
   2000's acpi.sys is ACPI 1.0b and must parse these at table load. All
   other ACPI 2.0 opcodes on this board (`CreateQWordField`, `ToInteger`,
   `Continue`, one `QWordConst` in an SSDT) are inside method bodies, which
   only matter if 2000 runs those methods (`PCI0._CRS` uses the QWord fields
   only `If (MAL)`, and MAL is 0 here).
3. Not blockers on paper: FADT revision 6 (2000 reads the 1.0 part), MADT
   with 16 threads (Pro uses 2, Server 4). 2000 and the MBR below use the
   RSDT; the dump only records the XSDT, Aptio normally fills both
   (unverified; with no RSDT the MBR still clears the HPET bit).

There is no licensed ACPI 2.0 driver for NT 5.0 to bundle (section 2 of the
2026-09-30 doc), so USOS fixes the tables and the clock itself.

## The fix: `w2k-acpi-mbr-440.bin` (own code, GPL-2.0-or-later)

`src/platform/bios/xp/xp_geometry_fix_mbr.S` built with `-DUSOS_W2K_ACPI`
(the default XP MBR stays byte-identical). Before the VBR it:
- clears HPET general configuration bit 1 (LegacyReplacement) when an HPET
  answers at FED00000h, so the PIT/RTC drive IRQ 0/8 again;
- walks RSDP (E0000h-FFFFFh) -> RSDT -> FACP.DSDT and every SSDT and turns
  each `Name(NNNN, QWordConst)` into `Name(NNNN, DWordConst)` + 4 `NoopOp`
  (same length), values above 4 GiB become 0, then makes the checksum valid.
  On the X470 dump this changes exactly 3 names (15 bytes + checksum) in the
  DSDT and nothing in the SSDTs.

`legacy_xp_staging.sh` selects it for Windows 2000 when ACPI is on (no
`acpi-off.txt`); `prepare_xp_target.sh` / `prepare_xp_ntfs_target.sh` write
it, `legacy_xp_resume.sh` recognises it by the marker hash. With
`acpi-off.txt` nothing changes.

Test: `tools/tests/legacy_bios/test_w2k_acpi_mbr.py` (unicorn; synthetic HPET
and tables, fail-safe run without them, wiring checks).

## X470 run 2026-10-13 (B261013-105536-DAC4910E): black `_` again

User video (2000 Pro SP4 PL, `acpi-off.txt` renamed, answer file
`usos-2000-full.sif`):
- SETUPLDR loads every file; the last status line is "Instalator ładuje
  pliki (System plików Windows NT (NTFS))...", the last driver of the list.
- the next frame is black; from then on only a blinking `_` near the bottom
  left. No USOS row (usosrst rows 1-10, AHCINT row 0) ever appears.

Evidence read afterwards (no writes):
- stick ESP `EFI\USOS-XP\legacy-xp-prepare.log`: `ACPI kept (ACPIEnable
  unchanged); HAL chosen by Setup`, `[XP_WINDOWS] Windows 2000 answers: ...
  HAL none`. The answer file cannot pin a HAL: `usos_w2k_hw_sif` drops every
  `ComputerType`/`OemPreinstall` row of a chosen .sif or profile and only
  `acpi-off.txt` decides ACPI. The ACPI path did run.
- BIOSTAR target, MBR = `w2k-acpi-mbr-440.bin` byte for byte.
- BIOSTAR LBA 2046 (AHCINT marker): boot counter still 0, LBA 2045 (write
  test) and 2040-2043 (trace ring) empty: AHCINT never started.

Meaning: the kernel stops before the group-less boot drivers (AHCINT,
usosrst; they have no service key in SETUPREG.HIV, so they start after the
grouped ones: acpi, pci, isapnp ...). Candidates: HAL/kernel phase 0-1,
the MP start, or a STOP in acpi.sys/pci.sys. A STOP there is invisible:
the Microsoft BOOTVID.DLL's 640x480 mode never shows behind CSMWrap, and
usosrst's own STOP rows are not registered yet. So "black `_`" can be a
STOP 0xA5 as well as a hang.

## Diagnostic: own text-mode BOOTVID.DLL (usosvid 1.0)

`tools/w2k/usosvid` (GPL, own code, the 11 exports and argument sizes of the
2000 BOOTVID.DLL). With ACPI on, `w2k_stage.sh` (section 8) puts it into
`$WIN_NT$.~BT` only (the installed system keeps Microsoft's) and adds `/SOS`
to the text-mode load options. DATA `bootvid-ms.txt` turns it off; with
`acpi-off.txt` nothing changes. It keeps VGA text mode and writes B8000h:

| row | content |
| --- | --- |
| 11 (green) | `usosvid 1.0 (text BOOTVID): kernel phase 1 reached` |
| 12 | `hpet <caps> cfg=<general config>` (bit 1 = LegacyReplacement), `rsdp@<addr> r<rev> rsdt=<addr>(<entries>) xsdt=<addr>` |
| 13 | `facp r<rev> sci<irq> dsdt=<addr> q<QWord names left> ssdt<n> q<n> bad<checksum/missing> lapic <enabled>/<total> x2 <x2APIC> nmi<n> io=<id>@<gsi>,...` |
| 14 (red) | the `*** STOP` line |
| 15 (red) | the last other `***` line (driver name of the STOP) |
| 16-24 | everything the kernel prints (/SOS banner, processor line, STOP text) |

One X470 run reads like this:
- SETUPLDR's blue screen stays, no green row 11: the stop is before kernel
  phase 1 (HAL phase 0 / kernel phase 0) - next: MADT/APIC (16 of 32
  local APICs, I/O APIC ids) or the HAL's clock.
- row 11 present, row 14 `*** STOP: 0x000000A5 ...`: acpi.sys rejects the
  tables; parameters + row 15 say what - next: AML work (or an own DSDT).
- row 11 present, a STOP other than A5: row 15 names the driver.
- row 11 present, no STOP, console shows the processor line: hang after
  the MP start, in a boot bus driver (acpi/pci enumeration) - next: an early
  marker driver in the Boot Bus Extender group.
- row 11 present, no processor line, no STOP: hang in HAL phase 1 / MP start.
- row 12 `cfg` with bit 1 set or row 13 `q` not 0 or `bad` not 0: the USOS
  W2K ACPI MBR did not do its job (A20, RSDT) - that is the first thing to fix.

## Research round 2026-10-13 (after the usosvid run printed nothing)

| what | what it is | verdict |

| XP/2003 community ACPI drivers (DK_ACPI etc., winraid "Modded ACPI Drivers Depot") | patched or rebuilt acpi.sys for XP/2003; downloads removed; no 2000 build | not usable for 2000. Any build said to come from leaked Microsoft source: excluded |

No public fix targets a hang before kernel phase 1 on AM4; every report found is
about acpi.sys (STOP 0xA5) or storage (STOP 0x7B). The own path stays: fix
the tables before the OS and, if needed, an own HAL-independent clock fix.

### What the stop point rules in and out

- Text-mode Setup loads `halaacpi.dll` (TXTSETUP `[Hal.Load] acpiapic_mp =
  halaacpi.dll`), the uniprocessor APIC ACPI HAL with the uniprocessor kernel.
  No AP is started in text mode, so CPU count / MP start is not the cause of
  this stop.
- usosvid row 11 never appeared, so the stop is before the boot video driver
  starts (kernel phase 1 start); acpi.sys and the DSDT QWord names do not run
  yet (assuming usosvid shows on this board; it is not hardware-proven).
- The 2000 ACPI HAL finds its tables only through the RSDT address NTDETECT
  records from the RSDP (no XSDT path), reads the 32-bit FADT fields
  (FIRMWARE_CTRL -> FACS, DSDT, PM blocks) and needs an RTC interrupt in phase
  0 (it has its own failure path for that). A phase-0 failure is a bugcheck
  that nothing can show behind CSMWrap.

### X470 facts (stick micro-Linux dmesg, EFI\USOS-XP\menu-hardware.txt)

- Firmware publishes both RSDPs (`efi: ACPI=0xbd069000 ACPI 2.0=0xbd069014`),
  so an RSDT probably exists, but its address and the 32-bit FADT fields were
  never recorded (the old dump kept only AML). FACS at 0xBD063000 (ACPI NVS).
- MADT: IOAPIC[0] id 17 GSI 0-23, IOAPIC[1] id 18 GSI 24-55, overrides
  IRQ0->GSI2 and IRQ9 low/level, LAPIC_NMI uid 0xFF, 16 enabled CPUs.
- PM timer 0x808, 24-bit. HPET at FED00000, 3 comparators, routed IRQ 2/8/0.
- CSMWrap copies the 2.0 RSDP to the F segment and, for its helper core,
  writes a new MADT plus new RSDT/XSDT copies (EfiACPIReclaimMemory) and
  points the RSDP copy at them.

### Ranked causes

1. ACPI 1.0 view broken: RsdtAddress 0 / RSDT invalid, or FADT 32-bit
   FIRMWARE_CTRL / DSDT / PM block fields 0 (AMI fills X_ fields; OVMF in
   QEMU leaves X_FIRMWARE_CTRL 0, firmware can do the reverse). Unverified
   either way; it is the only class the MPS HAL (works) never touches.
2. RTC/timer interrupt not arriving in ACPI-APIC routing (IRQ0 via override
   to GSI2, IRQ8 on IOAPIC[0] pin 8) while the HPET is still in legacy mode.
   The MBR clears the bit before the VBR; SeaBIOS leaves A20 on and Zen has
   no A20 mask, so the write should land, but nothing records it.
3. MADT shape (two IOAPICs with ids 17/18, LAPIC_NMI 0xFF, a removed helper
   entry): the MPS HAL works with the same IOAPICs from CSMWrap's MP table,
   so lower.
4. acpi.sys / AML: after phase 1, out for this stop.

### The cheapest test: raw ACPI dump (no Windows run)

`src/platform/uefi/acpi_dump.zig` now also writes
`EFI\USOS\Logs\acpi\<machine>\raw\` once per machine (own marker, so the
already-dumped X470 gets it): RSDP20/RSDP10/RSDT/XSDT/FACS and every table
as .bin, and `summary.txt` with the ACPI 1.0 view (RsdtAddress, RSDT entries,
XSDT tables missing from the RSDT, decoded FADT 32-bit and X_ fields with
`!!` warnings, every MADT entry, HPET registers as the firmware leaves them).
QEMU OVMF check: summary correct (RSDT 6 entries, FACP, MADT, HPET cfg 0).

User: boot the stick with this build on the X470 into the USOS menu, wait
10 s, power off. Then `raw\summary.txt` decides:
- `!! RsdtAddress is 0` or an RSDT problem -> CSMWrap patch: always publish an
  RSDT built from the XSDT (own code, small).
- `!! FIRMWARE_CTRL is 0` / `DSDT is 0` / `PM_TMR_BLK is 0` -> CSMWrap patch:
  a FADT copy with the 32-bit fields filled from the X_ fields.
- HPET `general config` bit 1 set -> confirms the legacy-mode handover (the
  MBR fix stays needed).
- all clean -> cause 2/3: next step is a progress marker the HAL path can't
  skip (CSMWrap verbose + a timer-interrupt self-test before the VBR).

## CSMWrap 3.1.2-usos5: ACPI 1.0 view and the legacy FADT (2026-10-13)

## STOP 0xA5 (0x2, ...) on q35: QWord PCI window above 4 GiB (2026-10-13)

q35 + CSMWrap usos5 + `acpi_legacy_fadt` on the 2000 Pro SP4 PL target:
`STOP 0x000000A5 (0x00000002, 0x85CE37E8, 0x85CB4C88, 0x00000001)`.

Decode by binary analysis of the stock `acpi.sys` 5.00.2195.6655 (W2KPLCMA4.811
I386\ACPI.SY_, image base 0x10000). 0xA5 P1=2 has four call sites; the
parameters match only the one at RVA 0x1be93 (P3 a pointer, P4 a count):

- function 0x1bd6a = the PCI root bus resource sanity check, called from the
  _CRS/IRP_MN_QUERY_RESOURCE_REQUIREMENTS path (0x2aebc) for the PCI root only;
- P2 = PCI0's ACPI device extension, P3 = the IO_RESOURCE_REQUIREMENTS_LIST
  made from PCI0._CRS, P4 = number of bad descriptors (1);
- per descriptor: Port/Memory: Max - Min + 1 (64-bit) must equal the 32-bit
  Length, Alignment != 0 and Min aligned; Bus number: Max - Min + 1 ==
  Length; Memory windows must not overlap the loader's memory map entries
  other than type 2 (helper 0x1bc4a). Any mismatch is "fixed" and counted,
  and a count != 0 is the STOP.

The QWord Address Space handler (0x2ed39, tag 0x8A in the descriptor switch
at 0x2f6cd) skips Length == 0 descriptors, but otherwise stores only the low
32 bits of the 64-bit Length in IO_RESOURCE_DESCRIPTOR.u.Memory.Length.
QEMU q35's PCI0._CRS (dumped from guest memory) ends with
`QWordMemory 0x100000000-0x8FFFFFFFF, Length 0x800000000`: low 32 bits 0,
so Max - Min + 1 != Length -> count 1. A/B: `-global
q35-pcihost.pci-hole64-size=0` (no QWord in the DSDT) -> the same target boots
to the 2000 logon screen with the ACPI HAL. The 2000 acpi.sys also has no
CreateQWordField (opcode 0x8F) in its interpreter name table, and tags
0x82-0x84 / 0x8B are skipped.

Fix (own code, CSMWrap 3.1.2-usos5 patch 0006 amended; usos5 had never been
deployed): with `acpi_legacy_fadt = true` (the 2000 ACPI flow only) the DSDT
the legacy FADT copy points at, and every SSDT in the RSDT, become copies in
which each static resource template (AML Buffer whose initializer parses as
resource items ending with the End Tag exactly at its end) has its QWord
Address Space descriptors that reach above 4 GiB cleared to
Min/Max/Translation/Length 0 (the firmware's own "unused window" form, which
acpi.sys skips); an End Tag checksum in use is recomputed. Firmware tables,
the XSDT and X_DSDT view stay unchanged. Log line: `USOS ACPI10: legacy DSDT
copy at ...: 1 QWord window(s) above 4 GiB cleared`. Result flag 0x100.
Binary `1207f8cc287372b32cc3ddce2ea4cc67c022a8d7844f7651bff476ca3fb1598b`
(built twice identical; unpatched build still equals upstream_rebuild).
Host test: 4 new cases (DSDT+SSDT, checksum, option off, revision-1 FADT).
On the real q35 DSDT the filter changes exactly that one QWord.

### X470 tables

The X470 DSDT's PCI0._CRS (CRS1/CRS2 templates in a Method) holds a QWord
memory template that is all zero in the static data (skipped by acpi.sys) and
is filled at run time with CreateQWordField only `If (MAL)`. The dump has
`Name(MAL, Zero QWord)` (Above 4G Decoding off), so the If body never runs.
The static templates have no window above 4 GiB (filter: 0 hits on the DSDT
and all 7 SSDTs). The zero-length Word/DWord entries are skipped the same
way. Consequence for the X470 run: keep **Above 4G Decoding off** for
Windows 2000 (with it on, `_CRS` executes CreateQWordField, which the 2000
interpreter does not know -> _CRS fails -> STOP 0xA5 (0x2, PCI0, 0, ...)
from the call site at 0x2af11). With 32-bit AML integers MBB+MBL wraps to 0,
so the DSDT takes its "below NBTP" branch: window 0xC0000000-0xFFFFFFFF;
overlaps only reserved (type 2) memory-map entries, which the check skips
(not verifiable without the X470 E820).

## X470 run 2026-10-13 (B261013-211100-44407FD3): kernel phase 1, then a hang

CSMWrap usos5 with `acpi_legacy_fadt = true`, W2K ACPI MBR, usosvid 1.0.
The screen (photo) showed row 11 (green) and the two ACPI rows, nothing in
rows 14-24:

| field | value | meaning |
| --- | --- | --- |
| `hpet 10228201` | caps | AMD (1022), 3 comparators, 32-bit counter, LegacyReplacement capable |
| `cfg=00000000` | general config | HPET halted and LegacyReplacement off: PIT/RTC reach IRQ 0/8 |
| `rsdp@F6520 r2` | RSDP | CSMWrap's copy in the F segment, revision 2 |
| `rsdt=BC95F000(15)` | RSDT | CSMWrap's RSDT copy, 0x15 = 21 entries (as the firmware's) |
| `xsdt=BC95E000` | XSDT | CSMWrap's copy |
| `facp r1` | FADT | the 116-byte revision-1 legacy copy: the phase-0 fix is active |
| `sci09` | SCI | IRQ 9 (MADT override: level, active low) |
| `dsdt=BC98A000 q0` | DSDT | firmware DSDT (no QWord window > 4 GiB, so no copy), no `Name(x, QWord)` left (MBR rewrite done) |
| `ssdt7 q0 bad0` | SSDTs | 7 SSDTs, no QWord names, every checksum valid |
| `lapic 0F/1F` | MADT | 15 enabled of 31 local APICs (firmware: 16/32; CSMWrap hides its helper CPU) |
| `x2 00 nmi1` | MADT | no x2APIC entries, one LAPIC NMI entry |
| `io=11@00,12@18` | MADT | I/O APIC 17 at GSI 0, I/O APIC 18 at GSI 24 (firmware values) |

What it bounds (SP4 `ntoskrnl.exe` 5.0.2195.6717 PL, Phase1Initialization
at RVA 0x14f6a0):
- `HalInitSystem(1)` returns before `InbvDriverInitialize` (the call that
  runs usosvid's VidInitialize), so **HAL phase 0 and phase 1 completed**:
  the I/O APICs, the RTC clock vector (enabled in phase 0) and the profile
  and IPI vectors are set up. The FADT fix works on the hardware.
- The empty console is expected and does not bound anything: text-mode
  Setup's `OsLoadOptions` (TXTSETUP.SIF) contain `/noguiboot`; the kernel
  then calls `InbvEnableBootDriver(FALSE)` (RVA 0x1e9cd: display state
  "disabled"), and every `InbvDisplayString` is dropped. The 2000 kernel
  never prints driver names itself (SETUPLDR does, before the kernel), so
  `/SOS` adds nothing after this point. Only a bugcheck re-acquires the
  display, so a STOP would still show in rows 14-24.
- So the hang is somewhere between `InbvDriverInitialize` and setupdd.sys's
  blue screen: the rest of kernel phase 1, then IoInitSystem with the boot
  drivers in group order (acpi.sys first, pci.sys, ..., then usosrst and
  AHCINT, which have no group), then setupdd.

Why the MADT / I/O APIC shape is not the cause: CSMWrap builds the MP table
the MPS HAL uses from the same MADT (`src/mptable.c`: I/O APIC ids 17/18,
same addresses, IRQ 0 -> pin 2, the helper CPU removed), and the MPS HAL boots
this machine. Both HALs share the I/O APIC code (`HalpInitializeIOUnits`

ids. No x2APIC entries exist. Renumbering ids or dropping the second I/O
APIC is not supported by any evidence; not changed.

Ranked causes (no hardware run yet):
1. acpi.sys, the first boot driver and the only big new code on this path
   (the MPS flow never loads it): AML at load / `_INI` / `_PIC(1)`
   (`\_SB.DSPI` reprograms the FCH PCI IRQ routing, `PCI0.NAPE` writes the
   root complex), busy loops in the AML that poll hardware with no timeout
   (`\_SB.SECR/DSAD/HSAD`, several `While (One)` in the DSDT), the ACPI mode
   switch (SMI_CMD 0xB2 / 0xA0), or an SCI (IRQ 9, level low) that stays
   asserted (an interrupt storm looks like a hang).
2. No clock interrupt after phase 1 (RTC IRQ 8 through I/O APIC 17 pin 8).
   HPET is off and the MPS HAL uses the same pin, so less likely; it would
   hang at the first timed wait (AML `Sleep`, a driver's delay).
3. The group-less boot drivers (usosrst, AHCINT) under ACPI interrupt
   routing (PCI interrupts now on GSI 16-23 via `_PRT`). If the photo had
   usosrst's rows 1-10 or AHCINT's row 0, this moves to the top.

## Step A: ACPI mode switched on by CSMWrap before the boot (2026-10-14)

Hypothesis (from an outside review of the SP4 binaries, Codex report
2026-10-14, written with the user's NT5 sources as a map; not confirmed):
acpi.sys 5.0.2195.6655 (`ACPIEnableInitializeACPI`, RVA 0x1483C) checks
PM1a_CNT.SCI_EN and, only when it is 0, writes FADT.ACPI_ENABLE to
FADT.SMI_CMD (RVA 0x147F8; X470: `out 0xB2, 0xA0`) and polls SCI_EN. If the
AMI SMI handler behind that write changes RTC/FCH state, the HAL's RTC IRQ 8
clock stops, which matches `t=--------` on usosvid row 16. When SCI_EN is
already 1, acpi.sys sends no SMI. The test: do the transition earlier, from
code we control, and record the RTC around it.

Implementation (own code from the ACPI specification 6.5: 4.8.2.1 SCI_EN,
5.2.9 FADT, 16.3.1 legacy to ACPI mode; MC146818 RTC register layout):
CSMWrap **3.1.2-usos6** = usos5 + patch
`tools/vendor/csmwrap/3.1.2-usos6/patches/0007-acpi-enable-before-legacy-boot.patch`
(`src/usos_acpien.c`, `.h`, `src/usos_acpien_efi.c`):

- only with `csmwrap.ini acpi_legacy_fadt = true` (written by
  `tools/xp_csmwrap_esp.sh` only for Windows 2000 with ACPI); XP, 2003,
  Vista/7 x86, DOS/9x and every other CSMWrap flow run the usos5 code path;
- before ExitBootServices: SMI_CMD, ACPI_ENABLE, PM1a_CNT_BLK, PM_TMR_BLK,
  TMR_VAL_EXT and HW_REDUCED_ACPI from the FADT the RSDT lists (the ACPI 1.0
  copy 2000 reads; X_ GAS in System I/O as a fallback); logged
  `USOS ACPIEN: armed ...`;
- after SeaBIOS's Legacy16PrepareToBoot (which runs clock_setup: RTC A =
  0x26, B = 24-hour mode, DSE kept) and right before Legacy16Boot: RTC A/B
  read (index 70h with the NMI-disable bit; register C never read); SCI_EN
  1 -> `a`; else `out SMI_CMD, ACPI_ENABLE`, SCI_EN polled for at most 3 s
  on the PM timer (24/32-bit; cap 8,000,000 polls when the timer is missing
  or stuck) -> `o` or `t`; no usable fields -> `n`; RTC A/B and PM1a_CNT
  read again; the serial line `USOS ACPIEN: status ...` (serial only:
  SeaBIOS owns the screen by then);
- 8 result bytes at physical 0x4F4-0x4FB, the BIOS data area's
  inter-application communication area (0040:00F0-00FF; SeaBIOS keeps it
  as padding `other_b0` and never writes it; 0x4F0-0x4F3 are the USOS
  MBR's boot drive/heads slots): `'A' 'E' status, RTC A before, RTC A
  after, RTC B before, RTC B after, PM1a_CNT low byte after`. `s` is stored
  before the SMI and replaced after it, so a machine that never comes back
  from the SMI keeps `s` (and does not boot at all: a hang right after
  CSMWrap, before the USOS MBR). The store goes through the firmware's
  identity page tables with CR0.WP cleared and the entry for VA 0 made
  present for the store only (firmware with NULL-pointer detection).

What can still change RTC B after CSMWrap: SeaBIOS's INT 15h AH=83h/86h
waits and thread preemption toggle the periodic-interrupt bit
(rtc_use/rtc_release), INT 1Ah AH=03h/05h/06h/07h rewrite B, and the 2000
HAL programs A (rate) and B (= DST kept | 0x42: PIE, 24 h) itself in HAL
phase 1. The record therefore shows the state the SMI left, not the HAL's.

What the pre-enable does not change for acpi.sys: it reads SCI_EN = 1 and
skips its SMI; acpi.sys keeps the result of that check in its own state,
and no reader of it was found that would change later behaviour (MBR draft
notes). SCI is level/low on IRQ 9; with SCI_EN = 1 from the boot on, a
pending fixed/GPE event raises IRQ 9 already in real mode; SeaBIOS unmasks
only the PIC lines of its own handlers (timer, RTC, keyboard, mouse, floppy,
ATA), not IRQ 9, and the HAL leaves the SCI pin masked until acpi.sys
connects its ISR. Risk to watch: a GPE storm right after acpi.sys connects
(it would show as acpi.sys filling usosvid row 20, not as a stopped tick).

usosvid **1.2** (`tools/w2k/usosvid`, manifest re-pinned) shows the record
on row 12. Row 12 now reads
`hpet <cap> cfg=<low byte> rsdp@<addr> r<rev> rsdt=<addr>(<entries>) x+|x- en=<s> a<A0>><A1> b<B0>><B1> c<P>`
(the XSDT address became `x+`/`x-` to make room; cfg keeps only the low
byte: bit 0 enable, bit 1 LegacyReplacement).

| field | meaning | X470 reading |
| --- | --- | --- |
| `en=o` | SCI_EN was 0, the SMI set it within 3 s | the transition worked before the loader; if row 16 now ticks, the SMI is harmless early and the problem is when acpi.sys sends it (or not at all); if it still shows `t=--------`, the SMI is not the cause or its effect persists |
| `en=a` | SCI_EN was already 1, no SMI sent | the firmware hands over in ACPI mode under CSMWrap: acpi.sys never sends the SMI either, so the hypothesis is out |
| `en=t` | SMI sent, SCI_EN still 0 after 3 s | the AMI SMI handler did not switch; acpi.sys would STOP 0xA5 (0x11, 6) in that case, so this would point at a different SMI state under CSMWrap |
| `en=n` | no SMI_CMD / ACPI_ENABLE / PM1a_CNT in the RSDT FADT | nothing sent (should not happen on the X470: 0xB2 / 0xA0 / 0x804) |

| `en=-` | no record | CSMWrap older than usos6, or not the 2000 ACPI flow |
| `aXX>YY` | RTC register A before > after the SMI | expected `26>26` (SeaBIOS rate 1024 Hz, divider 32.768 kHz); a change = the SMI touched the RTC divider/rate |
| `bXX>YY` | RTC register B before > after | SeaBIOS leaves `02` (24 h, no PIE/AIE/UIE); bit 7 SET, bit 6 PIE or bits 4-5 changed by the SMI = the SMI touched the RTC |

## 2026-10-17: the fix, CSMWrap 3.1.2-usos11 patch 0012 (HPET and AMD GPIO hidden)

### What the Codex rounds found (2026-10-16/17, X470, diagnostic firmware)

Codex ran several X470 rounds with a one-shot BSP NMI snapshot (its patch
"0012-one-shot-bsp-nmi-diagnostic" on usos10, explicit `w2k_nmi_snapshot`
option, staged through a separate diagnostic capsule initramfs; outputs in
`Documents\Codex\2026-10-16\outputs\w2k-acpi-*`). Result chain on the
installed 2000 SP4 ACPI HAL:

1. The original fault is a page fault in acpi.sys (C0000005, RVA 9AAA, read
   at offset 10h of a NULL interface) during the early boot IRQ arbitration
   (boot allocation -> arbiter -> AddAllocation -> IRQ routing), before the
   PCI IRQ routing interface exists; the visible STOP 1E is secondary.
2. The device holding the boot IRQ was first the HPET (PNP0103). Hiding it
   (its `_STA` returns 0 in the legacy DSDT copy) left the same fault with
   IRQ 7, level / active low / shared.
3. The X470 DSDT has `\_SB.GPIO`, `_HID`/`_CID` AMDI0030, IRQ 7 level/low/
   shared, MMIO FED81500 length 400h; its `_STA` returns 0Fh for
   TSOS >= 70h, and TSOS is 75h, so the GPIO controller is shown to every OS.
   A minimal own SSDT with the same resources reproduced the fault in QEMU;
   hiding AMDI0030 too removed it (an AMDI0031 control kept failing).
4. Firmware-13 (`c1f1c4fa...`, Codex commit c6222cd): HPET + AMDI0030
   hidden. **X470: Windows 2000 reached the desktop** (user report
   2026-10-17). HAL on the installed system: halmacpi.dll 5.00.2195.6691
   (ACPI multiprocessor), ntkrnlmp.exe 5.00.2195.6717, acpi.sys
   5.00.2195.6655.

Windows 2000 has no driver for either device, so not showing them costs
nothing; the GPIO controller's pins remain usable by the firmware's own AML.

### The production patch (own code)

`tools/vendor/csmwrap/3.1.2-usos11/patches/0012-w2k-hide-hpet-amd-gpio.patch`,
`src/usos_w2k_hide.inc`, written for USOS from the ACPI 6.5 AML grammar
(chapter 20); it reimplements the behaviour of Codex's diagnostic filter,
not its code. Only with `csmwrap.ini acpi_legacy_fadt = true` (only the
2000 ACPI flow writes it), only in the private DSDT/SSDT copies patch 0006
already makes for the RSDT view:

- a Device with a flat TermList (NameOp / MethodOp terms only), exactly one
  `_HID` (Name: string or EISA ID integer), at most one `_CID` (Name: one ID
  or a Package of IDs) and exactly one `_STA` (Name with an integer, or a
  method without arguments) qualifies when its `_HID` **or a `_CID` entry**
  is `PNP0103`, `AMDI0030` or `AMD0030` (the older name of the same AMD
  controller; also matched as an EISA ID integer);
- its `_STA` returns 0 in place: Name -> Zero (or the prefix with value 0),
  method body -> `Return (Zero)` padded with Noop. Lengths, names and
  resources stay; only `_STA` bytes and the checksum change;
- dry run on the firmware table first: never writes, only a table with a
  valid checksum, a malformed PkgLength anywhere on the walked path makes the
  table count 0; the copy must give the same result, else the copy is
  restored and nothing is hidden. Firmware tables and the XSDT view unchanged.
- `_HID`/`_CID` methods, duplicates, devices inside If/Method bodies,
  non-flat devices (an OperationRegion inside, as in QEMU's HPET) are left
  alone. Logged as `USOS W2KHIDE`, result flags 0x200 (HPET) / 0x400 (GPIO).

Check against the real table (a local dump, not distributed): on the X470
DSDT the copy differs only in the HPET `_STA` body (31 bytes at 17114), the
GPIO `_STA` body (17 bytes at 19797) and the checksum; SHA-256 after =
`9a918db5...`, byte-identical to the table firmware-13 gave on the X470.
The B550 Taichi DSDT gives the same two hits; an FM2 board DSDT one (HPET);
QEMU q35 none.

### Provenance

Codex's diagnostic rounds used the user-supplied NT5 material as a map of
HAL/acpi.sys behaviour together with the SP4 binaries and hardware reads;
this is not a clean-room claim. The filter in patch 0012 is our own code
from the ACPI specification and implements a device-hiding rule found by
that diagnosis; it contains no Microsoft code. The X470 DSDT dump stays
private.

### Diagnostic switch (2026-10-17): `w2k-diag.txt`

Default (no flag) = the clean production setup: CSMWrap 3.1.2-usos11 (no
watcher, no NMI), usosvid 1.3 only in text-mode Setup's `~BT`, the
installed system with the Microsoft BOOTVID and no extra boot.ini options.

An empty file `DATA\Systems\Windows\<Windows 2000 folder>\Unattended\w2k-diag.txt`
(Codex's old `nmi-snapshot.txt` is accepted as an alias) switches the 2000
ACPI flow to the diagnostic setup; it needs ACPI on (with `acpi-off.txt`
the flow stops before any write):

| Part | Diagnostic setup | Built from |
| --- | --- | --- |
| CSMWrap on the target ESP | 3.1.2-usos11-diag = usos11 + 0011 tick watcher + 0013 one-shot BSP NMI snapshot (Codex's firmware-13 code without its ACPI filter parts); csmwrap.ini also `w2k_nmi_snapshot = true`; its patch series in `\CSMWRAP\patches-diag` | `tools/vendor/csmwrap/3.1.2-usos11-diag` (pinned VM build, `a100cae3...`, twice identical; ROM 130656/131072, F-segment zone 20682 B, CONFIG_SDCARD off in this variant only); pin `PINNED_DIAG` in `tools/xp_csmwrap_esp.sh` |
