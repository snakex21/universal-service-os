# WINSOCK.DLL dla Win16 - rozpoznanie Trumpeta i szkielet USOS (2026-10-23)

Galaz: `ds/winsock16`, baza `074dfe0d`.  Plan nadrzedny:
`docs/win3-winsock-options-2026-10-23.md` (M2 = wlasna, GPL, `WINSOCK.DLL`
Win16 oparta o mTCP + USOSPKT).  Trumpet Winsock 3.0 sluzy wylacznie jako
wzorzec ABI: nie skopiowano z niego zadnego kodu ani zadnego pliku.

### 1.1 Kompresja: gzip, nie SZDD/KWAJ/LZP

Pierwsze 16 bajtow kazdego `*.*_` to `1f 8b 08 00 00 00 00 00 02 00 ...`, czyli
strumien **gzip** (deflate), a nie formaty SZDD (`SZDD`), KWAJ (`KWAJ`) ani LZP
Tattama.  Dekompresja zwyklym gunzipem (GZipStream) dala poprawne moduly `MZ`:

```
WINSOCK.DL_ -> WINSOCK.DLL  168192 B  MZ, e_lfanew=0x100
TWSK16.DL_  -> TWSK16.DLL     6336 B  MZ, e_lfanew=0x80
WSOCK32.DL_ -> WSOCK32.DLL   39936 B  MZ, e_lfanew=0x80
```

Naglowek NE `WINSOCK.DLL`: `NE`, link 6.1, entry table 0x103 (0x0B04 B),
9 segmentow, exetyp = Windows, oczekiwana wersja Windows 0x0300, tablica
nazw rezydentnych pod NE+0xA0 (`WINSOCK` @0, `WEP` @0x0400), tablica nazw
nierezydentnych pod offsetem 0x0D07 - tam sa nazwy eksportow.

### 1.2 Realna tablica ABI Trumpeta

Z tablicy nazw nierezydentnych odczytano 72 eksporty (pliki: `WINSOCK.DLL`).
Ordinalе pokrywaja sie dokladnie z publiczna specyfikacja Winsock 1.1
(zalacznik "Name and ordinal"): `accept`=1 ... `socket`=23, baza danych
51..57, rozszerzenia WSA 101..116, `__WSAFDIsSet`=151.  **`WSAStartup` to
ordinal 115, nie 1.**  Pelna tabela: `docs/win16-winsock-abi.tsv`.

Dodatkowo Trumpet eksportuje wlasne, nieznormalizowane funkcje (ordinalе
1000-1023): `TCPCONTROL`, `TCPINFOPTR`, `TCPSOCKETINFO`, `TCPGETPKTVEC`,
`TCPSETPKTVEC`, `TCPSETIPADDR`, `TCPGETVERSION`, `TCPSETSLIPINFO`,
`GET_COMM`, `PUT_COMM`, `TCP_METER`, `SOCKS_SETUP`, `ROUTE_ADD/DEL/GET`,
`TCPSETPPPOPTIONS`, `TCPSETBUFFERS`, `TCPSETDRIVERADDRESS`,
`TCPGETDRIVERADDRESS`, `TCPSETSLIPBUF`, `TCPSETFILTERPROC`, `TCPSENDPKT`,
`TCPGETERRORMESSAGE`, `TCPPPPDONE`.  To ich prywatne ABI (np. dla `TCPMAN`),
swiadomie **nie** jest czescia naszej tablicy eksportow.

`TWSK16.DLL` eksportuje te same nazwy Winsock (podzbiór, m.in. `SEND` @19,
`WSASTARTUP` @115) plus `DLLENTRYPOINT` @2001, `THK_THUNKDATA16` @2000 -

### 2.1 Stan builda: kompilacja i link OK (`WINSOCK.DLL` 3 236 B, 48 eksportow)

`wcc` (Open Watcom `ow-bac354f3c75f`, `binnt64`) kompiluje plik bez bledow:

```
wcc -bt=windows -bd -ml -zW -zq -w3 -I<ow>\h\win -fo=...\winsock16.obj winsock16.c
```

Dwie realne poprawki ABI wyszly dopiero na kompilatorze, bo `winsock.h` jest
autorytatywny: `WSANOTINITIALISED` (nie `WSAENOTINITIALISED`) oraz
`WSAAsyncGetHostByAddr(HWND, u_int, const char FAR*, int len, int type,
char FAR*, int)` - 7 parametrow, w tym `type`; bez niego kompilator zglaszal
E1071/E1151.

**Link przechodzi**, ale ten `wlink.exe` (Open Watcom Linker 2.0 beta, build
2026-09-01, 64-bit "EXPERIMENTAL") wymaga innej skladni niz klasyczny Watcom.
Ustalona recepta (w `tools/build_win16_winsock.py`):

* `format windows dll` zamiast `system windows_dll` - system name jest
  nierozpoznawany (`W1107: undefined system name: windows_dll`); help linkera
  podaje `FORMAT "WIndows" ["DLl"]`, wiec dziala forma niska.
* `file ...lib286\win\libentry.obj` dodaje `__DLLstart_`, `library ...clibl.lib`
  dodaje `__STK` i `_big_code_` (bez tego: `E2028` na te trzy symbole).
* Plikow definicji modulu ten build **nie czyta** (`E3146: ... is an invalid
  object file` jako `file`, `E3033` dla `option definition=`), wiec tabela
  eksportow jest restatowana z `.def` jako dyrektywy `export name.ordinal=SYMBOL`
  w pliku odpowiedzi `@zig-out/win16/obj/winsock16.lnk` - po jednym eksporcie
  na linie. Jedna dluga linia `export a.1=A,b.2=B,...` nie przechodzi
  (`E3033: directive error near '"export'` - cytowanie w parserze linkera).
* Nazwy wewnetrzne sa **wielkimi literami i bez podkreslnika**
  (`FAR PASCAL`: `accept` -> `ACCEPT`, `__WSAFDIsSet` -> `__WSAFDISSET`,
  `WEP` -> `WEP`); eksporty `=_accept` konczyly sie `E2044: exported symbol
  _accept not found`.
* `wcc` nie zglosil braku `ioctlsocket`, bo funkcji po prostu nie bylo w
  zrodle - wyszlo to dopiero przy linkowaniu (`E2028: IOCTLSOCKET is an
  undefined reference`).  Funkcja (ordinal 12) zostala dopisana.

Wynik: `zig-out/win16/WINSOCK.DLL`, NE, 3 236 B, 48 eksportow (47 funkcji
Winsock 1.1 + `WEP@1024`).  `tools/build_win16_winsock.py` bez OW daje czytelny
komunikat i `exit 0` (`--strict` zamienia to w blad), a blad kompilacji/linku to
`exit 1` z komenda przy `--verbose`.

## 3. Nastepny krok (M2 krok 2)

1. Silnik TCP/UDP/DNS na kodzie mTCP (GPL-3.0) pod Win16: warstwa `select`
   oparta o WSAAsyncSelect + pompe komunikatow, bufor per socket.
2. USOSPKT w trybie kolejkowym jako transport pod mTCP (bez WINPKT - wlasny
   packet driver juz jest w `src/platform/bios/msdos/usospkt.S`).
3. Uruchomienie w QEMU z Windows 3.1: `WSAStartup`, `socket/connect/send/recv`,
   `gethostbyname`, test z `ping`-em po TCP; pomiar `iMaxSockets`.
4. Test NE jest juz twardy (artefakt powstaje); zostaje wlaczenie builda
   `WINSOCK.DLL` do `build.bat` i sprawdzenie `WSAStartup` w QEMU.

## 4. Czego nie sprawdzono

* Dzialania `WSAStartup` na zywej instalacji Windows 3.1/QEMU - DLL sie
  buduje i ma poprawne eksporty, ale nie byla jeszcze zaladowana przez Windows.
* Zawartosci `TRUMPWSK.HLP` - tryby real/standard/enhanced, DHCP i klucze
  `TRUMPWSK.INI` pozostaja niepotwierdzone; `README.TXT` ich nie opisuje.
* `WSOCK32.DLL` (wariant Win32) - tylko rozpakowany i sprawdzony naglowek.
* Zgodnosci ordinalow z dokumentacja Microsoftu - potwierdzone dwustronnie:
  tablica NE Trumpeta + zalacznik specyfikacji Winsock 1.1 (oba zgodne).
* `build.bat` nie byl uruchamiany (opcjonalny).

## Silnik (etap 2)

Milestone 2b: za ABI stoi wlasny stos IPv4/UDP/TCP/DNS/ARP/ICMP, a transportem
jest tryb kolejkowy USOSPKT (`INT 2Fh AX=5553h`, blok `'USQ1'`).  Nadal bez
`select` i bez `WSAAsyncSelect`: kazde wywolanie blokujace samo kreci petla
pobierania ramek i pompuje kolejke komunikatow.

### Architektura

```
winsock16.c            ABI Winsock 1.1 (48 eksportow), mapowanie WSAE*,
                       WSAStartup/WSACleanup, connect/send/recv,
                       gethostbyname, get/getsockname, hton*/inet_*
   |
   +-- net/win16_sock.c   gniazda (4 sloty), demultiplekser RX, ARP-resolve
   |                      przy wysylce, resolver DNS, petle blokujace
   +-- net/win16_pkt.c    DPMI + kolejka: INT 31h AX=0300h/0002h/0100h/0101h,
   |                      naglowek 'USQ1', pierscienie RX/TX, ATTACH/TX_KICK/
   |                      RELEASE/GET_STATE
   +-- net/{checksum,ip,arp,udp,icmp,tcp,dns}.c
                          przenosny rdzen: czyste C89, zero Windows/DOS,
                          bez alokacji dynamicznej, wszystko na statycznych
                          buforach z net.h
```

Podzial wlasnosci: `net.h` to kontrakt rdzenia (typy `usos_u8/u16/u32`,
rozmiary, kody wyniku `USOS_NET_ERR_*`, struktury `net_tcp`, `net_arp`,
`net_udp_view`, `net_ip_view`).  Rdzen nie zna zegara ani przerwan - pyta
o czas przez `usos_abi_now()` i oddaje maszyne przez `usos_abi_idle()`, oba
dostarcza `winsock16.c`.  Dzieki temu `net/*.c` poza `win16_pkt.c` nie
include'uje `windows.h` (pilnuje tego test hostowy).

| `WSAStartup` | `usos_sock_startup()` = `usos_pkt_init()` + `usos_pkt_attach()`; brak sterownika/DPMI -> `WSASYSNOTREADY` bez inkrementu licznika; `iMaxSockets=4`, `iMaxUdpDg=512`, opis `USOS Winsock 1.1 (Win16)` |
| `WSACleanup` | ostatni klient: zamkniecie gniazd + `RELEASE` + zwolnienie deskryptorow i bloku DOS |
| `socket` | `AF_INET` + `SOCK_STREAM`/`SOCK_DGRAM` (protokol 0/TCP/UDP), inaczej `WSAEAFNOSUPPORT`/`WSAEPROTONOSUPPORT`, brak slotu -> `WSAEMFILE` |
| `connect` | TCP: SYN, retransmisje co 1 s, 15 s -> `WSAETIMEDOUT`, RST -> `WSAECONNREFUSED`; UDP: zapamietuje peera.  Nazwa hosta: sciezka standardowa to `gethostbyname` + `connect` na zwroconym adresie; dodatkowo rozszerzenie USOS - `INADDR_NONE` w `sockaddr_in` i nazwa za struktura |
| `send` | TCP: segmenty po MSS z czekaniem na ACK (okno 1), retransmisja po RTO, zwraca liczbe wyslanych bajtow (czesciowy zapis dozwolony); UDP: jeden datagram; flagi != 0 -> `WSAEOPNOTSUPP` |
| `recv` | TCP: bufor per gniazdo, ACK po kazdym segmencie, FIN -> 0 (EOF), RST -> `WSAECONNRESET`, 20 s -> `WSAETIMEDOUT`; UDP: jeden datagram |
| `closesocket` | FIN + czekanie na ACK, `SYN_SENT` -> RST, zwolnienie slotu |
| `gethostbyname` | zapytanie A UDP do `usos_pkt_dns()` z portu efemerydalnego, 2 proby po 5 s, odpowiedz z kompresja nazw; brak -> `WSAHOST_NOT_FOUND`, timeout -> `WSATRY_AGAIN`; nazwa liczbowa obslugiwana bez sieci |
| `getsockname`/`getpeername` | `sockaddr_in` z lokalnym/zdalnym adresem i portem (porty w porzadku sieciowym) |
| `htonl/htons/ntohl/ntohs`, `inet_addr`, `inet_ntoa` | deleguja do rdzenia; `inet_addr` bez reszty funkcji (tylko `a.b.c.d`) |
| `WSAGetLastError`/`WSASetLastError` | bez zmian, kody z mapowania `usos_map_error()` |
| `select`, `WSAAsyncSelect`, `WSAAsyncGet*`, `WSASetBlockingHook`, `listen/accept/bind/sendto/recvfrom/...` | nadal stuby (te same sygnatury i ordinaly) |

### Czego NIE zweryfikowano

* **Brak Windows w QEMU = brak realnego polaczenia.**  Etap 1 konczy sie na
  Setupie Windows 3.1 (patrz wyzej), wiec `WINSOCK.DLL` nie byla jeszcze
  zaladowana przez Windows: nie ma dowodu, ze `WSAStartup` widzi sterownik,
  ze DPMI mapuje blok `'USQ1'` i ze ramki wychodza na karte.
* DPMI: sciezki `1687h`, `0002h` (z fallbackiem `0007h/0008h/0009h`) i
  `0300h` sa napisane, ale nie byly wykonane na zadnym hostcie DPMI.
* ARP/DNS/TCP na zywym medium: adresy MAC, retransmisje i okno sprawdzone
  tylko na ramkach syntetycznych; brak pomiaru przepustowosci.
* Brak DHCP i konfiguracji adresu - na sztywno `10.0.2.15`/`10.0.2.3`.
* `select`, `WSAAsyncSelect`, `WSAAsyncGet*`, `bind/listen/accept/sendto/
  recvfrom/setsockopt/shutdown/ioctlsocket/gethostbyaddr` pozostaja stubami.
* Brak testu, ze sterownik i DLL zgadzaja sie co do wersji bloku w czasie
  dzialania (zgodnosc wynika tylko z odczytu `usospkt.S`).
