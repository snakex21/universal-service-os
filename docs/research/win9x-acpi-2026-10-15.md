# Windows 9x power-off / ACPI on the X470 (research, 2026-10-15)

Scope: Windows 98 SE / 98 FE / ME / 95 OSR2 installed by USOS on the ASRock X470
Master SLI/ac (Ryzen 5700X, CSM off, CSMWrap 3.1.2-usos6 = SeaBIOS CSM). Research
only: no build, no disk or stick write, nothing tested yet. Sources: this repo,
the CSMWrap 3.1.2 source tree (SeaBIOS fork, `seabios/src/apm.c`, `stacks.c`,
`fw/biostables.c`, `fw/csm.c`), the X470 DSDT from the stick's ACPI dump
(`DSDT-01.bin`, 25402 bytes), forum posts listed at the end.

## 1. Today

- **ACPI is off.** Phase 1 of 98 / 98 FE / ME Setup runs in QEMU (`pc,acpi=off`,
  pentium3, 1 vCPU, SeaBIOS) with `/P I` (`src/platform/bios/dos_startup.cmd`
  lines 222-225, `U9VM=1`). 95 has no ACPI and gets no `/P`. No `ACPIOption`
  value is written. Even without `/P I` 98 would not pick ACPI on its own under
  SeaBIOS: the BIOS date at F000:FFF5 is SeaBIOS's fixed `06/23/99`, older than
  98's ACPI date list (force only by `/P J` or `Detect\ACPIOption=1`).
- **APM is the power manager**, "APM left on" (docs/win9x-modern-2026-09-30.md).
  Whether 98's "Advanced Power Management support" node (`*PNP0C05`, VPOWERD) is
  installed and enabled on our targets has never been checked.
- **Power-off does not work.** ME on the X470 ends at "Można teraz bezpiecznie
  wyłączyć komputer" (memory, 2026-10-06); 98 SE the same in practice (open
  polish item "Soft power-off for 9x"). A text message means Windows did not
  even try an APM power-off (an attempt that failed inside the BIOS would leave
  a black/hung screen or reset instead), so the first suspect is the 9x side
  (APM node missing / disabled), not the BIOS call.
- **What CSMWrap's SeaBIOS already does for APM 5307h (BX=1, CX=3):**
  `apm_shutdown()` first calls `bios_proxy_reset(3)` = UEFI
  `ResetSystem(EfiResetShutdown)` run through the helper core (CSMWrap keeps one
  AP alive for this), then falls back to `outw(0x2000, acpi_pm1a_cnt)` and `hlt`.
  `acpi_pm1a_cnt` comes from `find_acpi_features()` in `fw/csm.c` (FADT
  PM1a_CNT_BLK = 0x804 on the X470). Two holes:
  1. The fallback writes SLP_TYP = 0. That is right for QEMU (PIIX4/ICH9 `_S5`
     = 0) and wrong for the X470: DSDT `Name(_S5, Package(4){5,0,0,0})` ->
     SLP_TYPa = 5, the correct write is `0x3400` (SLP_EN | 5<<10) to 0x804.
     SLP_TYP 0 on AMD FCH = S0 -> nothing happens, CPU halts.
  2. `bios_proxy_reset` is VISIBLE32FLAT. From real/V86 mode it goes through
     `call32` -> helper-core mailbox (designed for that). 9x's VPOWERD connects
     the **32-bit protected-mode** APM interface (5303h; SeaBIOS returns
     `entry_apm32`, code base SEG_BIOS), where `MODE16` is 0 and the flat
     function is called directly with segmented addressing and 9x paging on.
     Whether that reaches `uefi_reset_call` cleanly is unverified; a reset or
     hang instead of power-off is plausible.
  USOS's own legacy menu "Shut down" uses real-mode APM 5307h; it powers off
  QEMU under plain SeaBIOS, on the X470 via CSMWrap it is marked "not tested"
  (docs/design/bios-via-csmwrap.md).
- **CPUs / RAM:** 9x is uniprocessor and ignores the MADT; the helper core is
  hidden anyway. RAM is capped at 1020 MB by U9FIX; ACPI changes nothing here.

## 2. What ACPI on 98 would bring, and its known problems

Realistic gain on the X470: soft-off and a graceful power button. Not sleep:
S3 needs a resume path through firmware that CSMWrap/SeaBIOS does not provide
(SeaBIOS resume vector != the board's), S1 is unreliable on Ryzen.

Costs / risks:
- 98's ACPI.SYS is a 1.0b-era WDM driver (same lineage as 2000's acpi.sys):
  the X470 DSDT has ACPI 2.0 constructs (`Name(MAB/MAL/MAM, QWordConst)` in
  `\_SB.PCI0`, CreateQWordField paths, v6 FADT in the XSDT). Expect the same
  class of failures as 2000 (namespace load errors, PCI root resource checks),
  plus 98's own enumerator bugs on large DSDTs. No HAL in 9x, so the 2000
  `halaacpi` FADT-copy overflow does not apply, but ACPI.SYS's own handling of a
  0x114-byte FADT is unknown.
- IRQ routing changes from PCI BIOS `$PIR` IRQ steering to ACPI `_PRT` / link
  devices (`\_SB` PIRQ index port 0xC00). Every PCI IRQ can move; xhci98,
  vmdisp9x VESA (no IRQ), NVMe (usosnvme 9x) and the SeaBIOS-driven USB
  keyboard/mouse path (USOSKEY/USOSMOUS rely on SeaBIOS USB IRQ/timer handling)
  are all at risk. SCI_EN=1 also changes what the AMI SMI handler does (USB
  legacy handoff, power button).
- Phase 1 runs in QEMU with ACPI off; ACPI would have to be added on the
  target afterwards (`ACPIOption=1` + Add New Hardware), which forum reports
  call unreliable, and VOGONS users note ACPI cannot be turned off again
  without reinstalling.
- RAM > 2 GB issues are already handled by the 1020 MB cap and are unrelated.

Verdict: weeks of work, high regression risk for the parts that work now
(input, display, NVMe), for one feature that APM can give.

## 3. Does the 2000 work transfer?

- `acpi_legacy_fadt=true` (patch 0006: rev-1/116-byte RSDT FADT copy, QWord
  windows above 4 GiB zeroed in DSDT/SSDT copies) and patch 0007 (ACPI enable
  before Legacy16Boot) would be the starting point if 98 ACPI were ever tried;
  98 would need the same gate in `xp_csmwrap_esp.sh` (today only
  `USOS_W2K_ACPI=on` writes it). The w2k-acpi MBR Name-QWord rewrite is 2000
  only. Not needed for the APM route below (APM path must work with the option
  off, i.e. SCI_EN as the firmware left it).
- 2000's remaining clock hang (RTC IRQ8 after ACPI enable) suggests the AMI SMI
  side is still not understood; another reason not to put 9x on ACPI now.
- Community: 98 on modern boards is run with `/P I` almost always; forum advice
  for power-off is "enable APM, use ATX PSU, Q239887 shutdown fix" (old boards).
  R. Loew's patches (PATCHMEM etc.) are closed, commercial-licence binaries; I
  found no rloew or open package for 98 ACPI on modern AML. Patcher9x (MIT) does
  not touch power management. So no ready open solution; our own CSMWrap code
  is the only redistributable option.

## 4. Cheaper route: APM power-off done right in CSMWrap

Patch 0008 for the SeaBIOS side of CSMWrap (own code, from the ACPI spec 4.8.3.2
/ 7.4.2, APM 1.2 spec 5307h):
1. At `find_acpi_features()`: read `\_S5` from the DSDT (byte pattern
   `08 5F 53 35 5F 12` -> package, first one/two elements, ByteConst 0x0A xx or
   Zero/One) -> store SLP_TYPa/SLP_TYPb, plus PM1b_CNT_BLK. X470 bytes:
   `_S5_ 12 07 04 0A 05 00 00 00` -> 5.
2. In `apm_shutdown()`: if running from the 32-bit/16-bit **protected-mode**
   APM entry, do not call `bios_proxy_reset`; do the direct S5 write
   (`PM1a_CNT = (cnt & ~0x1C00) | SLP_TYPa<<10`, then `| 0x2000`; same for PM1b)
   - pure port I/O, mode-independent, VPOWERD calls at ring 0. From real/V86
   mode keep the UEFI ResetSystem helper path first (firmware's own S5
   housekeeping), fall back to the corrected S5 write.
3. Serial/verbose line `USOS APMOFF: path=uefi|s5 typ=5 cnt=804` and a
   breadcrumb byte in low memory (as 0007 does at 0x4F4) for a dead-screen case.

Not run: `_PTS(5)` (X470: LEDs, TPM, SIO, GPIO wake prep). Firmware's
ResetSystem does its own equivalent; the raw S5 write skips it - acceptable
(Linux `acpi=off` boards behave the same), worst case wake-on-LAN/LED states.
With SCI_EN=0 an AMI board traps the SLP_EN write in SMI and normally completes
S5 itself; if it does not, setting SCI_EN first is a one-line change (gated).

9x side (no build, registry/INF): make sure `*PNP0C05` "Advanced Power
Management support" exists and power management is enabled after phase 1
(QEMU SeaBIOS offers APM 1.2, so 98 should detect it; ME/95 to check). If it is
missing, add it in the first-boot batch like VESA95/TZFIX.

Payoff beyond 9x: the same fix covers 95, 98 FE, ME, Win 3.1 (POWER.DRV),
DOS power-off tools and USOS's own legacy menu "Shut down".

Effort: 9x check 1-2 h; patch 0008 ~0.5 day code + Alpine VM build (twice,
hash-identical) + unit test on the `_S5` parser (Unicorn/host C) ~0.5 day;
X470 test 15 min. Risk: low; APM path only runs when an OS asks for power-off,
everything else unchanged.

Optional later: power button -> graceful shutdown via APM event (5308/530Bh
"system suspend request" when PM1a_STS.PWRBTN_STS is set) - only if 98 maps it
to shutdown; low priority, the 4 s override always works.

## Recommendation (least resistance)

1. **Zero-build X470 check (5 min):** boot the stick to USOS's legacy BIOS menu
   via CSMWrap, POWER -> Shut down. Off = helper-core ResetSystem works on the
   X470 from real mode. Stays on with "APM power-off is unavailable" or hangs =
   proxy path broken there too.
2. **Zero-build 9x check (QEMU, 20 min):** existing installed 98 SE target image
   (QEMU OVMF + CSMWrap usos6, `-machine pc` ACPI on, as the w9x e2e tests)
   with `csmwrap-verbose.flag` and serial: Device Manager -> System devices ->
   APM node present/enabled? Start -> Shut down -> QEMU exits? Serial shows
   `UEFI reset (type=3)` or `falling back to direct ACPI S5`. QEMU cannot show
   the SLP_TYP bug (its `_S5` is 0), only the 9x side and the 32-bit-PM path.
3. If the APM node is missing: first-boot batch/registry fix (no CSMWrap
   build). If APM is present and power-off fails on hardware: patch 0008.
4. **X470 test (one run, no fresh install):** after 0008 (or the 9x fix) in a
   build, patch the target disk's ESP CSMWrap binary or registry in place (per
   lowest-resistance rule), boot 98 SE, Start -> Shut down -> PC must power
   off; repeat on ME. Fresh install only for the release build.
5. Do **not** pursue ACPI on 9x now; park it behind the 2000 ACPI work.
