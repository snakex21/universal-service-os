# NVMe for Windows 95 OSR2 / 98 / 98 SE / ME: design study (2026-10-13)

Status: research only, no driver code yet. Goal: 9x on an NVMe disk runs in
32-bit protected mode, not in MS-DOS compatibility mode (INT 13h through
CSMWrap's SeaBIOS NVMe driver, see [win98-feasibility.md](win98-feasibility.md) §4.1).
Related: [../nvme-nt-2026-10-11.md](../nvme-nt-2026-10-11.md) (usosnvme for NT),
[../win9x-modern-2026-09-30.md](../win9x-modern-2026-09-30.md) (9x flow).

## 0. Verdict

| Question | Answer |
|---|---|
| Feasible | **Yes.** It is cheap if it is built as a SCSI miniport (`.MPD`) on the stock `SCSIPORT.PDR`. |
| Architecture | **`usosnvme.mpd`**: the same `usosnvme.c` core with a `USOSNVME_W9X` build, as AHCINT does with `AHCI_W9X`. A native `.PDR` port driver is parked. The INT 13h path stays as the fallback. |
| Toolchain | **WDK 7.1, which we already use for usosnvme.** A 9x `.MPD` is a PE image (native subsystem) that imports from `SCSIPORT.SYS`, the same as on NT (checked on the 98 SE CABs, §2). No Win98 DDK, MASM or VxD linker is needed. |
| Prior art | nvme2k (Dominik Behr, **BSD-3-Clause**, GPL-compatible) and its 9x port nvme9x by LordOfMice/SweetLow (**no licence file**: user-supplied only, do not read its source for our code). The port shows that the `.MPD` route works on real 9x. |
| Effort | Driver about 3–4 days, flow integration about 2 days, X470 run. A native `.PDR` would take 3–5 weeks. |
| Main risks | SCSIPORT.PDR with **no interrupt** (polled), IOS taking over the boot disk from INT 13h, 64-bit BAR above 4 GiB, the SCSIPORT.PDR speed bug on 95 / 98 FE. |

## 1. What is local / available

- **Win98 DDK, MASM 6.11, MSVC 2.0: not present.** I searched `Desktop\Universal_Service_OS`
  and `usos-x470-98se\tools` (and excluded `Desktop\doors`). There are only DOS-era `MASM.EXE`
  copies in `tools\reference\msdos-reference` (16-bit, useless here).
- **OpenWatcom** `tools\cache\openwatcom\ow-bac354f3c75f\binnt64`: `wasm`, `wcc386`, `wlink`.
  wlink can link LE VxDs (`format windows vxd`), and vmdisp9x (vendored, MIT) builds its VxDs with
  OpenWatcom. That is the open toolchain if a native `.PDR` or `.VXD` is ever needed.
  JWasm/UASM plus jwlink is the other open option. Neither is needed for the `.MPD`.
- **AHCINT 1.3.0.0-usos4** (`tools\vendor\ahcint`, GPL-3.0) already has a 9x target:
  `src\9X\makefile`, `ahcint9x.lnk` and `#ifdef AHCI_W9X` in `ahcimain.c`. It was never built by
  USOS because its recipe needs the 98 DDK `scsiport.lib`, MSVC 2.0 and MASM 6.11. The **pattern** is
  what we reuse (our own code, the same technique):
  - `HwAdapterState` must be non-NULL, or SCSIPORT.PDR reports "Init Failure".
  - It maps MMIO through VMM `_MapPhysToLinear` (an `int 20h` VxD call, KB Q169584) instead of
    `ScsiPortGetDeviceBase`.
  - It reads PCI config through CF8h/CFCh itself.
- **The 98 SE PL OEM ISO** (`OS\Windows\Windows 98 SE`) gives the reference binaries (§2) and
  `SCSI.INF` (§4). Windows 95 OSR2.1 PL ISO and ME media are also local.

## 2. Facts checked on the 98 SE CABs (BASE4.CAB etc., scratch only)

| File | Format | Notes |
|---|---|---|
| `aic78xx.mpd`, `symc8xx.mpd` | **PE**, subsystem 1 (native) 1.0, OS 4.0, base 0x10000, section align = file align (0x10), `.reloc` present | imports only `SCSIPORT.SYS` (ScsiPort* names) |
| `scsiport.pdr`, `ios.vxd`, `esdi_506.pdr` | LE VxD | |

`SCSIPORT.PDR` (4.0) resolves these names: CompleteRequest,
ConvertPhysicalAddressToUlong, ConvertUlongToPhysicalAddress, FlushDma, FreeDeviceBase,
GetBusData, GetDeviceBase, GetLogicalUnit, GetPhysicalAddress, GetSrb,
GetUncachedExtension, GetVirtualAddress, Initialize, IoMapTransfer, LogError, MoveMemory,
Notification, Read/Write Port/Register Uchar/Ushort/Ulong (+Buffer), SetBusDataByOffset,
StallExecution, ValidateRange, and ScsiDebugPrint.

The usosnvme NT4/2KXP imports are CompleteRequest, GetBusData, GetDeviceBase,
GetPhysicalAddress, GetUncachedExtension, Initialize, LogError, Notification,
Read/WriteRegisterUlong, SetBusDataByOffset and StallExecution, plus **`MmMapIoSpace` (ntoskrnl)**.
That one import is used for the VGA status line. Everything else is already in the PDR set.
The usosnvme PE already uses base 0x10000 and align 0x80 = file align 0x80.

## 3. Architecture options

| Option | What | For | Against |
|---|---|---|---|
| A. INT 13h via SeaBIOS (today) | CSMWrap SeaBIOS NVMe, 9x in compatibility mode | works now, zero code | slow, synchronous V86 BIOS calls, "compatibility mode" warning, swap/CD-burning issues, 137 GB boot limit through DOS |
| B. Real-mode INT 13h hook/TSR | our own DOS NVMe INT 13h driver | none over A (SeaBIOS already does this) | still compatibility mode, so **rejected** |
| **C. SCSI miniport `.MPD`** | `usosnvme.c` + `USOSNVME_W9X`, loaded by SCSIPORT.PDR under IOS | ~90 % code reuse, WDK 7.1, the same SRB/SCSI translation as NT, 95 OSR2 through ME (all ship SCSIPORT.PDR) | no IDE_PASS_THROUGH/SMART (MPD limitation, as SweetLow notes), SCSIPORT.PDR quirks |
| D. Native IOS port driver `.PDR` | own VxD: DDB, AEP handlers, DCB creation, IOP/IOR, ILB services, as in the ESDI_506 sample | full control, SMART, no SCSIPORT layer | needs the 98 DDK headers (Microsoft, not redistributable) or clean-room equivalents, an OpenWatcom LE build, about 3–5 weeks, a large new surface |

**Recommendation: C.** D only if C hits a SCSIPORT.PDR wall that cannot be worked around
(for example, the PDR refusing an adapter with no IRQ and IRQ routing failing under CSMWrap).

## 4. Design of `usosnvme.mpd` (option C)

**Source.** `tools/nt/usosnvme/src/usosnvme.c` with `#ifdef USOSNVME_W9X` (based on the
`USOSNVME_NT4` path):

- `DriverEntry` → `ScsiPortInitialize` with the NT 3.5/4-size `HW_INITIALIZATION_DATA` plus
  `HwAdapterState` (returns TRUE; on save, optionally set CC.SHN for a clean shutdown).
  `AdapterInterfaceType = PCIBus`, `NeedPhysicalAddresses = TRUE`, `MapBuffers = TRUE`,
  `Master = TRUE`, `Dma32BitAddresses = TRUE`.
- **PCI.** Use the existing `NvmeScan` / CF8h-CFCh code (class 01-08-02). 9x PCI.VXD handles
  64-bit BARs poorly, so the driver reads BAR0/BAR1 itself (as the NT4 build does).
  **If BAR1 != 0 (BAR above 4 GiB), refuse** with a red status line. VMM cannot map it, and 98/ME VMM
  has a known >4 GiB address bug (LordOfMice "vmm4gfix").
- **MMIO.** `_MapPhysToLinear(bar, 0x2000, 0)` through `int 20h` (VMM ordinal 0x006C), replacing
  `ScsiPortGetDeviceBase`. The same call maps the VGA line at 0xB8000 and replaces `MmMapIoSpace`.
  The registers are then accessed with `ScsiPortRead/WriteRegisterUlong` as now.
- **Queues.** Unchanged: admin queue + 1 I/O queue pair in `ScsiPortGetUncachedExtension`
  (physically contiguous; check that the PDR grants (NVME_PAGES+1)×4 KiB, otherwise
  shrink the depths). Polled: INTMS = all, PCI INTx disable, IEN = 0.
- **I/O.** Unchanged: READ/WRITE(10/16) → PRP1/PRP2/one PRP-list page, split at
  min(MDTS, 128 KiB). `ConfigInfo->MaximumTransferLength = 128 KiB`,
  `NumberOfPhysicalBreaks = 32`. FLUSH and the INQUIRY / READ CAPACITY / MODE SENSE
  emulation stay as they are. Only 512-byte LBA formats; 4Kn is refused, as on NT and as 9x requires.
- **Interrupt.** The NT4 build sets `BusInterruptLevel = 0` and completes every SRB inside
  `HwStartIo` (`RequestComplete` + `NextRequest`). The first thing to prove in QEMU is that
  SCSIPORT.PDR accepts this. Fallback 1: keep the PnP-assigned IRQ from ConfigInfo, register a
  no-op `HwInterrupt`, keep INTx masked and still poll. Fallback 2: real interrupts (CQ IEN = 1).
  Fallback 2 depends on CSMWrap `$PIR` routing, so it is the last resort.
- **Debug.** `_Debug_Printf_Service` (VMM 0x012D; WDEB386/DebugView) and, in QEMU builds,
  port 0xE9 (`-debugcon`). The VGA status line in row 9 is the same format as on NT.
- **Build.** `build.cmd w9x` in WDK 7.1: the same compiler, `-DUSOSNVME_W9X`, link
  `/SUBSYSTEM:NATIVE /ALIGN:0x80 /FILEALIGN:0x80 /BASE:0x10000 /ENTRY:DriverEntry`, no `INIT`
  discardable section (merge it into `.text`; the stock MPDs have only .text/.data/.idata/.rsrc/.reloc), and
  `scsiport.lib` from WDK 7.1 (it imports `SCSIPORT.SYS`, which the PDR resolves). Output `bin/W9X/usosnvme.mpd`.
- **Tests.** Extend `tools/tests/test_usosnvme.py`: the W9X image imports only `SCSIPORT.SYS` and
  only names from the §2 list, there is no ntoskrnl import, it has the PE layout above, and it has relocations.

**Not in scope (v1):** LBA > 32 bit (9x DCB sector counts and FAT32 cap far below
2 TiB), TRIM, SMART, multiple namespaces, hot removal, power states.

## 5. Install integration (9x CSMWrap flow)

Today's flow (`tools/w9x_csmwrap_target.sh`, `w9x_phase1_qemu.sh`): DOS from MEMDISK → INSTALL.BAT →
Setup from `C:\WIN98`. Phase 1 runs in a QEMU VM with an **IDE** disk, and phase 2 runs on the real PC.
`USOSVESA.INF` already shows how to emit per-PC PCI IDs (`w9x_add_display_ids`).

1. **Payload.** `build_win9x_support.py` stages `USOSNVME.MPD` and `USOSNVME.INF` into
   `EFI/USOS/dos-native/win9x/`. Add them to `STAGED`, the golden list and `third-party.json`
   (own GPL code, so no third-party entry).
2. **INF.** `Class=SCSIAdapter`, signature `$CHICAGO$`, `CopyFiles` to DestinationDirs 12
   (`SYSTEM\IOSUBSYS`), `AddReg`: `HKR,,DevLoader,,*IOS`, `HKR,,DontLoadIfConflict,,"Y"`,
   `HKR,,PortDriver,,usosnvme.mpd` (as in the stock SCSI.INF). Do not add `DoubleBuffer`.
   **Hardware IDs: per PC**, from the prep step (`PCI\VEN_xxxx&DEV_yyyy` of every class
   01-08-02 function, the same way as USOSVESA.INF). Whether 9x PCI.VXD emits a `PCI\CC_010802`
   compatible ID is unverified. The per-PC IDs work either way, and the QEMU test also checks the CC id.
3. **When it binds.** Phase 1 in the VM sees no NVMe, so the driver must be bound on the real machine.
   INSTALL.BAT copies `USOSNVME.INF` to `C:\WINDOWS\INF\OTHER` and the MPD to
   `C:\WINDOWS\SYSTEM\IOSUBSYS` (the same pattern as the VESA INF), so at the first real-hardware
   boot PnP finds the new PCI device, installs it silently, and IOS claims the disk at the next start.
   For a non-VM install (Setup on the target), the same copy happens before Setup's
   hardware-detection reboot. Alternative: `msbatch.inf [Install]` with `CopyFiles` plus a
   `RunOnce` reboot.
4. **Gating.** It runs only when the target disk is NVMe (as for NT: an `nvme-experimental.txt`
   flag until there is an X470 PASS). Check the BAR at UEFI-menu time. If BAR0 is above 4 GiB, show
   "disable Above 4G Decoding" and keep compatibility mode.
5. **95 / 98 FE.** Their SCSIPORT.PDR has the fast-CPU calibration bug. Patcher9x `speed`
   patches SCSIPORT.PDR, but so far it has never been exercised because no miniport loaded.
   Confirm that the patched SCSIPORT.PDR is the one in the install.

## 6. Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| SCSIPORT.PDR rejects or mishandles a no-IRQ adapter | medium | §4 fallbacks; QEMU proves it first |
| IOS does not match the INT 13h boot drive to the new DCB, so C: stays in compatibility mode or gets a double letter | medium | IOS matches by reading sectors; 98 boots from Adaptec SCSI the same way. Test the boot disk, not just a data disk. Check `IOS.LOG` and the Performance tab |
| 64-bit BAR above 4 GiB on X470 (Above 4G Decoding, CSMWrap) | low–medium | refuse + UEFI-menu warning |
| Uncached extension size or contiguity limits in the PDR | low | smaller queues (depth 16 is enough when polled) |
| Polled I/O blocks the VM during transfers | low | NVMe latency is µs–ms, as on NT4 |
| WDK 7.1 PE that the PDR loader dislikes (sections, alignment, OS version fields) | low–medium | match the stock MPD layout; patch the header fields after link if needed |
| 95 OSR2 SCSIPORT.PDR older API differences | low | test 95 separately; HwInitializationDataSize = NT 3.5 size |
| ME: no real-mode Setup step for the copy | low | the copy is done by our DOS stage / prep, not by Setup |

## 7. QEMU test plan

QEMU's SeaBIOS has NVMe INT 13h, like CSMWrap. Use `-device nvme,serial=usos,drive=n0`
(+ `-drive id=n0,if=none,format=raw`), `-debugcon file:e9.log`, and a CPU/RAM setup like
`w9x_phase1_qemu.sh`.

1. **Load (data disk):** 98 SE on IDE, NVMe as the second disk with an MBR + FAT32 partition. Copy the
   INF/MPD and reboot. PASS = Device Manager shows "USOS NVMe" under SCSI controllers, a new
   drive letter, e9.log shows `USOSNVME ... OK`, and no `IOS.LOG`. Also note the 9x PCI hardware/compatible IDs
   (`HKLM\Enum\PCI`) to answer the `PCI\CC_010802` question.
2. **No IRQ:** the same as 1 with the NT4-style `BusInterruptLevel = 0`, then decide the fallback.
3. **Data integrity:** copy about 1 GB of mixed files, compare with `FC /B` (DOS) and check CRC lists, then
   ScanDisk surface; repeat after a cold reboot. Writes that span more than 128 KiB exercise the splits and PRP lists.
4. **Boot disk:** run the full USOS 9x flow with the NVMe disk as the only disk (bootindex nvme).
   PASS = after the first boot System → Performance shows no compatibility mode, the swap file is
   on C:, shutdown and restart are clean (HwAdapterState), and there is no double drive letter.
5. **Matrix:** 98 SE (main), 98 FE, ME, 95 OSR2.1 (with Patcher9x), each step 1 + 4.
6. **Negative:** a 4Kn namespace (`logical_block_size=4096`) gives a red line, the disk stays in compatibility mode, and there is no crash.
   A BAR placed high (`-global` / `pci-bridge` with a 64-bit pref window, if reproducible) is refused.
7. **Hands-free e2e** in `tools/tests/` (as `run_*_qemu.py`), with the e9.log marker plus a file-hash
   check through mtools on the image afterwards.
8. **X470** (after QEMU PASS): Micron 3400 under CSMWrap, 98 SE fresh install, the same checks as step 4.
   This needs the user and the target disk identified by serial.
