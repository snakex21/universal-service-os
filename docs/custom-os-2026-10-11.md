# Custom OS (2026-10-11): Haiku, FreeBSD, ReactOS, KolibriOS, FreeDOS, TempleOS, own image

Stage "Custom OS" before 1.0: systems that are neither Windows nor Linux,
started through the normal USOS flow on the X470 (no CSM, AHCI, xHCI only,
RX 560). Status: **implemented and QEMU-verified** for Haiku, FreeBSD,
KolibriOS, FreeDOS, ReactOS (LiveCD behind CSMWrap since the ELCR MBR, 3.1)
and own hybrid images; TempleOS not possible on this hardware. X470 untested.

## 1. One recipe: the official image written to the target disk

Linux ISOs boot live from DATA because USOS maps the ISO file as a block
device for the Linux kernel (docs/design/linux-iso-boot.md). None of these
kernels can be given such a device, and none of them reads NTFS. What they
all ship instead is a **hybrid image**: an ISO/IMG whose first sectors are a
partition table, made to be `dd`-ed to a USB stick. USOS does exactly that,
to the disk the user picked and confirmed:

```
UEFI menu: Other systems -> Haiku -> image -> Start
  -> request.ini (system, image) -> micro-Linux step 620 (w9x_csmwrap_prepare.sh)
  -> disk picker + "FORMAT THE ENTIRE DISK?" (the one disk question)
  -> tools/image_disk_target.sh:
       classify: EFI system partition in MBR (type EF) or GPT?  -> mode uefi
                 MBR with boot code, no ESP, free slot?          -> mode csmwrap
                 anything else (CD-only ISO, TempleOS)           -> refused, no write
       clear both disk ends, dd the image, read back first/last 4 MiB
       GPT image: sfdisk --relocate gpt-bak-std (backup GPT to the disk end)
       FreeDOS: SETUP.BAT -> SETUP.OFF (start into the prompt, not the installer)
       hybrid ISO in csmwrap mode: El Torito id 'EL TORITO' -> 'XL TORITO' (see 4)
       csmwrap mode: xp_csmwrap_esp.sh (64 MiB CSMWrap ESP in a free MBR slot at the end)
       ReactOS / own image in csmwrap mode: ELCR MBR in sector 0, image MBR kept at LBA 1 (see 3.1)
  -> restart: the firmware boots the disk (own UEFI loader, or CSMWrap -> SeaBIOS -> MBR)
```

The rest of the disk stays unallocated (the OS's own tools can use it).
Profile `custom-image-uefi` (backend `win9x_uefi`, images `.iso` and `.img`,
method Automatic); the catalog category "Other systems" (UEFI menu only; the
BIOS Core keeps its five cards) with `Systems\Other\<OS>\Images`; FreeDOS keeps
its DOS-category entry and its BIOS Core routes and gains this UEFI route.

## 3. Per-OS notes

- **Haiku**: anyboot = MBR with a BFS partition (type EB) and a FAT ESP (EF).
  Written to a disk it is a normal Haiku boot volume (the Haiku team's "USB
  stick install"); changes persist. The BFS volume is only ~1.4 GB; for a
  full-size system run Installer (Deskbar -> Applications -> Installer), let
  DriveSetup create a BFS partition in the unallocated space and install
  there. Not verified yet: which volume the EFI loader picks afterwards
  (Haiku shows a boot volume menu when Space is held).
- **FreeBSD**: disc1 is a hybrid GPT (efi + freebsd-boot) ISO. It boots the
  installer; "Live System" gives a usable root shell (vt efifb console at
  the firmware resolution). A real install from this disk needs a second
  target disk. Next step (after 1.0): an unattended bsdinstall in the
  micro-Linux VM (like NT 4.0), or a memstick image + `installerconfig`.
- **KolibriOS**: the raw image boots UEFI-native with its own UEFI loader.
  Display, AHCI and the desktop are fine; input needs PS/2 (the X470 Master
  has a PS/2 port) because KolibriOS has no xHCI driver. Floppy image
  (kolibri.img) is an alternative only under BIOS (memdisk), not wired.
- **FreeDOS**: FullUSB image = FAT32 C: with KERNEL.SYS, \FREEDOS\BIN and the
  package repository. Its installer, started from its own disk, aborts
  (QEMU) and drops to the prompt anyway, so USOS renames SETUP.BAT and the
  disk starts straight into FreeDOS. The pendrive (usable-system 4) appears
  as a BIOS disk through SeaBIOS when plugged in before power-on.
- **ReactOS**: the 0.4.16 ISO is isohybrid and its LiveCD runs from an AHCI
  hard disk under SeaBIOS (QEMU). Two USOS changes were needed for the
  CSMWrap start: the CSMWrap ESP, and hiding the El Torito boot record (EDK2
  otherwise treats the whole disk as a CD and never reads the MBR, so the
  ESP was invisible). The third one is the ELCR MBR (3.1): without it
  ReactOS stops with 0x7B behind CSMWrap. With the firmware CSM on, the X470
  can also boot the written disk directly (legacy boot entry). No xHCI in
  ReactOS: PS/2 input.
- **TempleOS**: IDE/ATAPI PIO only; the X470 has AHCI SATA only, so neither
  a live boot (the kernel reads its files from the CD with its own ATAPI
  driver) nor an install is possible. Forks with AHCI exist (ZealOS: AHCI +
  Limine/UEFI) but are distributed from GitHub only; a user's ZealOS hybrid
  image can be tried through "Other system (own image)". Parked.
- **Own image**: anything the classifier accepts. Refusal text: "this image
  cannot start from a hard disk (a CD-only ISO ...)".

### 3.1 ReactOS 0x7B behind CSMWrap: the 8259 ELCR (2026-10-11)

Symptom (QEMU q35, OVMF without CSM, ICH9 AHCI, TCG): CSMWrap -> SeaBIOS ->
isohybrid MBR -> FreeLoader -> kernel; then
`*** Fatal System Error: 0x0000007b (0xAF779A0C,0xC0000034,0,0)` from
`IopMarkBootPartition` (ntoskrnl/io/iomgr/iomgr.c:428): the ARC boot device
`multi(0)disk(0)rdisk(0)partition(1)` was never created. Same disk under
plain SeaBIOS: LiveCD GUI.

Serial log (freeldr.ini `LiveImg_Debug` entry made the default on a scratch
copy: `/DEBUG /DEBUGPORT=COM1 /BAUDRATE=115200 /SOS`): FreeLoader passes
the same ARC path in both runs and both use the non-ACPI "PC Compatible
Eisa/Isa HAL" with the AHCI controller on IRQ 10. Behind CSMWrap the 0.4.16
atapi driver times out on IDENTIFY four times and gives up:

```
(drivers/storage/ide/atapi/portstate.c:926) AtaPortTimeout CH 0: Slot 0 (00000001) timed out 80618040 (10s) 0 ''
(drivers/storage/ide/atapi/portstate.c:949) AtaPortTimeout CH 0: TF ec:00:00:00:00:00:00
PxIS 0x00000000  PxCMD 0x0000C017  PxTFD 0x00000050  PxCI 0x00000000  PxSSTS 0x00000113
(drivers/storage/ide/atapi/portstate.c:245) AtaPortMarkDeviceFailed CH 0: Too many reset attempts for the device 0, giving up
```

The command completed (PxCI 0, TFD 50h) but the driver never saw the
interrupt. QEMU monitor `info pic`: under plain SeaBIOS `pic1 ... elcr=0c`
(IRQ 10 and 11 level-triggered); behind OVMF -> CSMWrap `elcr=00` on both
8259s, and `info irq` shows 4 interrupts on IRQ 10 instead of thousands.

Root cause: SeaBIOS sets the ELCR (ports 4D0h/4D1h) for the PCI IRQs in its
own PCI setup, which it skips in CSM mode; OVMF leaves the ELCR at 0 and
CSMWrap does not set it either. ReactOS's 8259 HAL takes the trigger mode
from the ELCR (HalpInitializePICs), so the level-triggered AHCI interrupt
is programmed edge-triggered and lost. This is a firmware/CSMWrap gap, not
a ReactOS bug (a real BIOS marks PCI IRQs level-triggered); a CSMWrap/SeaBIOS
patch could do the same for every OS (follow-up), but needs a rebuild.

USOS fix without a rebuild: `src/platform/bios/reactos/elcr_mbr.S` (224
bytes, built by `tools/build_xp_geometry_fix_mbr.ps1` as
`elcr-mbr-440.bin`, shipped in micro-Linux `/usr/lib/usos/`). It scans PCI
configuration space (mechanism #1, all buses), sets the ELCR bit of every
interrupt line 3..15 that belongs to a function with an interrupt pin
(never IRQ 0, 1, 2, 8, 13), then loads the image's own MBR from LBA 1 and
jumps to it with DL unchanged. `image_disk_target.sh` (`elcr_fix`, for
`reactos` and `other-os` in csmwrap mode, after the CSMWrap ESP so the kept
copy has the final partition table) writes it only when LBA 1 of the
written image is empty (ISO system area), with a read-back of both
sectors. Disk signature, partition table and 55AA stay in sector 0, so the
ARC disk match (signature + checksum of sector 0, read by FreeLoader and by
the kernel alike) is unaffected.

Results 2026-10-11 (TCG): `run_custom_os_micro_linux_qemu.py --system
reactos --boot 300 --tcg` -> `ELCR MBR written ... read-back PASS`, OVMF ->
CSMWrap -> ReactOS LiveCD language page (280 s); `info pic` behind CSMWrap
`elcr=0c`. Same disk under plain SeaBIOS: LiveCD GUI. Unit test:
`tools/tests/test_image_disk_elcr.py`. Open on the X470: the AMI firmware
may leave PCI interrupt lines (3Ch) at FFh without a CSM, then the stub
sets nothing and the non-ACPI HAL has no IRQ for the controller.

## 4. Tests

- `zig build test`: routing golden (custom-image-uefi rows), catalog
  categories (six on the host, five in the BIOS Core).
- `tools/tests/run_custom_os_micro_linux_qemu.py --image X --system ID --out
  DIR --boot SECONDS [--keys "t:k,k;..."] [--tcg] [--boot-only]`: runs
  image_disk_target.sh in the built micro-Linux (nested QEMU, scratch raw
  disk), then boots the disk with OVMF (no CSM), AHCI, qemu-xhci keyboard +
  mouse and no i8042 (USB-only input). Results of 2026-10-11: table above.
