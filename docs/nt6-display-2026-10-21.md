# NT6 display resolution without CSM, 2026-10-21

Branch `feat/nt6-display` (base `test/x470-98se-qemu` f28a3fd8). Status:
host-tested (Zig unit tests, answer goldens, shell/host tests, full
build). **Not yet run on the X470**, no Windows install was run.

## Finding

X470: Vista SP2 x64 via CSMWrap (RX 560 VBIOS POSTed by CSMWrap, Standard
VGA / vgapnp XDDM) installs at 800x600. 1920x1080 chosen by hand in Display
Settings works. No NT6 CSMWrap path set the resolution: the profile
`display` tweak covered only NT5 / NT4 / NT3 / 9x.

## Approach (option B: USOSRES at the first sign-in)

The resolution is chosen on the target, from what the running driver
offers, with the same tool, selector and transaction as 9x / NT4 / 2000
(`tools/windows_usos_res.c`, `display_policy.h`, `display_apply.h`;
docs/display-from-profile-2026-10-20.md): auto = the largest progressive
60 Hz / default mode up to 1920x1080 (32 bpp preferred), CDS_TEST before
every apply, DISPLAY.BAK + rollback, DISPLAY.DONE once settled, VM
deferral by the CPUID hypervisor flag. Option A (an `<Display>` value
computed at prep time) was not used for auto: the micro-Linux has no
reliable EDID / VBE list of the XDDM driver's modes, and Windows ignores
an unsupported value, so a guess would leave 800x600 just as silently.

Paths covered (all go through `tools/vista_csmwrap_target.sh`):

| Profile | Systems | Display |
| --- | --- | --- |
| `vista-x64-sp2-uefi-csmwrap` | Vista SP2 x64, Server 2008 x64 | USOSRES (auto or the profile's value) |
| `win-nt6-x86-uefi-csmwrap` | Vista / 7 / Server 2008 x86 | USOSRES (auto or the profile's value) |
| `win-x86-uefi-csmwrap` | 8.1 / 10 x86 | not covered (answers for 8+ carry no registration); open |
| Win7 x64 UefiSeven | 7 x64 | unchanged: only 1024x768 VBE there; the commands find no file and do nothing |
| native UEFI 8+ (GOP / WDDM) | 8 ... 11, 2012+ | nothing unless the profile sets a fixed value |

### Chain

1. **Answer** (`src/flow/answer/autounattend.zig`): every Vista / 7 /
   2008 / 2008 R2 answer gets two guarded specialize commands:
   `icacls "%SystemDrive%\USOS" /reset /t /c /q` and, in the Default user
   hive, `HKCU\...\Run USOSDisplay = %SystemDrive%\USOS\NT6\USOSRES.EXE`,
   both `if exist "%SystemDrive%\USOS\NT6\USOSRES.EXE"`. A profile request
   (`display=` / `display_bpp=` / explicit auto) adds
   `<!-- USOS-DISPLAY=WxHxbpp -->` before `<unattend>`.
2. **Staging** (`vista_csmwrap_target.sh` step 2b): right after formatting
   the Windows partition, when the answer contains the registration
   (`usos_display_nt6_answer`), it mounts the partition (ntfs3) and writes
   `\USOS\NT6\USOSRES.EXE` + `DISPLAY.TXT` (the comment's request, else
   `autoxauto`). Setup installs into that partition (InstallTo, no
   format), so the folder stays. Optional: every failure is logged
   (`DISPLAY ...` in prepare.log) and the preparation continues.
   A user's own DATA answer file has no registration: nothing is staged.
   No answer at all: nothing either (no command can register the helper).
3. **First sign-in** on the hardware: USOSRES applies (no CDS_GLOBAL on
   6.x: settings are per machine, and the first sign-in may run with a
   filtered UAC token). It removes its own HKCU Run value (no elevation
   needed), also later for every further user once DISPLAY.DONE exists.
   Log: `C:\USOS\NT6\USOSRES.LOG`, expected
   `DISPLAY request=autoxauto modes=...`, `DISPLAY selected=1920x1080x32
   reason=... test=0`, `DISPLAY applied`.

### Fixed value in a profile

`display=1024x768|1280x1024|1920x1080` is now offered for every 6.x+
system (schema `tweak_support` `.since = .vista`). It renders Shell-Setup
`Display` (ColorDepth 32, or 16 with `display_bpp=16`;
Horizontal/VerticalResolution) in specialize for all 6.x+ versions. Windows
ignores a mode the adapter lacks. Auto writes no `<Display>`: native UEFI
8+ keeps the GOP / WDDM driver's choice.

## Open / risks (for the X470 run)

- The vgapnp mode list must report 60 Hz or default (1) refresh; other
  values are rejected by the existing selector (then `no tested mode`).
- The ntfs3-made folder is reset to inherited permissions in specialize;
  if icacls failed the log/marker write could fail (no change, retried at
  the next sign-in).
- Auto stops at 1920x1080 (shared policy); a larger native monitor gets
  1920x1080.
- 8.1 / 10 x86 via CSMWrap and Win7 x64 UefiSeven are not covered.
- X470 check: Vista x64 (Micron) fresh install with a profile, expect
  1920x1080 after the first sign-in without user action; USOSRES.LOG.
