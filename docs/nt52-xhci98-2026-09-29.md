## 1. The driver

xhci98 (<https://github.com/yeokm1/xhci98>, Yeo Kheng Meng, GPL-2.0-only)
is a USBPORT miniport for xHCI controllers (`PCI\CC_0C0330`): it drives the
USB 2.0 ports of the controller under the system's own `usbport.sys`, so
the inbox hub, HID and mass-storage drivers work on top. No KMDF, no kernel
extender. USB 3 devices run at High Speed.

- **Pinned: 1.1.1.0** (tag `v1.1.1.0` = commit 7d0dd9d4, released
  2026-09-23, the latest release on 2026-09-29), in
  `tools/vendor/xhci98/1.1.1.0/`: the unmodified `release-x86/` and
  `release-x64/` `xhci98.sys` + `xhci98.inf`, `LICENSE`, `manifest.json`
  (SHA-256 of every file and of the release zip), `SOURCES.txt`. The
  source tarball of the tag is kept git-ignored in
  `tools/vendor/xhci98/1.1.1.0-src/` (third-party.json ships it in the
  sources zip). 1.1.0.0 in `tools/vendor/xp-modern` stays the Vista/9x
  research copy.
- **Builds:** `release-x86` (i386; the INF's `.NTx86` path covers
  Windows 2000, XP and, being NT 5.x x86, Server 2003 x86) and `release-x64`
  (amd64; `[XhciModels.NTamd64]` = XP x64 / Server 2003 x64). Upstream
  tests XP x64 SP2 in VMs; **Server 2003 x86 is not an upstream target**,
  but the x86 build fits it: every import (`ntoskrnl`, `hal`, `usbport`,
  12 names) resolves on the 2003 SP2 x86 media, the x64 build's 8 on XP x64
  SP2, and the 2003 x86 `usbport.sys` 5.2.3790.3959 returns the XP-lineage
  `USBPORT_GetHciMn` value `0x10000001` that xhci98 accepts.
- **Upstream's integration notes** (readme section 3, lessons "Phase 19"):
  on an xHCI-only machine XP/2003 never copy `usbport.sys`, `usbhub.sys`,
  `usbd.sys` (and `usbui.dll`) because LAYOUT/TXTSETUP give them the
  text-mode disposition "do not copy" (`,4,1,3`); without `usbport.sys` the
  controller shows Code 39 (unresolved import). The INF therefore copies
  them with flag 16 through `LayoutFile=layout.inf`. Upstream only
  documents installing into a running system, not text-mode integration.

## 2. Integration (`tools/nt52_usb_stage.sh`)

Applied on the target after the local-source copy and the storage step
(`prepare_xp_ntfs_target.sh`) for the profiles `w2k3-x86-sp2-uefi-csm`
(x86 build, after the Server 2003 ACPI/GenAHCI bundle) and
`xp-x64-sp2-uefi-csm` (amd64 build, after GenAHCI). XP x86 never runs it
and keeps its USB3 backport bundle. `legacy_xp_staging.sh` refuses the
start before any disk write when the package lacks the files.

- `xhci98.sys` in `$WIN_NT$.~BT` and the local source (`I386`/`AMD64`).
- TXTSETUP.SIF (the three copies): `[SourceDisksFiles]` `xhci98.sys`
  (system32\drivers) and `xhci98.inf` (dirid 20, `%windir%\inf`),
  `[HardwareIdsDatabase] PCI\CC_0C0330 = "xhci98"`,
  `[InputDevicesSupport.Load]` / `[InputDevicesSupport]` (text mode loads
  it for a USB keyboard and writes its service and
  CriticalDeviceDatabase entry into the new system), `[files.xhci98]`.
- **Forced USB/HID stack:** the rows of `usbport`, `usbd`, `usbhub`,
  `hidclass`, `hidparse`, `hidusb` and `kbdhid` go from `,4,1,3` to
  `,4,0,0` (copied on a new installation). `mouhid.sys` is not on the media
  outside `DRIVER.CAB`; GUI-mode PnP installs it (input.inf).
- `xhci98.inf` in the local source with `[SourceDisksNames]` row 1 =
  `1=%DiskName%,,,\amd64\xhci98` (or `\i386\xhci98`) and a second
  `xhci98.sys` in that folder. Text-mode Setup *moves* uncompressed files
  out of the local source, so the copy next to TXTSETUP.SIF is gone by GUI
  mode; the first QEMU runs stopped at "Files Needed: xhci98.sys on xhci98
  xHCI Miniport Disk, C:\$WIN_NT$.~LS\amd64". GUI-mode PnP installs the
  controller from `%windir%\inf\xhci98.inf`, and the installed system keeps
  the service, the INF and the stack.
- DOSNET.INF of the local source: `d1,xhci98.sys`, `d1,xhci98.inf`
  (`[Files]`), `d1,xhci98.sys` (`[FloppyFiles.1]`).

Package: `usr/lib/usos/nt52-usb/{x86,amd64}/xhci98.{sys,inf}`, `LICENSE`,
`SOURCE.txt` (added by `build_xp_uefi_csm_trial.py`, hashes checked against
the manifest). `NT52_USB3` stays `False`.

## 3. QEMU (2026-09-29)

TCG, `qemu-xhci` + `usb-kbd` + `usb-tablet` (the pointer routed to the
tablet with `mouse_set`), the 8042 present (NTDETECT needs it) but no key
goes to it: HMP `sendkey` reaches the USB keyboard, whose handler QEMU
activates last. Target on AHCI. usos-xp.ini with `user` and `computer` and
**no product key** (DefaultHide: Setup stops at the key page). Harnesses:
`run_seabios_xp_uefi_csm_textmode.py` (SeaBIOS, the firmware-CSM stand-in)
and `run_csmwrap_xp_prepared.py` (OVMF without CSM -> CSMWrap), both with
`--ahci --usb-only --run-through --type-at ...`.

| Run | Text mode | GUI Setup | USB keyboard at the product-key page | GUI-mode device installs (setupapi.log) |
|---|---|---|---|---|
| XP x64 SP2 (EN), SeaBIOS (CSM) | PASS (copy, restart) | PASS to the key page | **PASS**: `QWERT-123QW-ERT12-3QWER-T123` typed | xhci98 controller from `%windir%\inf\xhci98.inf` (file from `C:\$WIN_NT$.~LS\amd64\xhci98`), USB Root Hub (usbport.inf), USB keyboard + tablet, HID keyboard (kbdhid) + HID mouse (mouhid): all "finished successfully" |
| XP x64 SP2 (EN), OVMF -> CSMWrap | PASS | PASS (key page about 7 min after the CSMWrap boot) | **PASS** | the same |
| Server 2003 R2 SP2 Ent (PL), SeaBIOS (CSM) | PASS (with the ACPI/GenAHCI bundle) | PASS | **PASS** ("Klucz produktu" filled) | the same, `\i386\xhci98` |
| Server 2003 R2 SP2 Ent (PL), OVMF -> CSMWrap | PASS | PASS | **PASS** | the same |

- The typed text proves the whole chain: no PS/2 key is sent, SeaBIOS and
  CSMWrap's own USB drivers are gone once Windows runs, so the keys reach
  GUI Setup only through xhci98 -> usbport -> usbhub -> hidusb -> kbdhid.
  Before the GUI-mode device install the controller already runs from the
  CriticalDeviceDatabase entry text-mode Setup wrote
  (`[HardwareIdsDatabase]`): the first runs typed into the "Files Needed"
  dialog below.
- The pointer: QEMU's screendump does not show the hardware cursor at the
  key page, so the tablet is proven by the device installs (HID mouse on
  mouhid), not by a screenshot.
- First attempt (fixed): Setup asked "Files Needed: xhci98.sys on xhci98
  xHCI Miniport Disk" with `C:\$WIN_NT$.~LS\amd64`. Text mode had moved the
  plain file out of the local source (the image showed it only in
  `system32\drivers`); the second copy in `<src>\xhci98` fixed it on all
  four runs.
- Setup stops at the key page (no key anywhere in the tooling), so the
  installed system was not reached; `system` hive reads were refused
  (the killed VM left it dirty), setupapi.log is the record.
- **USB storage** (CSMWrap runs of both systems, `--usb-storage`: a blank
  64 MiB disk hot-plugged during GUI Setup behind a `usb-hub`): USB hub
  (`VID_0409&PID_55AA`), the mass-storage device (`VID_46F4&PID_0001`) and
  `USBSTOR\DISK&VEN_QEMU&PROD_QEMU_HARDDISK` all "finished successfully".
  A bare QEMU `usb-storage` is SuperSpeed-capable and lands on a USB 3 port,
  which xhci98 leaves unpowered by design, so it was not seen there (the
  first try): expected, and the reason for the hub.
- XP x86 SP3: not affected; the prepared target's digest equals
  `tools/tests/golden/xp_uefi_csm_target_digest.tsv` and the XP bundle id
  is unchanged (79b93ec0...).

|---|---|---|

  investigation), although the QEMU runs installed USBSTOR (section 3).
- **Staging bug found (first attempt):** after GUI Setup the system looped

**Workaround (user-facing):** Na płytach AM4 z XP x64/Server 2003 używaj

obsłuży kontrolera w procesorze.

### Test plan (before the run)

  mode, then GUI Setup; at "Klucz produktu" the USB keyboard and mouse on
  the **rear USB 2.0/3.0 ports** must work. Try both controllers: the

## 5. xhci98 1.1.1.0-usos1 (MODIFIED): the CPU xHCI 149C

### Diagnosis (offline SYSTEM hive of the X470 run in section 4)

- `PCI\VEN_1022&DEV_43D0` (Promontory, bus 1): `BootConfig` present (BAR
  `0xFCEA0000`), `DetectedLegacyBIOS=1` (the firmware's SMM still owned it),
  `SymbolicName` set: started, root hub and a Bluetooth device enumerated.
- `PCI\VEN_1022&DEV_149C` (CPU, bus 12 dev 0 fn 3): **no `BootConfig`**,
  only a `BasicConfigVector` (BAR `0xFC900000` preferred, INTx pin present),
  `DetectedLegacyBIOS=0`, no `SymbolicName`, no root hub. PCI.SYS writes a
  BootConfig only for decoders that are on, so the firmware left 149C with
  Memory Space (and Bus Master) off at ExitBootServices.
- NT 5.x PCI.SYS assigns the BAR and turns decoding on, but Bus Master
  Enable stays as the firmware left it. xhci98 1.1.1.0 refuses a controller
  whose BME it did not clear itself (`xhciCheckBusMaster`, init step 3,
  "refusing rather than running a controller that cannot DMA"). Linux never
  meets this: `pci_enable_device()` + `pci_set_master()` in xhci-pci.
- The Linux AMD quirks for 149C/145F (suspend delay, reset-on-resume,
  trust-TX-length, broken D3cold, PLL fix for older chipsets) concern
  transfers, suspend and runtime PM, none the first start. Upstream has no
  AMD fix after 1.1.1.0 (issues/commits checked 2026-09-29).

### The patch (`tools/vendor/xhci98/1.1.1.0-usos1/`)

`patches/0001-usos1-amd-cpu-xhci-start-and-file-log.patch` on the v1.1.1.0
tarball, every spot marked `MODIFIED (USOS 1.1.1.0-usos1)`; `MODIFIED.txt`
lists it. In short: D0 through the PM capability (BARs restored if the
transition reset them), then Memory Space + Bus Master Enable, before the
bus-master gate; CNR wait (10 s) before the first USBCMD write; HCRST/CNR
timeout 1 s -> 10 s; USBLEGSUP taken over (BIOS_OWNED cleared) when no SMM
answers; scratchpad cap 64 -> 256 (AMD never measured upstream).

**Log file:** `C:\WINDOWS\xhci98.log` (text mode writes
`C:\$WIN_NT$.~BT\xhci98.log`). A system thread appends every flush: a
successful start (reason 2), a refused start (reason 1) and a stop
(reason 0), retrying every 2 s for up to 15 min while `\SystemRoot` is not
reachable (boot-driver start). Header per flush:
`=== xhci98 1.1.1.0-usos1 flush reason=R pci=DDDDVVVV step=S status=X tick=T dropped=D ===`
(step 0x16 = done; see `XHCI_INIT_STEP_*`), then the note ring:
`usos.pci.command.before/enabled`, `usos.pci.pmcsr.*`, `usos.cap.*` (raw
HCSPARAMS/HCCPARAMS), `usos.res.*`, `usos.usbsts.*`, `handoff.*`,
`hc.scratchpad`, and the counter block. Switches in the device's software
key: `XhciLogFile` (1) and `XhciLogVerbosity` (2); on when absent.

**Build:** WDK 7.1 (7600.16385.1, user-downloaded
`GRMWDK_EN_7600_1.ISO`, SHA-256 `5edc723b...77657d`, unpacked with
`msiexec /a` into git-ignored `tools\WinDDK71`), `build.cmd`, WNET target for
x86 and amd64 (cl 15.00.30729.207); `docs/BUILDING.md` has the recipe. NT 5.2
only: upstream's MSVC 6/Win2K DDK x86 build (98/ME/2000) is not reproduced.
Imports: x86 ntoskrnl/HAL/USBPORT (adds ZwCreateFile/ZwWriteFile/ZwClose,
PsCreateSystemThread/PsTerminateSystemThread, KeWaitForSingleObject, ...),
all present on 5.2 SP2.

### What the next X470 run should show

Use the rear ports under the PS/2 combo (149C) and the chipset ports. Then
read `C:\WINDOWS\xhci98.log` (offline from another PC is fine):

- a `pci=149C1022` block with `step=00000016 status=00000000` and
  `usos.pci.command.enabled=...` with bits 1 and 2 set -> fixed;
- a `pci=149C1022` block with `reason=00000001` -> the `step`/`status` name the
  failing stage (e.g. 4 = capability read all-ones, 9 = reset/CNR,
  13 status 4 = more than 256 scratchpads); `usos.pci.*` and `usos.cap.*` give
  the raw values;
- no `149C1022` block at all -> StartController was never called (PCI.SYS
  gave no resources: check Device Manager for Code 12/10).
