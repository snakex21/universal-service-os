# Windows 7 x64 (UefiSeven, bez CSM): natywna rozdzielczość, 2026-10-21

Gałąź `feat/w7x64-native-res` (baza `test/x470-98se-qemu` f28a3fd8).
Status: **eksperyment, domyślnie WYŁĄCZONY** (decyzja: Win7 x64 zostaje
przy 1024x768, dopóki X470 nie potwierdzi lepszego wyniku; trasy przez
CSMWrap użytkownik nie chce). Po rundzie A/B (sekcja niżej) instalator
w QEMU dochodzi do ekranu Setup przy natywnym trybie GOP, ale Setup sam
wybiera 1024x768. Brak próby na X470. Bez scalania i bez wdrożenia.

## Przyczyna 1024x768

UefiSeven 1.30 (`tools/vendor/uefiseven/1.30`, BSD-2) na sztywno:
`SwitchVideoMode(1024, 768)` w `UefiMain`, a `ShimVesaInformation` wpisuje
do C0000 jedną tablicę VBE: lista trybów `{0x00F1}`, ModeInfo 1024x768x32,
LFB = framebuffer GOP. Handler (`Int10hHandler.asm`) zna tylko tryb 0xF1.
Windows na Standard VGA (vgapnp.sys, XDDM przez VBE) nie ma innego wyboru.
Przełączenie GOP przed UefiSeven nic nie daje: UefiSeven i tak ustawia
1024x768.

## Co zbudowano

| Plik | Rola |
| --- | --- |
| `src/platform/uefi/edid_mode.zig` | **wspólne, czyste API** (testy hosta): `preferredResolution(edid) ?Resolution` (blok bazowy EDID, nagłówek + suma kontrolna, pierwszy deskryptor DTD = preferowany timing, interlaced x2), `pickMode(candidates, preferred) ?Pick` (dokładny rozmiar EDID, inaczej największy użyteczny tryb; bez limitu 1920x1080; `Pick.reason` = `edid_native` / `largest_no_edid` / `largest_no_match`), typy `Resolution`, `Candidate{width,height,usable}` |
| `tools/windows7_native_mode.zig` | klej UEFI: `readEdid(bs, gop_handle)` (EDID_ACTIVE, potem EDID_DISCOVERED; najpierw uchwyt GOP, potem dowolny), wybór trybu, hooki StartImage / ExitBootServices, `enabled()` (plik flagi) |
| `tools/windows7_vbe_table.zig` | rozpoznanie tablicy UefiSeven w C0000 (`recognize`), wariant jednego trybu (`patch`), układ wielotrybowy USOS (`buildMulti`, `multiMode`); testy hosta |
| `tools/windows7_vbe_handler.S` | własny handler INT10 (135 B, wejście C000:0200 jak u UefiSeven): 4F00/4F01/4F02/4F03 dla N trybów 0xF1+i, nieznane funkcje -> 014F (nie wiesza się), AH=00 03/12h jak dotąd |

Interfejs i układ handlera wzorowane na UefiSeven (BSD-2, nota w nagłówku
`.S`); kod napisany w USOS. Źródła NT5 nie były używane.

Przebieg w dispatcherze (`tools/windows7_uefi_wrapper.zig`), tylko ścieżka
UefiSeven i tylko z flagą `usos-native-res.flag` obok dispatchera:

1. hook `StartImage`: gdy UefiSeven startuje menedżer rozruchu, USOS czyta
   EDID, wybiera tryb GOP, `SetMode`, sprawdza zapisywalność C0000 i
   zastępuje tablicę + handler: 0xF1 = 1024x768 (wyśrodkowane okno w
   natywnym framebufferze), 0xF2 = natywny. Log w ring logu dispatchera
   (`USOS native mode: ...`).
2. hook `ExitBootServices` (winload): jeśli biblioteka rozruchowa zmieniła
   tryb GOP, przywraca natywny (bez I/O plików i alokacji; ponowienie
   z nowym kluczem mapy, gdy firmware odrzuci stary). Tylko w QEMU notatka
   przez debugcon.

## Wyniki QEMU (`tools/tests/windows7_int10_ab.py usosrel`, OVMF, std VGA, TCG)

Win7 Professional SP1 PL x64, wariant `usosrel` (wydaniowy UefiSeven.efi).
OVMF nie publikuje EDID, więc wybór = największy tryb (2048x2048).

| Wariant | Wynik |
| --- | --- |
| bez eksperymentu (dowód 2026-09-26) | ekran Setup ok. 360 s |
| tylko natywny tryb 0xF1 = 2048x2048 | stop na "Starting Windows" (360 s), pasek śmieci u góry |
| 0xF1 = 1024x768 okno + 0xF2 = 2048x2048 (stan gałęzi) | stop na "Starting Windows" (360 s), czysty obraz |

Ustalone: menedżer rozruchu 6.1 **nie** zmienia trybu GOP (przy
ExitBootServices GOP nadal 2048x2048). Ekran "Starting Windows" w QEMU ma
1024x768, czyli jądro przeprogramowuje kartę samo. Nieustalone: czy blokuje
sam tryb 2048x2048 (np. 16 MB = cały vgamem QEMU, nietypowy kwadrat), czy
każdy tryb GOP inny niż 1024x768 w chwili przekazania. Dlatego domyślnie
wyłączone; zachowanie wydania bez zmian.

## Runda A/B (QEMU, 2026-10-21 wieczór, tylko do ekranu Setup)

Flaga przyjmuje słowa: `max=WxH` (limit wyboru), `single` (tylko tryb
natywny), `nativefirst` (natywny = 0xF1). Harness: `USOS_NATIVE_FLAG`,
`VGAMEM_MB`, `INT10_AB_TAG`, `INT10_AB_SLOT` w `windows7_int10_ab.py`.

Pierwsza seria pokazała błąd USOS: dispatcher czytał GOP z uchwytu ConOut
(wirtualny GOP konsoli). Tekstowa konsola bootmgr ("Windows is loading
files...") przełączała **fizyczny** GOP na 1024x768, a wirtualny dalej
pokazywał 1920x1080, więc hook ExitBootServices niczego nie poprawiał.
Poprawka: `findGop` wybiera fizyczny GOP (uchwyt z device path, nie ConOut).
Po niej hook przy ExitBootServices widzi tryb 7 i przywraca natywny.

| Konfiguracja (po poprawce) | vgamem | Wynik po 480 s |
| --- | --- | --- |
| kontrola `max=1024x768` (własny handler, GOP 1024x768) | 16 MB | ekran Setup (handler i hooki niczego nie psują) |
| `max=1920x1080`, dwa tryby | 16 MB | ekran Setup; skan 1920x1080, Setup w oknie 1024x768 na środku |
| `max=1920x1080`, dwa tryby | 64 MB | jak wyżej |
| `max=1280x1024`, dwa tryby | 16 MB | jak wyżej (1280x1024) |
| bez limitu (4096x2160), dwa tryby | 64 MB | jak wyżej (4096x2160) |
| `max=1920x1080 nativefirst` | 16 MB | jak wyżej: Setup i tak wybiera 1024x768 |
| `max=1920x1080 single` (tylko natywny) | 16 MB | stop przed Setup, czarny ekran |
| przed poprawką: `single` 2048x2048 / 1920x1080, vgamem 16 i 64 MB | | stop na "Starting Windows" |

Wnioski:
- Tryb GOP inny niż 1024x768 w chwili przekazania **działa**, o ile tablica
  VBE ma też 1024x768 (grafika rozruchowa jądra / Setup go wymaga). Sam
  tryb natywny (`single`) nie działa. Rozmiar pamięci VGA nie miał znaczenia.
- Setup PE wybiera 1024x768 niezależnie od kolejności numerów trybów. Na
  monitorze oznacza to Setup w małym oknie z czarnymi ramkami (dziś monitor
  skaluje 1024x768 na cały ekran), więc bez przełączenia Windows na tryb
  natywny eksperyment jest wizualnie gorszy niż stan obecny.
- Zainstalowany system nie był sprawdzany (bez pełnej instalacji). Tryb
  natywny powinien być na liście w Ustawieniach ekranu; samodzielnego
  wyboru Windows nie należy zakładać.

Konfiguracja, jeśli ktoś wróci do tematu: flaga `on` (lub `max=...`), dwa
tryby, plus ustawienie trybu natywnego w Windows (`<Display>` z rozmiarem
znanym przy przygotowaniu albo USOSRES z `feat/nt6-display`).

## Punkt 2 (`<Display>` w autounattend)

Nie zrobiony. Zależy od tego, czy jądro przyjmie natywny tryb GOP. Przy
liście dwóch trybów Windows może wybrać 1024x768 (Vista przez CSMWrap brała
800x600 z pełnej listy), więc docelowo potrzebny `<Display>` z trybem
znanym przy przygotowaniu albo USOSRES z `feat/nt6-display`. Nie ruszałem
`src/flow/answer`, żeby nie kolidować z tamtą gałęzią.

## Stan i ewentualne dalsze kroki (zaparkowane)

Win7 x64 zostaje przy 1024x768 (flaga domyślnie wyłączona). Gdyby wrócić:
1. `<Display>` / USOSRES dla ścieżki x64 UefiSeven (po nt6-display).
2. X470 (tak/nie): świeża instalacja z flagą `on` na ESP celu i WORK;
   czy pulpit po pierwszym logowaniu ma 1920x1080. Log:
   `usos-boot-uefiseven.log` (linie `USOS native mode`).

Uwaga: `readSmall` dispatchera otwiera plik w trybie read_write_create,
więc pusty `usos-native-res.flag` może powstać na ESP (pusty = wyłączone),
tak jak licznik resetów no-GOP.

## Test na X470 (2026-10-21, decyzja użytkownika)

Gałąź po scaleniu z `test/x470-98se-qemu` (z `feat/nt6-display`). EDID:
jeden pomocnik, `src/flow/display_edid.zig` (`native` z nt6-display +
`pickMode` z tej gałęzi); `src/platform/uefi/edid_mode.zig` usunięty.
Dispatcher bierze go jako moduł `display_edid`.

Włączenie (domyślnie WYŁĄCZONE, zwykłe instalacje bez zmian):

- plik **`native-res-on.txt`** (treść dowolna, np. `on`) w folderze
  **`DATA\Systems\Windows\Windows 7\Unattended\`** na pendrive, obok
  odpowiedzi USOS (`usos-unattend.xml` / profil);
- menu wstrzykuje go do WinPE jako `usos-native-res.flag`
  (`plan.zig`, `unattended_flag`, tylko Win7 / 2008 R2);
- finalizer (`windows7_uefi_publish.h`) kopiuje flagę na ESP celu obok
  dispatchera: `\EFI\Microsoft\Boot\usos-native-res.flag` i
  `\EFI\Boot\usos-native-res.flag` (treść `1`; stara flaga z ponownie
  użytego ESP jest najpierw usuwana);
- skrypty PE (`windows7_native_startup.cmd`, `windows7_modern_startup.cmd`)
  po zastosowaniu obrazu kopiują `<cel>\USOS\NT6\USOSRES.EXE` +
  `DISPLAY.TXT` (`autoxauto`); rejestracja USOSRES (Run w hive Default)
  pochodzi z odpowiedzi USOS (`autounattend.zig`, z nt6-display), więc
  **bez odpowiedzi USOS USOSRES nie wystartuje**.

Setup PE startuje jak dotąd przez UefiSeven z menu (bez dispatchera), więc
instalator ma zwykłe 1024x768 na cały ekran. Dispatcher z flagą działa
dopiero przy startach zainstalowanego systemu: GOP natywny (EDID), VBE
0xF1 = 1024x768 (okno), 0xF2 = natywny; USOSRES przy pierwszym logowaniu
wybiera natywny (auto = EDID, inaczej najwyższy).

Sprawdzenie na X470 (tak/nie): po świeżej instalacji Win7 x64 z flagą i
odpowiedzią USOS pulpit po pierwszym logowaniu ma 1920x1080. Do zebrania:
`\EFI\Microsoft\Boot\usos-boot-uefiseven.log` (linie `USOS native mode`),
`C:\USOS\NT6\USOSRES.LOG`. Ryzyka: grafika rozruchowa jądra i OOBE mogą
być widoczne jako okno 1024x768 z czarną ramką (do czasu USOSRES);
fizyczny GOP AMD może zachować się inaczej niż OVMF.
