# Windows NT 3.51 Workstation / Server without CSM (2026-10-08)

Profile `nt3-x86-qemu-csmwrap` (experimental, UEFI only). The NT 4.0 flow
(docs/nt4-2026-10-07.md) with the NT 3.51 CD: UEFI menu, micro-Linux step
620, the whole install in QEMU on the target PC, automatic restart, then the
target disk's CSMWrap entry starts the finished system.

## What the user needs on USOS_DATA

| What | Where |
|---|---|
| NT 3.51 Workstation CD | `Systems\Windows\Windows NT 3.51\Images\*.iso` |
| NT 3.51 Server CD | `Systems\Windows\Windows NT 3.51 Server\Images\*.iso` |

No product key: the 3.51 `INITIAL.INF` has `DisplayPidDlg = NO`, so neither
the menu nor GUI Setup asks for one. No service pack: SP5 for NT 3.51 is not
available here, so the RTM system is installed (it starts on Zen 3, QEMU
EPYC-Milan 2026-10-08). Microsoft files are never on the stick or in git.

## Flow

1. UEFI menu: `answer_profiles.stageWin9x` renders `EFI\USOS\answer\NT351.SIF`
   / `NT351S.SIF` (`src/flow/answer/nt3.zig`); `request.ini` as for 9x/NT4.
   Without a profile micro-Linux writes the same default answer itself
   (`w9x_nt3_default_sif` in `tools/w9x_csmwrap_prepare.sh`; both pinned to
   `src/flow/answer/testdata/golden/default.windows-nt-3-51.WINNT.SIF`).
2. micro-Linux (`tools/w9x_csmwrap_prepare.sh`, tags `NT351` / `NT351S`):
   the NT 4.0 branch without the SP6a lookup and the key check; the target
   script runs with `NT_MAJOR=3` and refuses a CD whose `TXTSETUP.SIF`
   `[SetupData] MajorVersion` is not 3 (and `MinorVersion` not 51).
3. `tools/nt4_csmwrap_target.sh` writes the winnt /b layout on a FAT16 C:
   (as NT4) with the NT 3.51 differences below and `\USOS\NT3`
   (AHCINT, usosrst, usosusb NT 3.51 builds, `USOSNT3.EXE`).
4. `tools/nt4_qemu_install.sh` runs the VM until `\USOS\NT3\DONE.TXT`, then
   BOOT.INI, cleanup and the CSMWrap ESP as for NT4.

## WINNT.SIF (CR LF)

```
[Data]           MsDosInitiated = 1, Floppyless = 1
[Unattended]     Method = express, ConfirmHardware = no, NtUpgrade = no,
                 Win31Upgrade = no, TargetPath = \WINNT,
                 OverwriteOemFilesOnUpgrade = no
[GuiUnattended]  !SetupNetwork = NO, !SetupApplications = NO,
                 ;USOS-TZ=<9x zone key>   (micro-Linux: !TimeZone per CD language)
[UserData]       !FullName, !OrgName, !ComputerName
empty [LicenseFilePrintData], [NetworkAdapterData], [TransportData], [DomainData]
```

The GUI-mode keys of NT 3.51 (`INITIAL.INF`) carry a `!` prefix. No
`ProductId`, no `OemPreinstall` (NT 3.51 has no `CMDLINES.TXT`, no RunOnce,
no REGEDIT4 import), no HAL pin, no `[Display]` (VGA only, 640x480x16; no
VESA driver for NT 3.51 yet).

micro-Linux adds:

- `[GuiUnattended] !DetachedProgram = "C:\USOS\NT3\USOSNT3.EXE"` with
  `!Arguments = "/setup"` (`nt3_detached_answer`): GUI Setup starts it early;
  it registers the one-shot USOS service that, at the first start of the
  installed system, copies and registers the drivers, turns atdisk/atapi off,
  writes VERSION.TXT / DRIVERS.TXT / DONE.TXT and restarts. The awk program
  keeps the backslashes (`\\U` in the awk string; commit cc57862).
- Server CD (`TXTSETUP.SIF ProductType` not 0): `!AdvServerType = SERVERNT`
  and `!AutoMode = PerServer`, `!AutoUsers = 5` (`nt4_server_answer` with the
  NT 3.51 prefix, also into the empty `[LicenseFilePrintData]`). The CD
  decides, not the menu entry; NT 3.51 Server uses the same flow.

## Root causes found on the way

1. **STOP 0x50 (CR2 FFBC3014) in text-mode Setup**, QEMU on any CPU model:
   the NT 3.51 loaders turn every E820 entry, reserved ones included, into a
   memory descriptor; the 3.51 kernel takes `MmHighestPhysicalPage` from the
   highest one (SeaBIOS FFFC0000 -> 0xFFFFF) while the PFN database covers
   RAM only, so `MiInitMachineDependent` faults on the first PTE that maps
   device memory. Fix: `src/platform/bios/nt3/nt3_e820_mbr.S` (own GPL), the
   XP geometry-fix MBR plus a resident INT 15h hook (1 KiB under the INT 12h
   top) that hides entries above 4 GiB and non-RAM entries at or above 1 MiB,
   clips RAM at 4 GiB and ends the low RAM entry below the hook. Built by
   `tools/build_xp_geometry_fix_mbr.ps1` as `nt3-e820-mbr-440.bin`, shipped
   in micro-Linux as `/usr/lib/usos/nt3-e820-mbr-440.bin`.
2. **STOP 0x6B (C000003A)**: NT 3.51 CDs have no `I386\SYSTEM32`; winnt.exe
   builds `~BT\SYSTEM32` from DOSNET `[FloppyFiles.1]` (ntdll.dll, usetup.exe
   as smss.exe). The target script does the same.
3. **Local source layout**: NT 3.51 Setup reads `\$WIN_NT$.~LS` flat
   (DOSNET `d1 = \`), not `~LS\I386` like NT 4.0 ("unable to copy the file
   kbdclass.sys" otherwise); `~BT` also gets the renamed `[FloppyFiles.x]`
   entries (DISK101..103 tag files) and `~LS\SIZE.SIF` as winnt.exe writes it.
4. **autochk run in text mode ("Checking drive C:")**: in the install VM it
   ended in a kernel-stack overflow (double fault, STOP 0x7F 8, triple
   fault). The local source gets `tools/nt3/usosachk` (own native stand-in
   that ends with success) as AUTOCHK.EXE; `nt4_vm_finish` restores the CD's
   AUTOCHK.EXE (kept as `\USOS\NT3\AUTOCHK.EXE`). With no AUTOCHK.EXE at all
   Setup says "Setup was unable to verify your C: drive ... Press ENTER"
   (the VM runner types it: `W9X_VM_TEXT_ANSWER=ret` on an idle text screen,
   QEMU dumps NT 3.51 text mode as 720x396), and removing its TXTSETUP.SIF
   `[Files]` line gives "Value 0 on line 0 in section [Media]".
5. **Post-install work**: no RunOnce/CMDLINES.TXT on NT 3.51, hence
   `!DetachedProgram` + the USOSNT3 service (above).

## Install disk: Am53c974 SCSI in the VM (2026-10-08 evening)

With the target disk on QEMU IDE, text mode triple-faulted after "Checking
drive C:": a kernel stack overflowed in nested interrupts through atdisk.sys
(gdbstub at KeBugCheckEx(0x7F, 8), main TSS context: interrupt object ->
HAL -> kernel dispatch -> atdisk ISR -> next interrupt, again and again;
QEMU raises the next per-sector PIO interrupt inside the ISR). Without atapi
the same; without atdisk STOP 0x7B; -smp 2, no VGA ROM, isapc did not help.
Fix: `nt4_vm_install` gives NT 3.51 the target disk as `scsi-hd` on an
**am53c974** adapter (`NT4_VM_HBA`, override `NT3_VM_HBA`; NT 3.51's in-box
amsint.sys; SeaBIOS boots it; lsi53c810 is not bootable by this SeaBIOS).
Setup still writes `multi(0)` ARC paths (BIOS disk). usosnt3 sets amsint
Start = 4 at the end (the real machine boots through AHCINT; SCM 7026
"amsint failed" otherwise).

Also needed on the way: `!SetupNetWork = NO` (INITIAL.INF reads that
spelling; the documented `!SetupNetwork` is ignored and GUI Setup waited on
"Network Adapter Card Detection"); the finish step clears a dirty bit that
NT 3.51 leaves after the service restart (fsck.fat -a only when -n reports
nothing else).

## X470 run 1 (B261008-150337): hang after the banner, Standard PC HAL

The install VM finished (DONE.TXT, POST.LOG `done`, BOOT.INI with the
`[USOS /SOS]` and `[VGA mode]` entries). On the X470 (CSMWrap) the installed
system stopped on the blue boot screen after "1 System Processor [1044100 KB
Memory]", with no usosrst load line and no AHCINT status line (row 0 still
showed the banner), so the kernel hung in phase 1 before the first boot
driver (usosrst is first: ServiceGroupOrder starts with System Bus
Extender). The E820 MBR is in the boot chain and the /MAXMEM cap works.

Offline (BIOSTAR, read-only image): `system32\hal.dll` is byte-identical to
the CD's HALAPIC.DLL. NTDETECT in the install VM (pentium3, APIC, SeaBIOS MP
table) made Setup pick `mps_up` ("MPS Uniprocessor PC", I/O APIC). On the
X470 the firmware leaves the HPET in LegacyReplacement mode (usosrst 1.3
photo, Win2000: `cfg:00000003 ... leg:1`, timer 0 interrupts off), so the
clock on I/O APIC pin 2 never ticks under the APIC HALs; NT 4.0 and 2000 got
as far as usosrst (which clears the bit), NT 3.51 waits on the clock before
that. The PIT -> 8259 IRQ 0 path works on the X470 (DOS, 9x, Win2000
"Standard PC" text mode).

Fix: `nt3_standard_hal` in `tools/nt4_csmwrap_target.sh` rewrites the
`[hal]` rows `mps_up` / `mps_mp` of every TXTSETUP.SIF copy to `hal.dll`
(the CD's Standard PC HAL; NT 3.51 text mode has no `[Unattended]
ComputerType`). `[Hal.Load]` stays. QEMU (q35, SeaBIOS, EPYC-Milan, 2 CPUs,
AHCINT) boots the installed system with that hal.dll to the logon.

## X470 run 2 (BIOSTAR with the Standard PC hal.dll): same hang

Video of the `[USOS /SOS]` entry: NTDETECT, the Last Known Good prompt
(about 2 s, so BIOS timer ticks run), then OS Loader /SOS loads
`ntoskrnl.exe`, `hal.dll`, `config\system`, `c_1252.nls`, `c_437.nls`,
`l_intl.nls`, `vgaoem.fon`, `usosrst.sys`, `ahcint.sys`, `SCSIPORT.SYS`,
`Scsidisk.sys`, `Fastfat.sys` (all loaded, no error). Blue screen:
"Microsoft (R) Windows NT (TM) Version 3.51 (Build 1057)" / "1 System
Processor [1044100 Kb Memory]", then nothing: no usosrst line, no AHCINT
line, no STOP. So the HAL choice was not the (only) cause: both HALs stop
in kernel phase 1 before IoInitSystem.

Second fix: the NT 3.x MBR (`src/platform/bios/nt3/nt3_e820_mbr.S`) now
clears HPET LegacyReplacement itself, before NTLDR, so the kernel starts
with the same HPET state as in QEMU (where 3.51 boots). It loads FS with a
flat 4 GiB descriptor (unreal mode, inside the cli window of the INT 15h
hook install), reads the HPET capabilities at FED00000h (skipped when the
read is FFFFFFFFh) and does `btr` on bit 1 of the general configuration.
Space: the INT 13h packet is now built on the stack and the unused XP
heads slot store is gone (437/440 bytes). `-DNT3_HPET_SET_LEGACY` builds
the opposite for QEMU; QEMU gates the PIT in legacy mode, so there even
NTLDR's countdown stops (not a faithful X470 copy: on the X470 the BIOS
ticks run). QEMU q35/SeaBIOS/EPYC-Milan with the new MBR: logon.

## X470 runs 3-4: the real cause, the PCI bridge scan (2026-10-09 fix)

Run 3 (HPET MBR) hung the same way. Run 4 used kernels patched to STOP
after single phase-1 stages (diagnostic copies, never shipped): STOP 0x62,
0x65, 0x67 and 0x68 appeared, the one after the LPC init did not, and
`/MAXMEM=64` and the APIC HAL hung too. So the hang is between FsRtl and
LPC init: `HalReportResourceUsage`, which in the 3.51 Standard PC HAL also
sets up the PCI buses.

The HAL takes the bus count from the NTDETECT PCI entry. NTDETECT gets it
from INT 1Ah B101h (last bus + 1) and caps it at 8. The HAL then scans the
PCI-to-PCI bridges (header type 1, class 0604h, bus master on) on those
buses; for a bridge whose secondary bus has no bus handler it sets the bus
count to that secondary bus number -- not one past it -- and scans again.
The bridge is still uncovered, so the loop never ends. The X470 has GPP
bridges leading to buses >= 8. QEMU repro: q35 + 12 `pcie-root-port`s
under OVMF + CSMWrap (CSMWrap's SeaBIOS reports last bus 0Ch): the
installed system hangs after "1 System Processor" exactly like the X470
(EIP in the HAL config-space routine); without the root ports it boots.
(SeaBIOS alone does not set bus master on the root ports, so it does not
hang there.)

Fix, own code only:
- `nt3_e820_mbr.S` asks the PCI BIOS (B101h) once. With a last bus >= 8 it
  hooks INT 1Ah and turns B101h into the unsupported B1FFh (AH = 81h,
  CF = 1). NTDETECT then records no PCI bus, the HAL creates no PCI bus
  handler and `HalReportResourceUsage` returns. With a last bus <= 7 every
  bridge lies below the count NTDETECT reports, nothing is hooked (Setup
  VM, small QEMU machines). The boot drive now lives in BP (B101h returns
  EDX = "PCI "); the HPET write is `and dword ..., 0FFFFFFFDh`; the old
  vectors sit behind the resident code; 440/440 bytes.
- AHCINT NT 3.51 build (patch 0008, "usos5"): registers for the Isa bus,
  finds the HBA itself through ports CF8h/CFCh on every bus, maps the
  ABAR through the Isa bus and reports the adapter as PCIBus so ScsiPort
  builds a PCI bus-master DMA adapter (as an Isa master the 3.51 HAL wants
  map registers and `ScsiPortGetPhysicalAddress` returned no address for
  the data buffers: READ(10) failed, STOP 0x7B). Without a PCI bus handler
  the ABAR range is left out of the resource report (a PCIBus report fails
  there: ScsiPortInitialize C0040003). `*Again = TRUE` lets ScsiPort call
  again for a second HBA.
- usosrst 1.6-nt351: the AHCI heartbeat reads PCI configuration space
  through CF8h/CFCh. usosusb already did; VGA is ISA.

QEMU 2026-10-09 (installed WS image, EPYC-Milan, 2 CPUs, 2 GB, ich9-ahci,
qemu-xhci keyboard + mouse): logon with OVMF + CSMWrap and with SeaBIOS,
each with and without 12 root ports (PCI BIOS hidden / present); keyboard
input reaches WinLogon with the PCI BIOS hidden.

NT 3.5 and 3.1: their NTDETECT and HAL most likely have the same cap and
loop (same PCI code generation); the MBR hook covers them too once those
CDs are supported, the drivers need the same CF8h/CFCh path.

## Limits

- PS/2 keyboard; display 640x480 (VGA).
- No service pack (SP5 not available); NT 3.5 and 3.1 CDs are refused.
- X470: runs 1-4 hung in the HAL PCI bridge scan; the PCI BIOS hiding MBR
  plus AHCINT usos5 / usosrst 1.6-nt351 (QEMU repro fixed) await the retest.
