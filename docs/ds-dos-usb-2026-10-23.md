## 1. Stan USOS — co już jest w repo (i czego nie ma)

USOS **nie wozi żadnego stosu USB dla DOS**. Grep po `tools/` na
`usbaspi|usbdrv|usbhid|usbmouse|usbflash|usbcdrom|duse|usb4dos` nie zwraca ani jednego
trafienia DOS-owego — jedyne wyniki to Linux (`tools/build_micro_linux.py:456`,
`tools/micro_linux_init.sh:63`) i Windows (`...\I386\LWUSBHID.IN_`). To wynik negatywny,
ale właśnie on jest najważniejszy dla rekomendacji: **nie ma czego „włączyć” — trzeba by
dodać nowy komponent.**

To, co USOS ma i na czym warto się oprzeć:

| Fakt | Dowód |
|---|---|
| Ścieżki BIOS (FreeDOS, MS-DOS, Windows 3.x) działają na UEFI bez CSM przez CSMWrap/SeaBIOS | `docs/design/bios-via-csmwrap.md:14` |
| Klawiatura USB w menu BIOS: release Core **FAIL** (czyta tylko porty 8042), prototyp **PASS** (fallback INT 16h) | `docs/design/bios-via-csmwrap.md:27` |
| FreeDOS + Doszip z klawiaturą **wyłącznie USB** — PASS (zrzut `a2-freedos-usb-keyboard.png`) | `docs/design/bios-via-csmwrap.md:28` |
| SeaBIOS obsługuje klawiaturę USB **tylko przez INT 16h**, bez emulacji 8042 | `docs/HOW-IT-WORKS.md:330` |
| Usługi trybu rzeczywistego BIOS: Int 10h, **Int 13h**, **Int 16h**, E820 | `docs/HOW-IT-WORKS.md:44` |
| Mysz USB jako urządzenie PS/2 przez INT 15h C2xxh (SeaBIOS), na tym `VBMOUSE.EXE` 0.67 (GPL-2.0-or-later) | `docs/dos-mouse-2026-10-18.md:3-12` |
| MS-DOS 6.22 pod CSMWrap wisi na A20; obejście `HIMEM.SYS ... /M:2` | `docs/design/bios-via-csmwrap.md:31-32`, `tools/build_dos_native_support.py:102-105` |
| Ładowany jest **tylko HIMEM**, nie ma EMM386 w domyślnej ścieżce | `tools/build_dos_native_support.py:102` |
| Znane ograniczenie: dwa dyski USB na jednym kontrolerze dzielą priorytet rozruchu | `docs/design/bios-via-csmwrap.md:123-124` |
| Wzorzec „uruchom z pierwszego dysku” = czytanie MBR przez INT 13h z mapowaniem USB | `docs/ROADMAP.md:141` |
| USOS wydawany na GPL-3.0-or-later | commit `1c0550d7` („1.0.0, GPL-3.0-or-later build info”) |

**Wniosek architektoniczny [R]:** USOS już dziś dostaje od CSMWrap/SeaBIOS *komplet*
usług DOS-owych dla USB: klawiatura (INT 16h), mysz (INT 15h C2xxh), dyski (INT 13h).
Problemem nie jest brak sterownika HID — problemem jest **hot-plug**, bo BIOS enumeruje
raz, przy starcie, i nie ma mechanizmu „rescan” w DOS.

## 4. Dlaczego xHCI w DOS to nie jest „jeszcze jeden sterownik”

1. **Architektura.** UHCI/OHCI/EHCI mają prosty model: listy TD/ED/QH w pamięci
   gospodarza. xHCI to pierścienie TRB, 64-bajtowe struktury, „slot/endpoint context”,
   bramkowanie portów, skalowanie do 255 urządzeń. To inny stos, nie „dopisanie case'a”
   do USBDDOS [M — analiza, ale zgodna z tym, że USBDDOS xHCI nie ma i ma go tylko
   w planach [W]].
2. **Adresacja.** xHCI na nowoczesnych płytach ma rejestry w **64-bitowym BAR**, często
   mapowane powyżej 4 GiB przez UEFI. DOS w trybie rzeczywistym nie zaadresuje tego bez
   unreal mode / własnego trybu chronionego i własnego mapowania [M]. To tłumaczy, dlaczego
   DOSUSB 3.0 jest produktem komercyjnym, a nie weekendowym projektem [W].
3. **Właściciel kontrolera.** Na X470 z CSM off kontrolerem zarządza SeaBIOS (CSMWrap) i to
   on daje INT 16h/INT 13h [R: `docs/HOW-IT-WORKS.md:330`, `docs/HOW-IT-WORKS.md:44`].
   DOS-owy sterownik musiałby odebrać kontroler BIOS-owi — a to dokładnie ten scenariusz,
   w którym USBDDOS zawisa na płytach Intela (handoff SMM) [W]. Na AM4 problem jest inny
   (SeaBIOS to software, nie SMM), ale konsekwencja ta sama: **albo BIOS, albo sterownik**,
   nie oba naraz.
4. **Hot-plug.** BIOS nie ma pętli hot-plug — enumeruje przy starcie [M]. Więc nawet
   „działający” pendrive w DOS jest widoczny tylko wtedy, gdy był wpięty przed bootem.
   To jest sedno zadania i **żaden** z darmowych sterowników tego nie rozwiązuje na xHCI,
   bo żaden nie obsługuje xHCI.

**Werdykt:** nie ma darmowego, zgodnego licencyjnie sterownika xHCI dla DOS. Jedyny
istniejący można **wskazać użytkownikowi** („kup licencję sam”), ale nie wolno go włożyć
do wydania USOS.

### Wariant B — port własny: **NIE TERAZ** (ryzyko/wartość złe)

- **Co trzeba by napisać:** enumeracja xHCI (slot context, address device, konfiguracja
  endpointów), klasa HID (raport → INT 16h/INT 15h), klasa MSC (CBW/CSW → INT 13h lub
  własny blok), hot-plug (port status change event → nowe litery dysków), plus własny
  tryb chroniony do MMIO powyżej 4 GiB.
- **Realistyczna ocena:** to projekt rzędu **miesięcy**, nie dni; zespół ma już doświadczenie
  z xHCI w Windows 98 (`xhci98`, `docs/ROADMAP.md:42`) [R], ale DOS to inny świat: brak
  DPMI, brak stronicowania, własny alokator pamięci poniżej 1 MiB.
- **Szansa na sukces:** dla pełnego stosu (HID+MSC+hot-plug) **niska (ok. 10–15%)**;
  dla wąskiego „xHCI → jeden pendrive, bez hot-plugu” — **średnia (30–40%)** [M — ocena,
  nie fakt].
- **Blokada licencyjna:** port USBDDOS (GPL-2.0) do GPL-3.0 jest niedozwolony bez zgody
  autorów [W] — trzeba by pisać od zera albo pozyskać zgodę.

### Wariant C — obejść się bez sterownika: **TAK, to rekomendacja**

Dla **klawiatury** — nic nie robić: działa przez INT 16h SeaBIOS [R:
`docs/design/bios-via-csmwrap.md:28`, `docs/HOW-IT-WORKS.md:330`]. Jedyne, co warto
naprawić, to **własne menu BIOS USOS**, które w release Core czyta tylko 8042 i nie widzi
klawiatury USB — prototyp z fallbackiem INT 16h już to rozwiązywał [R:
`docs/design/bios-via-csmwrap.md:27`]. To osobne zadanie, tanie i pewne.

Dla **myszy** — już jest: `VBMOUSE.EXE` czyta INT 15h C2xxh [R:
`docs/dos-mouse-2026-10-18.md:3-12`]. Nie dokładać CuteMouse.

Dla **pendrive'ów** — trzy poziomy, w kolejności kosztu:

1. **BIOS INT 13h (dziś, zero kodu):** stick wpięty **przed** bootem → litera dysku w DOS.
   Ograniczenie: brak hot-plugu [M], dwa dyski USB dzielą priorytet [R:
   `docs/design/bios-via-csmwrap.md:123-124`].
2. **„Rescan przez restart” (tanie, pewne):** TSR/hotkey, który przy zmianie nośnika robi
   ciepły restart i wraca do DOS; USOS ma już ścieżkę `REBOOT` przez CSMWrap [R:
   `docs/design/bios-via-csmwrap.md:29`]. To realizuje *efekt* hot-plugu bez sterownika
   i bez ryzyka. **Rekomendacja: to wdrożyć.**
3. **Własny sterownik xHCI (wariant B)** — dopiero gdy pojawi się realny wymóg „zmiana
   nośnika bez restartu” i budżet na miesiące pracy.

Dla **SATA/PATA** — brak sterownika AHCI w DOS [M], więc nie jest to alternatywa dla
pendrive'a na X470.

**Podsumowanie jednym zdaniem:** xHCI w DOS istnieje **komercyjnie** (DOSUSB 3.0) i tylko
tam; darmowe stosy kończą się na EHCI. USOS powinien zostać przy modelu
„BIOS daje HID i INT 13h”, dołożyć restart-rescan dla pendrive'ów i naprawić INT 16h
we własnym menu — a pisanie xHCI od zera odłożyć.

## 6. Co trzeba by potwierdzić przed decyzją o wariancie B

- Czy USBDDOS ma jakikolwiek branch/PR z xHCI (dziś: „planned feature” [W]) — **do sprawdzenia
  w issues**.
- Czy DOSUSB 3.0 faktycznie działa na X470 (brak raportów AM4) — **test dopiero po zakupie**.
- Czy FreeDOS `usbdrv` jest GPL-2.0-**or-later** (decyduje o zgodności z GPL-3.0) [M].
- Czy SeaBIOS/CSMWrap potrafi ponownie wyenumerować nośnik bez resetu — **niepotwierdzone**.
