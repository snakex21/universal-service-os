# DOS network under Windows 1.x / 2.x / 3.x (2026-10-23)

Goal: every Windows 1.0x / 2.x / Windows/386 / 3.0 / 3.1 / WfW 3.11 install
gets the same DOS-level network as the MS-DOS install
(`docs/dos-usospkt-2026-10-23.md`): own packet driver USOSPKT.COM (Intel
I211 / I210 / 82576) + mTCP in `C:\NET`, loaded from the start menu
**before** Windows starts, so mTCP works at the DOS prompt, after leaving
Windows and in a DOS box.

Status: **QEMU only (82576 `-nic user,model=igb`, not I211)** - Windows 1.01,
2.03, 3.0a and 3.1 PL start with the driver resident and `HTGET
http://68k.news/` works after leaving Windows; 3.1 standard mode also from a
DOS box. **Not run on the X470.** A Winsock for Windows applications is a
separate topic: `docs/win3-winsock-options-2026-10-23.md`.

## Change

| file | change |
|---|---|
| `src/platform/bios/msdos/install.cmd` (INSTALL.BAT) | the network block copies `C:\NET` for every install (`if not exist C:\NET\NUL md C:\NET`, so a re-run does not fail); only the `call C:\NET\NETSTART.BAT` line in AUTOEXEC.BAT stays MS-DOS only. The Windows Setup stage (stage 1 AUTOEXEC.BAT -> W3START.BAT) runs without the driver, as before |
| `src/platform/bios/msdos/windows_early_auto.cmd` (W1AUTO.BAT / W1AUTO.CSM; Windows 1.0x, 2.x, Windows/386, 3.0) | after USOSV10 / VBMOUSE / USOSKBC: `if exist C:\NET\NETSTART.BAT call C:\NET\NETSTART.BAT`, before the DOSONLY branch and WIN; skipped in the diagnostic items D1-D6 (they keep their isolation) |
| `src/platform/bios/msdos/windows_auto.cmd` (W3AUTO.BAT / W3AUTO.CSM; Windows 3.1, WfW 3.11) | the same guarded call after `set TEMP` (in the CSMWrap copy after VBMOUSE / USOSKEY), so every menu item including DOSONLY gets it |
| `tools/tests/test_dos_network.py` | staging for every install, AUTOEXEC line MS-DOS only, both menus call NETSTART before WIN, not in the D items |

NETSTART.BAT itself is unchanged (MS-DOS and FreeDOS are closed): no
supported NIC = USOSPKT exits with errorlevel 1, nothing resident, one line;
no DHCP answer = at most two 6-second tries (Esc skips); link wait in USOSPKT
at most 5 s. A second load is refused by USOSPKT (errorlevel 2, nothing
resident). The start menu is written once by WINMENU.BAT (MENU.TAG), so
existing Windows 1.x-3.x installs get the network only after a fresh install
(or by adding the one line to `C:\AUTOEXEC.BAT` and copying `C:\NET` by hand).

Not changed: the BIOS-Core RAM-disk path (`src/platform/bios/dos6_native_iso.zig`,
real BIOS PCs, only 3.1 / 3.11) still has its explicit helper list without
the 14 network files, so its installs have no `C:\NET` and the guarded call
does nothing there. Adding them is a Legacy Core change (RAM-disk size,
Core hash) and was left for a later round.

## Memory budget (QEMU, MEM after leaving Windows, 64 MiB)

| start menu | DOS config | resident before WIN | conventional free | largest program |
|---|---|---|---|---|
| W1AUTO (1.01, 2.03, 3.0a) | HIMEM /M:2, SETVER, no DOS=HIGH (2.x needs the HMA) | USOSV10, VBMOUSE, USOSKBC /R /M, USOSPKT | 509 KiB | 508 KiB |
| W3AUTO (3.1 PL, standard item) | HIMEM /M:2, DOS=HIGH | VBMOUSE, USOSKEY, USOSPKT | 564 KiB | 563 KiB |

USOSPKT takes about 42 KiB (0A8Eh-0A94h paragraphs: code + 34 KiB DMA block).
That is far above what every version needs (1.0x and 2.x real mode run in
256-320 KiB, 3.0 real mode about 384 KiB, 3.1 standard / 386 enhanced well
below 500 KiB conventional), so **no version skips the auto-load and nothing is
loaded high**. Loading high is also not wanted: our CONFIG.SYS files have no
UMB provider (no EMM386), and the DMA block's physical address is taken at
load time - a UMB under EMM386 would be remapped memory handed to WIN386.

## QEMU results (QEMU only)

Harness: scratch copies of the earlier Windows-early harness (fresh FAT16
target from the integration build's `zig-out/dos-native/msdos` plus this
branch's INSTALL.BAT / W1AUTO / W3AUTO, CSMWRAP.TAG, MS-DOS 6.22 boot
floppy), QEMU 11.1 `-machine pc,smm=off,vmport=off`, SeaBIOS, pentium3,
64 MiB, `-nic user,model=igb`, USB keyboard + USB mouse on qemu-xhci only
(no keys sent during Setup). Every run: unattended Setup, start menu, menu
boot (NETSTART: driver + DHCP 10.0.2.15), Windows desktop, exit Windows,
then at the DOS prompt `HTGET -o C:\P.HTM http://68k.news/` = `200 OK`,
97 500 bytes. VM images deleted afterwards.

| system | Windows mode | Windows starts with USOSPKT | after exit: DHCP.LOG / HTGET |
|---|---|---|---|
| Windows 1.01 | real (MS-DOS Executive) | PASS | PASS |
| Windows 2.03 | real (MS-DOS Executive) | PASS | PASS |
| Windows 3.0a | real (`WIN /R`, default item) | PASS (Program Manager) | PASS |
| Windows 3.1 PL | standard (`WIN /S`, default item) | PASS | PASS; DOS box (MS-DOS Prompt): `C:\NET\HTGET` 200 OK, 97 500 bytes |
| Windows 3.1 PL | 386 enhanced (`WIN /3`) | desktop drawn, then no USB keyboard / mouse | not testable: **control without USOSPKT** (NETSTART renamed) shows the same state, CPU in SeaBIOS code in V86 mode -> the known QEMU/SeaBIOS USB-in-V86 limit (as 3.0 enhanced in `windows-early-2026-10-07.md`), not the driver |
| WfW 3.11 PL | 386 enhanced (only mode) | PASS as far as visible: menu boot loaded USOSPKT (INT 60h -> `PKT DRVR` / `USOSPKT` signature in guest memory, IRQ 11 count from DHCP), Program Manager drawn | not testable in QEMU: same USB-input loss in V86 as the 3.1 enhanced control (CPU in the same SeaBIOS code) |

So QEMU cannot show mTCP after leaving a 386 enhanced Windows; that, a DOS
box under 386 enhanced mode and the I211 itself need the X470.

## Limits and risks (documented, not fixed here)

- **DOS box + packet driver:** mTCP in a DOS box works (3.1 standard tested).
  Do not switch away (Alt+Tab) from a running mTCP program: the driver's
  receive upcall goes to the program's code, which standard mode swaps out
  and 386 enhanced mode maps only in its own VM (the problem WINPKT solves;
  see the Winsock note). mTCP releases its handle on exit, so with no mTCP
  program running nothing is called back.
- **386 enhanced mode (WfW 3.11, 3.1 item 2, Windows/386 2.x):** the driver
  must use the I/O BAR there (the MMIO fallback refuses V86 mode; an MMIO
  install from real mode would read all ones once WIN386 runs). The X470
  MS-DOS PASS used the I/O BAR. DMA block in low global memory (not moved by
  WIN386, expected; not verified on hardware).
- **X470 checks** (fresh install from a build with this branch; logs written
  silently): `C:\NET\USOSPKT.LOG` (I/O BAR line), `C:\NET\DHCP.LOG`, Windows
  starts, exit, `HTGET http://68k.news/`. Windows 2.03 / 1.0x are on the
  experimental list; 3.0a, 3.1, WfW 3.11 are the interesting ones.
