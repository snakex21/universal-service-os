# Windows NT 4.0 Workstation / Server without CSM (2026-10-07)

Profile `nt4-x86-qemu-csmwrap` (experimental). Same flow as Windows 95/98/Me:
UEFI menu, micro-Linux step 620, automatic restart, then the target disk's
CSMWrap entry. The difference: **the whole NT4 install runs in QEMU on the
target PC**, the real hardware only ever starts the finished SP6a system.

Why: the RTM text-mode kernel (1381.1) triple-faults on a Zen 3 CPUID, and the
SP6a kernel hangs in text-mode Setup when the RTM setupldr loads it (QEMU
matrix, 2026-10-07). An installed system updated to SP6a starts on a Zen 3
CPU model and on AHCI through AHCINT (NT4 build).

## What the user needs on USOS_DATA

| What | Where |
|---|---|
| NT 4.0 Workstation CD (any language; PL tested) | `Systems\Windows\Windows NT 4.0\Images\*.iso` |
| NT 4.0 Server / Enterprise Server CD 1 | `Systems\Windows\Windows NT 4.0 Server\Images\*.iso` |
| Service Pack 6a, `SP6I386.EXE` (same language as the CD) | `Systems\Windows\Windows NT 4.0\ServicePack\` (Server: its own `...\Windows NT 4.0 Server\ServicePack\` or the Workstation folder) |

Microsoft files are never on the stick or in git. The product key comes from the
answer profile (`key.windows-nt-4=` / `key.windows-nt-4-server=`, OEM
`ddddd-OEM-ddddddd-ddddd` or retail `ddd-ddddddd`) or the menu asks for it
("Enter the ... product key") before the start.

## Flow

1. UEFI menu: `answer_profiles.stageWin9x` renders `EFI\USOS\answer\NT4.SIF` /
   `NT4S.SIF` (`src/flow/answer/nt4.zig`), `request.ini` as for 9x.
2. micro-Linux (`tools/w9x_csmwrap_prepare.sh`, NT4 branch): disk picker and
   erase confirmation, SP6a found on DATA, VM available (qemu9x.cpio, about
   1 GiB RAM) - otherwise it stops before touching the disk.
3. `tools/nt4_csmwrap_target.sh`: MBR (USOS MBR code) + FAT16 C: (type 06,
   LBA 63, 2000 MiB, 32 KiB clusters), `winnt /b` layout
   (`$WIN_NT$.~LS\I386`, `$WIN_NT$.~BT` + WINNT.SIF, `$LDR$`, TXTSETUP.SIF),
   `$OEM$\CMDLINES.TXT`, `C:\USOS\NT4` (POST.CMD, .REG files, AHCINT.SYS,
   USOSRST.SYS, USOSUSB.SYS, USOSVBE.SYS, USOSOFF.EXE, SP6I386.EXE, and
   `FRAMEBUF.DL_` copied from the user's CD), syslinux + `chain.c32 ntldr=/$LDR$`.
   The time zone marker becomes the CD's own display string (Polish and
   English CDs; other languages: Setup asks on the time zone page).
4. `tools/nt4_qemu_install.sh`: QEMU `-cpu pentium3 -m 512`, IDE, only the
   first 4 GiB of the disk visible, `-no-reboot`; every guest restart ends a
   run, the next run starts until `C:\USOS\NT4\DONE.TXT` exists (at most 6):
   text mode, GUI mode (MPS multiprocessor HAL pinned, `OemPreinstall=Yes`),
   one automatic Administrator logon: POST.CMD copies and registers AHCINT
   (boot, SCSI miniport) and usosrst (boot, HPET legacy off, RTC fix), runs
   `SP6I386.EXE -u -z`, exports the version keys, turns the automatic logon
   off, disables atapi (no legacy IDE on the target), `USOSOFF.EXE /r`.
5. After the VM: `fsck.fat -n`, SP6a check (CSDVersion), BOOT.INI
   `/NUMPROC=2 /MAXMEM=1024`, `timeout=5`, Setup leftovers removed, then the
   CSMWrap ESP at the disk end (`xp_csmwrap_esp.sh`). Logs:
   `EFI\USOS\win9x\nt4\` on the USOS ESP.

## On the real PC

- **Keyboard and mouse: PS/2 and USB.** NT 4.0 has no USB stack. Under
  CSMWrap, SeaBIOS polls xHCI only from its INT 08h handler, and NT never
  calls it. The helper core only serves the V86 BIOS proxy mailbox; it does
  not poll on its own. USOS installs **usosusb** (`tools/nt4/usosusb`, own
  GPL driver), a keyboard and pointer port driver with its own polled xHCI
  engine and HID boot-protocol keyboard and mouse support. It handles devices
  on root ports only, with no hubs. Its state line is in
  `Services\usosusb\Parameters\Diag`.
- NTDETECT still needs an 8042 at ports 60h/64h. In QEMU with `i8042=off` it
  hangs at "Sprawdzanie sprzętu". The X470 has a PS/2 controller (Super I/O).
- **Display: VESA, 1024x768 16 bpp by default** (Display applet: the VBE
  modes the video BIOS lists). Miniport `usosvbe.sys` (own GPL code,
  `tools/nt4/usosvbe`) + **NT 4.0's own `framebuf.dll` from the user's CD**.
  USOS never ships framebuf.dll: text-mode Setup installs it from the CD
  anyway (`[files.vga]` in TXTSETUP.SIF; checked on the Workstation PL and
  Enterprise Server EN CDs). POST.CMD uses that copy, else expands the CD's
  `I386\FRAMEBUF.DL_` (carried in `C:\USOS\NT4`) with NT's own expand.exe;
  with neither it skips VESA (`vesa off` in POST.LOG) and the system stays on
  vga.sys at 640x480x16. VESA.REG: `Services\usosvbe` (Group Video, Start 1),
  `Device0\InstalledDisplayDrivers` = `framebuf`, `DefaultSettings.*`
  1024x768x16 at 60 Hz, `VgaStart` Start=4 (it would win otherwise).
  `VgaSave` stays for full-screen consoles and the `[VGA mode]` boot entry.
  Our own display DLL `usosvbe.dll` stays in the repo as WIP (logon hang,
  `tools/nt4/usosvbe/README.md`) and is not shipped.
- No network.
- First logon: Ctrl+Alt+Del, Administrator, empty password.
- Files SP6a could not replace while in use are renamed by SMSS at the first
  real start (the SP6a kernel and HAL are already in place).

## Status

- QEMU lab (2026-10-07): text mode + GUI mode unattended, SP6a, desktop on
  ich9-ahci + EPYC-Milan (see the plan in section 6b of the NT4 notes).
- Integrated flow, e2e (nested micro-Linux writes the target, host QEMU runs
  the install loop): syslinux -> chain.c32 -> `$LDR$` works; two fixes from it
  (`NTDETECT.COM` in C:\, `I386\SYSTEM32` in `~BT`, else STOP 0x6B
  C000003A).
- e2e rerun (later on 2026-10-07): **the install is hands-free** (zero
  keypresses, about 5 minutes under TCG: 3 VM runs = text mode, GUI mode,
  first logon). CMDLINES.TXT, the automatic logon, POST.CMD, SP6a
  (`SP6I386.EXE -u -z`) and USOSOFF all work. Fixed from it: NT 4.0 `COPY`
  has no `/Y` (the drivers were not copied), the SP6a check reads
  `Control\Windows` CSDVersion (0x600; the CurrentVersion string says
  Service Pack 1 until a restart), the micro-Linux check finds NT's
  lower-case 8.3 names (vfat lookup is case-sensitive there), BOOT.INI loses
  the `C:\` entry (the syslinux boot sector saved as BOOTSECT.DOS).
- The finished disk reaches the NT 4.0 logon screen on q35 + ich9-ahci +
  EPYC-Milan + 2 CPUs with SeaBIOS (and on `-machine pc` + AHCI), served by
  AHCINT. Through **OVMF + CSMWrap**: first STOP 0x7B (C0000034): ScsiPort
  dropped AHCINT after HwFindAdapter, the port still had the firmware's
  command list. Fixed in AHCINT patch 0006 (NT4 build connects no
  interrupt; the driver polls). Then **STOP 0xC0000143 "DISPLAY DRIVER.DLL"**
  (vga.sys / vga.dll do not start under CSMWrap in QEMU; also with the
  `/basevideo` entry). Same STOP on the X470 (RX 560, build
  B261007-133548-5EC9AE82).
- **Cause of the C0000143 (found 2026-10-07, gdbstub trace):** CSMWrap's E820
  map marks A0000h-FFFFFh as reserved (`e820.c`, "Reserve Expansion BIOS");
  SeaBIOS proper leaves A0000h-EFFFFh out. The NT 4.0 kernel turns that into
  `HARDWARE\RESOURCEMAP\System Resources\Reserved` = 9F000h+61000h,
  device-exclusive. videoprt's `VideoPortVerifyAccessRanges` for vga.sys
  (3B0h, 3C0h, A0000h+20000h, 1CEh, shared) then gets a conflict from
  `IoReportResourceUsage` and returns ERROR_INVALID_PARAMETER, VgaStart and
  VgaSave fail `VideoPortInitialize`, no display driver loads and Win32k
  stops with 0x4C / C0000143. `Ke386CallBios` (INT 10h) is never reached, so
  the video BIOS is not involved. **Fix: usosrst 1.5-nt4** (boot driver,
  runs before the video drivers) cuts A0000h-BFFFFh out of every memory range
  in that key's `.Translated`/`.Raw` lists; the load line shows `vgao` (cut),
  `vga-` (nothing to cut, e.g. SeaBIOS) or `vgax`. With it the same disk
  reaches the logon screen through OVMF + CSMWrap. A CSMWrap-side fix (no
  reserved E820 entry for the VGA window) would also do, but changes the
  firmware shim for every system.
- Server: same flow, `windows-nt-4-server` (servers section). The Enterprise
  Server CD 1 (English, ProductType 1, retail Pid) is wired but untested.
- **"A service or driver failed" at logon on the X470** (B261007-133548): the
  event log on the test disk has i8042prt event 16 (KeyboardPort0) and
  **Mouclass** event 7: no PS/2 mouse means no pointer port, so mouclass
  (ErrorControl 1) fails and the Service Control Manager warns at every start.
  usosusb always creates a pointer port, which fixes this.
- **USB keyboard and mouse: usosusb** (feature/nt4 2de1b4b). QEMU e2e
  (hands-free install with the driver in POST.CMD, then OVMF + CSMWrap +
  EPYC-Milan, qemu-xhci + usb-kbd + usb-mouse): Diag
  `usosusb 1.0-nt4: hc0=00:02.0(8 ports) p5:s1K- p6:s2-M`. The USB mouse moves
  and clicks (QEMU's active mouse was the HID mouse). With i8042prt disabled
  (Start=4) Ctrl+Alt+Del and the logon worked from the USB keyboard alone.
  No error events in SysEvent.
- **VESA display** (usosvbe miniport + the CD's framebuf.dll). QEMU e2e
  (hands-free Workstation PL install, then OVMF + CSMWrap + EPYC-Milan, std
  VGA, qemu-xhci + usb-kbd + usb-mouse): target log `display: VESA`,
  POST.LOG `vesa on` (Setup's own framebuf.dll was there, no expand needed).
  Logon dialog and desktop at **1024x768, 65536 colours**; Display
  Properties > Settings shows 1024x768 / 65536 / 60 Hz and "List all
  modes" lists the VBE modes (640x480 up to 1440x900 and more, 16 bpp shown
  first). The USB mouse (HID, the active QEMU mouse) moves the pointer, the
  keyboard works (Ctrl+Alt+Del, logon, Start > Run). With the `[VGA mode]`
  entry first in BOOT.INI the system starts at 640x480x16 (VgaSave). Note:
  in QEMU NTLDR's boot menu took no keys under CSMWrap (sendkey), so the
  `[VGA mode]` check used a reordered BOOT.INI.
- Open: NIC, ConvertNTFS, USB hubs in usosusb, own display DLL (usosvbe.dll).
