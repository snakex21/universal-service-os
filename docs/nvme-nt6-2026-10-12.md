Polish-round follow-up to [nvme-nt-2026-10-11.md](nvme-nt-2026-10-11.md)
(usosnvme for NT 3.1 to 2003). Branch `feature/nvme-nt6`.

## 2. Windows 7 / Vista / Server 2008 x86 (`tools/windows_x86_csmwrap.cmd`)

micro-Linux writes `target_bus=nvme` into `usos-csmwrap-target.ini` when the
confirmed disk is `/dev/nvme*` (`vista_csmwrap_target.sh`).

**Setup's own check.** Vista / 2008 / 7 Setup refuses the NVMe disk when
the controller's driver in the PE (stornvme) does not exist in the new
system: "System Windows potrzebuje sterownika urządzenia [Standardowy
kontroler NVM Express]" (QEMU, Server 2008 SP2 x86). It accepts the disk
once a driver for the controller was loaded, so for an NVMe target and
Setup 6.0 / 6.1 only:

* `usosnvme.sys` + `usosnvme.inf` are copied to `X:\USOS-nvme` and
  `usos-x86-csmwrap.exe before` (env `USOS_NVME_DRIVERS`) adds
  `Microsoft-Windows-PnpCustomizationsWinPE` / `DriverPaths` to the windowsPE
  pass of the answer. Setup force-installs usosnvme on the controller in the
  donor PE and migrates it to the new system. From then on **usosnvme
  serves the disk inside the PE10 donor** (Windows 10 x86 SCSIPORT): the
  whole image copy ran through it.
* `usos-x86-csmwrap.exe nodump` runs first: the donor booted from the NVMe
  staging partition, so its crash-dump stack (`dump_stornvme.sys`) was armed
  for that controller and the driver swap bugchecked there
  (KMODE_EXCEPTION_NOT_HANDLED, "What failed: dump_stornvme.sys"). The step
  sets CrashControl CrashDumpEnabled = 0 / AutoReboot = 0 and calls
  NtSetSystemInformation(SystemCrashDumpStateInformation) so the kernel
  re-reads it; the swap is then clean.
* The INF copy in `modern-support.cpio` carries `DriverVer=01/01/2001`
  (older than any stornvme.inf).
* Rejected: `pnputil /add-driver` (stage only) waits on an unsigned-driver
  prompt nobody sees; `findstr` does not exist in this WinPE (`find` does).

**After Setup** (`:nvme`, after the USB steps, never fatal), NT 6.0 / 6.1:

* NT 6.1 with the user's Microsoft packages: when DATA
  `Systems\Windows\Windows 7\Updates` holds both
  `windows6.1-kb2990941-v3-x86.msu` and `windows6.1-kb3087873-v2-x86.msu`
  (Microsoft Update Catalog; the user's folders have only the x64 pair,
  `driwer\nvme\`), both CABs go in with this WinPE's DISM (as the USB 3 KMDF
  step) and usosnvme is not registered. Official, interrupt-driven, and the
  same driver family as the x64 decision; not tested (no x86 files).
* Otherwise, and always on NT 6.0 (DISM 10 cannot service Vista / 2008):
  `usosnvme.sys` (the 2KXP build) into `system32\drivers`; offline SYSTEM
  hive: `Services\usosnvme` (Type 1, Start 0, ErrorControl 1, group
  `SCSI miniport`, `Parameters\PnpInterface\5 = 1`) and
  `Control\CriticalDeviceDatabase\pci#cc_010802` (Service usosnvme, ClassGUID
  SCSIAdapter); `usosnvme.inf` to `Windows\inf`. 32-bit Windows does not
  enforce kernel-mode signatures.

**NT6 build.** The 2KXP binary is used as it is: its 13 imports (12 ScsiPort
calls + `MmMapIoSpace`) resolve on Server 2008 SP2 x86 (kernels, HALs and
SCSIPORT 6.0.6001.18000 in `tools/tests/data/nt60sp2_x86_exports.txt`,
`test_usosnvme.py::Imports::test_nt6_x86`); it also ran under the Windows 10
x86 SCSIPORT of the donor. A separate build would be the same code.

Only for an NVMe target (as on XP / NT 4.0): a SATA install never carries a
boot-start driver for a controller it may not have.

## 7. 2026-10-13: Setup from a patched sources copy (hwcompat route)

The serviced-install.wim plan of section 3 was not needed. Setup's disk
check ("Disk 0 does NOT have the necessary driver support") is a lookup of
the disk stack's device IDs in the media's `sources\hwcompat.txt`
(`IsDeviceIDPresent: Found device ID [GenDisk] in hwcompat list`); the 7 /
Vista lists predate NVMe, so the donor's inbox stornvme on
`PCI\CC_010802` fails it, independent of what the image contains. The
check runs before image selection.

`usos-x86-csmwrap.cmd :nvme_setup` (NVMe target, Setup file version 6.0 /
6.1 via `usos-x86-csmwrap.exe setupver`):

1. `robocopy` the ISO's `sources` folder except `install.wim/.esd/.swm`
   to `X:\USOS-src\sources` (Windows 7 x86 ~230 MB incl. boot.wim; the x86
   PE10 donor's RAM disk had 477 MB free after the first ~110 MB copy);
2. append `stornvme.inf:` / `PCI\CC_010802` to the copy's `hwcompat.txt`;
3. `subst` a free letter to `X:\USOS-src` and start Setup from it with the
   original `/installfrom:<ISO>\sources\install.wim`. Run from `X:` itself,
   Vista / 2008 Setup takes itself for booted Setup media ("Media boot",
   `Could not determine the source media path`) and asks for a CD/DVD
   driver; from a SUBST drive it also needs `sources\boot.wim` next to
   setup.exe (hence copied; no symbolic links on the WinPE RAM disk);
4. `usos-x86-csmwrap.exe nodump` (crash dump off, AutoReboot off): without
   it the donor bugchecked as soon as Setup started copying
   (KMODE_EXCEPTION_NOT_HANDLED, "What failed: dump_stornvme.sys", both
   Windows 7 and Server 2008 runs) - the same dump stack fault as with the
   usosnvme swap of section 2.

No driver is injected into the PE (`PnpCustomizationsWinPE` /
`USOS_NVME_DRIVERS` no longer set), so Setup has nothing to migrate and the
0x80070032 wall is gone. The installed system gets its boot driver in the
existing `:nvme` step after Setup: NT 6.1 with both x86 MSUs on DATA ->
DISM `/Add-Package` (Microsoft stornvme), plus a check that
`CriticalDeviceDatabase\pci#cc_010802` exists (added -> stornvme, Start 0
if DISM left none); otherwise and on NT 6.0 usosnvme (offline service +
CDD). The picker gate for 7 / Vista / 2008 x86 on NVMe stays until a full pass.

QEMU (pc, TCG, NVMe-only target, real menu path, builds B261012-213003 /
B261012-220640):

## 8. 2026-10-13 (afternoon): Windows 7 x86 pass, Vista / 2008 root cause

Test build B261013-105536-DAC4910E (gate opened for the runs), QEMU pc,
TCG, OVMF without CSM, NVMe-only target, USOS stick on xHCI, real menu path
(Windows -> Windows 7 -> ISO -> Automatic -> DATA answer -> picker ->
erase confirmation), both x86 MSUs on the test DATA in
`Systems\Windows\Windows 7\Updates\` as on the stick.

* **Windows 7 Ultimate SP1 PL x86: PASS** (third run). Setup from
  `X:\USOS-src` passed the disk check, copy, expansion, features, updates;
  the `:nvme` step installed KB2990941 + KB3087873 (Microsoft stornvme);
  first start from the NVMe ("updating registry settings"), second start
  ("Completing installation"), then the desktop, hands-free.
  Two earlier runs with the same build failed **inside** the image apply,
  each at a different point: `0x80070570` (ERROR_FILE_CORRUPT on
  `...\msdt.exe`) at 26 %, `0x80070003` ("Error applying .") at 79 %; the
  2026-10-12 SUBST run hit an access violation in WinSetup.dll right after
  the apply. The passing run differed only in guest RAM (`-m 3072` instead
  of the harness default 4096 on `pc`, i.e. no RAM above 4 GiB for the PAE
  x86 PE10). A write/read check through stornvme in a failed PE (146 MB
  copied twice on the NVMe, compared on the host) was clean, and a SATA
  control run (same build, same ISO, 4096 MB) passed the apply without
  problems and much faster (the NVMe apply is ~4x slower under TCG). Not
  proven: whether RAM above 4 GiB, timing, or Setup started from the
  RAM-disk copy causes the corrupt apply. **X470 (32 GB RAM) must
  confirm**; if the apply fails there the same way, the next step is to
  limit the PE to 4 GiB in the staging BCD (`truncatememory`) for the NVMe
  case.
* **Web Server 2008 SP2 PL x86: root cause found.** With automatic restart
  off, the loop is `STOP 0x7B (..., 0xC0000034, 0, 0)`. Offline
  `setupapi.dev.log` of the looping disk: in specialize the controller
  (`PCI\VEN_1B36&DEV_0010&...\3&267a616a&0&20`, started through the CDD
  entry) gets a hardware-initiated device install; SetupAPI finds
  `C:\Windows\INF\usosnvme.inf` but logs "Match in unpublished INF skipped -
  INF not properly staged to Driver Store" (signature check 0x490), selects
  no driver (0xe0000228) and **installs the NULL driver**: the Enum key loses
  Service / ClassGUID and gets ConfigFlags 0x40 (FAILEDINSTALL), so the next
  start no longer binds usosnvme -> 0x7B. Writing Service=usosnvme,
  ClassGUID and ConfigFlags=0 back into that Enum key offline (from a PE)
  made the disk start again (OOBE, desktop), which confirms it.
  Staging the package online is not hands-free: `pnputil -a` as
  Administrator shows "Windows can't verify the publisher" (unsigned), and
  run as SYSTEM without a desktop (scheduled task) it fails silently (result
  1, nothing staged). The CDD + Start 0 registration (the NT4 / XP approach)
  is what the `:nvme` step already does; NT 6.0 specialize overrides it.
  Ways forward (decision needed, not done):
  1. sign a catalog for usosnvme with a per-build certificate whose private
     key is discarded after signing, add that certificate to the target's
     Root + TrustedPublisher stores offline and stage the package from a
     specialize command (silent staging for trusted publishers); this
     touches the installed system's trust store;
  2. a non-PnP (legacy) SCSIPORT build of usosnvme for NT 6.0 that scans PCI
     itself (like the NT4 build), so the NULL driver on the PCI node does not
     matter; unverified whether NT 6.0 SCSIPORT accepts a legacy miniport
     for a PCI device PnP already enumerated (resource conflict);
  3. re-apply the Enum binding at every start (no clean hook before the
     boot driver phase; not pursued).
  Vista SP2 x86 takes the same path and stays gated with 2008.

## 9. 2026-10-13 (evening): signed usosnvme package for Vista / Server 2008 x86

User decision (option 1 of section 8): sign usosnvme for the NT 6.0 driver
store with a per-build certificate whose private key is destroyed right
after signing, and trust that certificate on the installed system only.

**Build** (`tools/build_usosnvme_nt6_signed.py`, called from
`build_windows_native_support.py`, output `zig-out/windows-modern/usosnvme-nt6`):

1. `New-SelfSignedCertificate -Type CodeSigningCert` in the build user's
   `CurrentUser\My` (RSA 2048, SHA-1 for NT 6.0, non-exportable key,
   subject `CN=USOS usosnvme <build id> (per-build test signature, key
   destroyed after signing)`). Validity 1990-01-01 .. 2049-12-31: the
   signature has no timestamp, so the target checks its own clock against
   the certificate; a certificate valid from "now" failed in QEMU (guest RTC
   = UTC, time zone CET -> the guest was two hours before NotBefore,
   `0x800b0101` CERT_E_EXPIRED), and a PC with a reset CMOS clock would fail
   the same way.
2. `signtool sign /fd sha1` on the copy of the committed 2KXP
   `usosnvme.sys` (embedded signature), `makecat` of `usosnvme.cat`
   (members `usosnvme.inf` + `usosnvme.sys`, OSAttr 2:6.0,2:6.1), `signtool`
   on the catalog. The NT6 INF copy gets `CatalogFile=usosnvme.cat`.
3. `finally`: `Remove-Item Cert:\CurrentUser\My\<thumbprint> -DeleteKey`,
   then the build fails if the certificate is still in the store. The
   private key never exists as a file and is never committed; after the
   build nothing can be signed with that certificate any more. Only the
   public `usosnvme.cer` is packed. Tools: signtool + makecat from the
   Windows 10 SDK/WDK (newest), else `%WDKROOT%\bin\x86` (WDK 7.1).

**Installed system** (NVMe target only, NT 6.0 SP2 x86):

* `usos-x86-csmwrap.cmd :nvme` keeps the boot registration (service Start
  0 + CDD `pci#cc_010802`) and puts the package (`inf`, `sys`, `cat`, `cer`)
  in `C:\USOS\nvme` (no longer an unstaged copy in `Windows\inf`).
* The Vista OOBE gate (`C:\USOS\oobe.exe`, first start, before windeploy /
  specialize) adds `usosnvme.cer` to the **LocalMachine Root and
  TrustedPublisher** certificate stores (`CertAddEncodedCertificateToStore`)
  and runs `pnputil -a C:\USOS\nvme\usosnvme.inf` (hidden, 120 s limit, then
  terminated; all logged in `C:\USOS\oobe-prep.log`). Specialize then finds
  a signed package from a trusted publisher in the driver store and binds
  usosnvme silently instead of the NULL driver.
* Trust store change on the installed system: one extra root + trusted
  publisher certificate, specific to that build. Because its private key
  was deleted at build time, the only things that can ever carry this
  signature are the usosnvme files of that build; it does not let anyone
  else sign code for that machine. It stays (removing it changes nothing
  for the installed driver). 32-bit NT 6.0 does not enforce kernel-mode
  signatures; the signature only matters for PnP's publisher trust.
* usosusb (own NT 6.0 xHCI keyboard / mouse driver) is a legacy non-PnP

## 13. Why stornvme fails under CSMWrap on the X470: analysis (no hardware run)

Research only: CSMWrap 3.1.2 source (the usos5 patches touch BBS priority,
the boot disk choice and the ACPI 1.0 RSDT/FADT view, nothing in the PCI,
APIC or NVMe paths), SeaBIOS `src/hw/nvme.c` of the pinned fork, and the
X470 logs above. QEMU results below are hints, not hardware evidence.

### 13.1 What the firmware leaves behind

| Item | Finding (source) |
|---|---|
| NVMe controller state at OS handoff | SeaBIOS `nvme_controller_enable`: bus master + memory decode on, any previous enable shut down (CC.SHN normal, then CC.EN=0), new admin queue pair + **one I/O SQ/CQ pair**, CC.EN=1, CSTS.RDY=1. Nothing quiesces it at `Legacy16PrepareToBoot` / `Legacy16Boot`: the controller stays enabled with SeaBIOS's queues, as with a vendor CSM NVMe option ROM. It cannot be shut down at boot either, because bootmgr / winload read the PE through INT 13h after that point. |
| Queue memory | `ZoneHigh` = top 256 KiB of CSMWrap's 4 MiB HiPmm block (`AllocatePages(EfiRuntimeServicesData)` below 4 GiB). E820 marks it reserved (CSMWrap converts RTData to reserved, SeaBIOS re-adds the ZoneHigh range as reserved; only the free part below its allocations goes back to RAM). The OS does not reuse the queue pages. Identify buffers come from ZoneTmpHigh and are freed before boot; no command is outstanding at handoff (SeaBIOS is synchronous). |
| Interrupts from SeaBIOS's use | Pin-based only. The I/O CQ is created with IEN=0; only the admin CQ (always interrupt-enabled) asserts INTx, and SeaBIOS rings the CQ head doorbell after every completion, so INTx is deasserted at handoff. INTMS is not touched (0). PCI Command INTx Disable unchanged. |
| MSI / MSI-X | Neither CSMWrap nor SeaBIOS writes the MSI or MSI-X capability. Whatever the AMI UEFI left (normally disabled) reaches the OS; Windows' PCI driver programs MSI-X before starting stornvme. |
| PCI resources | `pci_late_initialize` relocates BARs and bridge windows **only on a root bus that has a BAR above 4 GiB** (after ExitBootServices; memory decode off during each BAR write, the old Command value restored). With *Above 4G Decoding* off (as for the 2000 tests) nothing moves. If it was switched back on, CSMWrap rewrote the Micron's BAR and its root port window before SeaBIOS ran, and Windows sees a layout that differs from the AMI UEFI's. Record the setting with the next run. |
| APIC / MADT | LAPIC put in virtual-wire mode for SeaBIOS (LINT0 ExtINT, LINT1 NMI per MADT); the OS reprograms it. One AP stays in CSMWrap's BIOS-proxy helper loop and is **removed from the MADT copy** (patched XSDT/RSDT); Windows only targets its own CPUs. IOAPIC entries and `_PRT` are not changed. AMD-Vi is disabled before handoff (`iommu_disable` default true); Win10 x86 does not use an IOMMU. |
| 8259 / ELCR / Interrupt Line | CSMWrap masks both PICs and builds a `$PIR` from `_PRT` (served by INT 1Ah B406h), but **does not program the PCI Interrupt Line registers, the ELCR (0x4D0/0x4D1) or the FCH PCI IRQ router**. A real CSM does. That is the ReactOS failure (PIC mode: ELCR 0 = edge, PCI INTx are level; USOS works around it with `elcr-mbr-440.bin`). The **ACPI APIC HAL of Win10 x86 ignores ELCR and Interrupt Line** (IOAPIC + `_PRT`, or MSI), and storahci in the same PE on the same board works, so this is not the stornvme cause. |

### 13.2 What stornvme does differently from what works

- **XP usosnvme on the same handoff works** (X470 PASS 2026-10-12): polled,
  its own CC.EN=0 reset, admin + one I/O queue, no MSI, no power management,
  and XP SP3's PAE kernel never uses physical memory above 4 GiB.
- **storahci in the same x86 PE10 on SATA works** (X470): StorPort, the HAL's
  interrupt and DMA paths and the CSMWrap ACPI tables are fine in general.
- **stornvme** (public behaviour): resets the controller (CC.EN 1 -> 0, waits
  for CSTS.RDY=0 up to CAP.TO), sets up its own admin queue, Identify, then
  per-CPU I/O queues with MSI-X vectors, Set Features (number of queues,
  volatile write cache and others), a host memory buffer when the drive asks
  for one, and runtime power management (NVMe power states) through
  StorPort's idle power framework.
- **This x86 WinPE uses all RAM**: PE10 x86 has no client 4 GiB cap (QEMU:
  memory top 9216 MiB, section 10 on `feature/nvme-pe-lowmem`), so on the
  32 GB X470 nearly every I/O buffer, and the HMB if any, sits above 4 GiB.
  Windows 10 x86 client never runs stornvme with RAM above 4 GiB, and XP
  never did either; storahci is the only x86 storage driver this
  configuration has been seen working with.

### 13.3 Hypotheses, ranked

1. **x86 stornvme with RAM above 4 GiB** (most likely, cheap to test). DMA
   or HMB addresses above 4 GiB in a 32-bit PAE stornvme configuration that
   Microsoft does not ship. A bad DMA address ends in an Unsupported Request
   or completer abort for the controller, which can leave it in a fatal
   state (CSTS.CFS) and, on some drive firmware, unrecoverable without power
   loss. Supporting hint (QEMU only): 2 of 3 Win7 x86 NVMe applies with 4 GiB
   guest RAM (part of it above 4 GiB) failed with corrupt files, the 3 GiB
   run passed (section 8). Fits "identify OK (low uncached buffers), first
   real I/O fatal".
2. **Link / power management on this slot** (ASPM L1 substates, NVMe power
   state transitions by stornvme): would also explain "gone until
   power-off". Not CSMWrap-specific; native Windows x64 on this Micron in
   the X470 has never been checked.
3. **USOS's own `nodump` step** (NtSetSystemInformation crash-dump re-init
   while the live stornvme owns the boot controller, which is also the dump
   target): it ran right before `before`. QEMU Win7 x86 runs with the same
   step and a live stornvme passed, so less likely.
4. **SeaBIOS handoff state** (controller left enabled with its queues):
   unlikely. Vendor CSM option ROMs leave it the same way, stornvme resets
   first, and XP usosnvme survives the identical handoff.
5. **Interrupt routing** (MSI-X / INTx not delivered): would give StorPort
   timeouts and resets (event 129), not a controller that is gone from PCI
   across warm resets. storahci's interrupts work on the same CSMWrap tables.

### 13.4 Firmware-side changes (proposals, none implemented)

- **F1, only if hypothesis 1 holds: `csmwrap.ini` option to hide RAM above
  4 GiB.** CSMWrap's `build_e820_map` drops everything above 4 GiB from the
  E820 map it hands SeaBIOS (INT 15h E820 is what winload reads on BIOS),
  written only for the 32-bit NT6 profiles. 32-bit Windows 7 / Vista client
  is capped at 4 GiB anyway, so the installed system loses nothing; Server
  2008 x86 would (PAE). The OS-side equivalent is ready on
  `feature/nvme-pe-lowmem` (`usos-x86-csmwrap.exe lowmem`, `truncatememory`
  in the staging BCD); it would also have to reach the installed system's
  first boots from NVMe.
- **F2: ELCR / Interrupt Line / PCI IRQ router programming in CSMWrap** (for
  PIC-mode systems: ReactOS, 9x, NT4 / XP / 2000 with a non-APIC HAL): after
  `pir_init`, for every function with an Interrupt Pin take the link's
  current IRQ from `_CRS` (or pick one from `_PRS` and `_SRS` it), write the
  Interrupt Line register and set the ELCR bit for that IRQ. Would replace
  the `elcr-mbr-440.bin` workaround and is upstreamable. **No effect on the
  Win10 x86 PE** (APIC HAL).
- **F3: SeaBIOS NVMe "quiet handoff"**: on `Legacy16Boot` delete the I/O
  queue pair (admin Delete SQ / Delete CQ) and keep only the admin queue;
  re-create it lazily in `nvme_process_op` if INT 13h is called again. A
  full shutdown (CC.SHN + CC.EN=0 + bus master off) is not possible for the
  boot disk, because the OS loader still uses INT 13h. Low expected value
  (hypothesis 4).
- **F4: defensive MSI / MSI-X reset** (MSI-X Enable = 0, Function Mask = 0,
  MSI Enable = 0 in SeaBIOS's `nvme_controller_setup`) and **ASPM off on the
  NVMe link** (Link Control bits 1:0 on the device and its root port) as an
  experiment for hypothesis 2. Windows may re-enable ASPM per its policy.

11920 bytes`), but the controller `PCI\VEN_1344&DEV_5407` stayed at
**Problem 10 (CM_PROB_FAILED_START), status 0xC000000D** under
`stornvme.inf`. No disk: `lowmem` found only the stick (exit 4), the disk
report ran, then the flow went on to the Setup copy and `before`, which
stopped the same way. `lowmem` could not write `truncatememory` either,
because it needs the prepared disk (RAM top 32759 MiB).

**Mechanism (diagnosis):** `stornvme.inf` gives the device
`Interrupt Management\MessageSignaledInterruptProperties` with
`MSISupported = 1` (and `MessageNumberLimit`), so PnP hands the start IRP
an MSI-X message resource. The 2KXP usosnvme registers a stub
`HwInterrupt` (always FALSE) and forces `InterruptMode = LevelSensitive`.
With a `HwInterrupt`, ScsiPort's start path takes the first interrupt
descriptor of the translated resources and calls the line-based
`IoConnectInterrupt` with the miniport's interrupt mode; with
`HwInterrupt == NULL` it uses its "adapter has no interrupt" path
(synchronisation through its own spin lock, no interrupt object). A
LevelSensitive line connect on a message vector is the most likely source
of STATUS_INVALID_PARAMETER. The ScsiPort behaviour was confirmed by
reading the Windows Server 2003 scsiport source supplied by the user as a
reference (project policy CLAUDE.local.md, 2026-10-13); the fix below is
our own code. The Windows 10 scsiport.sys is newer than that source; the
X470 run decides.

**Fix (build B261014-181541-1DF29D51, not deployed):**

1. **usosnvme NT6 build** (`tools/nt/usosnvme/build.cmd nt6`: `src\2KXP`
   with `-DUSOSNVME_NT6`, `bin\NT6\i386\usosnvme.sys`): `HwInterrupt =
   NULL`, no forced interrupt mode, and in HwFindAdapter the message
   vectors are masked at the function (MSI-X Function Mask on, MSI Enable
   off; INTx stays off through PCI Command bit 10). The driver was already
   fully polled. `build_usosnvme_nt6_signed.py` signs this build, so the
   PE's `stornvme.sys`, the installed system's `usosnvme.sys` and the
   signed NT 6.0 package are all the NT6 build (12432 bytes signed). The
   2KXP (2000 / XP / 2003), NT4, NT3 and 9x binaries are unchanged. There
   is no amd64 usosnvme build yet (build.cmd is x86 only).
2. **MSI off in the PE (belt and braces).** Patching the PE's
   `stornvme.inf` copy in micro-Linux was not done: the inbox INF is
   covered by its catalog hash, and the WinPE does not read the INF at
   boot for a preinstalled inbox driver (its `Interrupt Management`
   values come from the image's driver database), so the edit would
   either break signature checks or have no effect, and micro-Linux has no
   registry hive editor for the image's DRIVERS / SYSTEM hives. Instead
   `usos-x86-csmwrap.cmd :nvme_pe_driver` checks the controller after
   boot: if it has a problem code, the device instance (from
   `Services\stornvme\Enum\0`) gets `MSISupported = 0` under its
   `Device Parameters` (RAM WinPE only) and `pnputil /restart-device`
   restarts it once; the result is listed in the log.
3. **truncatememory at prepare time.** micro-Linux edits the staging BCD
   copy for NVMe targets of the 32-bit WinPE before it is written
   (`usos-fb-ui --bcd-truncatememory`, `src/platform/linux/bcd_lowmem.zig`):
   bootmgr's default entry (`{9dea862c-...}\Elements\23000003`) gets
   element `15000007` = 0x100000000 (REG_BINARY, 8 bytes). The edit is
   append-only on a clean hive (one new 4 KiB hbin with the key, value list,
   value, data and a new sorted `lh` list of the parent; old list cell
   freed; security cell reference count + 1; hbins size and base-block
   checksum updated), read back before it is written, and never fatal (a
   refusal keeps the donor's BCD; the PE-side `lowmem` remains the
   fallback and finds the limit already set). Checked on the Win10 22H2 x86
   ISO's `boot\bcd`: Windows' own `bcdedit /store ... /enum all` lists
   `truncatememory 0x100000000` on the "Windows Setup" entry. Log line in
   `prepare.log`: `[BCD_LOWMEM] truncatememory 0x100000000 added`.
4. **Stop after `lowmem` exit 4**: the disk report runs and the cmd exits
   (no Setup copy, no `before`).
5. **Disk report**: also `reg query` of the stornvme device's
   `Device Parameters\Interrupt Management /s` and
   `HKLM\HARDWARE\RESOURCEMAP\PnP Manager /s`.

Unrelated in the same build (user request): the UEFI menu shows the
architecture as a solid colour chip (`src/gui/arch_badge.zig`: x86 orange,
x64 blue, ARM64 green, x64/x86 purple, IA64 grey; label colour from the
theme, WCAG 4.5:1 and panel distance checked in every built-in theme) on
ISO rows and, for systems whose ISOs were already probed in this menu
session, on the system rows (nothing extra is read for the systems list).
