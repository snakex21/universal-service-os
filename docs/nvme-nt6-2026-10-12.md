# NVMe targets for Windows 7 / Vista / Server 2008 (2026-10-12)

Polish-round follow-up to [nvme-nt-2026-10-11.md](nvme-nt-2026-10-11.md)
(usosnvme for NT 3.1 to 2003). Branch `feature/nvme-nt6`.

## 1. Which environment sees the disk

| Path | Setup runs in | Installed system's NVMe driver |
|---|---|---|
| Windows 7 SP1 x64 / 2008 R2, original ISO (native UEFI) | Win7 WinPE 6.1 + KB2990941 / KB3087873 bootstrap files (`prepare_windows7_nvme.sh`, bundled, 2026-09-13, `docs/windows7-nvme.md`) | Microsoft stornvme (both CBS packages through Setup's own servicing) |
| Windows 7 SP1 x64, updated image with its own WinPE 10 (6in1) | the image's own PE10 | whatever the image integrated (the 6in1 2019-07 has stornvme) |
| Windows 7 / Vista / Server 2008 x86 (`win-nt6-x86-uefi-csmwrap`) | the x86 PE10 donor runs the 7 / Vista setup.exe | **new**: usosnvme (or the user's KB2990941 x86 on 7), section 2 |
| Windows 8.1 / 10 x86 (`win-x86-uefi-csmwrap`) | the ISO's own WinPE | inbox stornvme, nothing to do |
| Vista / Server 2008 x64 (`vista-x64-sp2-uefi-csmwrap`) | PE10 donor | none: **stops** on the disk picker (section 4) |

User decision 2026-10-12: Windows 7 x64 / 2008 R2 use Microsoft's official
NVMe update (KB2990941 + KB3087873); no x64 usosnvme, no test signing for
it. usosnvme covers the 32-bit systems.

## 2. Windows 7 / Vista / Server 2008 x86 (`tools/windows_x86_csmwrap.cmd`)

micro-Linux writes `target_bus=nvme` into `usos-csmwrap-target.ini` when the
confirmed disk is `/dev/nvme*` (`vista_csmwrap_target.sh`).

**Setup's own check.** Vista / 2008 / 7 Setup refuses the NVMe disk when
the controller's driver in the PE (stornvme) does not exist in the new
system: "System Windows potrzebuje sterownika urządzenia [Standardowy
kontroler NVM Express]" (QEMU, Server 2008 SP2 x86). It accepts the disk
once a driver for the controller was loaded, so for an NVMe target and
Setup 6.0 / 6.1 only:

* `usosnvme.sys` + `usosnvme.inf` are copied to `X:\USOS-nvme` and
  `usos-x86-csmwrap.exe before` (env `USOS_NVME_DRIVERS`) adds
  `Microsoft-Windows-PnpCustomizationsWinPE` / `DriverPaths` to the windowsPE
  pass of the answer. Setup force-installs usosnvme on the controller in the
  donor PE and migrates it to the new system. From then on **usosnvme
  serves the disk inside the PE10 donor** (Windows 10 x86 SCSIPORT): the
  whole image copy ran through it.
* `usos-x86-csmwrap.exe nodump` runs first: the donor booted from the NVMe
  staging partition, so its crash-dump stack (`dump_stornvme.sys`) was armed
  for that controller and the driver swap bugchecked there
  (KMODE_EXCEPTION_NOT_HANDLED, "What failed: dump_stornvme.sys"). The step
  sets CrashControl CrashDumpEnabled = 0 / AutoReboot = 0 and calls
  NtSetSystemInformation(SystemCrashDumpStateInformation) so the kernel
  re-reads it; the swap is then clean.
* The INF copy in `modern-support.cpio` carries `DriverVer=01/01/2001`
  (older than any stornvme.inf).
* Rejected: `pnputil /add-driver` (stage only) waits on an unsigned-driver
  prompt nobody sees; `findstr` does not exist in this WinPE (`find` does).

**After Setup** (`:nvme`, after the USB steps, never fatal), NT 6.0 / 6.1:

* NT 6.1 with the user's Microsoft packages: when DATA
  `Systems\Windows\Windows 7\Updates` holds both
  `windows6.1-kb2990941-v3-x86.msu` and `windows6.1-kb3087873-v2-x86.msu`
  (Microsoft Update Catalog; the user's folders have only the x64 pair,
  `driwer\nvme\`), both CABs go in with this WinPE's DISM (as the USB 3 KMDF
  step) and usosnvme is not registered. Official, interrupt-driven, and the
  same driver family as the x64 decision; not tested (no x86 files).
* Otherwise, and always on NT 6.0 (DISM 10 cannot service Vista / 2008):
  `usosnvme.sys` (the 2KXP build) into `system32\drivers`; offline SYSTEM
  hive: `Services\usosnvme` (Type 1, Start 0, ErrorControl 1, group
  `SCSI miniport`, `Parameters\PnpInterface\5 = 1`) and
  `Control\CriticalDeviceDatabase\pci#cc_010802` (Service usosnvme, ClassGUID
  SCSIAdapter); `usosnvme.inf` to `Windows\inf`. 32-bit Windows does not
  enforce kernel-mode signatures.

**NT6 build.** The 2KXP binary is used as it is: its 13 imports (12 ScsiPort
calls + `MmMapIoSpace`) resolve on Server 2008 SP2 x86 (kernels, HALs and
SCSIPORT 6.0.6001.18000 in `tools/tests/data/nt60sp2_x86_exports.txt`,
`test_usosnvme.py::Imports::test_nt6_x86`); it also ran under the Windows 10
x86 SCSIPORT of the donor. A separate build would be the same code.

Only for an NVMe target (as on XP / NT 4.0): a SATA install never carries a
boot-start driver for a controller it may not have.

## 3. QEMU results (build of the branch, B261012-111850 + support archive updates)

OVMF without CSM, `-device nvme` as the **only** internal disk, the USOS
test stick on xHCI (`new_native_stick.ps1`), real menu path.

* **Windows 7 SP1 x64** (`Windows 7 SP1 6in1 PL x64 (2019-07).iso`,
  Ultimate STD, q35, TCG; `qemu_native.py`, DATA answer with local account +
  autologon): menu "Win7 x64 hybrid / own modern PE and Setup", Setup's disk
  page shows the NVMe, install, first start from the NVMe ("Starting
  Windows", "updating registry settings", "Completing installation" ~45 min
  TCG), **desktop**; then the VM stopped hard (`quit`), the disk started
  alone with the same NVRAM: **desktop again**. PASS.
  - QEMU 11 reports NN = 256; Windows 7 stornvme walks every NSID (phantom
    disks, docs/windows7-nvme.md). `tools/tests/windows_native/qemu_nvme_nn1.py
    PID` patches the controller's Identify data in the QEMU process to NN = 1
    (real controllers, e.g. the Micron 3400, report 1). Test harness only.
  - WHPX: the donor PE sat on its background for 10 min (no Setup); TCG works.
  - The original-ISO path (Win7 WinPE 6.1 + bundled KB2990941) needs the
    x64 PE10 donor (`PE10_x64_19041_USOS.iso`), which exists only on the
    sticks; not re-run here.
* **Web Server 2008 SP2 PL x86** (`win-nt6-x86-uefi-csmwrap`, pc, TCG, DATA
  answer index 1): picker `NVME /dev/nvme0n1 logical_block=512`, prepared
  disk, CSMWrap -> PE10 from the NVMe -> Setup accepted the NVMe disk (no
  disk page) -> copy and expansion through usosnvme in the PE ("Kopiowanie",
  "Rozpakowywanie 100%", "Instalowanie funkcji") -> **FAIL** in "Instalowanie
  aktualizacji": "Nie można kontynuować instalacji systemu Windows, ponieważ
  nie powiodło się instalowanie wymaganego sterownika".
  `C:\$WINDOWS.~BT\Sources\Panther\setupact.log`:
  `AddDriverPackageIntoDriverStore: Failed to add the driver package
  [X:\USOS-nvme\usosnvme.inf] into driver store. Error code is [0x80070032]`,
  `Driver package is [Critical]`. Vista Setup migrates the PE-loaded boot
  driver through the running (Windows 10) SetupAPI offline driver store,
  which refuses an NT 6.0 image (ERROR_NOT_SUPPORTED; the same wall as
  DISM 10 / pkgmgr, csmwrap-integration 12.3). Not a usosnvme fault: the
  driver served the whole copy in the PE.

  Consequence: the gate now **stops Vista / Server 2008 x86 on NVMe** (DATA
  folder `Windows Vista` / `Windows Server 2008` on the x86 profile).
  Ways forward (not done):
  1. let Setup's disk check see the driver but keep it out of the migration
     list, relying on the offline CDD registration of the `nvme` step (no
     driver store needed);
  2. Vista's own WinPE 6.0 for the NVMe case (hands-free, no keyboard
     needed) with usosnvme in its boot.wim: its SetupAPI services 6.0
     images; needs an offline boot.wim hive edit in micro-Linux.
* **Windows 7 Ultimate SP1 PL x86** (NT 6.1, run 2026-10-12, build
  B261012-190545-DD00AEA1, pc, TCG, NVMe-only target, DATA answer index 5,
  no x86 NVMe MSUs on DATA): picker `NVME /dev/nvme0n1 logical_block=512`,
  CSMWrap -> PE10 from the NVMe -> Setup accepted the disk, copy and
  expansion through usosnvme (~40 min TCG) -> **FAIL** in "Instalowanie
  aktualizacji" with the same message and the same
  `AddDriverPackageIntoDriverStore ... 0x80070032` (`Image architecture is
  [0x0]`), then rollback. The expectation above was wrong: DISM 10 services
  NT 6.1 images through its own downlevel provider, but Setup's
  `winsetup.dll` calls `DriverStoreOfflineAddDriverPackageW` of the running
  Windows 10 `drvstore.dll` (Windows 10 `setupapi.dll` delay-loads it from
  System32), which refuses NT 6.1 as well.

  The user's KB2990941 + KB3087873 x86 do not help as wired: the `:nvme`
  step runs after Setup, and Setup aborts before it (it still needs a
  driver for the controller to accept the disk, and the one it is given
  must be migrated).

  Consequence: the gate now stops **every** `win-nt6-x86-uefi-csmwrap`
  install (7 / Vista / 2008 x86) on NVMe, on the picker, before any write.
  Way forward (not done, needs the x86 MSUs to test): give Setup an image
  that already has an NVMe driver, so PE10's inbox stornvme is accepted
  without any injected package (as with the 6in1 x64 image, whose
  install.wim carries stornvme): in the donor PE, before Setup, copy
  `install.wim` to the empty Windows partition, `DISM /Mount-Wim` the chosen
  index, `/Add-Package` the two x86 CABs (or `/Add-Driver /ForceUnsigned`
  usosnvme when they are missing), `/Unmount-Wim /Commit`, then
  `setup.exe /installfrom:` that copy; no `PnpCustomizationsWinPE`.

## 5. x64 assessment (not implemented)

* **Vista / Server 2008 x64**: an x64 usosnvme (WDK 7.1 `fre x64 WLH`; the
  source needs 64-bit clean pointer / PRP arithmetic, ULONG_PTR for the
  uncached extension, no inline asm) plus a signature: Vista x64 enforces
  kernel-mode signing for boot drivers. The Vista x64 CSMWrap path already
  runs the installed system in test mode (USB v11), so a USOS test-signed
  build would load there; that conflicts with the 2026-10-12 decision (no
  test signing for NVMe), so Vista / 2008 x64 keep stopping. Alternative:
  KB2990941 does not exist for NT 6.0. Effort for the driver itself: about
  a day (build, PE setup check as in section 2, x64 test); the signing
  question decides.
* **XP x64 / Server 2003 x64**: no signature enforcement; needs the x64
  build plus the AMD64 text-mode integration in `xp_driver_overlay.py`
  (TXTSETUP AMD64 sections, the NVME/ set per architecture). About a day.
* **Windows 7 x64 / 2008 R2**: Microsoft's update (decision above).

## 7. 2026-10-13: Setup from a patched sources copy (hwcompat route)

The serviced-install.wim plan of section 3 was not needed. Setup's disk
check ("Disk 0 does NOT have the necessary driver support") is a lookup of
the disk stack's device IDs in the media's `sources\hwcompat.txt`
(`IsDeviceIDPresent: Found device ID [GenDisk] in hwcompat list`); the 7 /
Vista lists predate NVMe, so the donor's inbox stornvme on
`PCI\CC_010802` fails it, independent of what the image contains. The
check runs before image selection.

`usos-x86-csmwrap.cmd :nvme_setup` (NVMe target, Setup file version 6.0 /
6.1 via `usos-x86-csmwrap.exe setupver`):

1. `robocopy` the ISO's `sources` folder except `install.wim/.esd/.swm`
   to `X:\USOS-src\sources` (Windows 7 x86 ~230 MB incl. boot.wim; the x86
   PE10 donor's RAM disk had 477 MB free after the first ~110 MB copy);
2. append `stornvme.inf:` / `PCI\CC_010802` to the copy's `hwcompat.txt`;
3. `subst` a free letter to `X:\USOS-src` and start Setup from it with the
   original `/installfrom:<ISO>\sources\install.wim`. Run from `X:` itself,
   Vista / 2008 Setup takes itself for booted Setup media ("Media boot",
   `Could not determine the source media path`) and asks for a CD/DVD
   driver; from a SUBST drive it also needs `sources\boot.wim` next to
   setup.exe (hence copied; no symbolic links on the WinPE RAM disk);
4. `usos-x86-csmwrap.exe nodump` (crash dump off, AutoReboot off): without
   it the donor bugchecked as soon as Setup started copying
   (KMODE_EXCEPTION_NOT_HANDLED, "What failed: dump_stornvme.sys", both
   Windows 7 and Server 2008 runs) - the same dump stack fault as with the
   usosnvme swap of section 2.

No driver is injected into the PE (`PnpCustomizationsWinPE` /
`USOS_NVME_DRIVERS` no longer set), so Setup has nothing to migrate and the
0x80070032 wall is gone. The installed system gets its boot driver in the
existing `:nvme` step after Setup: NT 6.1 with both x86 MSUs on DATA ->
DISM `/Add-Package` (Microsoft stornvme), plus a check that
`CriticalDeviceDatabase\pci#cc_010802` exists (added -> stornvme, Start 0
if DISM left none); otherwise and on NT 6.0 usosnvme (offline service +
CDD). The picker gate for 7 / Vista / 2008 x86 on NVMe stays until a full pass.

QEMU (pc, TCG, NVMe-only target, real menu path, builds B261012-213003 /
B261012-220640):

* **Web Server 2008 SP2 PL x86** (DATA answer, hands-free): first try
  from `X:\USOS-src` directly -> "Media boot" / CD/DVD driver page (fixed by
  SUBST + boot.wim); then dump_stornvme bugcheck at "Copying 0%" (fixed by
  `nodump`). Final build: disk check passed, copy, expansion, features,
  updates, Setup exit 0, `:nvme` registered usosnvme, first start **from the
  NVMe** via usosnvme (safe mode list shows usosnvme.sys + SCSIPORT +
  disk.sys) to "Completing installation" (specialize). **FAIL** after that:
  every following start resets right after the boot drivers (Windows Error
  Recovery loop, safe mode too). Most likely PnP's device install in
  specialize finds no driver-store package for PCI\CC_010802 (the unsigned
  usosnvme INF cannot be staged silently on NT 6.0) and drops the CDD
  binding -> 0x7B. Not verified (no dump; next step: boot with
  "disable automatic restart" or read setupapi.dev.log offline). Ideas:
  stage usosnvme into the 6.0 driver store online from a first-boot
  command, or a legacy (non-PnP) SCSIPORT build of usosnvme for NT 6.0
  (as the NT4 build).
* **Windows 7 Ultimate SP1 PL x86** (answer index 5, both x86 MSUs on
  DATA): disk check passed ("Disk 0 has the necessary driver support"),
  copy, expansion to 100%, then Setup **FAIL** 0xC0000005 (setuperr:
  ACCESS_VIOLATION in Z:\sources\WinSetup.dll +0x153B66 = a hash-table free
  loop, right after `WIMApplyImage` returned; run from the SUBST copy). The
  first try (from `X:\USOS-src`, before `nodump`) died in the dump_stornvme
  bugcheck. A retry from `X:\USOS-src` without SUBST in the same PE was
  still running at the time limit and got past that point: expansion done, "Installing features" done, "Installing updates" running when the session ended (no end result). The script now uses the SUBST drive for Setup 6.0 only; Setup 6.1 runs from `X:\USOS-src` (not rebuilt / re-run end to end). The post-Setup MSU / CDD
  step was therefore not reached on 7.
* Gate: unchanged (7 / Vista / 2008 x86 stop on NVMe). The new code path
  only runs for an NVMe target, which the gate stops, so SATA installs are
  unaffected.
