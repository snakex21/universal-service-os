## Testy automatyczne

Wszystkie techniczne testy mają jedno wejście: `tools/tests/run.ps1`.

- `-Suite all` - testy jednostkowe, selftest oraz QEMU x86_64 i ARM64,
- `-Suite unit` - tylko testy jednostkowe,
- `-Suite selftest` - krytyczne kontrole startowe,
- `-Suite x86_64` - automatyczny boot UEFI x86_64 w QEMU,
- `-Suite aarch64` - automatyczny boot UEFI ARM64 w QEMU.

Przykład pełnej macierzy: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/tests/run.ps1 -Suite all`.

`build.bat` pozostaje osobnym wejściem do pełnego builda ReleaseFast programu USB i instalatora. Zawsze generuje jeden identyfikator buildu (`build/generated/build-info.ini`), przekazuje go do bootmanagera i instalatora, przebudowuje payload, uruchamia testy Go i kończy się kontrolą spójności SHA-256. Przed zbudowaniem EXE `usos-payload-pack -verify-fresh-only` porównuje czas `payload.zip` z każdym rzeczywistym plikiem źródłowym pakowanym do ESP; choćby jeden nowszy plik oznacza twardy FAIL, nie ostrzeżenie. `verify_release_consistency.ps1` dodatkowo wymaga, żeby `build-info.ini`, BOOTX64.EFI i payload były z tego samego przebiegu.

Identyfikator ma format `BYYMMDD-HHMMSS-XXXXXXXX`: część czasowa daje porządek wersji potrzebny do ochrony przed downgrade, a końcówka jest skrótem SHA-256 bieżących źródeł releasu. Pełny fingerprint oraz epoch są zapisane w `EFI/USOS/build-info.ini`. Bootmanager pokazuje ID obok zegara. `Aktualizuj USOS` odczytuje ID nośnika z ESP i ID własnego osadzonego payloadu; próba wgrania starszego buildu jest zatrzymywana, dopóki użytkownik jawnie nie potwierdzi cofnięcia. Log aktualizacji zapisuje parę `VERSION media=... installer=...`, ewentualne `DOWNGRADE CONFIRMED` oraz SHA-256 BOOTX64.EFI po zapisie.

## QEMU x86_64

Preferowana lokalizacja: `tools/qemu/`.

Do ręcznego testu pełnej instalacji używaj `TEST-USOS.cmd`. Skrypt uruchamia aktualny USOS w QEMU, automatycznie przebudowuje bazę tylko wtedy, gdy zmienił się kod lub zawartość `media/`, tworzy świeży stan sesji i osobny wirtualny dysk docelowy Windows. Można przejść cały przepływ od menu USOS, przez ekran `Loading Windows ISO`, mikro-Linux i Windows Setup aż do instalacji systemu na tym wirtualnym dysku. **Domyślnym akceleratorem pełnych przebiegów jest wielowątkowy TCG** (`-accel tcg,thread=multi -cpu max`). WHPX pozostaje opcją wyłącznie do szybkich testów przygotowania/Fazy A i innych prób, które nie wymagają restartu VM ani przekazania sterowania do kolejnego obrazu EFI.

WHPX nie nadaje się do startu pełnego Windowsa w tym środowisku i temat jest zamknięty do czasu zmiany QEMU/WHPX/hosta. W tej samej sesji wystąpiły trzy niezależne awarie warstwy WHPX: (1) `-cpu max` powodował panic Linuksa w `fpu__init_system_xstate`/`fpstate_reset`, ponieważ CPUID deklarował XSAVE nieobsługiwane poprawnie przez WHPX; `Skylake-Client-v4` na tym hoście nie usunął problemu, a `qemu64,-xsave` pozwolił uruchomić mikro-Linuksa; (2) po poprawnym `phase=prepared` reboot gościa kończył QEMU błędem `WHPX: Unexpected VP exit code 4`; (3) osobna Faza B dochodziła poprawnie do `WINDOWS STARTIMAGE BEGIN`, po czym WHPX ponownie kończył się `Unexpected VP exit code 4` podczas przekazania sterowania do Windows Setup. Dlatego pełny przebieg zawsze uruchamiamy na TCG. WHPX można wymusić tylko świadomie przez parametr launchera `-AccelerationMode whpx` do szybkich testów niewymagających handoffu. UEFI pokazuje nazwę bieżącej operacji handoffu bez zmyślonego procentu, mikro-Linux pokazuje kolejne etapy przygotowania, a rzeczywisty procent, liczbę bajtów, prędkość i ETA pokazujemy dopiero podczas mierzalnego kopiowania plików Windows.

Finalna macierz startu pełnego Windowsa pod WHPX z 5 września 2026 (`tools/run_windows_whpx_matrix.ps1`, limit 12 min na wariant): `-cpu qemu64` -> `EXIT_NO_PROBE` po 192,7 s, logo Windows na czarnym tle, stderr `WHPX: Unexpected VP exit code 4`; `-cpu qemu64,-xsave` -> `EXIT_NO_PROBE` po 381,6 s, ten sam stan wizualny i ten sam VP exit code 4; `-cpu Skylake-Client-v4` -> timeout po 722,4 s, nadal logo Windows; `-cpu host` -> timeout po 722,5 s bez uruchomienia probe; `-machine q35,accel=whpx -cpu qemu64,-xsave` -> timeout po 722,4 s i ponownie `WHPX: Unexpected VP exit code 4`. Żaden wariant nie uruchomił bootstrap probe i żaden nie dał BSOD. W połączeniu z wcześniejszymi awariami WHPX przy reboot/StartImage zamyka to dalsze strojenie WHPX w tym środowisku: nie próbujemy kolejnych modeli CPU. Domyślny pełny start Windowsa pozostaje na `-accel tcg,thread=multi -cpu max`; WHPX zostaje tylko dla krótkich testów mikro-Linuksa i innych ścieżek, dla których jest osobno potwierdzony.

Komunikat Windows Setup `Brak sterownika nośnika wymaganego przez komputer` oznacza w tym przepływie przede wszystkim, że WinPE nie zamontował WORK. Do tej pory potwierdzone były dwa powody: (1) własny typ GPT WORK — naprawione przez użycie Microsoft Basic Data; (2) atrybut GPT `NoDefaultDriveLetter` (bit 63) — naprawione przez wymuszenie bit63=0. Test kontrolny z 3 września 2026 wykazał, że pełny TCG z WORK bit63=1 dochodził do `WINDOWS STARTIMAGE BEGIN`, ale WinPE nie montował WORK; po zmianie wyłącznie `NoDefaultDriveLetter=True` na `False` Faza B doszła do ekranu `Wybierz lokalizację do zainstalowania systemu Windows 11` i pokazała `USOS_DATA`, `USOS_WORK` oraz pusty dysk docelowy 64 GiB. Przy następnym wystąpieniu tego komunikatu najpierw sprawdzać typ GPT oraz atrybuty partycji WORK. Nowe nośniki i aktualizacja istniejących nośników mają wymuszać Microsoft Basic Data oraz bit63=0. Fixture E2E również jawnie czyści ten atrybut, ponieważ `New-Partition` na file-backed VHD potrafi ustawić go automatycznie, gdy partycja nie dostaje litery.

Po zakończonym teście `RESET-USOS-TEST.cmd` usuwa wyłącznie wirtualny dysk z zainstalowanym Windowsem oraz stan sesji USOS. Baza z prawdziwym ISO pozostaje, dzięki czemu kolejna próba nie wymaga ponownego kopiowania obrazu 7,8 GB. Fizyczne dyski hosta nie są przekazywane do tego testu.

### Windows XP SP2 PL — czysty wzorzec `makelocalsource`

Kontrola na czystym `windows_xp_professional_service_pack_2_x86_pl.iso` została wykonana 7 września 2026 w VirtualBox na maszynie `USOS-XP-SP2-Control-VBox`. ISO ma `I386\SETUPP.INI` z `Pid=76447000`, czyli kanał Retail. Windows XP Professional SP2 PL został zainstalowany i uruchomił pulpit. Po nieplanowanej utracie zasilania hosta instalacja została podjęta z HDD i system wrócił do działającego pulpitu; test nie wymagał ponownego formatowania obrazu.

Z działającego XP uruchomiono `D:\I386\WINNT32.EXE /makelocalsource /noreboot`. Klucz znajdujący się w `I386\UNATTEND.TXT` tego samego ISO został odrzucony przez ekran ProductKey, natomiast poprawny klucz Retail podany interaktywnie został przyjęty. Po jego przyjęciu `WINNT32` ukończył przygotowanie lokalnego źródła. VM została następnie zamknięta normalnie przez ACPI, bez restartu.

Inspekcja wyłączonego `zig-out/virtualbox/xp-sp2-clean-control.vhd`, zamontowanego na hoście tylko do odczytu, potwierdziła poprawny wynik: `$WIN_NT$.~BT` ma 121 plików i 6 585 622 bajty, a `$WIN_NT$.~LS` ma 5474 pliki i 381 831 707 bajtów. `$WIN_NT$.~BT` zawiera między innymi `BOOTSECT.DAT`, `setupldr.bin`, `ntdetect.com`, `txtsetup.sif` i `winnt.sif`; `$WIN_NT$.~LS` zawiera pełne `I386` oraz `SIZE.SIF` z `Size=402219008`. `boot.ini` po `makelocalsource` ustawia domyślny start na `C:\$WIN_NT$.~BT\BOOTSECT.DAT` i dodaje pozycję `Instalator systemu Microsoft Windows XP Professional`.

Ważne: ręcznie zaakceptowany klucz nie został zapisany z powrotem do wygenerowanego `$WIN_NT$.~BT\winnt.sif`; pola `ProductKey`/`productid` nadal zawierają wartość z wejściowego pliku odpowiedzi. Tor USOS nie może więc zakładać, że interaktywna walidacja ProductKey z `WINNT32` zapisze poprawny klucz do lokalnego źródła. Obsługę klucza trzeba traktować osobno.

Dodatkowy test bootu wykonano wyłącznie na klonie `zig-out/virtualbox/xp-sp2-localsource-boot-test.vhd`. ISO zostało całkowicie odpięte od VM, kolejność bootu pozostawiono `disk` -> `dvd`, a maszyna wystartowała z HDD przez przygotowane `BOOTSECT.DAT`. Log przeszedł do trybu tekstowego 640x480, a klon VHD zaczął być modyfikowany przez Setup mimo braku jakiegokolwiek CD/ISO. To potwierdza kluczową własność dla USOS: po poprawnym przygotowaniu `$WIN_NT$.~BT` + `$WIN_NT$.~LS` instalator XP może kontynuować z lokalnego dysku bez emulacji ISO. Testową kopię wyłączono i oryginalny `xp-sp2-clean-control.vhd` przywrócono do VM w stanie `poweroff`; czyste ISO ponownie podpięto wyłącznie jako nośnik kontrolny.

Dalsze testy redukcyjne na osobnych klonach potwierdziły, że nie trzeba odtwarzać dwóch zachowań `WINNT32` 1:1, aby zachować działający lokalny start. Po usunięciu wyłącznie `$WIN_NT$.~BT\migrate.inf` (`xp-sp2-no-migrate-test.vhd`) i odpięciu ISO Setup nadal wszedł w ten sam niebieski tryb tekstowy (`640x480` po 15 s, następnie `720x396`; dominujący kolor `RGB 0,0,168`). `migrate.inf` z wzorca zawiera wyłącznie `[Version]` oraz wpisy `[Addreg]` odtwarzające konkretne `HKLM\SYSTEM\MountedDevices` dla kontrolnej VM (A:, D: CD-ROM, C: i Volume GUID); nie wolno kopiować go do produkcji jako stałego pliku zależnego od tej maszyny.

Drugi klon (`xp-sp2-full-i386-test.vhd`) dostał do `$WIN_NT$.~LS\I386` pełne `6701` plików z ISO zamiast przefiltrowanych `5473`, po czym zachowano kontrolne przemianowanie `I386\USETUP.EXE -> I386\SYSTEM32\SMSS.EXE`. Bez ISO Setup ponownie osiągnął ten sam tryb tekstowy. Osobny klon z pełnym `I386` i oryginalnym `ISO\I386\SYSTEM32\SMSS.EXE` również osiągnął ten sam etap. Wniosek produkcyjny: filtr `5473/6701` jest optymalizacją rozmiaru `WINNT32`, nie wymaganiem wczesnego startu; USOS może kopiować pełne `I386`, a przemianowanie `USETUP.EXE -> SYSTEM32\SMSS.EXE` zachowujemy dla zgodności z wzorcem do czasu pełnego E2E przez fazę graficzną.

Stałe `118` plików `$WIN_NT$.~BT` dają się odtworzyć bez manifestu konkretnej wersji XP. Są dokładnie wynikiem wszystkich wpisów `d1,...` z sekcji `DOSNET.INF` `[FloppyFiles.*]`: bez jawnego celu zachowuje się fizyczną nazwę pliku źródłowego z ISO (łącznie z kompresją typu `ACPI.SY_`), z jawnym celem używa się podanej ścieżki (`disk1 -> disk101..disk104`, `ntdll.dll -> system32\ntdll.dll`, `usetup.exe -> system32\smss.exe`), a samotny `ntldr` bez celu nie trafia do BT. Tak wyliczony zbiór ma dokładnie `118` pozycji i różnica względem kontrolnego `$WIN_NT$.~BT` wynosi `0/0`. ## Legacy BIOS Core

Produkcyjny Legacy Core nie używa już atrybutu GPT `Legacy BIOS Bootable` do wyboru partycji. Ten atrybut był wyłącznie etapem testowym wcześniejszego `Stage 1 -> Core -> VBR`. Docelowo Core jest platformowym odpowiednikiem `BOOTX64.EFI`; chainload VBR pozostaje późniejszą metodą dla systemów wymagających BIOS-u, a nie sposobem uruchamiania samego USOS.

ABI Stage 1 jest celowo małe i zamrożone: Stage 1 czyta przez INT 13h Extensions pierwsze 32 sektory od LBA64 do pamięci `0x10000` i skacze na offset 64. Cały slot Core ma jednak 512 sektorów = 256 KiB i zajmuje LBA64..575. Pierwsze 16 KiB to stałe okno bootstrapu, a reszta jest doczytywana przez bootstrap porcjami maksymalnie po 32 sektory. Przy standardowym ESP zaczynającym się od LBA2048 pozostaje 736 KiB niewykorzystanej rezerwy przed ESP. Installer nie może zakładać LBA2048: przed każdym zapisem liczy koniec slotu z rzeczywistego rozmiaru sektora i porównuje go z rzeczywistym początkiem ESP odczytanym z GPT.

Format Core v1 ma stały 64-bajtowy nagłówek `USOSCORE`: magic, wersję formatu, rozmiar nagłówka, rozmiar slotu i bootstrapu, rzeczywisty rozmiar obrazu/payloadu, adres ładowania, entry offset, CRC32 treści i CRC32 nagłówka. Bootstrap odrzuca nieobsługiwaną wersję, niespójne rozmiary, niezerowe pola reserved, błędny CRC nagłówka albo błędny CRC treści. Treść objęta CRC zaczyna się za 64-bajtowym nagłówkiem i obejmuje kod bootstrapu, jego padding do 16 KiB oraz rzeczywisty 32-bitowy Core. Mutable runtime state (DAP, liczniki odczytu, boot drive, scratch CRC/A20) leży poza checksummowanym obrazem w osobnym obszarze pamięci konwencjonalnej; uruchomiony bootstrap nie modyfikuje własnej chronionej treści.

Po walidacji nagłówka bootstrap doczytuje Core do `0x20000`, sprawdza CRC32 przed skokiem, włącza i weryfikuje A20, ładuje własne GDT, przechodzi do 32-bit protected mode i dopiero wtedy skacze do Core main. Bootstrap przekazuje przez wersjonowany 24-bajtowy `LegacyBootContext` zachowany BIOS drive `DL`, rozmiar sektora i LBA slotu; Core odrzuca niespójny kontekst. Kod Zig Core jest budowany jako `i386` baseline. `tools/build_legacy_bios.ps1` emituje assembly Core jako artefakt audytowy i jest twardą bramą: obecność dowolnego rejestru `xmm*`, `ymm*` lub `zmm*` kończy build FAIL. Core nie może polegać na SSE/AVX ani na stanie CR0/CR4 pozostawionym przez BIOS.

Regresję nagłówka/bootstrapu uruchamia `tools/tests/legacy_bios/run_seabios_core_bootstrap.ps1`. Macierz SeaBIOS nadal wymaga trzech przypadków: (1) poprawny slot przechodzi header/load/CRC/A20/PM i wchodzi do produkcyjnego Core; niefomatowana ESP tego fixture kończy się dopiero kontrolowanym `FAT32 FAIL error=InvalidBPB`; (2) nagłówek z wersją 2, ale poprawnie przeliczonym CRC nagłówka, kończy się `CORE HEADER FAIL` przed PM; (3) uszkodzona treść przy poprawnym nagłówku kończy się `CORE CRC FAIL` przed PM. Fixture nie używa atrybutu `Legacy BIOS Bootable`.

Czytnik GPT/FAT32 jest kodem wspólnym w `src/storage/`: nie zna BIOS-u ani UEFI i dostaje wyłącznie mały interfejs `readAt(offset, buffer)`. Legacy BIOS zapewnia ten interfejs przez cienki thunk PM32 -> PM16 -> real mode -> INT 13h Extensions -> PM32 z jednym 512-bajtowym bounce bufferem poniżej 1 MiB. Po fizycznym Socket 939 klawiatura menu została całkowicie odpięta od INT 16h i od bufora BDA: Core w PM32 używa wyłącznie pollingu 8042 przez `0x64`/`0x60`, konsumuje tylko bajty klawiatury i odrzuca AUX/mouse. Scancode'y są dekodowane jako AT Set 1: `0xE0` jest prefiksem rozszerzonym, break code (`make | 0x80`) nigdy nie generuje zdarzenia, a po zaakceptowanym make code następny klawisz nie jest przyjmowany do czasu zgodnego break code. To tłumi zarówno podwójne make/break, jak i typematic repeat po przytrzymaniu. Obsługiwane bez BIOS-u są wszystkie klawisze potrzebne frontendowi: strzałki, Enter, Esc, Backspace i `D`. Timeout nie zależy od IRQ0/BDA tick — liczy czas z bieżącego licznika PIT channel 0 przy `IF=0`. Dzięki temu menu nie wymaga żadnego wejścia do real mode po zakończeniu discovery tylko po to, by obsłużyć klawiaturę. Core czyta tylko dysk wskazany przez zachowane `DL`; na tym dysku wymaga dokładnie jednej partycji o typie EFI System Partition i nazwie GPT `USOS_ESP`. Zero kandydatów i wieloznaczność są błędami fail-closed. Parser FAT32 jest wyłącznie read-only, obsługuje LFN, sprawdza granice partycji przed każdym I/O, aktywną FAT, zakres klastrów, bad/reserved/free cluster, przedwczesny EOC oraz pętle z limitem wyprowadzonym z rzeczywistej liczby klastrów.

`tools/tests/legacy_bios/run_fat32_host_matrix.ps1` najpierw tworzy prawdziwy file-backed VHD, formatuje jego ESP przez Windows `Format-Volume FAT32`, zapisuje wieloklastrowy `EFI/USOS/usos-menu.ini`, a następnie uruchamia ten sam parser na hoście. Wariant poprawny daje `GPT_NAME=USOS_ESP`, surowe pole etykiety EBPB `FAT32_LABEL=NO NAME` i `USOS_MENU_INI_READ_OK bytes=75249`. Cztery kopie z pojedynczymi mutacjami muszą odmówić odpowiednio: zły BPB -> `UnsupportedSectorSize`, zerwany łańcuch -> `BrokenClusterChain`, pierwszy klaster pliku poza partycją -> `InvalidCluster`, pętla FAT -> `ClusterChainLoop`.

`tools/tests/legacy_bios/run_seabios_fat32_matrix.ps1` wprowadza te same obrazy przez pełne `Stage1 -> bootstrap -> PM32 -> INT13 -> GPT -> FAT32/LFN`. Przypadek poprawny musi wypisać `GPT NAME: USOS_ESP`, `FAT32 BPB LABEL: NO NAME`, listing `ROOT DIRECTORY` i `EFI DIRECTORY` oraz `USOS-MENU.INI READ OK bytes=75249`. Wszystkie cztery uszkodzone warianty muszą zakończyć się przewidzianym komunikatem `FAIL` i nie mogą nigdy wypisać `USOS-MENU.INI READ OK`. Enumeracja katalogów korzysta z tego samego `src/storage/fat32.zig`; nie ma osobnego parsera diagnostycznego w BIOS Core.

`tools/tests/legacy_bios/run_seabios_production_menu.ps1` oprócz produkcyjnego katalogu musi regresyjnie przejść klawiaturą przez `CATEGORIES -> D -> ESC -> CATEGORIES`, `Windows submenu -> D -> ESC -> submenu`, `submenu -> ESC -> CATEGORIES` oraz `IMAGES: Windows 11 -> ESC -> submenu`. Normalne ekrany nie mogą zawierać serwisowych linii `KBD LIVE POLL CALLS`, `SCANCODES READ`, `RAW TAIL`, `MENU EVENTS` ani `INT13 READS`; cały ten blok jest dostępny wyłącznie pod `D`. `D` otwarte bezpośrednio z pierwszego ekranu prawidłowo daje `DISCOVERY CACHE HITS/MISSES: 0/0`; po pierwszym wejściu w Windows produkcyjny fixture daje `14/14`. Test dodatkowo wymaga, żeby `Down` z Windows 11 zaznaczył `Windows 10 [no image]`, Enter pokazał komunikat z dokładną ścieżką `Systems\Windows\Windows 10\Images`, a ESC wrócił na tę samą listę. Brak obrazu jest więc stanem aktywacji, a nie powodem pomijania pozycji przez kursor. W SeaBIOS snapshot z pierwszego ekranu wynosił `INT13 SECTOR READS: 162`, dokładnie tyle samo co na fizycznym Socket 939; wyższe wartości po wejściu w systemy wynikają z faktycznego discovery.

Fizyczny test Socket 939 z 5 września 2026 potwierdził `GPT NAME: USOS_ESP`, `FAT32 BPB LABEL: NO NAME` i poprawny mount FAT32, ale `EFI/USOS/usos-menu.ini` zakończył się `NotFound`. Późniejszy read-only odczyt tego samego fizycznego ESP z Windows pokazał root `EFI`, `UI`, `loader`, `Systems`, `Utilities`; w `EFI` są `USOS` i `BOOT`, a w `EFI/USOS` są `micro-linux`, `ntfs_x64.efi`, `systemd-bootx64.efi`, `install-state.ini`, `usos-device.ini`, `build-info.ini`. Produkcyjny installer nie tworzy `usos-menu.ini`; plik istnieje tylko w fixture FAT32. Historycznie frontend budował discovery z projekcji `Systems/` i `Utilities/` na ESP; po wdrożeniu bezpośredniego NTFS źródłem prawdy jest drzewo `Systems/`/`Utilities/` na `USOS_DATA`, a ESP nie niesie już markerów nazw obrazów.

Legacy `CATEGORIES` zawiera również `POWER`. `ESC`/`Backspace` z kategorii przenosi zaznaczenie na POWER tak jak w UEFI; `Restart` wykonuje triple fault w PM32, a `Shut down` przechodzi przez real-mode APM (`INT 15h`, finalnie `AX=5307 BX=0001 CX=0003`). SeaBIOS pod QEMU potwierdza oba skutki: restart kończy maszynę uruchomioną z `-no-reboot`, a APM shutdown wyłącza QEMU. Jeżeli APM nie jest dostępne albo wywołanie wróci bez wyłączenia sprzętu, Legacy pokazuje komunikat o ręcznym wyłączeniu. Wejście do firmware setup pozostaje wyłącznie funkcją UEFI, bo Legacy BIOS nie ma jednego standardowego interfejsu.

**VESA-2 używa tego samego `gui.Surface` / `gui.text` / `font5x7` co pozostałe framebufferowe frontendy; VBE jest providerem framebuffera, nie osobnym rendererem.** Inicjalizacja wykonuje jedną sekwencję `INT 10h AX=4F00`, `4F01` dla każdego ID z listy (limit 256) i jedno `4F02` dla wybranego trybu z bitem LFB. Preferencja wyboru to `1280x800`, `1280x1024`, `1024x768`, `800x600`, a dopiero potem scoring pozostałych poprawnych trybów 32-bit Direct Color z LFB. Far pointer listy trybów jest kopiowany w real mode do własnego low-memory scratch; segment `0000` jest legalny, a pointer jest normalizowany do kanonicznego `segment:offset`, żeby skan nie zależał od granicy 64 KiB. Tryby bankowane są odrzucane, `PhysBasePtr` jest adresowany bezpośrednio w płaskim PM32, a `Surface.init()` odrzuca adresy nieosiągalne w bieżącym `usize`.

Fizyczny VESA-1 na Socket 939 / Radeon X1950 Pro potwierdził VBE 3.0, 73 BIOS mode IDs, 22 tryby 32-bit LFB i brak `1280x800`; scoring poprawnie wybrał `0x011B 1280x1024x32`, pitch 5120, framebuffer `0xD0000000`, BGRX8. VESA-2 zachowuje ten sam probe/scoring, ale po `4F02` uruchamia normalne menu przez wspólny, rozdzielczościowo niezależny `gui/menu_canvas.zig`. Marginesy, header/footer, wysokość wierszy, liczba widocznych pozycji oraz geometria kafelków 2x3 są liczone z bieżącego `width/height`; test renderuje kompletne ekrany do buforów o dokładnym rozmiarze `1280x1024` i `1024x768` oraz sprawdza także geometrię `800x600`. Graficzne kategorie używają tej samej nawigacji 2D co UEFI, natomiast tekstowy fallback zachowuje pionową nawigację listy. VESA-2 zapisuje bezpośrednio do fizycznego LFB i nie ma pełnoekranowego software backbuffera. Zwykła zmiana zaznaczenia nie może więc wywoływać `beginList()` ani czyszczenia całego ekranu: kategorie przerysowują tylko dwa kafelki, a listy systemów, obrazów, metod, unattended, utilities i POWER tylko wiersz tracący oraz zyskujący zaznaczenie. Dopiero przesunięcie okna przewijania może odświeżyć wnętrze panelu listy; header, tło i footer pozostają bez zmian.

`tools/tests/legacy_bios/run_seabios_vbe_probe.ps1` waliduje produkcyjny Stage1/bootstrap/Core pod SeaBIOS. `std VGA` daje 20 trybów 32-bit LFB, wybiera `1280x800`, rysuje graficzne CATEGORIES, wchodzi do listy Windows i wymaga wielokolorowego obszaru 32x32 w miejscu ikony pierwszego systemu, a sekwencja `D -> VGA text diagnostics -> ESC -> 4F02` musi zakończyć się `VESA-2 GRAPHICS RESTORED`. Ikony Legacy są generowane podczas builda z tych samych `media/UI/Icons/Systems/*.png`, których używa UEFI: generator skaluje je do 32x32 RGBA i linkuje gotowe piksele zamiast dekodować duże PNG w runtime; 21 obecnych ikon zajmuje 86016 bajtów i nie wymaga BSS. System bez własnego PNG dostaje mały kafelek z pierwszą literą nazwy, więc żaden wiersz nie ma pustej przestrzeni po ikonie. Nagłówki graficzne pobierają RTC bezpośrednio z CMOS i pokazują pełny dzień tygodnia, datę, rok i godzinę (`SUNDAY 06.09.2026 15:42`); podczas oczekiwania na klawisz prawy fragment nagłówka odświeża się mniej więcej raz na sekundę bez pełnego redrawu. Ten sam test z `cirrus VGA` daje VBE 3.0 / 31 ID / 0 trybów 32-bit LFB i musi przejść do `VESA-2 TEXT FALLBACK ACTIVE`, wyrenderować stare tekstowe CATEGORIES oraz reagować klawiaturą (ESC zaznacza POWER). Jeżeli probe, brak odpowiedniego LFB albo późniejsze przywrócenie `4F02` zawiedzie na sprzęcie, sesja graficzna jest wyłączana i ten sam controller menu kontynuuje w trybie tekstowym.

**Legacy Linux boot protocol — etap parsera nagłówka.** `src/platform/bios/linux_boot_header.zig` parsuje setup header bzImage bez założeń o konkretnym buildzie kernela, normalizuje historyczne `setup_sects=0` do 4 sektorów i oddziela samo parsowanie od walidacji kontraktu USOS. Walidator bieżącego mikro-Linuksa wymaga co najmniej protocol 2.15 (`0x020F`), `LOAD_HIGH`, flagi `XLF_KERNEL_64`, niezerowego `cmdline_size`, `init_size` i `initrd_addr_max`. `tools/tests/legacy_bios/run_linux_boot_header.ps1` uruchamia testy syntetyczne oraz test na faktycznym `zig-out/micro-linux/vmlinuz-virt`; nazwa pliku pozostaje zgodnościowa, ale od 8 września 2026 zawartość to stockowy Alpine `6.18.35-0-lts`. `build.bat` wykonuje tę bramę bezpośrednio po `zig build ... micro-linux`, więc zmiana przypiętego kernela nie może po cichu zmienić kontraktu Legacy loadera. Bieżący LTS musi dać dokładnie: `protocol=0x020F`, `setup_sects=39`, protected-mode file offset `0x5000`, `vid_mode=0xFFFF`, `code32_start=0x00100000`, `initrd_addr_max=0x7FFFFFFF`, `kernel_alignment=0x01000000`, `relocatable_kernel=1`, `min_alignment=21`, `xloadflags=0x007F`, `cmdline_size=2047`, `pref_address=0x01000000`, `init_size=44236800`, `kernel_info_offset=0x00DC5900` oraz kernel version zaczynające się od `6.18.35-0-lts`.

**Bariery sprzętowe obecnego mikro-Linuksa (Legacy):** (1) Legacy Core/menu jest i386 baseline i może działać na starszym 32-bit x86, ale przypięty mikro-Linux LTS jest x86_64. Dlatego ścieżka `Legacy USOS -> mikro-Linux -> przygotowanie Windows/XP` wymaga long mode: Athlon 64 / Pentium 4 z EM64T lub nowszy CPU. Pentium III i 32-bitowy Athlon XP nie uruchomią obecnego środowiska przygotowawczego, nawet jeżeli samo menu Legacy działa. Osobny 32-bitowy mikro-kernel dla starszego sprzętu jest zapisany jako późniejszy kamień i **nie** jest częścią bieżącej implementacji Linux boot protocol. (2) Po migracji na Alpine `6.18.35-0-lts` i pruned dependency closure granica pamięci została ponownie sprawdzona: przy **128 MiB** loader poprawnie mieści kernel/initramfs i wykonuje skok do `startup_32`, ale LTS panicuje podczas rozpakowywania initramfs komunikatem `System is deadlocked on memory`; przy **136 MiB** ten sam obraz dochodzi do `[MICRO-LINUX] boot PASS kernel=6.18.35-0-lts` i `[USOS-FB-UI] FIRST_FRAME`. 136 MiB pozostaje jedynie granicą emulacyjną bez rozsądnego marginesu na firmware i realny sprzęt, dlatego **wspierane minimum sprzętowe nadal wynosi 256 MiB RAM**.

**Legacy Linux boot protocol — pełny SeaBIOS handoff.** Runner `tools/tests/legacy_bios/run_seabios_linux_boot.ps1 -MemoryMb 256` tworzy produkcyjny Stage1/bootstrap/Core z prawdziwym `vmlinuz-virt` i `initramfs-usos` na FAT32 ESP, wykonuje E820, ładuje protected bzImage i initramfs, buduje `boot_params`/cmdline, sprawdza CPU long mode oraz tuż przed skokiem wykonuje VBE `INT 10h AX=4F03`. Dla `std VGA` wymagane jest `expected=0x017A current=0x017A match=yes`; jakakolwiek zmiana trybu kończy handoff fail-closed. Kernel startuje przez 32-bit entry `startup_32` z `CS=0x10`, `DS/ES/SS=0x18`, paging off, IF=0, `ESI=boot_params` i `EBX/EBP/EDI=0`. Zielony wynik wymaga jednocześnie `[MICRO-LINUX] boot PASS`, `[USOS-FB-UI] FIRST_FRAME`, screendumpu preparation UI oraz resource sysfs framebuffera zaczynającego się pod tym samym fizycznym adresem co VBE LFB. Referencyjny SeaBIOS: BIOS handoff `fb=0xFD000000`, Linux resource `start=0x00000000fd000000`; simpledrm przejmuje więc ten sam LFB zamiast ustawiać nowy tryb.

Fizyczny Socket 939 potwierdził działającą ścieżkę klawiatury po trzech poprawkach. Po pierwsze Legacy bootstrap nie korzysta już z `INT 15h AX=2401`; A20 jest sprawdzane, a jeśli trzeba je włączyć, używany jest wyłącznie Fast A20 przez port `0x92`, z wyzerowanym bitem Fast Reset i bez dotykania 8042. Po drugie dekoder tłumi tylko typematic tego samego klawisza, więc zgubiony break podczas BIOSowego `INT 13h` nie blokuje kolejnych make code. Po trzecie sekwencja Socket 939 `E0 2A E0 50 E0 D0 E0 AA` jest obsługiwana jako rozszerzony Down otoczony fake Shift: `E0 2A` i `E0 AA` są ignorowane, `E0 50` generuje Down, a `E0 D0` zwalnia stan klawisza. Fizyczny test potwierdził rosnące `MENU EVENTS`, poprawne `LAST MENU EVENT: ENTER/ESC`, wejście Enterem do systemów i powrót ESC do kategorii. Ostatecznie brak ruchu kursora przy samym Windows 11 okazał się poprawnym, ale mylącym zachowaniem `moveEnabled`: pozostałe systemy miały `[no image]`. Obecna polityka wspólna dla BIOS i UEFI rozdziela nawigację od aktywacji: pozycja zgodna z bieżącym firmware jest nawigowalna nawet bez obrazu, a Enter na `[no image]` pokazuje dokładny katalog `...\Images`; tylko firmware mismatch pozostaje niewybieralny. Telemetria `POLL CALLS`, `SCANCODES READ`, `LAST RAW`, `LAST ACCEPTED`, `RESP-LIKE BYTES`, `RAW TAIL`, `MENU EVENTS`, `LAST MENU EVENT`, `MENU SCREEN`, `SELECTED INDEX`, `INT13 READS` i A20/8042 jest nadal zbierana, ale nie jest drukowana na normalnych ekranach — jest dostępna wyłącznie pod `D`. Snapshoty BEFORE/AFTER/NOW/LAST TIMEOUT pozostają zamrożonymi punktami pomiarowymi.

Referencyjny SeaBIOS dla rozszerzonej diagnostyki daje po discovery `A20=ON PIC1=0xB8 IRR=0x10 ISR=0x00 8042=0x1C`, `IDTR=00000000/03FF`, a BDA head/tail przesuwają się normalnie. Bezpośrednia ścieżka wejścia PM32 przechodzi `CATEGORIES -> Windows -> D -> ESC -> Windows -> Images -> ESC -> Windows -> ESC -> CATEGORIES` bez INT 16h, a 30-sekundowy auto-return działa z PIT przy `IF=0`. Osobny smoke na fixture bez obrazów potwierdza `Windows 11 [no image] -> Down -> Windows 10 [no image] -> Enter -> NO IMAGES -> Systems\Windows\Windows 10\Images -> ESC -> Windows 10`, więc nawigacja po pustych pozycjach i komunikat o brakującym obrazie są częścią wymaganej regresji.

Ścieżka zapisu instalatora traktuje LBA64..575 jako jeden stały slot. Przed zapisem nowego Core waliduje osadzony header v1/CRC, zeruje pełne 256 KiB, flushuje, odczytuje całe 256 KiB i wymaga samych zer (`LEGACY_BOOT SLOT ZERO READBACK PASS`), następnie zapisuje pełny slot, ponownie flushuje i porównuje cały 256 KiB read-back. Stage 1 w LBA0 jest zapisywany dopiero po poprawnym read-backu slotu; bajty LBA0 440..511 pozostają bit-identyczne. `Clear Legacy` zeruje LBA0 0..439 oraz cały slot LBA64..575 bez repartitioningu. Test plikowego raw handle w `installer/internal/winhost/legacy_boot_area_windows_test.go` zaczyna od slotu wypełnionego `0xA5` i wymaga audytu zerowania, finalnego pełnego read-backu i zachowania LBA0 440..511.

**Granica bezpieczeństwa targetu instalacji XP:** nośnik USB z USOS **nigdy nie jest kandydatem na dysk docelowy instalacji systemu**. Kod wyboru targetu i `target_disk_guard.sh` muszą fail-closed odrzucać cały fizyczny dysk zawierający bieżący `USOS_ESP`, niezależnie od modelu, numeru `/dev/sdX`, trybu BIOS/UEFI lub przyszłych zmian UI. XP v1 nie kasuje istniejących partycji ani nie tworzy partycji docelowej Windows: wymaga istniejącego dysku DOS/MBR z niezerową disk signature, co najmniej jednego pustego primary MBR entry i ciągłego nieprzydzielonego obszaru >=2 GiB. Snapshot wiąże model/serial/WWN/size/sector size z dokładnym 512-bajtowym MBR, rezerwacją `XPSETUP` (slot/start/4194304 sektorów) oraz dokładną listą aktywnych wpisów MBR. Bezpośrednio przed write MBR i stan aktywnych flag muszą być identyczne ze snapshotem; jakakolwiek zmiana istniejącej tablicy albo zajęcie wybranego extentu oznacza STOP. Sam zapis tworzy jeden 16-bajtowy wpis MBR typu `0x0C` z flagą aktywną `0x80`. Jeżeli inna partycja była wcześniej aktywna, guard pokazuje ten fakt użytkownikowi **przed** `CREATE XPSETUP`, a write może zmienić w tym istniejącym wpisie wyłącznie pierwszy bajt `0x80 -> 0x00`; geometria, typ i pozostałe 15 bajtów muszą być bit-identyczne. Po read-backu `XPSETUP` ma być jedynym aktywnym wpisem. Boot code, disk signature, sygnatura `55AA` i wszystkie nieobjęte przełączeniem wpisy pozostają bit-identyczne. Confirmation ma postać `CREATE XPSETUP <MODEL> <SERIAL>` — nie ma trybu `ERASE`. E2E musi zawierać istniejącą partycję z plikiem sentinel o znanym SHA-256 i po przygotowaniu wymagać identycznego SHA; osobny test TOCTOU modyfikuje MBR między snapshotem i pre-write i musi zakończyć się `STOP: MBR changed after target selection`.

**Brama fizyczna:** Kingston, na którym wcześniej zapisano wariant 16 KiB, nie może dostać nowego Stage 1/slota 256 KiB, dopóki zatwierdzony kamień Legacy nie przejdzie wymaganej emulacji i użytkownik nie wyda osobnego polecenia wykonania fizycznego zapisu. Zielony SeaBIOS bootstrap/PM sam w sobie nie jest zgodą na zapis fizyczny.

## Szybki test na fizycznym pendrivie

Po zmianach uruchom `build.bat`, a następnie `installer\USOS Installer.exe` i wybierz `Aktualizuj USOS`. Ten tryb ponownie identyfikuje istniejący nośnik USOS, zapewnia zgodność WORK z Windows Setup (czyści GPT `NoDefaultDriveLetter`, bit 63 = 0), wgrywa aktualny statyczny payload ESP oraz bieżący instalator na DATA. Obrazy ISO/WIM/IMG/VHD/VHDX nie są już reprezentowane zerobajtowymi znacznikami na ESP: Legacy i UEFI odkrywają je bezpośrednio z `USOS_DATA` przez wspólny read-only parser NTFS. Na ESP mogą pozostać jedynie małe artefakty potrzebne poza discovery, np. wykonywalne kopie `.efi`, ikony profili i zgodnościowe pliki unattended. Aktualizacja usuwa stare znaczniki, ponieważ przebudowuje te małe projekcje ESP od zera. Nie formatuje partycji ani nie usuwa danych użytkownika. Updater liczy i loguje SHA-256 **każdego** pliku statycznego payloadu przed i po zapisie (nie tylko `BOOTX64.EFI`) i zatrzymuje aktualizację, jeśli po zapisie choć jeden plik nie zgadza się z payloadem EXE. Końcowa weryfikacja sprawdza także Legacy Stage 1/Core oraz zgodność wymaganych małych artefaktów ESP.

Od 5 września 2026 `Aktualizuj USOS` ma osobny etap Legacy przed kopiowaniem zwykłego payloadu: najpierw zapisuje/odczytuje Stage 1 i Core z pełnym SHA-256 oraz read-backiem GPT, więc FAIL raw-write zatrzymuje aktualizację zanim pliki ESP/DATA zostaną zmienione. Historyczna regresja `tools/run_legacy_update_cycle_qemu.ps1` dla wcześniejszego slotu 16 KiB zakończyła się `RESULT=PASS` i zachowała GPT oraz sentinel DATA, ale po zmianie formatu na slot 256 KiB ten wynik nie jest bramą dla nowego fizycznego zapisu — pełny cykl musi zostać powtórzony przed kolejną operacją na Kingstonie. `Clear Legacy` jest osobną wąską operacją: w aktualnym formacie zeruje wyłącznie LBA0 bajty 0-439 oraz pełny Core slot LBA64-575, zachowuje LBA0 bajty 440-511 i nie repartitionuje nośnika. Pełnego `Uninstall` nie wolno używać jako rollbacku Legacy, ponieważ przebudowuje układ partycji.

Na fizycznym USB ścieżki `/dev/disk/by-partuuid/...` są zawsze budowane przez wspólny `tools/partuuid.sh`, który normalizuje GUID-y do lowercase. Dotyczy to `micro_linux_init.sh`, `device_guard.sh` i `prepare_work.sh`. Mikro-Linux jawnie ładuje host/storage USB przed detekcją oraz czeka do 5 s na pojawienie się ESP/DATA/WORK, bo enumeracja `usb-storage`/UAS na realnym sprzęcie jest asynchroniczna. Sam napis w framebufferze nie pokazuje wielkości liter wiarygodnie: font 5x7 celowo renderuje małe litery tymi samymi glifami co wielkie.

Automatyczny wariant x86_64 uruchamia `tools/tests/run.ps1 -Suite x86_64`: buduje specjalny obraz testowy, startuje UEFI w QEMU, przekazuje log przez port szeregowy i używa `isa-debug-exit`, więc emulator kończy się jednoznacznym PASS/FAIL. Lokalny `tools/qemu/` ma pierwszeństwo; dla x86_64 runner potrafi też użyć `C:\Program Files\qemu`.

## Bezpośrednie discovery NTFS — Legacy + UEFI

Menu nie używa już zerobajtowych znaczników obrazów na ESP. Wspólny `src/storage/ntfs.zig` jest read-only i obsługuje MFT, USA/fixup, resident/non-resident attributes, runlisty, `$INDEX_ROOT`, `$INDEX_ALLOCATION`/`INDX`, przechodzenie po drzewie katalogów oraz kontrolę granic partycji. `tools/tests/legacy_bios/run_ntfs_host_matrix.ps1` tworzy prawdziwy NTFS przez Windows, wypełnia `Systems\\Windows\\Windows XP\\Images` setkami plików tak, aby katalog wymagał `$INDEX_ALLOCATION`, a następnie celowo przebudowuje `$MFT` na dwie runlisty. Bieżący hard fixture ma `NTFS_MFT_RUNS=2`, `NTFS_INDEX_ALLOCATION=yes`, `NTFS_IMAGES_ENTRIES=321` i discovery liczy wszystkie `320` ISO mimo stronicowania katalogu. Macierz negatywna wymaga: zły VBR -> `InvalidBPB`, zła sygnatura rekordu MFT -> `InvalidMftSignature`, uszkodzony USA -> `InvalidFixup`, run poza partycją -> `RunlistBounds`, nakładające/pętlowe VCN -> `RunlistLoop`.

**Regresja fizyczna Socket 939 (7/8 września 2026):** po aktualizacji Kingstona do bezmarkerowego direct-NTFS Legacy menu potrafiło pokazać `[no image]`, mimo niezmienionych SHA-256 ISO na `USOS_DATA`. Read-only host probe uruchomiony bezpośrednio na `\\.\\PhysicalDrive8` tym samym parserem potwierdza faktyczne media: `USOS_DATA` start LBA `2099200`, `88707072` sektorów, VBR `NTFS` + `55AA`, `bytes_per_sector=512`, `sectors_per_cluster=8`, `MFT_LCN=786432`, `$MFT` ma 1 run, `\\Systems` otwiera się z 5 wpisami, a discovery widzi `XP_IMAGES=1` i `WIN11_IMAGES=1`. Dodatkowo `\\Systems\\Windows` to rekord MFT `40` i katalog z `$INDEX_ALLOCATION` (`1` run, pierwszy LCN `5512`). Na fizycznym DATA tworzenie nazw 8.3 jest wyłączone (`fsutil 8dot3name query J:`), więc `Windows 11`/`Windows XP` nie mają aliasów typu `WINDOW~1`; samo 8.3 nie może wyjaśniać tej regresji.

**Legacy XP UI/storage regresje — 8 września 2026:** fizyczna brama LTS może być uruchamiana bez klawiatury przez `EFI/USOS/lts-storage-probe.ini`. Po samej enumeracji dysków micro-Linux zapisuje pełną diagnostykę PCI/storage oraz trzy jawne checki (`modalias`, przypięty driver, dokładnie jeden `/dev/sdX` candidate) do `EFI/USOS/legacy-xp-disk-enumeration.txt` i `EFI/USOS/lts-storage-probe.txt`, po czym zatrzymuje się w pętli bez wejścia w target selection, snapshot, confirmation ani staging. QEMU wymaga PASS dla PIIX/`ata_piix` oraz ICH9 AHCI/`ahci`; fizyczny MS-7100 używa `vendor=0x10de`, `device=0x0054`, `driver=sata_nv`, `candidates=1`. FAIL któregokolwiek checku = stop i analiza reportu.

**Legacy XP UI/storage regresje — 8 września 2026:** dla obrazu XP w BIOS `boot_method_model` musi mieć dokładnie jedną metodę `enabled`: `Automatic -> xp_staging`; `Direct ISO` nie jest drugim aliasem tego samego backendu. Gdy `singleEnabledIndex()` istnieje, zarówno BIOS, jak i UEFI pomijają ekran wyboru metod; UEFI przechodzi dalej do unattended/podsumowania, a BIOS bezpośrednio do unattended/wykonania backendu. Po zatwierdzeniu unattended, także `None`, Legacy VESA-2 musi natychmiast pokazać nienumerowany ekran `LOADING ENVIRONMENT`; ładowanie kernela i initramfs z ESP raportuje rzeczywisty procent na podstawie liczby przeczytanych bajtów FAT32, zamiast pozostawiać poprzedni ekran i wyglądać na zawieszenie. Właściwa numeracja `[1/5] STARTING ENVIRONMENT` → `[5/5] VERIFICATION AND FINALIZATION` zaczyna się dopiero po handoffie w micro-Linuksie. Fizyczny log dysków pozostaje oddzielną diagnostyką: przy `candidates=0` zapisuje `/sys/class/block`, PCI class `0x01*` z `vendor/device/subsystem/driver/modalias`, dostępne i załadowane moduły oraz pełny `dmesg` do `EFI/USOS/legacy-xp-disk-enumeration.txt`. Fizyczny MS-7100 rozstrzygnął przypadek SATA1 jako NVIDIA CK804 `10de:0054/0055`, wymagający `sata_nv`. Z tego powodu bazę przygotowawczą przełączono strategicznie z Alpine `virt` na stockowy `6.18.35-0-lts`: builder zachowuje pełną rodzinę `drivers/ata` przez dependency closure, a runtime ładuje sterownik wyłącznie przez PCI modalias. Pierwsza fizyczna brama po tej zmianie wymaga `driver=sata_nv`, pojawienia się SSD jako `/dev/sdX` i `candidates=1`; brak któregokolwiek warunku oznacza FAIL=stop.

**Legacy XP Strategy B / AH=08 — 9 września 2026:** `tools/tests/legacy_bios/test_xp_geometry_fix_mbr_ah08.py` wykonuje dokładny zbudowany artefakt `zig-out/xp-geometry-fix-mbr/xp-geometry-fix-mbr-440.bin` w trybie x86 real mode. Wymagane jest 6/6 PASS: poprawne BIOS `240/63` ma zmienić wyłącznie RAM-owe `BPB heads` z `255` na `240`; błąd CF z `AH=08`, `DH=0`, `DH=255`, `SPT=0` i SPT różne od BPB muszą zostawić `255/63` i nadal dojść do VBR. Żaden przypadek błędnej geometrii nie może zakończyć się crashem ani zapisem zmienionego BPB na dysk. Test wymaga pakietu Python `unicorn` wyłącznie jako emulatora testowego; nie jest on częścią runtime ani payloadu USOS.

**Legacy XP Strategy B / produkcyjny staging — 9 września 2026:** artefakt 440 B jest teraz obowiązkową częścią initramfs (`/usr/lib/usos/xp-geometry-fix-mbr-440.bin`). `prepare_xp_target.sh` instaluje go dopiero po pełnym skopiowaniu `~BT/~LS` i przejściu kontroli FAT32/free-space. Zapis obejmuje wyłącznie MBR `0..439`; bajty `440..511` (disk signature, tabela partycji i `55AA`) są porównywane przed/po bit-for-bit. `run_seabios_xp_menu_staging.ps1` wymaga dokładnego SHA-256 `D065FD99272307E1B1AA7335C18F3F2F3C658A28BC7BAD50B18AA3A15CF5FA5C` na targetcie po stagingu. Świeży blank-target 4 GiB przeszedł pełny produkcyjny staging, a następnie ten sam RAW uruchomiony jako jedyny dysk przy SeaBIOS `1024/240/63` doszedł do ekranu „Zapraszamy do programu instalacyjnego”. To jest brama wydania dla ścieżki: USOS USB -> staging -> wyjęcie USB -> target jako BIOS `0x80` -> XP Text Mode.

Macierz NTFS została rozszerzona tak, aby nie maskować tego przypadku: prawdziwy NTFS ma wyłączone 8.3, pośredni `Systems\\Windows` jest celowo powiększony do `$INDEX_ALLOCATION`, ścieżka `Systems\\Windows\\Windows 11\\Images` zawiera spacje, a lookup jest sprawdzany również z inną wielkością liter. Hard fixture nadal łączy to z pofragmentowanym `$MFT` i dużym `Windows XP\\Images`. Host matrix i SeaBIOS przechodzą. Parser obsługuje także namespace-2 DOS `$FILE_NAME` jako alias do lookupu: alias nie jest pokazywany jako drugi wpis menu, ale w razie potrzeby jego MFT record jest przeszukiwany po wszystkich resident `$FILE_NAME`, żeby odzyskać długą nazwę Win32.

Do następnego fizycznego bring-upu `D` ma dodatkowo pokazać `\\Systems\\Windows` (record/index runs/first LCN), wynik rozwiązania pełnej ścieżki Win11 **przed** i **po** inicjalizacji VBE oraz FNV32 pierwszego sektora `$INDEX_ALLOCATION` odczytanego przed/po VBE dwiema ścieżkami BIOS readera: pojedynczy `bios_read_sector` i batch `bios_read_sectors`. Dzięki temu kolejny test ma rozstrzygnąć, czy problem pojawia się już w parserze przed VBE, po zmianie trybu VESA, czy w konkretnej ścieżce INT 13h; nie zmieniamy produkcyjnego discovery readera na podstawie zgadywania.

Diagnostyka klawiszem `D` w Legacy Core pokazuje teraz przed telemetrią klawiatury: wynik znalezienia `USOS_DATA` w GPT wraz ze start LBA/rozmiarem, odczyt VBR i `NTFS`/`55AA`, `bytes_per_sector`, `sectors_per_cluster`, `MFT_LCN`, wynik mountu i liczbę runlist `$MFT`, próbę otwarcia `\\Systems` oraz ostatni konkretny błąd parsera ze ścieżką. `run_seabios_ntfs_catalog.ps1` wymusza otwarcie `D` i asercje tych pól. Na fizyczny Kingston wgrano wyłącznie diagnostyczny Core przez ten sam guard/read-back co zwykła aktualizacja; fizyczny SHA-256 Core po zapisie: `5E5E9773346C93E4E746BFA9CF1AEB202FC138F957793DC3531F958D3AAE0E72`. ISO na DATA pozostały bit-identyczne, a markerów obrazów na ESP nadal nie ma.

**Rollback przygotowany, nie wykonany:** `tools/build_legacy_bios.ps1 -CatalogMode esp-fallback -OutputDirectory zig-out/legacy-bios-rollback` tworzy Core wymuszający stary katalog ESP; bieżący `zig-out/legacy-bios-rollback/core-slot.bin` ma SHA-256 `0F9FF68DE6328643F3A11132C2329F879FFEC0CD32FD1B83F65EC860B320C692`. `usos-physical-update.exe` przy jawnym `-legacy-core` używa nadal tej samej blokady woluminów, rewalidacji GPT i read-backu Legacy, a opcja `-restore-image-markers` odtwarza zerobajtowe markery ISO/WIM/IMG/VHD/VHDX na ESP dopiero po poprawnym rollbacku Core. Normalna instalacja/aktualizacja tych opcji nie używa. Test jednostkowy wymaga, aby odtworzenie markera nie zmieniło bajtów ISO na DATA.

Legacy Core montuje `USOS_DATA` bezpośrednio przez ten parser nad swoim `random_reader`/INT13. `tools/tests/legacy_bios/run_seabios_ntfs_catalog.ps1` używa fixture z pustym `ESP\\Systems\\Windows\\Windows XP\\Images`, a ISO istnieje tylko na DATA; wymagany wynik to `Windows XP [images=1]` i taki sam bezpośredni discovery dla Windows 11. UEFI używa dokładnie tego samego parsera przez `BlockIo`: `src/platform/uefi/block_reader.zig` zapewnia read-only byte reader nad whole-disk `BlockIo`, wspólny GPT wybiera na tym samym dysku `USOS_ESP` i `USOS_DATA`, a `tools/tests/legacy_bios/run_ovmf_ntfs_catalog.ps1` wymaga `DATA BLOCKIO NTFS PASS`, `XP IMAGES=1`, `WIN11 IMAGES=1` i `UEFI NTFS CATALOG PASS` przy pustych markerach ESP.

`ntfs_x64.efi` **nie bierze udziału w discovery menu** i pozostaje w payloadzie bez zmian. Nadal jest ładowany wyłącznie w potwierdzonej ścieżce Windows Setup handoff, gdzie firmware musi dostać `SimpleFileSystem` dla przygotowanego NTFS. `src/platform/uefi/ntfs_driver.zig` oraz `tools/fetch_ntfs_driver.ps1` nie zostały zmienione przez przełączenie discovery; test aplikacji handoffu nadal się kompiluje. W projekcji `Systems/`/`Utilities/` na ESP instalator nie tworzy już `.iso/.wim/.img/.vhd/.vhdx` ani innych markerów nazw. Kopie `.efi` pozostają prawdziwymi plikami wykonywalnymi, ponieważ metoda Direct EFI nadal uruchamia je z FAT32 przez firmware; ikony i małe zgodnościowe metadane pozostają niezależne od discovery obrazów.

## QEMU NTFS Windows handoff

`zig build fetch-ntfs-driver` pobiera EfiFs 1.12 `ntfs_x64.efi` i sprawdza jego rozmiar oraz SHA-256. `zig build prepare-ntfs-handoff-image` używa tymczasowego file-backed VHD wyłącznie do przygotowania systemów plików, po czym zapisuje bazę `tools/tests/artifacts/qemu/usos-handoff-base.qcow2` i usuwa staging VHD. `zig build prepare-ntfs-handoff-overlay` tworzy świeżą warstwę różnicową `tools/tests/artifacts/qemu/usos-handoff.qcow2`. QEMU uruchamia overlay, a nie pełną kopię obrazu. Test nie może wskazywać fizycznego dysku.

`zig build run-ntfs-handoff-qemu` uruchamia obraz z modelem CPU `max`, wymaganym przez testowane Windows 11 25H2. Domyślny model QEMU `qemu64` nie ma kompletu wymaganych cech procesora i prowadzi do triple fault około 15 sekund po `StartImage`, co nie jest błędem EfiFs ani chainloadera.

Wszystkie trwałe obrazy testowe QEMU są trzymane w `tools/tests/artifacts/qemu/`; nie tworzymy nowych raw `usos.img` w katalogu głównym. Pełne bazy są współdzielone, a kolejne próby używają warstw różnicowych.

**Zasada E2E:** nośnik USOS używany do walidacji backendów przygotowuje wyłącznie produkcyjny kod instalatora i aktualizatora. Nie wolno dodawać do `prepare_e2e_base.ps1` ręcznych skrótów składających pliki, BCD, template'y WIMBoot/VHDBoot, `usos-device.ini` ani katalog ESP w sposób inny niż produkcyjna ścieżka. Jeżeli wymaganego stanu nie da się uzyskać przez `install.Engine` / `Aktualizuj USOS` i jego `CopyInstallPayload()`, traktujemy to jako brak implementacji lub brak wejścia testowego, a nie powód do obejścia. WIM/VHD/VHDX mogą być przygotowane osobno wyłącznie jako dane wejściowe użytkownika na DATA; template'y powstają dopiero przez produkcyjne `ensureWimBootTemplate()` / `ensureVHDBootTemplates()`.

Backendowe E2E używa `tools/prepare_backend_e2e_base.ps1`: pełny `install.Engine` tworzy file-backed nośnik USOS w Windows/QEMU, test dodaje na DATA rzeczywiste ISO, WIM i bootowalny VHDX jako zwykłe obrazy użytkownika, a następnie produkcyjny `Aktualizuj USOS` generuje template'y backendów oraz tylko małe artefakty ESP wymagane poza discovery. Obrazy pozostają źródłem prawdy wyłącznie na DATA i menu ma widzieć je bez osobnej synchronizacji nazw. Dopiero tak przygotowany obraz jest bazą dla regresji ISO oraz WIMBoot/VHDBoot. Produkcyjny instalator zapisuje GUID-y w `usos-device.ini` w kanonicznym formacie Windows/GPT z wielkimi literami; mikro-Linux musi normalizować PARTUUID do małych liter wyłącznie przy budowaniu ścieżek `/dev/disk/by-partuuid/`, a wszystkie porównania GUID muszą być case-insensitive. Wcześniejszy fixture generował identyfikatory w formie zgodnej z linuksowymi nazwami ścieżek i przez to maskował ten błąd — to jest przykład, dlaczego E2E nie może ręcznie składać nośnika inaczej niż kod produkcyjny.

**Fizyczne USB ma dodatkową klasę regresji, której QEMU nie odtwarza:** virtio-blk w QEMU pojawia się praktycznie natychmiast, natomiast prawdziwy kontroler USB/xHCI i pendrive mogą zostać wyliczone dopiero po uruchomieniu wczesnego userspace. Jednorazowe `mdev -s` + natychmiastowy test `/dev/disk/by-partuuid/...` jest więc wyścigiem i może dać fałszywe `PARTUUID path missing` mimo poprawnego GUID-u oraz poprawnego casing. Produkcyjny `usos-init` ma jawnie załadować stos hosta USB/storage, odświeżać namespace PARTUUID i przez ograniczony czas czekać na ESP/DATA/WORK; po timeout nadal obowiązuje FAIL=stop. `blkid -p -s PARTUUID -o value` nie jest wiarygodnym źródłem PARTUUID na fizycznym USB: na Kingston DataTraveler zwrócił `rc=0` z pustą wartością, mimo że zwykły `blkid`, `lsblk` i kernelowy `uevent` zawierały prawidłowy GUID. Produkcyjna detekcja PARTUUID używa wyłącznie `/sys/class/block/*/uevent`; `blkid -p` nie może wrócić do tej ścieżki. To, obok asynchronicznej enumeracji USB, jest drugą różnicą sprzętową, której QEMU/virtio nie odtwarza. Zielone E2E na virtio nie jest dowodem, że enumeracja ani odczyt PARTUUID na fizycznym USB są poprawne — tę ścieżkę trzeba potwierdzać na fizycznym nośniku po zmianach w initramfs, modułach storage albo discovery.

`zig build prepare-e2e-base` pozostaje testem regresyjnym wcześniejszej ścieżki ISO/guarda. Nie wolno rozszerzać go o ręcznie składane fixture'y backendów. `zig build prepare-e2e-overlay` tworzy świeży `tools/tests/artifacts/qemu/usos-e2e.qcow2` z backing file `usos-e2e-base.qcow2` dla regresji `USOS → prepare-requested → mikro-Linux → prepared → reboot → handoff → Windows Setup`.

**GPT NO_BLOCK_IO_PROTOCOL — odrzucone:** test `tools/tests/run_gpt_no_block_io_probe.ps1` ustawia wyłącznie na kopii obrazu bit 1 (`EFI_PART_ATTR_NO_BLOCK_IO_PROTOCOL`) dla DATA i WORK, przelicza CRC obu kopii GPT i uruchamia OVMF z prawdziwym `ntfs_x64.efi`. Wynik dla obu partycji: `DATA SIMPLEFS MISSING`, `WORK SIMPLEFS MISSING`, `NO-BLOCK-IO VISIBILITY FAIL`. Atrybut usuwa wymagane partycyjne Block I/O również z drogi używanej przez sterownik NTFS, więc nie wolno stosować go w produkcyjnym layoucie USOS ani testować na fizycznym Kingstonie. Zgodnie z zasadą FAIL=stop pełny E2E ISO nie jest uruchamiany po tym wyniku; trzy wpisy firmware pozostają akceptowanym ograniczeniem.

`zig build micro-linux` buduje rzeczywisty kernel i initramfs mikro-Linuksa, statyczny `usos-fb-ui` oraz loader EFI. Artefakty Alpine są przypięte wersją i SHA-256 w `tools/micro_linux.lock.json`. Initramfs zawiera tylko narzędzia potrzebne do identyfikacji partycji, kontroli guarda, NTFS, kopiowania, publikacji stanu oraz minimalnej obsługi ekranu przygotowania. Hostowy PowerShell służy wyłącznie do utworzenia plikowych obrazów qcow2; przygotowanie WORK wykonuje mikro-Linux uruchomiony wewnątrz QEMU.

Po każdej zmianie przypiętego kernela obowiązkowa jest regresja framebuffera zarówno w Legacy, jak i UEFI. Dla Alpine 3.24.1 `6.18.35-0-lts` simpledrm jest dostępny bez osobnego `simpledrm.ko`; builder nie kopiuje więc całego DRM ani stockowego `modloop-lts`. Bazowy `initramfs-lts` jest rozpakowywany, jego szerokie `usr/lib/modules` i firmware są usuwane, a następnie builder odczytuje `modules.dep`/`modules.alias` z `modloop-lts` i dodaje wyłącznie dependency closure wymaganych modułów USOS: pełną rodzinę `kernel/drivers/ata/*.ko`, USB storage/host, virtio, NVMe, potrzebne filesystemy oraz ich zależności. Strategiczne moduły `sata_nv`, `pata_amd`, `sata_sil24`, `sata_via`, `sata_sis`, `ata_piix`, `sata_promise` i `sata_sil` są twardą asercją buildera. `tools/tests/run_ovmf_micro_linux_lts.ps1` wymaga OVMF -> systemd-boot -> `[MICRO-LINUX] boot PASS kernel=6.18.35-0-lts` oraz `[USOS-FB-UI] FIRST_FRAME`; `run_seabios_linux_boot.ps1` pozostaje równoległą bramą Legacy. Runtime nie ładuje wszystkich starych sterowników: dla PCI class `0x01*` wywołuje `modprobe` na faktycznym modaliasie urządzenia i loguje wynikowy driver. W jądrze LTS transport `virtio_pci` (z `virtio_pci_modern_dev`/`virtio_pci_legacy_dev`) jest modułem, a nie jest wbudowany jak w `virt`: bez niego `virtio_blk`/`virtio_scsi` ładują się, ale nie widzą żadnego dysku. Builder dodaje go do listy i asercji strategicznych, a `usos-init` ładuje go jawnie; `python tools/tests/run_micro_linux_virtio_qemu.py` sprawdza w QEMU (rdinit=/bin/sh + linie storage z prawdziwego `/usos-init`), że dysk virtio-blk jest widoczny jako `/dev/vdX`, a virtio-scsi jako `/dev/sdX`.

Pomiar przejścia UEFI → framebuffer wykonuje `py -3 tools/tests/framebuffer/measure_handoff.py --project-root . --accelerator whpx`. Skrypt używa wyłącznie tymczasowego overlayu qcow2 i mierzy pojawienie się `MICRO-LINUX STARTIMAGE BEGIN` oraz pierwszej klatki produkcyjnego `usos-fb-ui`. Dla bieżącego obrazu trzy kolejne przebiegi WHPX dały 1392,9 ms, 1401,0 ms i 1404,3 ms od `StartImage` do pierwszej klatki (mediana 1401,0 ms). Linux `/proc/uptime` wskazywał przy pierwszej klatce około 700 ms; marker bezpośrednio przed inicjalizacją framebuffera wypadał przy 600-620 ms, więc cały etap załadowania minimalnego stosu simpledrm + pierwszego renderu zajmuje około 90-100 ms. Pozostałe około 1,3 s przed tym punktem to loader, start kernela i wczesny userspace. Faktyczny czarny błysk po przejęciu GOP przez końcowy `simpledrm.ko` jest krótszy niż te 90-100 ms, bo ten przedział obejmuje również załadowanie jego modułów zależnych, podczas których poprzednia klatka UEFI nadal może pozostać widoczna.

Pomiar startu mikro-Linuksa jest logowany jako `[USOS-PERF]` na podstawie `/proc/uptime`. Dla bieżącego kernela/initramfs bezpośredni start do wejścia w `/usos-init` wyniósł 0,61 s na WHPX (`qemu64,-xsave`) i 2,16 s na TCG (`-cpu max`, 2 vCPU). Poprzednie pełne przebiegi TCG dochodziły do `Run /usos-init as init process` w 2,39-2,68 s. Parametry produkcyjne już zawierają `quiet loglevel=3 vt.global_cursor_default=0`; kontrolny start WHPX z `loglevel=7` bez `quiet` trwał 0,82 s, więc samo ograniczenie logowania oszczędza około 0,2 s w tym środowisku. Dalsze skracanie startu należy szukać przede wszystkim w rozmiarze initramfs i liczbie inicjalizowanych modułów/podsystemów, nie w kolejnych flagach `quiet`.

`mkfs.ntfs` jest wywoływany jako `mkfs.ntfs -f -F -L USOS_WORK ...`: `-f` to szybkie formatowanie, a `-F` zezwala na formatowanie jawnie zweryfikowanego urządzenia blokowego. Czasy `device_guard`, `mkfs.ntfs`, kopiowania i finalizacji są oznaczane osobnymi wpisami `[USOS-PERF]`, żeby następny pełny E2E pokazał realny podział czasu bez zgadywania.

Test negatywny można zbudować parametrem `-GuardTestBadPartuuid` skryptu `tools/prepare_e2e_base.ps1`. Parametr trafia wyłącznie do testowej linii poleceń kernela: mikro-Linux przekazuje błędny identyfikator do prawdziwego `device_guard.sh`, wymaga jego niezerowego wyniku i zatrzymuje się przed `mkfs.ntfs`. Każda próba korzysta ze świeżego differential overlayu, a nie z fizycznego urządzenia.

Potwierdzony pełny przebieg używa `-cpu max` i wykonuje w jednej VM: menu USOS, `prepare-requested`, backup `BootOrder`, `BootNext`, mikro-Linux, guard, format i marker WORK, ekstrakcję z weryfikacją, `prepared`, reboot, EfiFs oraz Windows Setup. Sukces wizualny oznacza ekran wyboru lokalizacji instalacji z widocznymi `USOS_DATA` i `USOS_WORK`; test kończy się przed rozpoczęciem instalacji.

Regresja UI/backend musi potwierdzić, że dla Windows 11 + ISO działające opcje `Automatic (ISO)`, `ISO` i `Chainload` korzystają z faktycznie zaimplementowanych backendów. `Automatic` rozwiązuje się do konkretnego backendu i dziedziczy jego status walidacji. Jedynym źródłem statusu jest `src/flow/backend_validation.zig`: brak odznaki oznacza zieloną walidację w QEMU i na sprzęcie, `[TESTED IN VM]` oznacza zielone E2E w QEMU bez zakończonego testu fizycznego, a `[EXPERIMENTAL]` brak zielonej walidacji backendu. Po każdym nowym zielonym teście aktualizacja odpowiedniego wpisu w `backend_validation.zig` jest obowiązkową częścią procedury walidacji; UI nie może zawierać własnej kopii tych statusów. Metody niezgodne z typem obrazu albo bez zaimplementowanego backendu pozostają widoczne z powodem niedostępności, ale nie dostają fałszywej odznaki walidacji.

Artefakty, testy i logi wcześniejszego przebiegu pozostają zachowane co najmniej do czasu przejścia przez nowy build całej tej samej macierzy. Dowody sprzed scalenia oraz manifest SHA-256 znajdują się w `docs/evidence/pre-merge/`.

Runner zachowuje:

- `serial.log` z etapami USOS i zweryfikowaną ścieżką `LoadedImage`,
- serię `screen-*.ppm` (gęstą w pierwszych sekundach, rzadszą później),
- `qmp-events.log`, który odróżnia reset gościa, shutdown i zatrzymanie przez runner,
- `qemu-debug.log` z resetami CPU i triple fault,
- `qemu.stderr.log`.

Samo `WINDOWS STARTIMAGE BEGIN` nie jest wynikiem końcowym. Screenshot musi potwierdzić GUI Setup, a osobny dowód po przejściu początkowych ekranów musi potwierdzić, że Setup widzi `sources/install.wim`.

## QEMU / WinPE — instalator Windows host backend

`tools/run_installer_gpt_qemu.ps1` uruchamia Windows Setup/WinPE w QEMU i podłącza osobny plik `tools/tests/artifacts/qemu/usos-installer-gpt-target.qcow2` jako `usb-storage` z `removable=on` oraz testowym serialem `USOS-GPT-TEST`. Kod testowy odmawia działania, jeżeli nie znajdzie dokładnie jednego urządzenia z tym serialem i oczekiwaną pojemnością. Fizyczne dyski hosta nie są przekazywane do QEMU i nie mogą być celem testu.

Potwierdzony destrukcyjny przebieg wykonuje na tym obrazie: blokadę i rewalidację otwartego `PhysicalDrive`, `IOCTL_DISK_DELETE_DRIVE_LAYOUT`, `IOCTL_DISK_CREATE_DISK`, `IOCTL_DISK_SET_DRIVE_LAYOUT_EX` oraz ścisły read-back przez `IOCTL_DISK_GET_DRIVE_LAYOUT_EX`. Rewalidacja porównuje model, serial i pojemność z zatwierdzoną tożsamością urządzenia. Read-back porównuje disk GUID, PARTUUID-y, typy GPT, offsety i rozmiary; każda niezgodność zatrzymuje test bez próby naprawy.

Test wykrył również niedyskowy wolumin WinPE, dla którego `IOCTL_VOLUME_GET_VOLUME_DISK_EXTENTS` zwraca `ERROR_INVALID_FUNCTION`. Guard klasyfikuje taki przypadek dodatkowo przez `IOCTL_STORAGE_GET_DEVICE_NUMBER`: wolumin niedyskowy może zostać pominięty, natomiast wolumin należący do celu lub niemożliwy do jednoznacznej klasyfikacji nadal powoduje FAIL przed pierwszą operacją niszczącą.

Potwierdzony wynik testu dla obrazu 40 GiB: ESP 1 GiB, DATA do granicy WORK oraz WORK 12 GiB, trzy unikalne PARTUUID-y i poprawny `qemu-img check` po zakończeniu.

WinPE wystarcza do testów niskopoziomowego układu GPT i guardów, ale **nie jest środowiskiem produkcyjnego `install.Engine`**. Produkcyjna ścieżka formatuje ESP/DATA/WORK przez Windows PowerShell (`powershell.exe` / `Format-Volume`), którego odchudzony WinPE testowy nie zawiera. Zostało to potwierdzone dwukrotnie w E2E błędem `Windows PowerShell is required for Format-Volume: exec: "powershell.exe": executable file not found in %PATH%`. Dlatego testy produkcyjnego `install.Engine`, kopiowania payloadu oraz przygotowania WIMBoot/VHDBoot uruchamiamy w pełnym Windowsie QEMU. Nadal obowiązuje twarda zasada: celem jest wyłącznie file-backed wirtualny dysk QEMU, nigdy fizyczny pendrive.

**Bazy pełnego Windowsa QEMU nigdy nie uruchamiamy z `-no-reboot`.** Pierwszy start obrazu po `DISM /Apply-Image` przechodzi przez Windows Setup/Sysprep/OOBE i wymaga co najmniej jednego rzeczywistego restartu. Zatrzymanie QEMU na tym restarcie zostawia bieżący overlay w niespójnym stanie i kolejny start może zakończyć się komunikatem `Komputer został nieoczekiwanie uruchomiony ponownie lub wystąpił nieoczekiwany błąd`. Taki overlay jest jednorazowo odrzucany, nie naprawiany ani nie używany jako nowa baza. Zdrowie bazy sprawdzamy wyłącznie na świeżym overlayu; jeśli świeży overlay powtarza błąd Setup, bazę odbudowujemy od zera przez produkcyjną ścieżkę przygotowania Windows/DISM.

## Obrazy UEFI

Po pełnym buildzie:

- `zig-out/usb/EFI/BOOT/BOOTX64.EFI` - x86_64,
- `zig-out/usb/EFI/BOOT/BOOTAA64.EFI` - ARM64.

Oba pliki mogą znajdować się na tej samej partycji EFI/FAT.

`BOOTX64.EFI` dla `zig-out/usb` i `zig-out/manual-usb` powstaje z jednego obiektu kompilacji, więc wersja testowa i wersja zapisywana na pendrive nie mają osobnych implementacji. `tools/verify_release_consistency.ps1` porównuje ich SHA-256 i sprawdza, że ZIP wbudowany w instalator zawiera wyłącznie aktualne statyczne pliki ESP (`EFI` i `UI`). `Systems`, `Utilities`, `Programs`, obrazy i unattended nie są statycznie dublowane w EXE. Instalator/updater może tworzyć na ESP tylko małą projekcję potrzebną poza discovery (np. kopie `.efi`, ikony); nazwy ISO/WIM/IMG/VHD/VHDX są czytane bezpośrednio z DATA.
